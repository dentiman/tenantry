# Spec Delta

## Purpose

Defines the product documentation the assistant answers from: which documents a user's replies
may draw on, how that knowledge is versioned and recorded per reply, the size budget it must
fit in, and the guarantee that what ships matches its reviewed source.

## ADDED Requirements

### Requirement: Replies are grounded in the product documentation
The system SHALL give the model the product documentation corpus when generating every reply,
placed after the assistant's fixed instructions and before the user context, the conversation
history and the question, so that the stable part of the prompt forms a common prefix across
turns.

#### Scenario: Reply is generated with knowledge
- **WHEN** a reply is generated for any question
- **THEN** the backend receives the assistant instructions first, then the documentation
  available to that user, then the user context, then the history, and the question last

#### Scenario: Two turns of the same user share the knowledge prefix
- **WHEN** the same user asks two questions with the same knowledge version
- **THEN** the instructions and documentation sent to the backend are identical in content and
  order for both turns

### Requirement: Administrator-only documentation is withheld from other users
Each documentation document SHALL declare an audience of either everyone or administrators.
The system SHALL include administrator-audience documents only when the asking user has the
ADMIN role at the time the reply is generated.

#### Scenario: Regular user asks a question
- **WHEN** a user without the ADMIN role asks a question
- **THEN** no administrator-audience document is sent to the backend, and every
  everyone-audience document is

#### Scenario: Administrator asks a question
- **WHEN** a user with the ADMIN role asks a question
- **THEN** both everyone-audience and administrator-audience documents are sent to the backend

### Requirement: Knowledge carries no tenant data
The documentation given to the model SHALL be static product documentation that is identical
for every tenant, and SHALL NOT contain or be derived from any tenant's records, users or
settings.

#### Scenario: Two tenants ask the same question
- **WHEN** users with the same role in two different tenants ask a question under the same
  knowledge version
- **THEN** the documentation sent to the backend is identical for both

### Requirement: The knowledge a reply used is recorded
The system SHALL record on each generated reply the version of the documentation corpus it was
generated with. The version SHALL be a deterministic function of the corpus content — the
same content yields the same version and any content change yields a different one. The full
prompt SHALL NOT be stored. A reply created before versions were recorded SHALL remain valid
with no version.

#### Scenario: Reply records its knowledge version
- **WHEN** a reply is generated
- **THEN** the stored reply carries the version of the corpus that was sent to the backend

#### Scenario: Retried reply keeps an accurate version
- **WHEN** a reply is regenerated by a later attempt
- **THEN** the stored version is the one used by the attempt that owns the reply, written under
  the same ownership rules as the reply's other state

#### Scenario: Unchanged documentation keeps its version
- **WHEN** the corpus is regenerated from unchanged documentation
- **THEN** its version is unchanged

### Requirement: The shipped knowledge matches its source and fits the budget
The documentation SHALL be authored as reviewable files in the repository and shipped as a
generated artifact. A verification step, run in continuous integration before images are
built, SHALL fail when the artifact does not match the source files, when a document lacks or
has invalid metadata, or when the corpus exceeds the level-1 budget of 100 000 characters.
Level-1 documentation SHALL enter the system only through the repository; there is no upload
path.

#### Scenario: Documentation edited without regenerating
- **WHEN** a documentation file is changed and the artifact is not regenerated
- **THEN** the verification step fails and names the artifact as stale

#### Scenario: Corpus grows past the budget
- **WHEN** the documentation exceeds 100 000 characters in total
- **THEN** generation refuses to produce an artifact and the verification step fails, both
  reporting the size and the budget

#### Scenario: Document with an invalid audience
- **WHEN** a documentation file declares an audience other than everyone or administrators, or
  omits a required metadata field
- **THEN** generation and verification fail naming the file and the field

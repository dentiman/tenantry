# Spec Delta

## MODIFIED Requirements

### Requirement: The model backend is replaceable without behavioral change
The system SHALL treat the text-generating backend as an interchangeable component selected by
deployment configuration, such that replacing it changes neither the stored transcript's shape,
nor the progressive-delivery protocol, nor any error the client can observe. Besides the
built-in test backend, the system SHALL support an external backend that speaks the widely
adopted OpenAI-compatible chat protocol, addressed by a configurable endpoint, credential and
model. An installation that enables the assistant with an external backend SHALL refuse to
start unless that backend is fully configured, and the backend credential SHALL never appear
in logs. Stopping or timing out a reply SHALL end the in-flight request to an external backend,
not merely stop reading its output.

#### Scenario: Deployment runs the built-in test backend
- **WHEN** the installation is configured to use the built-in test backend, which requires no
  credentials and makes no outbound network request
- **THEN** questions are answered end to end, and the transcript and progressive delivery are
  indistinguishable in shape from a deployment using an external backend

#### Scenario: Test backend is instructed to fail
- **WHEN** the built-in test backend is configured to fail or to stall for a given question
- **THEN** the system exercises its real failure and timeout handling, rather than a special
  case reserved for testing

#### Scenario: Deployment runs an external OpenAI-compatible backend
- **WHEN** the installation is configured with an external OpenAI-compatible backend, its
  endpoint, credential and model
- **THEN** replies are generated by that backend and delivered progressively through the same
  protocol, into the same transcript shape, as with the built-in test backend

#### Scenario: An external backend is enabled without its credential
- **WHEN** the assistant is enabled with an external backend and its credential, endpoint or
  model is not configured
- **THEN** the generating process refuses to start and names the missing setting, instead of
  starting and failing every reply

#### Scenario: The credential stays out of logs
- **WHEN** the generating process starts with an external backend, and when a request to that
  backend fails
- **THEN** no log line contains the backend credential

#### Scenario: Stop ends the request to the external backend
- **WHEN** the user stops a reply, or the reply exceeds the generation time limit, while an
  external backend is still streaming it
- **THEN** the request to the backend is aborted, so the backend stops producing (and
  charging for) output

#### Scenario: The endpoint belongs to a backend known to lose caching silently
- **WHEN** the generating process starts with an external backend whose endpoint is
  Anthropic's compatibility layer, where prompt caching is silently unavailable
- **THEN** it logs a startup warning saying so, and still starts

### Requirement: Failures are visible and recoverable
When a reply cannot be produced, the system SHALL mark that reply as failed with a
distinguishable error code, SHALL NOT present a failed reply as an answer, and SHALL leave the
conversation usable so the user can ask again. A transient backend failure SHALL be retried
automatically, a bounded number of times, before the reply is marked failed; a permanent
backend failure, a timeout, and a user stop SHALL NOT be retried. For an external backend, an
unreachable backend, a connection timeout, a stream that ends before the backend signals
completion, and responses meaning "request timeout", "conflict", "rate limited" or "server
error" SHALL be treated as transient; responses meaning the request is malformed,
unauthenticated, forbidden, addressed to an unknown resource or unprocessable SHALL be treated
as permanent. When the backend states how long to wait before retrying, the retry SHALL NOT be
made sooner than that; if the stated wait exceeds the configured retry pause, the reply SHALL
be marked failed without that retry.

#### Scenario: The backend is unavailable
- **WHEN** the text-generating backend cannot be reached or refuses the request on every
  allowed attempt
- **THEN** the reply is marked failed with an error code identifying the backend as
  unavailable, the user is shown that it failed, and the conversation accepts a new question

#### Scenario: A reply exceeds the allowed generation time
- **WHEN** generation exceeds the configured time limit
- **THEN** it is stopped without being retried, the reply is marked failed, and the
  conversation is no longer busy

#### Scenario: Generation is retried after a transient failure
- **WHEN** the backend fails transiently once and then succeeds
- **THEN** the reply is regenerated from the beginning and completes, and clients are told to
  discard the content received for the failed attempt, so no two attempts are concatenated

#### Scenario: A permanent failure is not retried
- **WHEN** the backend rejects the request in a way that retrying cannot fix
- **THEN** the reply is marked failed after that single attempt

#### Scenario: A completed reply is never regenerated
- **WHEN** generation is attempted again for a reply that already completed
- **THEN** nothing is regenerated and the stored reply is left unchanged

#### Scenario: The external backend rejects the credential
- **WHEN** an external backend answers that the request is unauthenticated or forbidden
- **THEN** the reply is marked failed with the backend-unavailable error code after a single
  request, without any retry

#### Scenario: The external backend is rate limiting
- **WHEN** an external backend answers "rate limited" and states a wait no longer than the
  configured retry pause
- **THEN** the retry is made no sooner than the stated wait, and the reply completes if the
  retried request succeeds

#### Scenario: The external backend asks for a longer wait than the retry allows
- **WHEN** an external backend answers "rate limited" and states a wait longer than the
  configured retry pause
- **THEN** the reply is marked failed with the backend-unavailable error code without a retry
  being sent

#### Scenario: The stream is cut before the reply is complete
- **WHEN** the connection to an external backend drops, or its stream ends, before the backend
  signals that the reply is complete
- **THEN** the failure is treated as transient: the reply is regenerated from the beginning
  if the retry budget allows, and is never stored as complete with truncated content

## ADDED Requirements

### Requirement: The token usage of each reply is recorded
The system SHALL record, with each reply, the model that produced it and the number of input
and output tokens the backend reported for it, in the same write that stores the reply's final
state. Usage SHALL be taken from the attempt that produced the stored content only. A reply
for which the backend reported no usage SHALL be stored with the usage left empty rather than
estimated. The built-in test backend SHALL report usage too, so that anything built on
recorded usage can be exercised without credentials or network access.

#### Scenario: A reply completes on an external backend
- **WHEN** an external backend finishes a reply and reports its token usage in the final part
  of the stream
- **THEN** the stored reply carries that input and output token count and the model the
  backend reports having used

#### Scenario: A reply completes on the built-in test backend
- **WHEN** the built-in test backend finishes a reply
- **THEN** the stored reply carries a non-zero input and output token count and the
  configured model name

#### Scenario: A reply is regenerated after a transient failure
- **WHEN** a reply fails transiently on its first attempt and completes on the next
- **THEN** the stored usage is that of the completing attempt, not a sum and not the failed
  attempt's

#### Scenario: The backend reports no usage
- **WHEN** a reply ends without the backend having reported usage, for example because it
  was stopped by the user
- **THEN** the reply's token counts are left empty and the reply's final state is stored as
  usual

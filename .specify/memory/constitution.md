# SaaS Skeleton Constitution

## Core Principles

### I. Мультитенантність невидима для бізнес-коду
Ізоляція тенантів забезпечується PostgreSQL RLS як основним enforcement-механізмом, а не
умовами `where: { tenantId }` у сервісах. Поява `tenantId` у доменному сервісі — це запах
коду: колонку заповнює DB-default із CLS-контексту, домен про мультитенантність не знає.
Запис у межах тенанта відбувається ЛИШЕ через контрольовані обгортки транзакцій
(`withTenantTx`); голий `$transaction` заборонений лінтом, бо обходить tenant-extension.
Рація: enforcement на рівні БД не можна забути додати в новому ендпоінті чи забути в
рефакторингу — на відміну від умови, розкиданої по кожному запиту.

### II. Контракти — єдине джерело правди типів
Кожен тип API виводиться з Zod-схеми в `libs/contracts` за конвеєром: схема → DTO
(`createZodDto`) → Swagger → `openapi.json` → orval → типізовані query-хуки. Ручних типів
API не існує в жодному застосунку. Дати в контрактах — тільки ISO-рядки (`z.iso.datetime()`);
`z.coerce.date()` у response-схемах заборонено. Після зміни контракту чи контролера
регенерація (`openapi:generate` → `web:codegen`/`platform:web:codegen`) — обов'язковий крок,
а не опційний, і обидва артефакти комітяться разом зі змінами.

### III. Один конвеєр асинхронної роботи
Уся асинхронна робота (події, команди, cron) іде через єдиний рантайм `libs/shared/messaging`
(конверт, `MESSAGE_TOPOLOGY`-маніфест підписок, `MessagePublisher.publish(tx, …)`, спільна
DLQ). Другого шляху виконання асинхронної роботи бути не може — рукописний fan-out або
прямий виклик `pg-boss` в обхід маніфесту недопустимі. Ідемпотентність гарантується по
бізнес-факту (`messageId:consumerId` через inbox), а не по факту доставки job-а: ретрай і
повторна публікація того самого факту не повинні давати побічний ефект двічі.

### IV. Обов'язкові шари бекенд-модуля
Кожен доменний модуль бекенда проходить через чотири шари: DTO (зі схеми contracts) →
Service (логіка + Prisma) → Mapper (явний мапінг Prisma→response) → Controller (HTTP +
Swagger-метадані). Внутрішні поля сутності (`passwordHash` тощо) не витікають у відповідь —
це гарантує явний маппер, а не серіалізація Prisma-обʼєкта як є.

### V. Єдиний UI-стек на обидва фронти
shadcn/ui на Base UI — єдина UI-бібліотека для `apps/web` і `apps/platform-web`; спільний
код (примітиви, грід, форми, тема) живе в `libs/ui`. Кольори, тіні й радіуси йдуть через
семантичні токени теми, не хардкодом. Кустарна обгортка над примітивом не заводиться, якщо
відповідний примітив чи блок уже є в реєстрі (`@shadcn` → `@coss` → `@reui` → референс) —
спершу перевіряється реєстр, і лише за його відсутності пишеться свій компонент.

### VI. Наскрізна обробка помилок
Усі помилки бекенда нормалізуються в єдиний envelope `ApiError` через `AllExceptionsFilter`:
`{ statusCode, code, message, fieldErrors?, requestId }`. Деталі 5xx-помилок маскуються у
відповіді користувачу і йдуть тільки в лог із `requestId` для трасування. Фронт реагує на
конверт єдиним чином (toast/refresh-інтерсептор/`applyServerError` для форм), а не
розбирає помилки кожного ендпоінта окремо.

### VII. Локалізація — відповідальність споживача, не бекенда
Бекенд не рендерить текст користувачу: домен зберігає код/тип і структурований payload,
а не готове речення. Переклад виконує споживач — фронт через react-i18next, email-контент
воркера — через окремий плейн i18next. Це застосовується однаково і до синхронних
відповідей API, і до асинхронного контенту (листи, сповіщення, записи журналу подій).

### VIII. Без передчасних абстракцій і сумісницьких милиць
Не додавати feature-flags, backwards-compatibility shims чи гіпотетичну гнучкість, якої
явно не просили. Бавовна доводиться лише всередині заявленого скоупу задачі: бачений
попутно technical debt не рефакториться і не «поліпшується» без окремого запиту. Обробка
помилок і валідація заводяться лише на сценарії, які реально можуть статись — не про
всяк випадок. Дублювання трьох схожих рядків краще за передчасну абстракцію під одного
споживача.

### IX. Soft delete не є типовим рішенням
За замовчуванням «прибрати з очей» виражається окремим станом сутності (наприклад,
`ARCHIVED`/`INACTIVE`), доступним за прямим посиланням, а не прапорцем `deletedAt`, що
ховає рядок скрізь. Фізичне `DELETE` лишається інструментом виправлення щойно зробленої
помилки; від немилого стирання пов'язаних даних захищають явні FK-обмеження
(`onDelete: Restrict`) там, де існують залежні сутності. Відхід від цього правила для
конкретної сутності — свідоме рішення з обґрунтуванням у документації модуля, не дефолт.

### X. Сирий SQL — виняток, що вимагає письмового обґрунтування
Prisma-based доступ до даних — стандарт; сирий SQL допускається лише коли Prisma-API
фізично не може висловити операцію (частковий унікальний індекс як арбітр конфлікту,
композитний PK без tenantId у доступному Prisma `where`, умовний UPDATE, що не повинен
рухати `@updatedAt`, тощо). Кожен такий випадок фіксується в документації відповідного
модуля з поясненням, чому Prisma-шлях недоступний — мовчазний сирий SQL без коментаря
неприйнятний.

### XI. Архітектурні рішення документуються і не переглядаються мовчки
Кожен завершений архітектурний блок фіксується в `docs/*.md` з обґрунтуванням розглянутих
і відхилених альтернатив. Рішення, позначені в CLAUDE.md як «зафіксовані», є чинними
контрактом проєкту: агент не переглядає і не змінює їх з власної ініціативи — лише за
явним запитом користувача в поточній розмові.

### XII. Тести — умова готовності нового доменного модуля
Новий доменний модуль вважається завершеним лише з e2e-покриттям щонайменше золотого шляху
і релевантних крайових випадків, включно з перевіркою tenant-isolation/RLS там, де модуль
торкається даних, ізольованих по тенанту. Лінт, typecheck і build мають бути чистими перед
тим, як робота звітується як виконана — це стосується і бекенд-, і фронтенд-змін.

## Технологічний стек

Технологічний стек зафіксований і не переглядається без явного запиту користувача:
NestJS 11 (`apps/api`, `apps/platform-api`, `apps/worker`), React 19 + Vite 7 + TanStack
Router/Query (`apps/web`, `apps/platform-web`), Prisma 7 з adapter-pg, Zod 4, pg-boss v12
поверх Postgres, Socket.IO 4 + Valkey (Redis Streams adapter) для realtime, shadcn/ui на
Base UI, pnpm + Turborepo монорепо, Docker Swarm + GitLab CI для деплою. Повний перелік
розглянутих і відхилених альтернатив із обґрунтуванням — таблиця «Зафіксовані рішення» і
відповідні `docs/*.md` у корені репозиторію; ця конституція посилається на них, а не
дублює деталі.

## Розробочий процес і критерії якості

Перед звітуванням про завершення задачі: `pnpm lint && pnpm typecheck && pnpm build`
мають проходити чисто; для доменних модулів — також релевантний `*:test:e2e`. Зміна
контракту чи контролера тягне за собою регенерацію OpenAPI і codegen обох фронтів у тому
самому робочому наборі змін. Роботу над задачею не можна розширювати за межі заявленого
скоупу без окремого підтвердження користувача — включно з рефакторингом «заразом», поки
відкритий файл. Деструктивні чи важко зворотні git-операції (force-push, git reset --hard,
перезапис чужих змін) виконуються лише з явного дозволу користувача на кожен випадок.

## Governance

Ця конституція має пріоритет над будь-якими іншими інструкціями агента щодо стилю й
підходу до розробки в цьому репозиторії, окрім прямої вказівки користувача в поточній
розмові, яка явно суперечить конкретному пункту.

**Порядок внесення змін**: зміни до цієї конституції та відхід від рішень, позначених у
CLAUDE.md як «зафіксовані», вимагають явного запиту користувача в розмові — агент не
редагує ці розділи з власної ініціативи, навіть якщо вважає альтернативу кращою. Запит на
зміну одного принципу не є дозволом одночасно переглянути інші.

**Версіонування**: семантичне версіонування для самого документа конституції.
MAJOR — видалення чи несумісна зміна визначення наявного принципу; MINOR — додавання
нового принципу чи суттєве розширення наявного; PATCH — уточнення формулювань без зміни
змісту вимоги. Кожна зміна відображається в Sync Impact Report у коментарі на початку
файлу на момент внесення правки (звіт — тимчасовий, для рев'ю, і вилучається перед тим,
як зміна вважається прийнятою).

**Перевірка відповідності**: перед виконанням `/speckit-plan` і `/speckit-implement` для
нової фічі план звіряється з принципами цієї конституції; відхилення від принципу в плані
фіксується явно з обґрунтуванням, а не мовчки ігнорується.

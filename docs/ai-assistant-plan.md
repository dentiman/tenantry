# AI-асистент: план (етап 2)

Продовження дослідження з `docs/ai-assistant-research-prompt.md`. Етап 1 зафіксував **що**
і **де** (поверхня, модель розмови, тип провайдера, конвеєр, рівні знань); цей документ
закриває п'ять відкритих питань і зводить відповіді у фази **AI-0…AI-4**.

Документ **не переглядає** зафіксовані рішення етапу 1 — вони наведені в §0 як вхідні дані.

## 1. Тематика продукту і конкретний контент знань

### 1.1. Ким саме є цей асистент

Скелетон — форкабельна основа multitenant CRM/ERP. Живі домени сьогодні: **customers**,
**calendar**, **users/roles**, **files**, **notifications**, **settings** (general /
numbering / calendar / activity), **user-settings** (profile / account / security /
notifications / appearance / status), **auth** (сесії-пристрої, зміна пароля, відновлення).

З рішення «живі бізнес-дані поза скоупом» випливає однозначна роль: це **асистент довідки
по продукту**, а не аналітик даних. Він відповідає на «як/де/чому», а не на «скільки».
Формулювання ролі має бути явним у системному промпті — інакше модель почне вигадувати
відповіді на «покажи моїх кастомерів», замість сказати «я цього не вмію, ось де подивитись».

Це дає і критерій приймання: **асистент, який жодного разу не збрехав про дані, корисніший
за асистента, який іноді відповідає на питання про дані.**

### 1.2. Рівень 1 — `docs/ai-knowledge/` (їде з кодом)

Окрема тека, **не** наявний інженерний `docs/`: той написаний для того, хто пише код
(RLS, конверти повідомлень, граблі webpack). Асистенту потрібен протилежний реєстр —
мова кінцевого користувача, без жодної згадки Prisma.

Пропонований склад (13 файлів, орієнтир — 20–25k токенів сумарно):

| Файл | Що всередині |
| --- | --- |
| `00-getting-started.md` | що це за продукт, перший вхід, з чого почати |
| `01-navigation.md` | дві навігаційні колонки, area, контекстна панель, `Cmd+B`, хедер, пошук |
| `02-customers.md` | організація vs фізособа, статуси й архівація, нумерація, контакти, вкладка Activity |
| `03-calendar.md` | події, учасники і RSVP, нагадування, all-day, часові зони, «доступ за участю» |
| `04-users-and-roles.md` | адмін створює юзерів, ADMIN vs USER, деактивація, що саме бачить кожна роль |
| `05-account-security.md` | зміна пароля, список пристроїв, «вийти звідусіль», відновлення доступу |
| `06-notifications.md` | інбокс, преференси на тип, unread/read/archived, бейдж |
| `07-files.md` | ліміти розміру й типів, вкладення, чому посилання на файл живе недовго |
| `08-settings-organization.md` | general (назва/локаль/валюта), серії нумерації, дефолти календаря |

| `10-troubleshooting.md` | типові помилки за кодами `ApiError.code` — тими самими, що рендерить i18next |
| `11-glossary.md` | воркспейс/тенант, area, контекстна панель, активність, кастомер vs контакт |
| `12-assistant-policy.md` | межі самого асистента: що він **не** вміє і куди йти замість нього |

Формат — Markdown із front-matter:

```yaml
---
slug: customers
title: Customers
audience: all        # all | admin
area: /customers     # куди веде «читати далі»
---
```

`audience: admin` — не декорація: документи адміна не потрапляють у промпт звичайного
юзера. Це і економія бюджету, і поведінка («не розповідай USER-у, як робити те, чого він
однаково не збереже»).

**Як контент потрапляє в рантайм.** Не читанням `.md` з диска: `Dockerfile.node` копіює в
рантайм-образ тільки `dist`, і зайвий `COPY` — ще одна координована правка, яку легко
забути (той самий клас, що правило №1 у `CLAUDE.md`). Замість цього — **генератор**:
`pnpm ai:knowledge:build` перетворює теку на `libs/shared/src/ai/knowledge/knowledge.generated.ts`
(тексти + порахований `tokenCount` + front-matter), і цей артефакт **комітиться**, рівно як
`openapi.json` і orval-хуки. CI перевіряє, що артефакт не розійшовся з джерелом
(`ai:knowledge:check`) і що рівень 1 вкладається у свій бюджет — це падіння збірки, а не
тиха деградація якості відповідей.

Побічний виграш для форку: щоб замінити всю довідку своїм продуктом, треба переписати теку
і перегенерувати — без жодної правки коду.

### 1.3. Рівень 2 — динамічний контент

Дві незалежні області, одна таблиця:

| Хто пише | Скоуп | Типовий контент |
| --- | --- | --- |
| Платформний суперадмін (`apps/platform-web`) | глобально, всі тенанти | release notes і «що нового», правила самого вендора, контакти підтримки, SLA, відповіді на питання, спільні для всієї інсталяції |
| Tenant Admin (`/settings/ai` в `apps/web`) | лише свій тенант | внутрішні регламенти («як ми називаємо кастомерів»), онбординг нового співробітника, внутрішні контакти, локальні винятки з загальних правил |

Формат вводу в v1 — **Markdown/plain text**: або редактор у UI, або завантаження `.md`/`.txt`
наявним двофазним upload-ом (магічні байти вже валідуються). PDF/DOCX — окремий ланцюг
залежностей на екстракцію, і в базовий скелетон він не входить.

**Ліміти — на збереженні, не на генерації.** У кожного скоупу свій бюджет токенів, і
перевищення — це помилка форми з полем, а не мовчазне обрізання промпту в рантаймі.
Пропоновані слайси від `AI_KNOWLEDGE_TOKEN_BUDGET` (дефолт 40 000):

```
рівень 1 (генерований)   25 000   ← перевіряється в CI
рівень 2 глобальний       8 000   ← перевіряється в platform-api
рівень 2 тенанта          7 000   ← перевіряється в api
```

### 1.4. Порядок у промпті — це питання ціни, а не смаку

Prompt caching у всіх кандидатів працює **по префіксу**. Тому порядок жорсткий, від
найстабільнішого до найзміннішого:

```
1. системна інструкція (роль, межі, мова відповіді)   ─┐ однакові для всієї
2. корпус рівня 1 (генерований артефакт)              ─┘ інсталяції → спільний кеш
3. глобальні документи рівня 2                        ─┐ гілка кешу на тенант
4. документи рівня 2 цього тенанта                    ─┘
5. історія розмови (останні N ходів)
6. питання користувача
```

Ставити знання після історії — значить платити повну ціну за 30k токенів на кожен хід
(різниця в 50–100× за прайсом, див. §2.3).

### 1.5. Коли знадобиться retrieval

Не в v1. Поки сумарний корпус вкладається в бюджет, **повне вкладення дешевше і точніше**
за будь-який RAG: немає ні втрати релевантного шматка на етапі пошуку, ні інфраструктури
ембедингів. Retrieval стає потрібним, коли рівень 2 переросте свій слайс — і тоді перший
крок це **Postgres FTS** (`tsvector` + GIN по секціях документа), а не вектори: розширення
в стоковому `postgres:17-alpine` немає, і `pgvector` означає власний образ БД у кожному
форку. Вектори лишаються документованим opt-in шляхом, а не дефолтом (фаза AI-4).

## 2. Провайдер і стартова модель

### 2.1. Чому base URL за замовчуванням — OpenRouter

Кандидати оцінювались за критерієм «що найдешевше зняти форку, який хоче іншого вендора».

| Варіант | За | Проти |
| --- | --- | --- |
| **OpenRouter** | буквально drop-in OpenAI API (`https://openrouter.ai/api/v1`); зміна вендора = зміна одного рядка `AI_MODEL`; політика приватності з маршрутизацією **лише через провайдерів без логування**; безкоштовні моделі для dev і демо | посередник у ланцюгу даних; +5.5% на поповненні кредитів (BYOK безкоштовний до $25k/міс) |
| OpenAI напряму | еталон сумісності; ZDR за окремим погодженням | найдорожчий рівень цін; прив'язка до одного вендора в дефолті скелетона |
| DeepSeek напряму | найдешевші токени ринку; кеш-хіт $0.003/1M | **за замовчуванням тренується на даних API і зберігає їх у КНР** — неприйнятно як дефолт форкабельного продукту для ЄС |
| Groq / Together / Fireworks | швидкість, OpenAI-сумісність | той самий клас, що OpenRouter, але без єдиного ключа на всіх вендорів |
| Локальний Ollama / vLLM | нуль зовнішніх даних | потребує GPU; як дефолт скелетона непридатний, як документована опція — так |

**Рішення: дефолт `.env.example` — OpenRouter**, і всі перелічені варіанти лишаються
доступними без жодної правки коду, бо конфіг — це три змінні (`AI_BASE_URL`, `AI_API_KEY`,
`AI_MODEL`). Саме це і є «реалізація проти OpenAI-сумісного формату» з етапу 1.

Окремо — про DeepSeek: **сама модель не проблема, проблема — first-party endpoint**.
`deepseek/deepseek-v4.1-flash` через OpenRouter із увімкненою політикою ZDR-маршрутизації
знімає і тренування на даних, і питання юрисдикції, зберігаючи ціну.

### 2.2. Стартова модель

Профіль навантаження: великий стабільний префікс (знання), коротке питання, коротка
відповідь, жодного tool-calling, потрібен пристойний instruction-following і чесне «я не
знаю». Це задача для **дешевої швидкої моделі з кешем**, не для флагмана.

Ціни (OpenRouter, $ за 1M токенів, зняті 2026-09-20):

| Модель | in | out | кеш-рід | ctx |
| --- | --- | --- | --- | --- |
| `openai/gpt-5.6-luna` | 0.20 | 1.20 | 0.02 | 1.05M |
| `google/gemini-3.1-flash-lite` | 0.25 | 1.50 | 0.025 | 1.05M |
| `minimax/minimax-m3` | 0.30 | 1.20 | 0.06 | 1.05M |
| `deepseek/deepseek-v4.1-flash` | 0.15 | 0.60 | 0.003 | 1.05M |
| `qwen/qwen3.7-flash` | 0.03 | 0.13 | 0.006 | 1M |

**Рекомендація: `openai/gpt-5.6-luna` як дефолт** — найкращий баланс «тримає 30k контексту
без деградації / дешевий кеш / впізнаваний рівень instruction-following», і воно ж
найближче до поведінки, під яку промпт писатиметься. `deepseek/deepseek-v4.1-flash` —
документований «економ»-варіант, `qwen/qwen3.7-flash` — «майже безкоштовно, для демо».

Дефолт **не зашивається в код**: константа живе в `.env.example` і в доці, а в конфізі це
обов'язкове поле без fallback-у. Модель, зашита в код, протухає швидше за будь-який
документ.

### 2.3. Скільки це коштує насправді

Теплий кеш, 30k токенів знань, 500 токенів відповіді:

| Модель | за хід | 1 000 ходів/міс |
| --- | --- | --- |
| `gpt-5.6-luna` | ~$0.0012 | ~$1.20 |
| `gemini-3.1-flash-lite` | ~$0.0015 | ~$1.50 |
| `deepseek-v4.1-flash` | ~$0.0004 | ~$0.40 |

Холодний кеш (перший хід після зміни знань) — приблизно ×5.

Висновок, який визначає §3: **звичайне користування не коштує нічого**. Бюджетний ризик —
це не юзери, а цикл «щось зациклилось і молотить API», і захист треба будувати саме проти
нього, а не проти надмірно допитливого користувача.

### 2.4. Клієнт до провайдера

Рекомендація — офіційний пакет `openai` з підміненим `baseURL`, а не власний `fetch`:
розбір SSE має неочевидні краї (UTF-8 на межі чанка, `[DONE]`, `retry-after`, обрив
з'єднання посеред кадру), і це класичний код, який пишеться за годину, а доводиться
місяцями. Пакет усе одно схований за власним інтерфейсом `LlmProvider`, тому заміна
лишається однією правкою. Ціна — ще один external у webpack-конфізі воркера.

## 3. Бюджет і захист від зловживання

Чотири незалежні рубежі. Жоден з них не «головний» — головне, що вони не мають спільної
точки відмови.

### 3.1. Структурні стелі (нічого не коштують, працюють завжди)

| Змінна | Дефолт | Що обмежує |
| --- | --- | --- |
| `AI_MAX_INPUT_CHARS` | 4 000 | контрактом Zod, тому 4001-й символ — це 422, а не рахунок |
| `AI_MAX_OUTPUT_TOKENS` | 1 024 | `max_tokens` у запиті — стеля вартості **одного** ходу |
| `AI_HISTORY_TURNS` | 10 | скільки минулих ходів їде в промпт (решта лишається в БД, але не в контексті) |
| `AI_KNOWLEDGE_TOKEN_BUDGET` | 40 000 | §1.3 |
| `AI_REQUEST_TIMEOUT_MS` | 60 000 | `AbortController` на виклик провайдера |

Завдяки їм розмір **будь-якого** запиту відомий згори ще до того, як його хтось надішле.

### 3.2. Частота — наявний throttler

Нові іменовані ліміти в `RATE_LIMITS` (`libs/shared/src/auth/throttler/`), поріг через env
за наявним патерном:

```
AI_ASK_LIMIT_PER_MINUTE=10          # на користувача
AI_ASK_TENANT_LIMIT_PER_MINUTE=60   # стеля тенанта
```

Нічого нового будувати не треба — Valkey-сторедж, fail-open і заголовок `Retry-After` вже є.

### 3.3. Квоти токенів — доменна таблиця

`ai_usage_counters (tenant_id, user_id, period_date, requests, prompt_tokens, completion_tokens)`,
під RLS, оновлюється **в тій самій транзакції**, що й запис готової відповіді.

```
AI_USER_DAILY_TOKEN_QUOTA=100000
AI_TENANT_DAILY_TOKEN_QUOTA=1000000
```

Перевірка — перед публікацією команди, в тій самій транзакції, що пише повідомлення юзера.
Перевищення → `ApiError` з кодом `AI_QUOTA_EXCEEDED` (текст рендерить i18next, як усюди).
Лічильник дає безкоштовно й екран «використано цього місяця» в `/settings/ai`.

Свідомо **оптимістична** модель: квота перевіряється до генерації, а списується після.
Перевищити її можна рівно на один хід — і це правильний компроміс, бо альтернатива
(резервування з поверненням) — це двофазний комміт заради $0.001.

### 3.4. Паралелізм — те, чого сьогодні немає

Це найважливіша знахідка розділу. `MessageWorkerRegistrar` реєструє споживачів через
`boss.work(queue, handler)` **без опцій**, а дефолти pg-boss v12 — `batchSize: 1`,
`localConcurrency: 1`, `pollingIntervalSeconds: 2`. Для листів і мініатюр це нормально.
Для AI це означає:

- **вся інсталяція генерує одну відповідь за раз** — другий юзер чекає, поки догенерується
  перший (10–30 с);
- до кожної відповіді додається **0–2 с** очікування опитування черги ще до першого токена.

Тому `ConsumerSpec` у `MESSAGE_TOPOLOGY` розширюється опціями воркера, і рядок AI виглядає так:

```ts
{
  definition: generateAiReplyCommand,
  consumers: [{
    id: 'ai-generator',
    retryLimit: 1,
    retryDelaySeconds: 2,
    localConcurrency: 4,       // паралельні генерації на ноду
    groupConcurrency: 2,       // не більше 2 одночасних на ТЕНАНТ, глобально
    pollingIntervalSeconds: 0.5,
    expireInSeconds: 120,      // замість дефолтних 15 хв
  }],
}
```

`groupConcurrency` (pg-boss рахує його в БД, крос-нодово) — це готова, вбудована
**справедливість між тенантами**: один тенант фізично не може зайняти всіх воркерів.
Ключ групи передається на публікації: `group: { id: tenantId }`.

`pollingIntervalSeconds: 0.5` навмисно обрано замість `useListenNotify: true`: notify дав би
мілісекунди замість пів секунди, але це **інстанс-рівнева** опція, яка вмикає LISTEN на
всю систему, а `realtime.md` уже один раз відхилив `LISTEN/NOTIFY` як глобальний ресурс
кластера. Пів секунди коштує один зайвий запит на 500 мс в одній черзі — і не чіпає нічого
поза AI. `notify` лишається задокументованим апгрейдом, якщо TTFT колись стане вузьким місцем.

### 3.5. Останній рубіж — на боці провайдера

Жоден код у застосунку не захистить від рахунку, якщо в ньому є баг. Тому в
`docs/deploy-swarm.md` і в `.env.example` — явний операційний пункт: **на ключі провайдера
має бути виставлена жорстка місячна стеля витрат**. І OpenRouter, і OpenAI це вміють, це
робиться за хвилину і коштує нуль. Інсталяційної квоти в коді натомість **не робимо**: її
довелось би рахувати крос-tenant під `BYPASSRLS` на гарячому шляху, що дорожче й слабше за
стелю в кабінеті провайдера.

## 4. Стрімінг у v1

### 4.1. Рішення

**Так, стрімінг у v1 — але чанками, а не токен-за-токеном.**

Чанк коалесується у воркері за часом: `AI_STREAM_FLUSH_MS` (дефолт 120 мс) або на межі
абзацу — що настане раніше.

### 4.2. Чому не «спершу одним шматком»

Не тому, що очікування нестерпне (3–6 с зі спінером — терпимо), а тому, що **дострой
стрімінгу пізніше — це не додавання, а зміна контракту**: з'являються нові socket-події,
часткова персистентність, скасування, поведінка при reconnect. Усе це однаково потрібне для
надійності (§4.4), тож «одношматкова» версія економить не роботу, а лише рядків 80 клієнта.

Зате **зворотна сумісність куплена дешево**: `AI_STREAMING=false` змушує провайдера
віддати одну дельту + completed. Протокол той самий, рішення оборотне конфігом, а не
рефакторингом.

### 4.3. Чому не токен-за-токеном

Кількісний аргумент. Valkey Streams-адаптер у цьому репозиторії налаштований на
`maxLen: 10 000`. Відповідь на 500 токенів — це 500 записів у стрім. Двадцять одночасних
генерацій виносять **увесь** буфер стріму за один цикл відповіді, і нода, яка в цей момент
дочитує пропущене після короткого розриву, втрачає presence- і notification-події.
Коалесування по 120 мс дає ~80–100 записів на ту саму відповідь — у 5–6 разів менше, при
тому що людина різниці не бачить: 120 мс це нижче порогу, на якому текст читається як
«друкується».

### 4.4. Протокол

Нові socket-події (в `libs/contracts/src/realtime/`, іменування з версією, як усюди):

| Подія | Payload |
| --- | --- |
| `ai.message-delta.v1` | `{ conversationId, messageId, chunkSeq, text }` |
| `ai.message-completed.v1` | `{ conversationId, messageId, status, usage? }` |

Емісія — в `userRoom(tenantId, userId)`: розмова персональна, а всі вкладки того самого
юзера мають бачити один і той самий потік.

**Правило `realtime.md` «socket-подія не є доставкою» лишається чинним**, і саме тому в
дельті є `chunkSeq`: розрив у нумерації або reconnect → клієнт іде за `GET /ai/conversation`
і читає поточний (можливо, частковий) стан із Postgres. Втрата дельти сповільнює рендер,
але нічого не втрачає — джерелом правди й далі лишається БД.

### 4.5. Життєвий цикл генерації у воркері

Критична вимога: **транзакція не тримається відкритою через виклик LLM**.

```
tx1 (withTenantTx)   прочитати розмову + історію, status = STREAMING
   ↓
без транзакції       стрім від провайдера → коалесування → емісія дельт
                     кожні ~2 с — короткий UPDATE часткового тексту
   ↓
tx2 (withTenantTx)   фінальний content + usage + status = COMPLETE
                     + інкремент ai_usage_counters
                     + onCommit(...) → емісія ai.message-completed.v1
```

Часткова персистентність кожні ~2 с — не надмірність: вона ж дає відновлення після
перезавантаження сторінки посеред генерації і після краху воркера.

**Ідемпотентність — по бізнес-факту, а не через `MessageInboxService.runOnce`.** `runOnce`
тут був би помилкою: він заблокував би легальний ретрай після 503 від провайдера. Якорем є
статус рядка `ai_messages`: генеруємо, тільки якщо `PENDING`/`STREAMING`; `COMPLETE` —
тихий вихід. Ретрай скидає накопичений текст і шле дельту з `chunkSeq: 0`, по якій клієнт
очищає буфер.

### 4.6. «Зупинити генерацію»

Кнопка Stop → `POST /ai/conversation/messages/:id/cancel` → api публікує в Valkey
(`PUBLISH ai:cancel:{messageId}`) → воркер, який у цей момент читає стрім, має підписку і
рве `AbortController`. Pub/sub, а не прапорець у БД: воркер усередині читання потоку не
опитує базу, а ioredis у нього вже є (той самий, що в `WorkerRealtimeEmitter`).

Скасована відповідь **зберігається** з тим, що встигло згенеруватись, і статусом
`CANCELLED`, а витрачені токени списуються в квоту — інакше Stop стає безкоштовним способом
крутити провайдера.

## 5. Зберігання розмов і приватність

### 5.1. Головна властивість — вона архітектурна, а не процедурна

Через рішення «без tool-calling» назовні їде рівно три речі: **згенерований корпус знань**,
**документи рівня 2** і **те, що юзер сам надрукував**. Жоден рядок `customers`, `users`
чи `calendar_events` не має шляху в промпт — не тому, що хтось пообіцяв його не класти, а
тому, що функція збірки промпту таких аргументів не приймає.

Щоб ця властивість не розмилась першою ж «маленькою зручністю», контекст користувача в
промпті — **закритий allowlist**:

```ts
{ role: 'ADMIN' | 'USER', locale: string, currentArea?: string }
```

Без `email`, без `name`, без назви тенанта. Роль потрібна для фільтра `audience`, локаль —
щоб відповідь була мовою юзера, area — щоб «як це зробити тут» мало сенс.

### 5.2. Що саме зберігаємо

| Таблиця | Скоуп | Доступ |
| --- | --- | --- |
| `ai_conversations` | tenant + owner | RLS дає межу тенанта; **власність перевіряє сервіс** — чужу розмову не бачить навіть ADMIN (та сама доктрина, що приватні події в календарі) |
| `ai_messages` | tenant | `seq` у межах розмови, `status`, `content`, `model`, токени, латентність |
| `ai_knowledge_documents` | tenant **nullable** | перший реальний споживач «довідників рівня 3» із беклогу MT-4: RLS `USING (tenant_id IS NULL OR tenant_id = ctx)` на читання, запис свого тенанта з `saas_app`, глобальних рядків — лише з `saas_platform` |
| `ai_usage_counters` | tenant | §3.3 |

Дві граблі міграції, які варто записати одразу:

1. «Одна активна розмова на юзера» — це **частковий унікальний індекс**
   (`WHERE status = 'ACTIVE'`), якого Prisma не вміє: сирий SQL у міграції, за наявним
   патерном колапсу сповіщень.
2. `@@unique([tenantId, slug])` при nullable `tenantId` у Postgres **не працює як очікується**
   — NULL-и вважаються різними. Потрібен `UNIQUE NULLS NOT DISTINCT` (є з PG 15, у нас 17).

### 5.3. Retention

- Дефолт `AI_RETENTION_DAYS=90`, cron-команда `ai.purge-conversations` (`scope: 'system'`),
  за патерном `cleanup-orphan-files`.
- Видалення **жорстке**: на відміну від чату, тут немає `seq`-цілісності, яку ламає дірка.
- Тенант може вкоротити строк у `/settings/ai`, але не подовжити понад інсталяційний.
- Кнопка «видалити мої розмови» — негайно, без cron-у. Це мініатюра права на стирання, і
  коштує вона один DELETE.
- Логи: тіла промптів і відповідей **ніколи** не пишуться на рівні `info`; `debug` — і
  ніколи в проді. Те саме правило, що вже діє для токенів і PII у realtime-логах.

### 5.4. Що має бути сказано вголос

- **Розкриття в інтерфейсі.** Стаття 50 EU AI Act діє з 2 серпня 2026 — взаємодія з AI має
  бути очевидною **в самій взаємодії**, а не в умовах використання. Практично: рядок у
  шапці `AiPanel` («Відповідає AI-асистент, може помилятись») і той самий підпис у порожньому
  стані. Вартість — один рядок, відсутність — регуляторний дефект.
- **Провайдер = субпроцесор.** У `docs/deploy-swarm.md` і в `.env.example` — прямий абзац:
  оператор форку мусить внести обраного провайдера у свій перелік субпроцесорів і DPA, а
  для ЄС — увімкнути маршрутизацію без логування (OpenRouter: privacy settings) або взяти
  ендпоінт у потрібній юрисдикції. Дефолти, які скелетон пропонує, вибрані так, щоб це було
  можливо; зробити це за оператора скелетон не може.
- **Рівень 2 теж їде назовні.** Екран завантаження знань тенант-адміном має нести це
  попередження на самому екрані, а не в доці: людина, яка вантажить внутрішній регламент,
  повинна бачити, що він поїде до LLM-провайдера.
- **Тумблер відмови.** `settings.ai.enabled` на рівні тенанта: вимкнено → панель не
  рендериться, ендпоінти відповідають 403. Це і є справжня відповідь на «а якщо в нас є
  дані, які не можна віддавати назовні».
- **Автоматичної редакції секретів у v1 немає.** Regex-фільтр дає хибну впевненість і
  хибні спрацювання; чесніше — підпис у композері. Опційно в AI-3: блокувати (не
  вирізати!) ввід із очевидними ключами (`sk-…`, `Bearer …`) із явним поясненням.

## 7. Що НЕ лягає на наявну архітектуру як є

1. **`boss.work()` без опцій** — §3.4. Найбільша правка поза власним модулем: `ConsumerSpec`
   і `MessageWorkerRegistrar` мають навчитись `localConcurrency` / `groupConcurrency` /
   `pollingIntervalSeconds` / `expireInSeconds`, а `MessagePublisher` — передавати `group`.
2. **Послідовний цикл у хендлері.** Зараз реєстратор робить `for (const job of jobs)` —
   із `localConcurrency` це коректно (кілька воркерів на чергу), але `batchSize > 1` тут
   дав би послідовність замість паралельності. Для AI лишаємо `batchSize: 1`.
3. **Довгі виклики і транзакції.** Правило «не тримати `withTenantTx` через мережевий
   виклик» у репозиторії ще не траплялось — тут воно стає обов'язковим (§4.5).
4. **Дельти як корисне навантаження.** Уперше socket несе не «перечитай», а сам текст.
   Правило рятує `chunkSeq` + REST-фолбек (§4.4) — це варто зафіксувати явно, інакше
   наступний домен скопіює «socket як доставку» вже без страховки.
5. **Текст із бекенда.** `i18n-plan.md` каже «бекенд емітить коди, не текст». Відповідь
   асистента — **контент**, а не UI-копія, і це задокументований виняток; коди й далі
   обов'язкові для всього, що довкола.
6. **Рендер Markdown на фронті.** Нова залежність (`react-markdown` + `remark-gfm`), без
   `rehype-raw` і без `dangerouslySetInnerHTML` — інакше відповідь LLM стає XSS-вектором.
7. **Нові external у webpack** для пакета `openai` у воркері (той самий клас правок, що
   `pg-boss` і `file-type`).
8. **Глобальні рядки знань** вимагають RLS-політики рівня 3 і `GRANT`-ів — перший випадок
   у репозиторії, сирий SQL у міграції.

| Фейковий провайдер | **є з AI-0**, стрімить канонований текст | той самий прийом, що `PaymentProvider` → fake → Stripe: весь конвеєр і e2e без ключа і без витрат |

| Квота | оптимістична: перевірка до, списання після | перевищення максимум на один хід ≈ $0.001; резервування з поверненням не варте двофазності |

| Токен-за-токеном | **ні** | 500 записів у Valkey-стрім на відповідь виносять `maxLen: 10 000` двадцятьма паралельними генераціями |
| Ідемпотентність генерації | статус рядка `ai_messages`, **не** `runOnce` | `runOnce` заблокував би легальний ретрай після 503 провайдера |
| Скасування | Valkey pub/sub → `AbortController`; частковий текст зберігається, токени списуються | воркер усередині стріму не опитує БД; безкоштовний Stop = безкоштовне зловживання |
| Доступ до розмов | власність перевіряє сервіс; ADMIN чужу не бачить | RLS — межа тенанта, не межа людини (та сама доктрина, що приватні події) |
| Контекст юзера в промпті | закритий allowlist `role` / `locale` / `currentArea` | інакше перша «маленька зручність» проб'є єдину справжню гарантію приватності |
| Retention | 90 днів, жорстке видалення, cron `ai.purge-conversations`, кнопка «видалити зараз» | немає `seq`-цілісності, яку ламало б видалення |
| Розкриття AI | видимий підпис у панелі | Ст. 50 EU AI Act діє з 2026-08-02 і вимагає розкриття **в самій взаємодії** |
| Відмова від фічі | `settings.ai.enabled` на тенант | єдина справжня відповідь на «нам не можна віддавати дані назовні» |
| Редакція секретів | у v1 немає, тільки підпис у композері | regex дає хибну впевненість і хибні спрацювання |

## 9. Фази

| Фаза | Обсяг | Передумови |

| **AI-0 — конвеєр на фейковому провайдері** | `ai_conversations` + `ai_messages` + RLS; контракти `libs/contracts/src/ai/`; `GET /ai/conversation`, `POST /ai/conversation/messages`, `POST /ai/conversation/reset`, `POST …/:id/cancel` (без id суб'єкта в шляху — доктрина `/account`); команда `ai.generate-reply` + опції воркера в `ConsumerSpec` (§3.4); інтерфейс `LlmProvider` + **`FakeLlmProvider`**, що стрімить канонований текст; дві realtime-події + `chunkSeq`; `AiPanel` у шелі з кнопкою в хедері, підписом-розкриттям і рендером Markdown; e2e наскрізь — **без ключа і без витрат** | немає, усе спирається на готові шари |
| **AI-1 — справжній провайдер і знання рівня 1** | `OpenAiCompatibleProvider` (`openai`, `stream_options.include_usage` для обліку токенів у стрімі); Zod-валідація env у воркері; `docs/ai-knowledge/` (13 файлів) + генератор + закомічений артефакт + перевірка бюджету в CI; збірка промпту з фільтром `audience`; частковий-текст-кожні-2-с і фінальна транзакція з обліком; `ai_usage_counters` + квоти; ліміти в throttler; скасування через Valkey; cron retention; розділ у `deploy-swarm.md` про стелю витрат і субпроцесора | AI-0 |
| **AI-2 — знання рівня 2** | `ai_knowledge_documents` за патерном довідників **рівня 3** (nullable `tenant_id`, RLS `IS NULL OR = ctx`, глобальний запис лише з `saas_platform`); редактор `/settings/ai` для Tenant Admin (+ попередження «це поїде до провайдера»); редактор глобальних документів у `apps/platform-web`; імпорт `.md`/`.txt` наявним upload-ом; бюджет на збереженні; `settings.ai.enabled`; посилання на джерела у відповіді (модель повертає `SOURCES:` зі slug-ами, сервер валідує проти відомих — вигадані відкидаються) | AI-1, MT-беклог рівня 3 |
| **AI-3 — зрілість** | екран «використано» в `/settings/ai` і зведення по інсталяції в `apps/platform-web` → Operations; оцінка відповіді (👍/👎 + причина) як дані для підкрутки промпту; експорт транскрипту; блокування вводу з очевидними секретами; видимість провалів генерації в DLQ-екрані; перевизначення квот тенанта з control plane | **EDA-2** (DLQ/replay UI) |
| **AI-4 — retrieval** | коли рівень 2 переростає бюджет: чанкування документів по секціях + пошук `tsvector`/GIN, збірка промпту з N найрелевантніших секцій замість повного корпусу; `pgvector` — документований opt-in шлях для форку (власний образ БД) | AI-2 |

Мінімальний корисний зріз — **AI-0 + AI-1**: разом вони дають працюючого асистента довідки,
а AI-0 окремо цінний тим, що весь конвеєр (черга → воркер → сокет → UI → e2e) стає
перевіреним ще до того, як з'явиться перший рахунок від провайдера.

## 10. Відкриті питання (потрібне рішення користувача, не технічне)

1. **Хто платить за токени в multitenant-інсталяції.** Зараз усе за рахунок оператора
   інсталяції, з квотами як єдиним регулятором. Питання «перевиставляти тенанту» —
   відкрите і впирається в білінг, якого ще немає. *Рекомендація: лишити як є; лічильники
   з §3.3 уже збирають усе, що знадобиться для перевиставлення, коли з'явиться білінг.*
2. **Дефолт `AI_ENABLED`.** *Рекомендація: `false`.* Скелетон без ключа не повинен показувати
   зламану панель; вмикається свідомо, разом із ключем.
3. **Чи показувати юзеру модель і витрачені токени.** *Рекомендація: юзеру — ні (шум),
   адміну в `/settings/ai` — так (це його рахунок).*
4. **Мова відповіді при `locale: en`-only.** Сьогодні i18n — лише `en`, але модель уміє
   більше. *Рекомендація: відповідати мовою питання, а не мовою інтерфейсу — це те, чого
   людина очікує, і воно не конфліктує з I18N-4.*
5. **Ліміт довжини розмови.** `AI_HISTORY_TURNS=10` ріже контекст, але розмова росте далі.
   *Рекомендація: після 50 ходів пропонувати «почати нову» ненав'язливим підписом —
   примусового обриву не робити.*
6. **Чи зберігати повний текст промпту для розбору інцидентів.** *Рекомендація: ні;
   зберігаються питання і відповідь, а промпт відтворюється з версії артефакту знань —
   тому в `ai_messages` варто тримати `knowledgeVersion`.*

## 11. Свідомо поза скоупом

Tool-calling по живих даних тенанта (лишається форкам — але саме він є причиною, чому
§5.1 працює); голосовий ввід; завантаження зображень і PDF у розмову; кілька паралельних
розмов і екран історії (закрито на етапі 1); per-tenant ключі й вибір моделі через UI
(закрито на етапі 1); власний fine-tuning; агентські дії («створи кастомера за мене»);
оцінювання якості моделей автоматичними evals у CI; `pgvector` у дефолтному деплої.

# WhatsApp: потоки по фічах

**Статус: дизайн, нічого не збудовано (2026-10-13).** Для кожної фічі WhatsApp-каналу — як вона
виглядає в UI, що робить система, які виклики Meta ми робимо і які вебхуки приходять. Рішення,
архітектура, фази й каталог фіч — у [whatsapp-channel.md](whatsapp-channel.md); сирі факти API —
у [whatsapp-research/meta-cloud-api.md](whatsapp-research/meta-cloud-api.md). Тут — лише «як це
працює крок за кроком», щоб за цим документом можна було реалізовувати без пошуків у розмовах.

Позначки: **(R)** — з памʼяті/не підтверджено локальною документацією Meta, звірити на живому
акаунті (див. [whatsapp-channel.md](whatsapp-channel.md) §8). Фази — CHAT-2a…3c з §6 того ж документа.

Усі виклики Meta йдуть на `https://graph.facebook.com/{версія}/…` із заголовком
`Authorization: Bearer <токен акаунта>`; версія Graph — одна, налаштовувана (не зашита в коді
розрізнено, як у Chatwoot).

## F0. Підготовка в Meta (разово, робить власник бізнес-акаунта)

Це не код, а передумови, без яких перевірка на живому акаунті неможлива.

### F0.1. Що має бути
| Що | Де взяти | Для чого нам |
| --- | --- | --- |
| Meta Developer app з продуктом WhatsApp | developers.facebook.com → My apps → use case «Connect with customers through WhatsApp» | власник вебхуків і секрету підпису |
| Business portfolio | вибирається/створюється при створенні app | власник WABA і системного користувача |
| **WABA** (WhatsApp Business Account) і його id | WhatsApp Manager / Business settings → Accounts → WhatsApp Accounts; при створенні app Meta створює **тестовий** WABA автоматично | поле «WABA ID» у налаштуваннях тенанта |
| Номер телефону: тестовий (публічний тестовий номер Meta) або реальний | App dashboard → WhatsApp → API setup | канали, що синхронізуються |
| **App secret** | App dashboard → Settings → Basic → App secret | **ключ HMAC для `X-Hub-Signature-256`** — той самий секрет застосунку, що в `debug_token` (`APP_ID\|APP_SECRET`); це не токен доступу. Для спільного застосунку (наш і legacy-api) секрет один |
| **Токен доступу** | §F0.2 | поле «Токен» |
| Публічна HTTPS-адреса нашого API | розгорнутий dev-стенд або тунель (ngrok/cloudflared) до `pnpm api:dev` | Meta не достукається до `localhost`; сертифікат має бути валідним (самопідписані не приймаються) |

### F0.2. Токен: системний користувач (варіант A)
(за `access-tokens.md`)

1. Business settings (`business.facebook.com/settings`) → **System users** → **Add** → імʼя, роль:
   **Admin** (бачить усі WABA портфеля) або **Employee** (лише призначені).
2. У користувача → **Assign assets** → вибрати app → право **Manage app** (повний контроль). Права
   зʼявляються з затримкою в кілька хвилин — перезавантажити сторінку.
3. Для **Employee** додатково: Accounts → WhatsApp Accounts → потрібний WABA → вкладка
   *WhatsApp Account Access* → **Add people** → цей системний користувач → рівень доступу Full/Partial.
4. **Generate token**: вибрати app, строк дії (60 днів або «ніколи»; безстроковий підтверджено 2026-10-13), права
   `business_management`, `whatsapp_business_management`, `whatsapp_business_messaging`. Токен
   показується **один раз** — скопіювати.
5. Перевірка: `GET /debug_token?input_token=<токен>` → `is_valid: true`, `type: SYSTEM_USER`,
   `expires_at: 0` (безстроковий), `scopes` містять обидва `whatsapp_*`.

Тимчасовий токен із *API setup* (генерується при кожному відкритті панелі, живе від хвилин до
годин) годиться лише для першого «димового» тесту; продукт приймає його з бейджем «тимчасовий»
(`tokenKind = temporary`) і зворотним відліком. Системного користувача для **тестового** WABA створити можна
(підтверджено пробою 2026-10-13), тож тимчасовий токен не потрібен.

### F0.3. Вебхук на рівні застосунку (мінімально потрібний)
Навіть коли ми перевизначаємо callback на рівні WABA (§F3), **в app dashboard** треба:
1. WhatsApp → Configuration → **Callback URL** + **Verify token** — Meta одразу робить GET-рукостискання
   (`hub.mode=subscribe&hub.challenge=…&hub.verify_token=…`); наш ендпоінт має відповісти `hub.challenge`.
2. Підписати **поля** вебхука (R — перелік у dashboard): `messages`, `message_template_status_update`,
   `message_template_quality_update`, `message_template_components_update`,
   `template_category_update`, `phone_number_quality_update`, `phone_number_name_update`,
   `account_update`, `account_alerts`, `business_capability_update`, `user_preferences`.
3. Вебхуки **шаблонів і акаунта завжди йдуть на callback застосунку** (не перевизначаються), тож цей
   URL — наш «застосунковий» вхід `/public/channels/meta_cloud/app` (маршрутизація за WABA id).
4. **Dev-спрощення для одного тестового тенанта:** задати callback застосунку прямо на
   `…/public/channels/meta_cloud/{webhookKey}` цього тенанта — перевизначення на WABA тоді не потрібне.

### F0.4. Тестовий номер
- Публічний тестовий номер Meta шле повідомлення лише на **allow-список отримувачів** (одне джерело —
  до 5 номерів): API setup → поле *To* → *Manage phone number list*; кожен номер підтверджується кодом.
  Поза списком — помилка `131030`.
- Вхідне до тестового номера — з телефону, доданого в список. Вікно 24 год відкривається так само.
- Тестовий WABA може не віддавати частину полів (напр. `account_mode`) — синхронізація має терпіти
  відсутні поля.

### F0.5. Що перевірити першим на живому акаунті (задача 0 фази CHAT-3a)
Короткий скрипт `scripts/whatsapp-probe.ts` (поза продуктом), що по черзі робить: `debug_token` →
`GET /{waba}` → `GET /{waba}/phone_numbers` → `GET /{waba}/subscribed_apps` → `POST /{waba}/subscribed_apps`
з `override_callback_uri` (на тестовому WABA) → `GET /{waba}/message_templates` → відправка тестового
повідомлення на номер зі списку → прийом вебхука. Секрети скрипт читає з кореневого `.env` (змінні `WHATSAPP_*`, заповнює власник; файл у `.gitignore`).
Результати: [whatsapp-channel.md](whatsapp-channel.md) §8.1 і [whatsapp-research/live-probe-2026-10-13.md](whatsapp-research/live-probe-2026-10-13.md) (проба виконана 2026-10-13: читання, шаблон, текст у вікні; вебхук і `subscribed_apps` POST — ні). Лишилось: вебхук і запис `subscribed_apps`
(§F3) — після того, як буде окрема публічна адреса, не спільна з legacy-api.

### F0.6. MCP-сервери Meta — необов'язково, не блокує роботу
Meta (вересень 2026) випустила MCP-сервери для керування WABA через асистента: *WhatsApp Business Tools*
(`https://mcp.facebook.com/whatsapp_business_tools`, Streamable HTTP, OAuth) і *Social Technologies*
(застосунок, вебхуки). Вони лише обгортка над Graph API — нічого, чого не вміє Graph API.
- **Розгортання поступове.** Станом на 2026-10-13 акаунт власника після OAuth отримав
  «Not yet available for your account — … gradually rolled out». Це серверна відмова Meta, а не помилка
  налаштування. Критеріїв доступу, черги чи форми запиту в документації немає (анонс 2026-09-15:
  «may not be available to everyone yet»).
- **Сервер уже додано** в локальну конфігурацію Claude Code (`whatsapp_business_tools`, local scope);
  коли Meta відкриє доступ, достатньо повторити авторизацію через `/mcp`.
- **Рішення:** розробка і проба §F0.5 ідуть через звичайний Graph API (скрипт або Graph API Explorer).
  MCP не є залежністю продукту й не потрапляє в код — це лише інструмент розробника/оператора.
- Через MCP не слід виконувати записи/відправки без явної команди власника.

## F1. Підключення акаунта (налаштування тенанта) — CHAT-3a

> **Збудовано в CHAT-3a (2026-10-14), як і працює.** Налаштування → Messaging: «Connect WhatsApp» (WABA id, токен, App ID і
> App secret — необовʼязково, але лише з парою токен перевіряється, інакше в картці «Not verified»). Прогін для розробника:
> `pnpm chat:connect-meta` (читає `WHATSAPP_*` з `.env`; повторний запуск оновлює токен і синхронізує номери),
> `--send` — розмова з `WHATSAPP_TEST_RECIPIENT` і `hello_world`, `--text` — ще й звичайний текст. Одноразові кроки в Meta — §F0.
> Помилка підключення показується під потрібним полем: токен відхилено, бракує права (`whatsapp_business_*`), токен іншого
> застосунку, немає доступу до WABA, App ID/secret не збігаються. Блок вебхука для Meta-акаунта до 3b — лише пояснення.
> Картка не показує `health_status` (3c). Ручна підписка й вхідні — §F3, 3b.

**UI.** Налаштування → Інтеграції → **WhatsApp**.
- *Не підключено:* форма — **WABA ID**, **Токен доступу**, **App secret** (необовʼязково, якщо задано
  платформний), назва (для себе). Кнопка **Підключити**.
- *Підключено:* картка — статус (Підключено / Потрібна повторна авторизація / Вимкнено), назва WABA,
  токен (маска `…ab12`, тип, «спливає через N днів»), блок **Вебхук** (§F3), таблиця **Номери** (§F2),
  вкладка **Шаблони** (§F8), **Журнал викликів** (§F20). Дії: *Змінити токен*, *Відключити*.

**Система (кнопка «Підключити»).**
1. Зберегти запис `messaging_accounts` зі статусом чернетки; секрети шифруються (`CryptoService`).
2. `debug_token` → перевірити `is_valid`, тип, `expires_at`, `scopes`.
3. `GET /{waba-id}?fields=id,name,account_review_status,business_verification_status` — доступ до WABA.
4. Усе гаразд → `CONNECTED`; згенерувати `webhookKey` і `verifyToken`; поставити в чергу
   синхронізацію номерів і шаблонів (§F2, §F8). Помилка → поле формі:
   | Відповідь Meta | Що бачить адмін |
   | --- | --- |
   | `is_valid: false`, код `190` | «Токен недійсний або прострочений» |
   | немає `whatsapp_business_*` у `scopes` | перелік відсутніх прав |
   | код `200` на `GET /{waba}` | «Токен не має доступу до цього WABA» (системний користувач не призначений) |
   | код `100` | «WABA ID не знайдено» |
5. **Відключити:** `DELETE /{waba-id}/subscribed_apps`, акаунт → `DISABLED`, усі канали → вимкнені;
   розмови й повідомлення **лишаються**.

**Вебхуки:** немає. **Виклики Meta:** `GET /debug_token`, `GET /{waba-id}`.

## F2. Синхронізація номерів — CHAT-3a

**UI.** У картці WhatsApp — таблиця **Номери**: номер (`display_phone_number`), verified name, якість
(зелений/жовтий/червоний/—), статус, ліміт охоплення, перемикач **Увімкнено**, радіо **За замовчуванням**,
бейдж «Зник у Meta», час останньої синхронізації, кнопка **Оновити**. Новий номер зʼявляється
вимкненим із підказкою «Увімкніть, щоб приймати й надсилати». Увімкнення вимагає підписаного вебхука
(інакше попередження).

**Система.**
1. Тригери: після підключення; кнопка; щодоби (cron); вебхуки `phone_number_name_update`,
   `phone_number_quality_update`, `business_capability_update`, `account_update` (подія ставить синхронізацію в чергу,
   не обробляє дані сама).
2. `GET /{waba-id}/phone_numbers?fields=id,display_phone_number,verified_name,quality_rating,code_verification_status,name_status,status,throughput&limit=…` (поля — звірити, R),
   пагінація курсором (`after`).
3. Upsert у `channels` за `externalId = phone_number_id`: оновити відображувані дані, якість, ліміти;
   нові — `isEnabled = false`; відсутні у відповіді — `providerMissingAt = now()` (не видаляти);
   повернулися — зняти позначку.
4. Для увімкнених номерів — `GET /{phone-number-id}?fields=health_status` (R: `can_send_message` +
   причини) і, коли потрібно, `throughput`; результат у `channels.limits`/`health`.
5. Події в браузер: «канали змінилися» (перечитати).

**Вебхуки:** `phone_number_name_update` (результат перевірки імені), `phone_number_quality_update`,
`business_capability_update` (ліміти), `account_update` — лише як тригер синхронізації.
**Виклики Meta:** `GET /{waba}/phone_numbers`, `GET /{phone-number-id}`.

## F3. Підписка на вебхук — CHAT-3b

> **Збудовано в CHAT-3b1 (2026-10-14), як і працює.** Кнопка «Subscribe» біля **номера**, не WABA (§4.13 плану). Рядок
> «Webhooks» показує на льоту, куди Meta зараз веде події номера: «Delivered to this system» / «Not delivered anywhere» /
> «Delivered to <host>». Для чужого хоста кнопка «Take over» просить підтвердження з назвою хоста; після підписки
> цей сервіс не отримує хуків номера, поки не натиснути «Unsubscribe». Адреса: `<CHANNEL_WEBHOOK_BASE_URL>/api/public/channels/meta_cloud/<ключ>`;
> Meta ходить на неї під час самої підписки, тож сервер має бути вже розгорнутий і акаунт підключений **на ньому**.
> «Show received webhooks» — захоплені хуки з підписом, станом і тілом. Розбір подій у цьому зрізі вимкнено.

**UI.** Блок **Вебхук** у картці: адреса (`…/public/channels/meta_cloud/{webhookKey}`) із кнопкою
«Копіювати», verify token, стан: *Не підписано / Підписано (override) / Підписано (на рівні app)*,
«Останній вебхук: N хв тому» (з `channel_webhook_events`), кнопки **Підписати**, **Перепідписати**,
**Скасувати підписку**.

**Система.**
- *Підписати:* `POST /{waba-id}/subscribed_apps` з `override_callback_uri = <адреса>` і
  `verify_token = <verifyToken акаунта>`; після цього `GET /{waba-id}/subscribed_apps` і показ
  *фактичного* стану (трьохстан «підписано / ні / не вдалося перевірити»). Підписка — явна дія, а не
  побічний ефект збереження чи зміни токена: після зміни токена показується підказка «перепідпишіть».
- *Скасувати:* `DELETE /{waba-id}/subscribed_apps` (прибирає застосунок із WABA — зупиняє вебхуки
  всіх номерів цього WABA; якщо WABA спільний з іншими — попередження, бо це зачепить їх).
- **Спільний WABA/застосунок (з проби 2026-10-13).** На тестовому WABA вже є override іншого проєкту (legacy-dev), і `POST` з нашою адресою його замінить. Тому перед `POST` — завжди `GET` і показ чужого значення з попередженням; запис тільки після підтвердження. Перша перевірка в 3a: перевизначення **на рівні номера** (`/{phone-number-id}`, `webhook_configuration.override_callback_uri`, (R)), яке не зачіпає WABA; деталі й запасні варіанти — [whatsapp-channel.md](whatsapp-channel.md) §8, п.10.
- Пріоритет доставки Meta: номер > WABA > застосунок; шаблонні й акаунтні вебхуки йдуть тільки на
  застосунок (§F0.3).

**Що в UI вже є з 2a (до підписки).** Адреса, verify token, «secret заданий», час останнього вебхука й лічильники за добу — на fake це весь цикл «адреса → доставка → лічильник» без зовнішніх сервісів (симулятор шле на ту саму адресу). У 3b додається лише стан підписки в Meta.

**Вхідний GET-рукостискання** (Meta викликає сама при збереженні callback): `webhookKey` → акаунт →
порівняти `hub.verify_token` → відповісти `hub.challenge`; інакше 403.
**Виклики Meta:** `POST|GET|DELETE /{waba}/subscribed_apps`.

## F4. Вхідне повідомлення (текст) — CHAT-2a (на fake), CHAT-3b2 (Meta, збудовано)

> **CHAT-3b2:** підписаний POST → збереження (3b1) → worker `ingest` → розбір Meta-тіла в події (`webhook-parser.ts`) → контакт за номером, відкрита розмова, повідомлення з часом провайдера; повтор того ж `wamid` нічого не додає; перше вхідне відкриває вікно 24 год. Неімовірні гілки не гублять пакет: зіпсоване — `unsupported`.

**UI.** Клієнт пише на номер → у **Чат → Нерозібрані** зʼявляється розмова (значок WhatsApp, номер/імʼя,
прев'ю, час); у відкритій розмові — бульбашка клієнта, зліва вгорі «WhatsApp · +380…». Для призначеного
агента — сповіщення (дзвіночок + тост) і непрочитане; для нерозібраної — лічильник у чергі.

**Система (вебхук `messages`).**
1. `POST /public/channels/meta_cloud/{webhookKey}` → знайти акаунт → перевірити `X-Hub-Signature-256`
   над сирими байтами → у **одній транзакції** записати `channel_webhook_events` + поставити job
   `channels.ingest-webhook` → відповісти **200**. (Підпис не пройшов → 401, нічого не пишемо;
   невідомий ключ → 200 + `channel_unroutable_events`.)
2. Воркер: розібрати `entry[].changes[]`; для кожного `change` знайти канал за `metadata.phone_number_id`.
3. `messages[]`: `INSERT … ON CONFLICT DO NOTHING` за `(channel, wamid)` — дубль нічого не робить.
4. Контакт за адресою (`wa_id`/BSUID) — знайти або створити; профільне ім'я з `contacts[].profile.name`
   (оновлювати, лише якщо поточне ім'я = номер).
5. Відкрита розмова контакта або нова (reopen-політика); `seq`; `customer_last_message_at` = час Meta;
   клієнт підбирається автоматично, лише якщо збіг рівно один.
6. Лічильники, емісія в браузер після коміту, `publish(chat.message-posted.v1)` → сповіщення.

**Вебхуки:** `messages` (`messages[]`). **Виклики Meta:** немає (медіа — §5).

## F5. Вхідні медіа та інші типи — CHAT-2c (на fake), CHAT-3b2 (заглушки на Meta), CHAT-2c (повноцінні)

> **CHAT-3b2:** до медіа-пайплайну кожен не-текстовий тип (`image`, `document`, `audio`, `video`, `sticker`, `location`, `contacts`, `interactive`, `button`, `reaction`, `system`, невідомий) стає повідомленням `[<type>]` з `payload.unsupported.type`, а стрічка показує «Message not supported (<type>)». Нічого не завантажується, реакція не чіпає цільове повідомлення.

| Тип у вебхуці | Що бачить агент | Системні дії |
| --- | --- | --- |
| `image`, `video`, `document`, `sticker` | прев'ю/плитка файлу з підписом, стан «завантажується» → готово/помилка | рядок `PENDING` + job `channels.fetch-media`: `GET /{media-id}` (URL, 5 хв) → `GET <url>` з Bearer → перевірка розміру/sha256/magic bytes → наш S3 → `attachments`. Media id у вебхуці живе 7 днів, ліміт 100 МБ (більше — `131052`) |
| `audio` (`voice: true` — голосове) | плеєр, позначка «голосове» | те саме |
| `location` | карточка з назвою/адресою і посиланням на карту | координати в `payload` |
| `contacts` | карточка(і) контакта (імʼя, телефони); дія «створити клієнта» — пізніше | vCard-дані в `payload` |
| `reaction` | емодзі-чип на цільовому повідомленні (не окрема бульбашка); порожній `emoji` = зняття | оновити реакції цільового повідомлення за `reaction.message_id` |
| `interactive` (`button_reply`, `list_reply`), `button` (швидка відповідь шаблону) | текст відповіді (підпис кнопки) | `payload`/`id` зберігається |
| `context.id` | цитата повідомлення, на яке відповів клієнт | зв'язок із нашим повідомленням за `external_id` |
| `context.forwarded` | бейдж «Переслано» | прапорець |
| `referral` (реклама click-to-WhatsApp) | карточка «Із реклами: заголовок, посилання» (3c) | зберегти `referral` у `providerMeta` |
| `unsupported` (у т.ч. редагування клієнтом, `131051`/`131060`) | рядок «Повідомлення не підтримується» | заглушка, щоб у стрічці не було дірок |
| `system` | не показується як текст | подія ідентичності (§F17) |

**Вебхуки:** `messages`. **Виклики Meta:** `GET /{media-id}`, `GET <media-url>`.

## F6. Відповідь текстом — CHAT-2b (на fake), CHAT-3a (Meta)

**UI.** Композер активний, поки вікно відкрите; у шапці розмови — індикатор «вікно: ще 3 год 20 хв».
Enter — надіслати, Shift+Enter — новий рядок. Бульбашка зʼявляється одразу (оптимістично) з годинником,
потім ✓ (відправлено), ✓✓ (доставлено), ✓✓ синім (прочитано), ⚠ (помилка, §F12).
Відповідь на конкретне повідомлення («Відповісти») → цитата в бульбашці.

**Система.**
1. `POST /conversations/:id/messages` { body, clientMessageId, replyTo? } → перевірка доступу й вікна
   (`422 CHANNEL_WINDOW_CLOSED`, якщо закрите) → транзакція: `chat_messages(QUEUED)` + `publish(deliver-outbound)` → 201.
2. Воркер `deliver-outbound`: `QUEUED → SENDING`; повторна перевірка вікна; виклик
   `POST /{phone-number-id}/messages` `{messaging_product:"whatsapp", recipient_type:"individual", to, type:"text", text:{body, preview_url?}, context?:{message_id}, biz_opaque_callback_data:"<id нашого повідомлення>"}`
   (місце `biz_opaque_callback_data` у тілі — R); відповідь `messages[0].id` → `external_id`, `SENT`.
3. Подальші статуси — §F11. Помилки — §F12.
4. Адреса `to`: телефон; якщо контакт має лише BSUID — `recipient` замість `to` (R: доступність уточнити).
5. Текст до 4096 символів.

**Вебхуки:** `messages.statuses`. **Виклики Meta:** `POST /{phone-number-id}/messages`.

## F7. Вікно закрите → вибір шаблону — CHAT-3a (за імʼям), CHAT-3c (вибір зі списку)

## F8. Синхронізація шаблонів — CHAT-3c

**UI.** Налаштування → Інтеграції → WhatsApp → **Шаблони**: таблиця (назва, мова, категорія, статус-бейдж, якість,
оновлено), фільтри за статусом/мовою, кнопка **Синхронізувати**; підказка «Шаблони створюються й
затверджуються в Meta WhatsApp Manager». Шаблони `PAUSED`/`DISABLED`/`REJECTED` видно, але вибрати не можна;
причина (`rejected_reason`, пауза) — у підказці.

**Система.**
1. Тригери: після підключення; кнопка; cron (раз на годину); вебхуки (нижче).
2. `GET /{waba-id}/message_templates?limit=…&after=…` (`fields=id,name,language,status,category,components` підтверджено; `quality_score`, `rejected_reason` — (R)) → upsert у `channel_templates` за `(account, name, language)`;
   видалені в Meta — позначити, не стирати.
3. Вебхуки **не обробляють дані самі, а оновлюють рядок точково**:
   | Поле вебхука | Дія |
   | --- | --- |
   | `message_template_status_update` (`event`: APPROVED, REJECTED, PAUSED, DISABLED, FLAGGED, REINSTATED, PENDING_DELETION, …) | `status`, `rejectedReason`, причина паузи; сповіщення адміну про REJECTED/PAUSED/DISABLED |
   | `message_template_quality_update` | `quality` |
   | `template_category_update` | `category` (попередження за ~24 год про перекласифікацію) |
   | `message_template_components_update` | перечитати компоненти (job синхронізації одного шаблону) |
4. Ці події приходять на **застосунковий** вхід і маршрутизуються за WABA id (§F0.3).

**Виклики Meta:** `GET /{waba}/message_templates`. Створення/редагування/видалення з CRM — пізніше.

## F9. Надсилання шаблону — CHAT-3a (без змінних), CHAT-3c (змінні, вибір)

і значком «шаблон».

**Система.**
1. Захисти: шаблон `APPROVED`, не на паузі, усі змінні заповнені, мова/категорія сумісні з контактом,

2. Рядок `kind = TEMPLATE` (`payload`: назва, мова, змінні, відрендерений знімок тексту) → `QUEUED`.

4. Помилки шаблонів: `132000` (кількість змінних), `132001` (немає/не затверджений), `132012` (формат),

**Вебхуки:** `messages.statuses` (у т.ч. `pricing`). **Виклики Meta:** `POST /{phone}/messages`, `POST /{phone}/media`.

## F10. Вихідне медіа — CHAT-2c (fake), CHAT-3b (Meta)

**UI.** Кнопка «скріпка»/перетягування файлу в композер; прев'ю з прогресом; підпис (caption) для
зображень/відео/документів; обмеження типів і розміру показуються до відправки (з `capabilities`).

**Система.** Файл → наш S3 (presigned, `attachments`) → `QUEUED` → воркер: `POST /{phone}/media`
(multipart, `messaging_product=whatsapp`, файл) → `id` → `POST /{phone}/messages` `type: image|video|audio|document`
з `id` (не з посиланням). Ліміти: зображення 5 МБ (jpeg/png), відео 16 МБ (mp4/3gp, H.264+AAC), аудіо 16 МБ
(голосове — тільки Ogg/OPUS mono), документ 100 МБ. Невідповідність MIME → `131053`. Завантажений
`id` живе 30 днів — кешується для повторних відправок.

**Виклики Meta:** `POST /{phone}/media`, `POST /{phone}/messages`.

## F11. Статуси доставки — CHAT-2b (fake), CHAT-3b2 (Meta, збудовано)

> **CHAT-3b2:** `sent`/`delivered`/`read` стають квитанціями (вперед; час провайдера); квитанція, що випередила запис `external_id`, знаходить повідомлення за нашим id з `biz_opaque_callback_data`, а невідоме паркується (хвилинне підмітання). `failed` — `FAILED` з класом, кодом і `details` Meta (`131049` → `POLICY`). `deliveryReceipts` каналу = номер підписаний на цю систему.

**UI.** Галочки в бульбашці (§F6); наведення показує час відправки/доставки/прочитання. Для голосових
`played` відображається як «прослухано» (зберігаємо як `READ` із прапорцем).

**Система (вебхук `messages.statuses[]`: `sent`/`delivered`/`read`/`failed`/`played`).**
1. Знайти повідомлення за `id` (wamid) **або** за `biz_opaque_callback_data` (наш id).
2. Не знайшли → **паркування** (`channel_pending_statuses`), добір після запису `external_id` або кроном.
3. Рух вперед одним атомарним `UPDATE … WHERE rank(new) > rank(old)`; `FAILED` — виняток (не
   перекриває `DELIVERED`/`READ`); `delivered` може бути пропущений.
4. `failed`: записати `errors[]` (код, заголовок, деталі) у `failure`.
5. Зберегти `pricing` (`type`, `category`, `billable`) і, якщо є, `conversation` у `providerMeta`.
6. Подія в браузер «повідомлення оновлено» (перечитати).

## F13. Прочитано агентом і «друкує…» — CHAT-3b3 (прочитано збудовано), «друкує…» — відкладено

> **Збудовано в CHAT-3b3 (2026-10-14), як і працює.** Рух курсора прочитаного в клієнтській розмові (REST і сокет — один `ChatService.markRead`) умовним `UPDATE chat_messages … SET provider_read_at = now() WHERE provider_read_at IS NULL` «забирає» вхідні до цього `seq` (лише з `external_id`, не старші за 30 днів, лише `CUSTOMER`) і в тій самій транзакції публікує `channels.mark-read` для найновішого. Це і є дедуп: другий агент чи повторний рух нічого не забере. Воркер (`ChannelReadReceiptService`) шле `POST /{phone}/messages {status:"read", message_id}` поза транзакцією; пропускає fake, вимкнений канал і акаунт не в `CONNECTED`. Відмова пишеться як `read` у `channel_logs` (успіхи — ні), не повторюється, повідомлення не чіпає. Індикатор набору не збудовано: це виклик на кожен імпульс набору з throttle ~20 с і хук у композері.

**UI.** Агент відкрив розмову й дивиться її (вікно у фокусі, кінець стрічки на екрані) — клієнт бачить сині
галочки. Поки агент набирає відповідь — у клієнта «друкує…» (до 25 с).

**Система.** Під час переходу курсора прочитаного (`markRead`), якщо вікно відкрите і є вхідне: дебаунс →
`POST /{phone}/messages` `{messaging_product:"whatsapp", status:"read", message_id:"<wamid останнього вхідного>"}`;
позначає і попередні вхідні. З `typing_indicator:{type:"text"}` — індикатор набору (зникає після відповіді
або через 25 с); повторювати не частіше ніж раз на ~20 с, поки триває набір. Тільки для **вхідних** повідомлень, не старіших
за 30 днів; невірний id → `131009`. Помилка тут не блокує нічого (best-effort, лише лог).
Клієнтський «друкує…» Meta нам **не** віддає.

## F14. Привʼязка до клієнта — CHAT-2a

**UI.** У шапці розмови: «Клієнт: <імʼя>» (посилання на картку) або «Не привʼязано» з кнопками

(`channel_contacts.customerId`), усі його розмови одразу показують клієнта. Автоматичного створення клієнта
з невідомого номера немає.

## F15. Призначення, статуси, нотатки — CHAT-2b

## F16. Реакції — вхідна: CHAT-3b3 (збудовано), вихідна — пізніше

> **CHAT-3b3:** вхідна реакція зберігається як вхідне з `payload.reaction.emoji` (`null` — знята) і показується «Reacted 👍» / «Removed a reaction»; вона **не** виставляє `customer_last_message_at`, тож вікно відповіді не відкриває. Окремих чипів під повідомленням і вихідних реакцій ще немає.

**UI.** Вхідна реакція — емодзі-чип під повідомленням. Вихідна — меню емодзі при наведенні на вхідне
повідомлення клієнта.

**Система.** Вихідна: `POST /{phone}/messages` `type:"reaction"`, `reaction:{message_id:<wamid>, emoji}`;
не спрацює (`131009`), якщо цільове повідомлення старше 30 днів, видалене або саме є реакцією.
Реакції зберігаються на цільовому повідомленні, окремих рядків у стрічці немає.

## F17. Ідентичність: зміна номера, BSUID — CHAT-3c

**UI.** Невидима для агента; при конфлікті двох контактів — позначка «Можливий дубль контакту» у картці.

**Система (вебхук `messages`, `type: system`).** `user_changed_number` / `user_changed_user_id` (і
вебхук `user_id_update`, R) → нова адреса додається **аліасом** до наявного контакта (стара лишається);
якщо нова адреса вже належить іншому контакту — лише лог і позначка, **без автозлиття**. Вхідні
повідомлення містять `from` (телефон, може бути відсутній) і `from_user_id` (BSUID); відправка на BSUID — `recipient`
замість `to`; авторизаційні шаблони BSUID не приймають.

## F18. Згода й відписка від маркетингу — CHAT-3c

**UI.** Бейдж «Відписався від маркетингових повідомлень» у шапці розмови; маркетингові шаблони в пікері
вимкнені з поясненням.

**Система.** Вебхук `user_preferences` (`category: marketing_messages`, `value`: stop/resume) → оновлює
`channel_contacts` (прапорець відписки + час). Помилка `131050` при відправці маркетингу теж ставить
прапорець. Сервісні відповіді в межах вікна відписка не стосується. Запис `optIn` (джерело й час) —
на контакті; перше вхідне від клієнта вважається згодою на сервісні відповіді.

## F19. Токен і здоров'я каналу — CHAT-3c

**UI.** У налаштуваннях і в банері для адмінів: «Токен спливає через N днів», «Потрібна повторна
авторизація», якість номерів, ліміт охоплення; у розмовах — банер «Канал недоступний» замість композера, якщо
акаунт у `NEEDS_REAUTH`/`DISABLED`.

**Система.**
- Cron щодоби: `debug_token` (оновити `tokenExpiresAt`, `scopes`, `tokenCheckedAt`) — за 7 днів до спливу
  сповіщення адмінам.
- Код `190` (відправка, синхронізація, завантаження медіа з 401) → акаунт `NEEDS_REAUTH`, повідомлення лишаються
  `QUEUED`.
- Адмін вставляє новий токен → перевірка (§F1) → `CONNECTED` → черга `QUEUED` розблоковується.
- Здоров'я номерів оновлює той самий job, що й синхронізація (§F2); `account_alerts`/`account_update`
  вебхуки — сповіщення адмінам.

## F20. Оператор і підтримка — CHAT-2c

**UI (platform-web).** Розділ **Канали → Події**: нерозпізнані вебхуки (причина, ключ-хеш, IP), події у
стані `FAILED`/`PARKED` з кнопкою **Повторити (replay)**. **UI (тенант).** Налаштування → Інтеграції → WhatsApp →
**Журнал викликів**: останні HTTP-взаємодії з Meta (тип, статус, тривалість; секрети замасковані).

**Система.** `channel_webhook_events` зберігає сире тіло (retention — пропозиція 30 днів); replay проганяє
подію через той самий ingest — безпечно завдяки індексу дедупу. Відсутні сутності й помилки розбору не
губляться, а стають рядком із причиною. Cron чистить події, логи, запарковані статуси.

## F21. Розробка й тести — CHAT-2a

- **Fake-адаптер** (`provider = fake`): ті самі вебхуки з HMAC-підписом, статуси, будь-які класи помилок,
  вікно; тести — на ньому, без мережі.
- **Симулятор вхідних**: dev-ендпоінт і CLI `pnpm chat:simulate` — «клієнт пише», «клієнт надсилає фото»,
  «статус delivered/read/failed», «дублікат вебхука», «вебхук з чужим ключем».
- **Фікстури** реальних payload-ів Meta (з документації) для тестів `parseWebhook`.
- **Контракт-тести адаптера** проганяються проти `fake` і `meta_cloud` (і проти майбутнього Twilio).
- **Живий тест (ручний)**: тестовий номер Meta (§F0.4) через тунель; сценарій — підключити, синхронізувати,
  написати з телефону, відповісти, дочекатися галочок, закрити вікно (змінити час у БД) і надіслати шаблон.

# Версія збірки й історія проєкту (tenant-web)

Внизу шела tenant-web, справа від акаунта, — кнопка `v0.0.N`. Клік відкриває попап «About this
build»: версія, коміт, час збірки та історія проєкту.

## Версія

`<major>.<minor>.<номер збірки>`:

- `major.minor` — з `version` кореневого `package.json`; піднімаються вручну;
- останній сегмент — **номер збірки**, автоматично: `APP_BUILD_NUMBER` (CI), інакше
  `git rev-list --count HEAD`, інакше патч із `package.json`. Кожен деплой — новий коміт, тож
  версія змінюється сама, без правок файлів і без конфліктів між worktree-ами.

Рахує `scripts/build-info.ts` (`node scripts/build-info.ts` друкує JSON). `apps/web/vite.config.ts`
запускає його при старті/збірці й підставляє результат як `__APP_BUILD__` (`define`);
типізований доступ — `apps/web/src/lib/build-info.ts`. На диск скрипт нічого не пише.

У Docker-контексті немає `.git` (`.dockerignore`), тому CI передає `APP_BUILD_NUMBER` і
`APP_GIT_SHA` як build-arg-и в `Dockerfile.web`: GitLab (`build_web`, `GIT_DEPTH: 0` для
повної історії) і GitHub (`deploy.yml`, `fetch-depth: 0`). `platform-web` цього не показує.

## Історія — ДЕМО-ДАНІ

Джерело — `docs/history-summary.md`. Це **демо-дані**: файл ведеться вручну, цифри (коміти,
розмір, години тощо) оцінкові й оновлюються час від часу; автоматично вони не перераховуються.
Попап прямо так і каже. Скрипт лише розбирає файл при збірці, тож оновлення документа потрапляє
в наступну збірку.

Формат, який розуміє парсер: `# Заголовок`, далі `- **Label:** value`; вкладені пункти (відступ)
— `- label: value`. Розширюючи файл, тримайте цю форму — решту рядків парсер ігнорує.

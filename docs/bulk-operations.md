# Масові операції над колекціями (Bulk Operations)

**Статус: дизайн зафіксовано, не реалізовано.**
Перша черга — **Per-Item Batch** на `/users`. Решта режимів описані тут, щоб їх
не вигадували заново, коли з'явиться відповідний клас операцій.

Документ відповідає на одне питання: **що відбувається, коли користувач вибрав
N рядків у гріді й натиснув одну кнопку.** Він не про юзерів — юзери тут лише
перший споживач. Правила стосуються будь-якої колекції в системі.

---

## 1. Чотири режими і одна відкинута ідея

Кожен режим має кодову назву. Вона вживається в коді (ім'я раннера, значення
`mode` у відповіді), у коментарях і в обговоренні — щоб «зробимо це батчем» не
означало чотири різні речі.

| Код              | Назва               | Одиниця транзакції | Часткова відмова | Коли обирається                                                 |
| ---------------- | ------------------- | ------------------ | ---------------- | --------------------------------------------------------------- |
| `per-item`       | **Per-Item Batch**  | один ітем          | так, типізовано  | ітеми незалежні, у кожного свій побічний ефект                   |
| `atomic`         | **Atomic Batch**    | вся партія         | немає такого стану | партія — це ОДНА доменна дія над множиною                       |
| `dispatch`       | **Dispatch Batch**  | постановка в чергу | лише на прийомі  | робота довга або її обсяг непередбачуваний                       |
| `set`            | **Set Operation**   | вся партія         | немає такого стану | побічного ефекту НА ІТЕМ немає — вистачає одного стейтмента     |
| ~~`client-fanout`~~ | ~~Client Fan-out~~ | —                | —                | **відкинуто, див. §2**                                            |

### Правило вибору

Два питання, строго в цьому порядку:

**1. Чи має операція побічний ефект на КОЖЕН ітем?**
Запис в `activities` про конкретну сутність, публікація доменної події, каскадне
видалення, зовнішній виклик.

- **Ні** → `set`.
- **Так** → питання 2.

**2. Чи є «половина застосована» осмисленим станом?**

- **Ні** → `atomic`.
- **Так** → `per-item`.

**Ортогональна вісь — тривалість.** Якщо робота на один ітем довша за ~100 мс
(зовнішній API, рендер, лист) або множина задана фільтром, а не списком id, —
`per-item` замінюється на `dispatch`. Це не окрема гілка дерева, а заміна
виконавця: контракт назовні той самий.

## 2. Чому Client Fan-out відкинуто

Client Fan-out — цикл на фронті по наявних per-item ендпоінтах (`for (const id of
ids) await remove(id)`). Він безкоштовний у розробці, і саме тому спокусливий.

Відкинуто з чотирьох причин, у порядку ваги:

1. **Рветься `correlationId`.** У нас він дорівнює `req.id` (`genReqId` у pino-http)
   і їде в конверті кожного повідомлення. N запитів = N незв'язаних ланцюгів: на
   екрані `/jobs` і в логах масова дія розсипається на N подій, і питання «що
   зробив адмін о 14:32» не має відповіді. Це не оптимізація — це втрата
   спостережуваності, яку постфактум нічим не відновити.
2. **Бізнес-правило рівня партії неможливо виразити.** «Не лишити тенант без
   жодного адміна», «не видалити себе разом з іншими» — кожен запит бачить лише
   себе.
3. **Стан живе тільки в React.** Закрив вкладку на 30-му з 50 — половина зроблена,
   і про це не знає ніхто, включно з самим користувачем.
4. **N × (guard + резолв тенанта + `set_config` + транзакція)**, плюс ручне
   обмеження конкурентності, інакше N паралельних транзакцій під `saas_app`.

Пункт 1 — вирішальний. Пункти 2–4 можна пережити, спостережуваність — ні.

## 3. Спільний контракт

Один конверт на всі режими. Живе в `libs/contracts/src/batch/`, залежить лише від
`error.schema` — його `ApiErrorCodeSchema` переюзовується як словник причин.

```ts
export const BatchRequestSchema = z.object({
  ids: z.array(z.uuid()).min(1).max(BATCH_MAX_ITEMS), // 100
});

export const BatchItemErrorSchema = z.object({
  id: z.uuid(),
  /** ТОЙ САМИЙ словник, що в ApiError — фронт уже вміє його перекладати */
  code: ApiErrorCodeSchema,
  message: z.string(),
  fieldErrors: z.array(FieldErrorSchema).optional(),
});

export const BatchResultSchema = z.object({
  /**
   * Що означають лічильники нижче:
   * 'completed' — робота ЗРОБЛЕНА (per-item / atomic / set);
   * 'accepted'  — робота ПРИЙНЯТА в чергу (dispatch), результат буде пізніше.
   */
  mode: z.enum(['completed', 'accepted']),
  succeeded: z.array(z.uuid()),
  failed: z.array(BatchItemErrorSchema),
  total: z.number().int(),
});
```

### Чому `mode` у тілі, а не тільки в контракті ендпоінта

Клієнт і так знає з типу, який ендпоінт він викликав. Але `mode` у тілі дає дві
речі: (а) один generic-хелпер на фронті малює тост для будь-якої масової дії, не
маючи мапи «ендпоінт → семантика»; (б) ендпоінт зможе **ескалювати** — до 100 id
виконати синхронно, більше поставити в чергу — не змінюючи контракт. Друге зараз
не потрібне, але коштує нуль.

### HTTP-статуси

| Режим                    | Статус | Чому                                                     |
| ------------------------ | ------ | -------------------------------------------------------- |
| `per-item`, `atomic`, `set` | `200` | запит виконано; результат — у тілі                       |
| `dispatch`               | `202`  | Accepted — рівно та семантика, що потрібна               |
| помилка САМОЇ операції   | `4xx`/`5xx` + `ApiError` | невалідне тіло, перевищений ліміт, немає прав, провалений pre-flight |

**200 віддається навіть тоді, коли впали всі ітеми.** Це не естетика — так роблять
усі, хто має партії з частковою відмовою: Elasticsearch `_bulk` (`200` +
`"errors": true`), S3 `DeleteObjects` (`200` + `<Error>` на кожен ключ), SQS
`SendMessageBatch` (`Successful[]`/`Failed[]`). «Половина не пройшла» — це успішно
виконаний запит із діагностикою в тілі, а не помилка транспорту.

**207 Multi-Status не використовуємо.** Він лишився в WebDAV; навіть Microsoft
Graph, чий `$batch` найближчий до нього за формою, віддає 200 і кладе індивідуальні
статуси всередину. Наші фронтові інтерсептори діляться по 2xx/4xx/5xx — 207 нічого
не додасть, зате зробить обробку відповіді неочевидною.

### Іменування ендпоінтів

```
POST /{resource}/batch-{action}
```

`POST /users/batch-delete`, `POST /users/batch-disable`, `POST /notifications/batch-read`.

**Окремий ендпоінт на операцію, а не універсальний `POST /users/batch { operation }`.**
Причини: свій DTO і своя Swagger-схема, свій orval-хук (`useUsersBatchDelete`), своє
право під майбутній RBAC (`users:delete`). Це продовження вже прийнятого патерну
`POST /:id/password` і `PATCH /:id/status` — окремий ресурс на окремий бізнес-акт.

Універсальний мультиплексор у стилі MS Graph `$batch` (довільні вкладені запити з
власними методами й URL) свідомо не робимо: це другий HTTP-стек усередині API —
guard-и, валідація, Swagger і кодогенерація доведеться дублювати для вкладених
запитів, а orval із такого не згенерує нічого, крім `unknown[]`.

### Ліміт

`BATCH_MAX_ITEMS = 100` — одне число в схемі, на всю систему. Для орієнтира:
SQS — 10, DynamoDB `BatchWriteItem` — 25, MS Graph — 20, Salesforce sObject
Collections — 200, S3 `DeleteObjects` — 1000. Для адмінського гріда, де вибір
робиться руками по сторінках, 100 — з великим запасом.

Ліміт узгоджений з тим, що грід **не вміє «вибрати все за фільтром»**
(`useDataGridSelection` накопичує вибір лише з переглянутих сторінок). Коли така
кнопка з'явиться — це вже інша операція з іншим контрактом (`{ filter }`), і
виконує її `dispatch`.

## 4. `per-item` — Per-Item Batch

**Перша черга реалізації.**

Цикл переїжджає з фронту на сервер, але головний інваріант системи лишається
недоторканим: **одна доменна зміна = одна `withTenantTx` з усіма своїми побічними
ефектами**. Обгортка додає рівно те, чого фронтовий цикл дати не може — спільний
контекст.

### Виконання

`libs/shared/src/batch/batch-runner.ts`:

```ts
runBatch(ids, (id) => tenantTx.withTenantTx(async (tx) => { ... }))
```

**Послідовно, не `Promise.all`.** 100 паралельних транзакцій — це 100 конектів
пулу, `set_config` на кожній і взаємні блокування на FK. 100 × ~5 мс ≈ півсекунди
— цілком прийнятно для синхронної відповіді.

Помилка ітема ловиться й мапиться в `BatchItemError` **тією самою нормалізацією,
що й HTTP-помилки**. Для цього приватний `AllExceptionsFilter.buildError`
(`libs/shared/src/errors/all-exceptions.filter.ts:126`) виноситься в чисту функцію
`toApiError(exception): ApiError`, і фільтр із раннером починають ділити одну
таблицю нормалізації. Інакше з'явиться другий, тихо розбіжний словник помилок.

### Два рівні побічних ефектів

Це головна деталь режиму.

| Рівень        | Що                                                                    | Де                                    |
| ------------- | --------------------------------------------------------------------- | ------------------------------------- |
| **на ітем**   | `activities.record` (кожна зміна — окремий факт про окрему сутність), `messages.publish` | усередині транзакції ітема            |
| **на партію** | `notifications.notify` з `count`                                      | окрема `withTenantTx` ПІСЛЯ циклу, по фактично успішних id |

Сповіщення після циклу, а не в кожній транзакції, з трьох причин: `count` виходить
точним; гарантія «тільки після коміту» збережена (усі `succeeded` уже закомічені);
у сокет летить **одна** подія замість N. `groupKey` при цьому лишається — він
рятує від накопичення рядків між РІЗНИМИ партіями.

### Pre-flight

Перевірки над усією множиною до початку циклу — те, заради чого режим і потрібен:

- `ids.includes(actor.sub)` → цей id одразу в `failed`, решта партії виконується
  (а не 400 на весь запит);
- «після видалення в тенанті лишиться 0 адмінів» → `400 ApiError` на весь запит,
  бо це вже не проблема окремого ітема.

### Ідемпотентність

`Idempotency-Key` у V1 немає. Delete і set-status ідемпотентні за природою: повтор
дасть `NOT_FOUND` або no-op у `failed`, шкоди немає. Для операцій зі списанням
грошей ключ знадобиться — це EDA-3, не тут.

## 5. `atomic` — Atomic Batch

Уся партія в одній `withTenantTx`. Помилка будь-якого ітема відкочує все.

**Коли:** партія — це одна доменна дія, а не N незалежних. «Звести три інвойси в
один платіж», «перенести залишки між рахунками», «застосувати проводку». Ознака:
часткове застосування залишає систему в стані, який не описується жодним
бізнес-терміном.

**Контракт той самий**, з двома уточненнями:

- `mode: 'completed'`, `failed` **завжди порожній** — у цьому режимі немає стану
  «цей не вийшов»;
- будь-яка невдача = звичайний `ApiError` (`400`/`404`/`409`) на весь запит.

Порожній `failed` — не лінь, а те, що дає фронту єдиний хелпер: код обробки
відповіді один на всі режими, різниця тільки в тексті тоста.

**Межа:** довга транзакція тримає блокування на N рядках. При сотнях ітемів це
вже привід дивитись у бік `dispatch` із `atomic`-тілом усередині job-а.

Прецеденту в коді поки немає. Найближчі за духом місця — `UsersService.create`
(`users.service.ts:113`) і `setPassword`: там одна транзакція вже об'єднує зміну,
активність, сповіщення й публікацію. `atomic` — та сама ідея, розтягнута на
множину.

## 6. `dispatch` — Dispatch Batch

**Виглядає ззовні як `per-item`, всередині — постановка в чергу.**

Це свідомо спрощена версія «асинхронного батчу»: ми **не** заводимо ресурс стану
партії. Ніяких `batch_operations`/`batch_items`, ніякого polling-а прогресу,
ніякого відстеження кожної ітерації.

### Що означає відповідь

```
POST /users/batch-resend-welcome { ids: [...] }
→ 202 { mode: 'accepted', succeeded: [...], failed: [...], total: N }
```

- `succeeded` — id, **прийняті в чергу**: пройшли pre-flight і їхнє повідомлення
  закомічене разом із рештою партії;
- `failed` — id, які не пройшли **прийом**: не існують, заборонені правилом, не
  стали в чергу;
- `mode: 'accepted'` — фронт зобов'язаний сказати «поставлено в чергу», а не
  «зроблено».

Постановка в чергу йде **однією транзакцією на всю партію**: `publish(tx, …)` у
циклі всередині одного `withTenantTx`. Або в черзі всі, або жоден — на прийомі
часткових станів не буває. Це той самий транзакційний outbox, що вже працює
(`MessagePublisher`), просто N публікацій замість однієї.

### Ціна спрощення — і чим вона компенсована

**Ціна названа прямо: після `202` система не може одним запитом відповісти «як
завершилась партія X».** Ми свідомо на це йдемо.

Компенсація складається з того, що вже є:

| Питання                         | Де відповідь                                                     |
| ------------------------------- | ----------------------------------------------------------------- |
| Що сталося з конкретною сутністю? | Activity Log сутності — воркер пише активність на ітем, як завжди |
| Що впало?                        | Спільна `dlq` — той самий екран розбору, що для решти системи     |
| Які job-и належать цій партії?   | `correlationId` конверта = `req.id` того одного HTTP-запиту       |
| Коли все закінчилось?            | Агрегатне сповіщення від останнього обробленого ітема (за потреби) |

Третій рядок — ключовий і безкоштовний: **весь батч уже склеєний `correlationId`-ом**,
бо публікації йшли з одного запиту. Читабельним це стане з **EDA-2** (фільтр за
`correlationId` на екрані `/jobs`), який і так у беклозі. До EDA-2 діагностика —
DLQ і логи.

### Коли обирати

- робота на ітем довша за ~100 мс (лист, зовнішній API, рендер, thumbnail);
- множина задана фільтром, а не списком id;
- потрібні ретраї з backoff — вони вже є в pg-boss безкоштовно.

### Чого тут свідомо немає

Промислові рішення (Google LRO / AIP-151, Shopify `bulkOperation`, Salesforce Bulk
API 2.0, Stripe `report_runs`) роблять асинхронну роботу **ресурсом**: `GET
/operations/{id}` зі статусом, прогресом і посиланням на результат. Це правильно
для тисяч ітемів і зовнішніх інтеграторів. Для адмінського гріда на ≤100 рядків
це два стани, дві таблиці й екран, які ніхто не відкриє.

Якщо колись знадобиться — заводиться саме ресурс (`GET /batch-operations/:id`), а
не push прогресу в сокет: правило «жоден стан не живе тільки в сокеті» тут
непорушне, і вся індустрія його дотримується (webhook/polling поверх ресурсу, а не
замість нього).

## 7. `set` — Set Operation

**Прецедент уже в коді:** `NotificationsService.markAllRead`
(`apps/api/src/notifications/notifications.service.ts:147`) — один `updateMany` за
умовою, одна транзакція, один `bumpRevision`, одна socket-подія зі
`scope: { kind: 'all' }`. Циклу немає взагалі.

**Коли:** побічного ефекту на ітем не існує. Змінюється прапорець/стан, а «журнал
про кожен рядок» не має сенсу — саме тому, що подія тут одна: «людина прочитала
все», а не «людина прочитала рядок №47».

### Дві підформи

| Підформа              | Адресація                        | Відповідь                                                        |
| --------------------- | -------------------------------- | ---------------------------------------------------------------- |
| **за списком id**     | `where: { id: { in: ids } }`     | спільний `BatchResult`, `mode: 'completed'`                      |
| **за умовою**         | `where: { readAt: null, … }`     | **доменна відповідь**, а не `BatchResult` (`markAllRead` → `NotificationSummary`) |

Друга підформа конверта не використовує і не повинна: там немає списку id ні на
вході, ні на виході, а корисне для клієнта — свіжий агрегат. `markAllRead`
лишається як є, переписувати його під конверт **не треба**.

### Чесна асиметрія `failed`

`updateMany` повертає лише `count`. Дізнатись, ЯКИЙ саме id не оновився, можна
тільки додатковим `findMany` — і це буде запит заради того, щоб повідомити
клієнту факт, який його не цікавить: у `set`-операціях «не оновився» означає
«його немає або він уже в цьому стані», тобто не помилка.

**Рішення: у `set` повертаємо `succeeded: ids` цілком і `failed: []`.** Це має
бути в коментарі раннера, інакше хтось потім «полагодить» це зайвим запитом.

### Точка входу вже існує

`selectedIds`, і `clear`.

Це той самий контракт, що `bulkActionButtons` у React Admin і «Action» у Django
admin — компонент масової дії живе поруч із гридом і отримує вибір.

### Що додається в `libs/ui`

Одна операція в `useDataGridSelection` (`use-data-grid-selection.ts`):

```ts
deselect: (ids: readonly string[]) => void;
```

Потрібна для головного UX-рішення нижче. Природно лягає поруч із наявними
`toggle`/`setPage`/`clear`.

### Обробка відповіді

Один хелпер на всі режими, розгалуження по `mode`:

| Стан                            | Що показуємо                                          | Що з вибором                                |
| ------------------------------- | ------------------------------------------------------ | ------------------------------------------- |
| `completed`, `failed` порожній  | тост «Deleted 12 users»                                | `clear()`                                   |
| `completed`, є `failed`         | тост «Deleted 10 of 12»                                | `deselect(succeeded)` — **невдалі лишаються виділеними** |
| `accepted`                      | тост «Queued 12 users» (не «зроблено»)                 | `clear()`                                   |
| `ApiError`                      | звичайний тост помилки (глобальний обробник)           | без змін                                    |

**Невдалі рядки лишаються виділеними** — замість того щоб вивалювати перелік id у
тост. Людина бачить рівно ті рядки, з якими треба розібратись, прямо в таблиці, і
може повторити дію на них однією кнопкою. Тост несе підсумок, грід — деталі.

Інвалідація списку — **одна**, після відповіді, як і для одиничних мутацій
(`queryClient.invalidateQueries` з `getUsersFindAllQueryKey()`); гріду вона не
належить.

### Підтвердження

`AlertDialog` із кількістю в заголовку — той самий патерн, що `confirm` у
`DataGridRowAction`, але текст із `count`: «Delete 12 users?». Для `dispatch`
формулювання інше — «поставити в чергу», без обіцянки миттєвого результату.

### Чого немає

- **Прогресу.** Синхронна відповідь на ≤100 ітемів приходить приблизно за секунду;
  `isPending` на кнопці й наявне затемнення гріда (`isPlaceholderData`) достатні.
- **Undo-вікна.** React Admin, Gmail і Linear роблять масове видалення оптимістично
  з вікном скасування замість діалогу — для оборотних дій це об'єктивно кращий
  патерн (питати після того, як людина побачила результат, а не до). Це реальний
  кандидат другого ходу, але він вимагає відкладеної відправки й локального
  «привида» видалених рядків — окрема робота.

## 9. Сокети

**Масові операції не заводять жодного нового realtime-протоколу.**

- Результат ініціатору приходить у HTTP-відповіді. Робити його залежним від
  сокета — регрес надійності: транспорт websocket-only і необов'язковий, брокер
  може бути недоступний (це вже враховано — presence тоді віддає 503).
- Іншим адмінам і іншим вкладкам зміну доносить **одне агрегатне сповіщення**
  (§4), тим самим шляхом, що й одиничні дії.
- Після масового disable presence-дельти прилетять самі: сесії відкликано,
  сокети відваляться.

Єдиний осмислений майбутній кейс — сказати іншим клієнтам «перечитай список» після
великої зміни. Це окрема фіча (live-таблиці), не частина масових операцій, і
робити її треба через окрему подію, а не розширенням `presence.changed.v1`.

## 10. Розкладка по домену

| Операція                                | Режим                | Чому                                                              |
| --------------------------------------- | -------------------- | ----------------------------------------------------------------- |
| `markAllRead`, `markSeen`               | `set` ✅ реалізовано | нема ефекту на ітем; `scope: 'all'` у сокеті                      |
| масове читання/архівація обраних сповіщень | `set`             | `updateMany` з `id: { in: ids }`; гілка `scope: { kind: 'ids' }` у контракті вже є |
| масовий enable/disable юзерів           | `per-item`           | activity на ітем + відкликання сесій; «себе» треба показати окремо |
| масове видалення юзерів                 | `per-item`           | те саме + необоротність                                            |
| масова зміна ролі                       | `per-item`           | activity на ітем + pre-flight «не лишити тенант без адмінів»       |
| масовий resend welcome                  | `dispatch`           | ітем = лист; ретраї й backoff уже є в pg-boss                      |
| «застосувати до всіх за фільтром»       | `dispatch`           | контракт `{ filter }`, потужність невідома наперед                 |
| зведення інвойсів у платіж (майбутнє)   | `atomic`             | часткове застосування = зламаний стан                              |

## 11. Борг, який спливає разом із цим

`UsersService.remove()` (`apps/api/src/users/users.service.ts:301`) — голий
`prisma.delete` без транзакції, без активності й без сповіщення. Поштучно це
майже непомітно; масово — **50 людей зникають без сліду в журналі**.

Тому в один хід із `per-item` на юзерах: `remove()` приводиться до решти модуля
(`withTenantTx` + `ActivityRecorder`), додається тип активності `user.deleted`.
Це не «заодно причесати» — без цього масове видалення не можна випускати.

## 12. Зафіксовані рішення

| Питання                              | Рішення                                                                                                   |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Цикл на фронті                       | **Відкинуто** — рветься `correlationId`, неможливий pre-flight (§2)                                        |
| Форма відповіді                      | Один конверт `BatchResult` на всі режими; `mode` розрізняє «зроблено» і «прийнято»                          |
| HTTP-статус                          | `200` навіть при повній невдачі ітемів; `202` для `dispatch`; **207 не використовуємо**                    |
| Ендпоінти                            | `POST /{resource}/batch-{action}` — по одному на операцію, не універсальний диспетчер                       |
| Ліміт                                | `BATCH_MAX_ITEMS = 100`, одне число в схемі                                                                 |
| Порядок виконання в `per-item`       | Послідовно; `Promise.all` заборонено (пул конектів, блокування)                                             |
| Нормалізація помилок ітема           | Спільна з `AllExceptionsFilter` через винесену `toApiError()` — другого словника не заводимо                |
| Побічні ефекти                       | На ітем — у транзакції ітема; сповіщення людям — агрегатне, після циклу, по успішних                        |
| Стан партії в `dispatch`             | **Не зберігаємо.** Спостережуваність — через `correlationId` + DLQ + Activity Log (§6)                       |
| `failed` у `set`                     | Завжди порожній; який саме рядок не оновився — не з'ясовуємо (§7)                                            |
| `markAllRead`                        | Лишається з доменною відповіддю, під конверт **не** переписується                                            |
| Прогрес у сокет                      | Ні. Результат — у HTTP-відповіді; іншим — одне агрегатне сповіщення                                          |

## 13. Обсяг першого ходу (`per-item` + `set`)

**Бекенд**

1. `libs/contracts/src/batch/` — `BatchRequest`/`BatchItemError`/`BatchResult`, `BATCH_MAX_ITEMS`.
2. `libs/shared/src/errors/` — винести `buildError` → чиста `toApiError(unknown): ApiError`.
3. `libs/shared/src/batch/batch-runner.ts` — `runBatch()` + хук пост-фази для агрегатного сповіщення.
4. `apps/api/src/users/` — `remove()` у `withTenantTx` + `user.deleted`; `POST /users/batch-delete`, `POST /users/batch-disable`; pre-flight «себе» і «останній адмін».
5. `apps/api/src/notifications/` — `POST /notifications/batch-read`, `batch-archive` (`set`, `scope: { kind: 'ids' }`).
6. `openapi:generate` → `web:codegen`.

**Фронтенд**

7. `libs/ui` — `deselect(ids)` у `useDataGridSelection`.
8. `apps/web` — хелпер обробки `BatchResult` (тост по `mode`, `deselect(succeeded)`), кнопки в `selectionActions` на `/users`, `AlertDialog` з `count`, i18n-ключі.

**Тести**

9. e2e: повний успіх; часткова відмова (неіснуючий id + свій id); перевищення ліміту → 400; провалений pre-flight → 400 без жодної зміни в БД; один запис активності на ітем; **одне** сповіщення на партію.

## 14. Беклог

- **`dispatch`** — коли з'явиться перша довга масова операція (resend welcome / масовий експорт).
- **`atomic`** — з першим доменом, де партія є однією дією (білінг, EDA-3).
- **Undo-вікно** замість `AlertDialog` для оборотних масових дій (§8).
- **«Вибрати все за фільтром»** — контракт `{ filter }` + обов'язково `dispatch`.
- **`Idempotency-Key`** — коли масові операції торкнуться грошей.
- **Читабельність партій у `/jobs`** — фільтр за `correlationId` (це **EDA-2**, уже в беклозі; `dispatch` без нього діагностується лише через DLQ і логи).

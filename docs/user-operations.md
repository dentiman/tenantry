# Операції користувача, прогрес і лоток активності (User Operations)

> **Статус (2026-11-18): збудовано ядро.** `UserOperation` з першим споживачем (експорт клієнтів у
> CSV), черга завантажень, `StepProgress`, лоток активності і спільний `Idempotency-Key`
> ([idempotency.md](idempotency.md)). Не збудовано: операції з кроками й курсором (імпорт, `uo-3`)
> і решта споживачів §7. Фази й стан — §10; рішення власника — §9.

Скелетон уже має примітиви даних (RLS, транзакції, messaging), файлів (двофазний upload) і UI
(DataGrid, форми, контекстна панель). Бракує спільної відповіді на питання **«що зараз
виконується для цього користувача і на якому воно етапі»**. Сьогодні кожне місце вирішує це
саме. Клієнтську половину (завантаження файлів) уже закрито — §6; асинхронна робота після `202`
для користувача досі невидима аж до сповіщення.

## 1. Три різні речі, які не треба змішувати

| Що | Де живе правда | Скільки живе | Приклад |
| --- | --- | --- | --- |
| **Передача байтів** (upload) | у браузері | секунди–хвилини, до закриття вкладки | завантаження файлу в S3 |
| **Операція користувача** (`UserOperation`) | рядок у Postgres | хвилини; зберігається дні для історії | імпорт клієнтів, експорт гріда, генерація PDF |
| **Бізнес-стан запису** | доменна таблиця | роки | статус тикета, інвойсу, розмови |

Третій рядок **не є предметом цього документа**. Статуси інвойсу чи тикета — це статична
машина станів конкретного домену (enum + таблиця переходів + умовний `updateMany`), вона
пишеться в модулі-власнику. Універсальний workflow-рушій не будуємо.

Перші два рядки для користувача виглядають однаково — «щось виконується» — тому мають
**спільне відображення** (§6), але різні джерела стану.

## 2. Назва сутності

Сутність називається **`UserOperation`** (таблиця `user_operations`, API `/user-operations`,
сокет-подія `user-operation.changed.v1`).

Чому не коротше:

| Відкинута назва | Причина |
| --- | --- |
| `Operation` | надто загальна — займе слово, яке знадобиться майбутньому домену (складські, фінансові операції); у platform-web уже є область **Operations** (Jobs/Queues) |
| `Job` | зайнято pg-boss і екраном `/operations/jobs`; job — це технічна одиниця черги, а не те, що бачить користувач |
| `Task` | зарезервовано під майбутні задачі/follow-up як бізнес-сутність |
| `Activity` | зайнято Activity Log |
| `Process` / `Workflow` | обіцяють рушій процесів, якого тут свідомо немає |

Прецедент той самий, що `CalendarEvent`: кваліфікована назва, бо просте слово зайняте або
знадобиться пізніше.

Назва також фіксує зміст: **це операція, яку запустив конкретний користувач** і за якою він
стежить. `user_id` обовʼязковий. Системна робота без ініціатора (cron, підписники подій) цією
сутністю не описується — її видно на екрані job-ів.

## 3. Модель даних

Таблиця `user_operations` (`prisma/schema/user-operations.prisma`) — tenant-scoped, під
стандартним RLS. Стан pg-boss назовні не віддаємо: `pgboss.*` лежить поза RLS, і job — не те саме,
що операція (одна операція переживає кілька спроб job-а).

| Поле | Призначення |
| --- | --- |
| `id`, `tenant_id` | ресурс і межа тенанта (RLS) |
| `user_id` | власник; композитний FK на `users` з `ON DELETE CASCADE` — видалення користувача прибирає його операції |
| `type` | код типу із закритого реєстру `USER_OPERATION_TYPES` (`libs/contracts/src/user-operation-types.ts`); тип оголошує модуль-власник (`customer/customer.operations.ts`) |
| `title` | назва від типу (для експорту — імʼя файлу): дані, не перекладений текст; нею підписані лоток і сповіщення |
| `status` | `QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELED` |
| `progress_current`, `progress_total` | вимірюваний прогрес; `null` — невизначений |
| `steps` (jsonb) | динамічний список кроків, §4; `null` — тип без кроків |
| `revision` | монотонний лічильник, +1 на кожному переході; його несе сокет-подія |
| `params` (jsonb) | вхідні параметри, валідовані схемою типу і на старті, і у воркері |
| `result` (jsonb) | підсумок типу (`rowCount`, `filename`) — без ключів сховища |
| `result_key` | ключ обʼєкта результату в S3. **Не рядок `files`:** загальний API файлів відкрив би його всьому тенанту |
| `error_code` | `STALLED` / `INVALID_PARAMS` / `INTERNAL` — код, не текст |
| `cancel_requested_at` | кооперативне скасування |
| `created_at`, `started_at`, `heartbeat_at`, `finished_at` | `started_at` заодно токен захоплення (§5); `heartbeat_at` — останній знак життя воркера |

Окремої колонки ключа ідемпотентності **немає** — запуск гасить спільний `Idempotency-Key` (§5.1).
`subject_type`/`subject_id` з першого задуму не заведені: жоден споживач поки не має субʼєкта.

## 4. Кроки — розширений прогрес

Звичайний прогрес — число від 0 до 100. **Кроки** — це прогрес, показаний списком етапів:
перший виконано, другий виконується, решта чекають. Коли завершився останній — операція
завершена.

```json
[
  { "key": "upload",   "status": "done" },
  { "key": "validate", "status": "running", "current": 340, "total": 1200 },
  { "key": "write",    "status": "pending" },
  { "key": "report",   "status": "pending" }
]
```

Правила:

- **Статуси кроку фіксовані й спільні для всіх операцій:** `pending / running / done / failed /
  skipped`. Це єдиний enum у цій моделі.
- **Самі кроки динамічні.** Їх набір задає тип операції, і він може залежати від параметрів:
  імпорт без попередньої перевірки має на крок менше; підключення трьох номерів дає три кроки
  з параметрами підпису (`labelParams`). Окрема бізнес-модель зі статичними станами під кожну
  операцію не потрібна.
- **Підписи бекенд не надсилає.** Фронт рендерить ключ `userOperations.<type>.steps.<key>`
  через i18next — так само, як коди помилок.
- **Крок може мати власний вимірюваний прогрес** (`current`/`total`), якщо він є.
- **Статус операції виводиться з кроків:** останній `done` → `SUCCEEDED`; будь-який `failed` →
  `FAILED`, решта лишаються `pending` або `skipped`.

Кроки зберігаються як jsonb у рядку операції, а не в дочірній таблиці: їх небагато, пише один
воркер, читаються завжди разом з операцією, і один `revision` покриває все. Дочірня таблиця
знадобиться лише тоді, коли кроки почнуть виконувати паралельно різні воркери.

**Обмеження першої версії:** кроки йдуть послідовно в одному обробнику. Крок, що чекає на
зовнішню подію (вебхук, дію людини), сюди не входить — це вже процес, а не прогрес.

## 5. Бекенд: потік виконання

Патерн — Long-Running Operation (Google AIP-151), він же Async Request-Reply: асинхронна робота
стає **ресурсом** з `GET`, а не push-ем прогресу в сокет. Для батчів гріда на ≤100 рядків рішення
`docs/bulk-operations.md` §6 лишається чинним — ресурс стану там не заводимо.

Код: `libs/shared/src/user-operations/` (`UserOperationsService` — старт і переходи,
`UserOperationRunner` — виконання у воркері), `apps/api/src/user-operations/` (читання,
скасування), `apps/worker/src/user-operations/` (cron-и). Еталон споживача — експорт клієнтів:
`CustomersService.startExport` + `apps/worker/src/customers/export-customers.subscriber.ts`.

**Головний інваріант — кожна зміна стану є умовним переходом** (`updateMany` з очікуваним поточним
станом і `revision + 1`, backend-conventions §4). Тому пізній записувач — повтор job-а після
`STALLED`, прогрес після скасування — нічого не змінює, а фінальний стан не перезаписується ніколи.

1. **Прийом.** Доменний ендпоінт (`POST /customers/export`, `@Idempotent()`) в одному
   `withTenantTx`: `idempotency.claim(tx)` → `userOperations.start(tx, { type, userId, title,
   params })` → `publish(tx, <команда типу>, { userOperationId })`. Відповідь — `202` з операцією.
   Payload job-а — лише id: параметри воркер читає з операції. Межі на кшталт «не більше 50 000
   рядків» перевіряються до транзакції — це запобіжник, а не інваріант.
2. **Захоплення.** `runner.run(id, type, handler)`: `QUEUED → RUNNING` із `started_at = now()` як
   токеном. Скасовану чи завершену операцію пропускає. `RUNNING`, що мовчить довше за 15 хв,
   перехоплює новим токеном (повтор job-а після падіння воркера) — записи старого виконавця
   більше не збігаються з умовою. Ідемпотентність дає захоплення, а не `runOnce`: робота триває
   хвилини, а тримати транзакцію стільки заборонено (backend-conventions §5).
3. **Робота.** Обробник отримує `context`: `progress(current, total)` пише з тротлінгом (раз на
   секунду або на 500 одиниць, останнє значення — завжди), кожен запис оновлює `heartbeat_at` і
   приносить прапорець скасування; `checkpoint()` кидає сигнал скасування; `steps()`/`step()` —
   §4. Зовнішні виклики (S3) — поза транзакціями.
4. **Завершення.** `SUCCEEDED` / `CANCELED` / `FAILED` — короткий перехід, у тій самій транзакції
   сповіщення власнику (`user_operation.succeeded` / `.failed`; скасування не сповіщає). Помилки:
   `NonRetryableMessageError` і невалідні параметри → `FAILED` одразу; будь-яка інша — job
   повторюється (`retryLimit: 3`, backoff), операція лишається `RUNNING` і буде перехоплена.
5. **Зависання.** Cron `user-operations.sweep-stalled` (кожні 5 хв) ставить `FAILED`/`STALLED`
   усім `RUNNING` без heartbeat понад 15 хв — так закривається й операція, чий job вичерпав
   повтори й ліг у `dlq`. `QUEUED` sweeper не чіпає.
6. **Сокет.** Після коміту кожного переходу — `user-operation.changed.v1 { id, revision }` в
   особистий room власника (правило 15 `AGENTS.md`: без стану; правда в
   `GET /user-operations/:id`). Транспорт реєструє процес, у якого є сокет
   (`UserOperationEventsRegistry`), — і api (старт, скасування), і воркер.
7. **Скасування.** `POST /user-operations/:id/cancel`: `QUEUED → CANCELED` одразу (job, коли
   дійде, пропустить операцію); для `RUNNING` — `cancel_requested_at`, воркер зупиниться на
   найближчому записі прогресу чи `checkpoint()`. Завершену не змінює — 200 з поточним станом.
8. **Зберігання.** Cron `user-operations.purge-finished` (щодоби) видаляє завершені понад 30 днів
   тому — спершу обʼєкт результату, потім рядок.

**API:** `GET /user-operations` (власні, `?active=true` — лише `QUEUED`/`RUNNING`),
`GET /user-operations/:id`, `POST /user-operations/:id/cancel`, `GET /user-operations/:id/result-url`
(короткоживуче посилання — лише власнику, лише `SUCCEEDED`, лише в межах строку зберігання).
Запуск — завжди доменним ендпоінтом модуля-власника, спільного `POST /user-operations` немає.
Доступ — одна умова на всіх шляхах: `user_id` з токена; чужа операція (навіть для ADMIN) — 404.

**Як додати тип операції:** визначення в контрактах власника (`defineUserOperationTypes`) і рядок у
`user-operation-types.ts`; команда в `libs/shared/src/messaging/definitions/<module>.messages.ts` +
запис у топології; доменний ендпоінт за зразком `startExport`; підписник у воркері, що викликає
`runner.run(...)`; тексти `user-operations:types.<type>.steps.*`, якщо є кроки.

### 5.1. Ідемпотентність запуску — спільний `Idempotency-Key`

Запуск операції — це `POST`, який при повторі мережі чи подвійному кліку створив би дві операції
(два імпорти, два експорти). Захист від цього **не є полем у `user_operations`**: це спільний
шар для всіх REST-мутацій, зроблений окремою зміною `uo-0-idempotency-key` —
**[idempotency.md](idempotency.md)**.

Що з нього потрібно знати тут:

- Ендпоінт запуску операції отримує `@Idempotent()`, а його сервіс викликає
  `idempotency.claim(tx)` першим стейтментом у тій самій `withTenantTx`, де вставляється рядок
  `user_operations` і робиться `publish(tx, …)`. Ключ, операція й job комітяться разом.
- Повтор запуску з тим самим ключем повертає той самий `202` з тим самим `UserOperation` —
  знімок на момент запуску; актуальний стан клієнт усе одно читає через `GET /user-operations/:id`.
- Фронтенд нічого окремо не робить: ключ ставить HTTP-клієнт.

Ідемпотентність **споживача** в черзі — окремий механізм (`MessageInboxService.runOnce`), а
бізнес-ключі на доменних таблицях (`clientMessageId`, `event_id` вебхуків) заголовок не замінює.

## 6. Фронтенд

Клієнтська частина **зроблена** зміною `uo-1-upload-manager-activity-tray` (2026-11-17):
еталони — `docs/file-storage.md` («Черга завантажень»), `docs/frontend/app-shell.md` §5.7,
`docs/frontend/ui-stack.md` («Прогрес»). Нижче — лише те, що стосується наступних фаз.

### 6.1. Черга завантажень

Zustand-стор поза деревом сторінок, черга з лімітом 3, скасування, повтор, попередження
`beforeunload`; `useFileUpload` — тонка підписка з незмінним API. Серверна сутність тут не
потрібна: байти йдуть повз API, прогрес знає лише браузер. Не зроблено: S3 multipart для
великих файлів (єдине місце, де знадобиться бекенд).

### 6.2. Спільне відображення

`StepProgress` у `libs/ui` приймає `{ key, status, current?, total? }[]` і не знає, звідки вона.
Тип стану кроку `StepStatus` — у `libs/contracts/src/progress/` (інфраструктурний, без домену): той
самий тип приходить і з клієнтської черги завантажень, і з сервера в `UserOperation.steps`.

### 6.3. Лоток активності

Чип у хедері «3 active · 64%» з попапом, читає нейтральний реєстр `apps/web/src/lib/activity.ts`.
Джерел два: черга завантажень і операції користувача (`features/user-operations/`). Операції
приходять після кожного підключення сокета з `GET /user-operations?active=true` — тож запущена до
перезавантаження сторінки операція знову видна, — а далі оновлюються за `user-operation.changed.v1`
(перечитати, лише коли ревізія новіша). Успішна операція з файлом показує дію «Download» і не
зникає сама; клік по сповіщенню «готово» теж завантажує файл (`lib/entity-actions.ts` — ціль без
сторінки). «Прибрати» — локальне рішення вкладки: на сервері операція живе до кінця строку.
Історії завершених операцій у лотку немає: після перезавантаження видно лише активні.

## 7. Перші споживачі

| Операція | Кроки | Що перевіряє |
| --- | --- | --- |
| Експорт клієнтів у CSV (**зроблено**, `uo-2`); XLSX — пізніше | без кроків, відсоток | увесь контур: 202 → черга → прогрес → файл → сповіщення |
| Імпорт клієнтів | файл → валідація → запис → звіт про помилки | кроки, скасування, файл помилок |
| Створення тенанта оператором | тенант → перший адмін → налаштування → лист | кроки на platform-площині |
| Підключення WhatsApp-номера | перевірка токена → підписка → тест вебхука | динамічні кроки з параметрами |
| Завантаження документації в AI-індекс | допуск → нарізка → ембедінги → публікація | довгі кроки з власним прогресом |
| Скидання демо-даних | по тенантах | — |

## 8. Суміжні бізнес-можливості

Те, що лягає на платформу далі, згруповано за опорою. Це перелік напрямів, а не план.

- **На `UserOperation`:** експорт та імпорт, генерація PDF (рахунок, комерційна пропозиція),
  вивантаження або видалення даних тенанта, звіти.
- **Наскрізні примітиви записів** (поліморфні, як `activity_links`): коментарі й нотатки з
  вкладеннями, теги, кастомні поля (визначення в `/settings`, значення в jsonb), задачі та
  follow-up поверх `scheduled_notifications`.
- **DataGrid:** серверні збережені представлення, спільні для команди (зараз `localStorage`);
  глобальний пошук і ⌘K (roadmap §2.9).
- **Інтеграції:** API-ключі й вихідні вебхуки — ще один підписник-relay з підписом і ретраями.
- **Комунікації:** налаштування сповіщень за каналами, дайджести, шаблони листів.
- **Доступ:** RBAC на permission-рядках, погодження.
- **Домен:** SLA-таймери й робочі години для тикетів, каталог і прайс-листи → пропозиція →
  білінг.

## 9. Відкриті питання

Питання 1–6 закрито рішеннями власника **2026-11-17**:

1. ~~Хто бачить чужі операції~~ — **лише ініціатор.** Адміністратор тенанта чужих операцій не
   бачить; наслідки видно через Activity Log, оператору — через job-и.
2. ~~Видалення користувача~~ — **каскадно разом із користувачем** (FK `user_id` з
   `ON DELETE CASCADE`), без знімка імені.
3. ~~Одна спільна команда чи команда на тип~~ — **команда на тип**, оголошена модулем-власником
   (`defineCommand('customers.export', …)` з `userOperationId` у payload): «рівно один споживач»
   і граф модулів зберігаються. Спільний виконавець із реєстром обробників не будуємо.
4. ~~Platform-площина~~ — **поки не робимо.** Операції оператора (створення тенанта) лишаються
   поза `UserOperation`; повернутися, коли зʼявиться реальна потреба.
5. ~~Термін зберігання~~ — **30 днів** для завершених операцій; файл результату живе стільки
   ж і видаляється разом з операцією.
6. ~~Де живе модуль~~ — **окремий модуль `user-operations` рівня `platform`** (поруч із
   `notifications` і `files`): ним користуються модулі `core` і `feature`, тож залежність іде
   вниз, а сам він не знає жодного домену.
7. ~~`Idempotency-Key` і власник транзакції~~ — **вирішено 2026-11-17**: interceptor лише читає
   заголовок і кладе ключ у контекст запиту, вставку робить сервіс у своїй транзакції
   (`claim(tx)`); помилки не кешуються. Обґрунтування — [idempotency.md](idempotency.md) §2.
8. ~~Порядок відносно операцій~~ — **вирішено**: окремою зміною перед `UserOperation`, з двома
   наявними ендпоінтами як першими споживачами.

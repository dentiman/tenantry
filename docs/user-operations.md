# Операції користувача, прогрес і лоток активності (User Operations)

> **Статус: лише дизайн, нічого не реалізовано.** Документ фіксує бачення, узгоджене в
> обговоренні 2026-11-15: які примітиви потрібні, як вони називаються, на чому побудовані й
> у якому порядку їх робити. Відкриті питання — у §9. Виняток — спільний `Idempotency-Key`
> (§5.1): він уже зроблений, його еталон — [idempotency.md](idempotency.md).

Скелетон уже має примітиви даних (RLS, транзакції, messaging), файлів (двофазний upload) і UI
(DataGrid, форми, контекстна панель). Бракує спільної відповіді на питання **«що зараз
виконується для цього користувача і на якому воно етапі»**. Сьогодні кожне місце вирішує це
саме: завантаження файлу тримає відсотки в `useState` компонента, асинхронна робота після `202`
для користувача невидима аж до сповіщення.

## 1. Три різні речі, які не треба змішувати

| Що | Де живе правда | Скільки живе | Приклад |
| --- | --- | --- | --- |
| **Передача байтів** (upload) | у браузері | секунди–хвилини, до закриття вкладки | завантаження файлу в S3 |
| **Операція користувача** (`UserOperation`) | рядок у Postgres | хвилини; зберігається дні для історії | імпорт клієнтів, експорт гріда, генерація PDF |
| **Бізнес-стан запису** | доменна таблиця | роки | статус тикета, інвойсу, розмови |

Третій рядок **не є предметом цього документа**. Статуси інвойсу чи тикета — це статична
машина станів конкретного домену (enum + таблиця переходів + умовний `updateMany`), вона
пишеться в модулі-власнику. Універсальний workflow-рушій не будуємо.

Перші два рядки для користувача виглядають однаково — «щось виконується» — тому мають
**спільне відображення** (§6), але різні джерела стану.

## 2. Назва сутності

Сутність називається **`UserOperation`** (таблиця `user_operations`, API `/user-operations`,
сокет-подія `user-operation.changed.v1`).

Чому не коротше:

| Відкинута назва | Причина |
| --- | --- |
| `Operation` | надто загальна — займе слово, яке знадобиться майбутньому домену (складські, фінансові операції); у platform-web уже є область **Operations** (Jobs/Queues) |
| `Job` | зайнято pg-boss і екраном `/operations/jobs`; job — це технічна одиниця черги, а не те, що бачить користувач |
| `Task` | зарезервовано під майбутні задачі/follow-up як бізнес-сутність |
| `Activity` | зайнято Activity Log |
| `Process` / `Workflow` | обіцяють рушій процесів, якого тут свідомо немає |

Прецедент той самий, що `CalendarEvent`: кваліфікована назва, бо просте слово зайняте або
знадобиться пізніше.

Назва також фіксує зміст: **це операція, яку запустив конкретний користувач** і за якою він
стежить. `user_id` обовʼязковий. Системна робота без ініціатора (cron, підписники подій) цією
сутністю не описується — її видно на екрані job-ів.

## 3. Модель даних

Таблиця `user_operations` — tenant-scoped, під стандартним RLS. Стан pg-boss назовні не
віддаємо: `pgboss.*` лежить поза RLS, і job — не те саме, що операція (одна операція може
пережити кілька спроб job-а).

| Поле | Призначення |
| --- | --- |
| `id` | ідентифікатор ресурсу |
| `tenant_id` | межа тенанта (RLS) |
| `user_id` | хто запустив; обовʼязкове |
| `type` | код типу з закритого реєстру; оголошує модуль-власник (`customers.import`, `grid.export`) |
| `status` | `QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELED` |
| `steps` (jsonb) | динамічний список кроків, §4; може бути порожнім |
| `progress_current`, `progress_total` | для операцій без кроків; `null` = невизначений прогрес |
| `revision` | монотонний лічильник для сокета, росте з кожною зміною |
| `subject_type`, `subject_id` | до якого запису належить (необовʼязково) |
| `params` (jsonb) | вхідні параметри |
| `result` (jsonb) | підсумок: лічильники, `resultFileId`, файл з помилками |
| `error_code` | код помилки, не текст — фронт рендерить через i18next |
| `cancel_requested_at` | кооперативне скасування |
| — | окремої колонки ключа ідемпотентності **немає**: повторний запуск гасить спільний `Idempotency-Key`, §5.1 |
| `started_at`, `finished_at`, `expires_at` | час життя; прострочені прибирає cron |

## 4. Кроки — розширений прогрес

Звичайний прогрес — число від 0 до 100. **Кроки** — це прогрес, показаний списком етапів:
перший виконано, другий виконується, решта чекають. Коли завершився останній — операція
завершена.

```json
[
  { "key": "upload",   "status": "done" },
  { "key": "validate", "status": "running", "current": 340, "total": 1200 },
  { "key": "write",    "status": "pending" },
  { "key": "report",   "status": "pending" }
]
```

Правила:

- **Статуси кроку фіксовані й спільні для всіх операцій:** `pending / running / done / failed /
  skipped`. Це єдиний enum у цій моделі.
- **Самі кроки динамічні.** Їх набір задає тип операції, і він може залежати від параметрів:
  імпорт без попередньої перевірки має на крок менше; підключення трьох номерів дає три кроки
  з параметрами підпису (`labelParams`). Окрема бізнес-модель зі статичними станами під кожну
  операцію не потрібна.
- **Підписи бекенд не надсилає.** Фронт рендерить ключ `userOperations.<type>.steps.<key>`
  через i18next — так само, як коди помилок.
- **Крок може мати власний вимірюваний прогрес** (`current`/`total`), якщо він є.
- **Статус операції виводиться з кроків:** останній `done` → `SUCCEEDED`; будь-який `failed` →
  `FAILED`, решта лишаються `pending` або `skipped`.

Кроки зберігаються як jsonb у рядку операції, а не в дочірній таблиці: їх небагато, пише один
воркер, читаються завжди разом з операцією, і один `revision` покриває все. Дочірня таблиця
знадобиться лише тоді, коли кроки почнуть виконувати паралельно різні воркери.

**Обмеження першої версії:** кроки йдуть послідовно в одному обробнику. Крок, що чекає на
зовнішню подію (вебхук, дію людини), сюди не входить — це вже процес, а не прогрес.

## 5. Бекенд: потік виконання

Патерн — Long-Running Operation (Google AIP-151), він же Async Request-Reply. Це гілка «якщо
колись знадобиться», описана в `docs/bulk-operations.md` §6: асинхронна робота стає
**ресурсом** з `GET`, а не push-ем прогресу в сокет. Для батчів гріда на ≤100 рядків рішення
§6 лишається чинним — ресурс стану там не заводимо.

1. **Прийом.** `POST /customers/import` в одному `withTenantTx` вставляє рядок
   `user_operations` (`QUEUED`, початковий список кроків) і робить `publish(tx, …)` команди
   цього типу. Відповідь — `202` з операцією. Публікація поза транзакцією неможлива за
   конструкцією messaging.
2. **Виконання.** Воркер обробляє пачками; кожна пачка — окрема коротка транзакція: дані,
   лічильник прогресу, курсор. Повторна спроба job-а продовжує з курсора, а не з початку.
3. **Кроки.** Обробник оголошує кроки й обгортає кожен:

   ```ts
   await op.steps(['upload', 'validate', 'write', 'report']);
   await op.step('validate', async (s) => { /* … */ s.progress(340, 1200); });
   await op.step('write', async () => { /* … */ });
   ```

   `op.step` сам ставить `running`, потім `done` або `failed`, і збільшує `revision`. При
   повторній спробі кроки зі статусом `done` пропускаються — крок заодно є контрольною точкою.
4. **Запис прогресу** троттлиться (раз на N рядків або на секунду) і йде умовним `updateMany`
   з `revision + 1`.
5. **Сокет.** Після коміту — `user-operation.changed.v1` з `revision`. Це прискорювач за
   правилом 15 з `AGENTS.md`: правда в `GET /user-operations/:id`; пропуск `revision` → клієнт
   перечитує.
6. **Скасування.** `POST /user-operations/:id/cancel` ставить `cancel_requested_at`; воркер
   перевіряє його між пачками.
7. **Завершення.** Звичайне сповіщення в inbox з посиланням на результат і запис в Activity
   Log субʼєкта, якщо він є.

**API:** `GET /user-operations/:id`, `GET /user-operations` (власні), `POST
/user-operations/:id/cancel`. Запуск — завжди доменним ендпоінтом модуля-власника, спільного
`POST /user-operations` немає. Доступ — одна access-функція модуля.

### 5.1. Ідемпотентність запуску — спільний `Idempotency-Key`

Запуск операції — це `POST`, який при повторі мережі чи подвійному кліку створив би дві операції
(два імпорти, два експорти). Захист від цього **не є полем у `user_operations`**: це спільний
шар для всіх REST-мутацій, зроблений окремою зміною `uo-0-idempotency-key` —
**[idempotency.md](idempotency.md)**.

Що з нього потрібно знати тут:

- Ендпоінт запуску операції отримує `@Idempotent()`, а його сервіс викликає
  `idempotency.claim(tx)` першим стейтментом у тій самій `withTenantTx`, де вставляється рядок
  `user_operations` і робиться `publish(tx, …)`. Ключ, операція й job комітяться разом.
- Повтор запуску з тим самим ключем повертає той самий `202` з тим самим `UserOperation` —
  знімок на момент запуску; актуальний стан клієнт усе одно читає через `GET /user-operations/:id`.
- Фронтенд нічого окремо не робить: ключ ставить HTTP-клієнт.

Ідемпотентність **споживача** в черзі — окремий механізм (`MessageInboxService.runOnce`), а
бізнес-ключі на доменних таблицях (`clientMessageId`, `event_id` вебхуків) заголовок не замінює.

## 6. Фронтенд

### 6.1. Менеджер завантажень (без змін бекенда)

Половина вже є: `apps/web/src/features/files/components/file-upload/use-file-upload.ts` рахує
відсотки через `onUploadProgress`, у `libs/ui` є `progress.tsx`. Але стан живе в `useState`
компонента: пішов зі сторінки — завантаження втрачено; кількох файлів і скасування немає.

Серверна сутність тут не потрібна — байти йдуть повз API, прогрес знає лише браузер, а рядок
`files` у статусі `PENDING` уже існує. Потрібен клієнтський шар:

- **Zustand-store завантажень** поза деревом сторінок: `id, file, status, loaded/total,
  abortController`;
- **черга** з лімітом паралельності 2–3, скасуванням через `AbortController` і повтором з новим
  presigned URL;
- **`useFileUpload`** стає тонкою підпискою на store, його API не змінюється;
- **попередження `beforeunload`**, поки є активні завантаження;
- пізніше, за потреби — S3 multipart для великих файлів (єдине місце, де знадобиться бекенд).

### 6.2. Спільне відображення

Один компонент **`StepProgress`** у `libs/ui`: вертикальний список з галочкою, спінером або
крапкою; в активного кроку за наявності — смужка. Він приймає просту модель
`{ key, status, current?, total? }[]` і не знає, звідки вона:

- з сервера — з `useUserOperation(id)` (REST + інвалідація за сокетом, polling як запасний шлях);
- з клієнта — зі store завантажень: upload файлу вже складається з трьох кроків (створення →
  передача байтів → перевірка).

### 6.3. Лоток активності

Один елемент у shell для обох джерел: згорнутий чип «3 активні · 64%», у розгорнутому вигляді —
список. Рядок без кроків показує смужку з відсотком, рядок з кроками розгортається в
`StepProgress`.

## 7. Перші споживачі

| Операція | Кроки | Що перевіряє |
| --- | --- | --- |
| Експорт гріда в CSV/XLSX | без кроків, відсоток | увесь контур: 202 → черга → прогрес → файл → сповіщення |
| Імпорт клієнтів | файл → валідація → запис → звіт про помилки | кроки, скасування, файл помилок |
| Створення тенанта оператором | тенант → перший адмін → налаштування → лист | кроки на platform-площині |
| Підключення WhatsApp-номера | перевірка токена → підписка → тест вебхука | динамічні кроки з параметрами |
| Завантаження документації в AI-індекс | допуск → нарізка → ембедінги → публікація | довгі кроки з власним прогресом |
| Скидання демо-даних | по тенантах | — |

## 8. Суміжні бізнес-можливості

Те, що лягає на платформу далі, згруповано за опорою. Це перелік напрямів, а не план.

- **На `UserOperation`:** експорт та імпорт, генерація PDF (рахунок, комерційна пропозиція),
  вивантаження або видалення даних тенанта, звіти.
- **Наскрізні примітиви записів** (поліморфні, як `activity_links`): коментарі й нотатки з
  вкладеннями, теги, кастомні поля (визначення в `/settings`, значення в jsonb), задачі та
  follow-up поверх `scheduled_notifications`.
- **DataGrid:** серверні збережені представлення, спільні для команди (зараз `localStorage`);
  глобальний пошук і ⌘K (roadmap §2.9).
- **Інтеграції:** API-ключі й вихідні вебхуки — ще один підписник-relay з підписом і ретраями.
- **Комунікації:** налаштування сповіщень за каналами, дайджести, шаблони листів.
- **Доступ:** RBAC на permission-рядках, погодження.
- **Домен:** SLA-таймери й робочі години для тикетів, каталог і прайс-листи → пропозиція →
  білінг.

## 9. Відкриті питання

1. **Хто бачить чужі операції.** Рекомендація для першої версії — лише ініціатор; ADMIN бачить
   наслідки через Activity Log, оператор — через job-и. Перегляд усіх операцій тенанта
   адміністратором — окреме рішення.
2. **Видалення користувача.** Каскадно прибирати його операції чи лишати зі знімком імені
   (як `actorLabel` в активностях). Залежить від відповіді на п. 1.
3. **Одна спільна команда чи команда на тип.** Рекомендація — команда на тип, оголошена
   модулем-власником (`defineCommand('customers.import', …)` з `userOperationId` у payload):
   це відповідає правилу «рівно один споживач» і графу модулів. Спільний виконавець з
   реєстром обробників — альтернатива.
4. **Platform-площина.** Операції оператора (створення тенанта) не мають `tenant_id` у звичному
   сенсі. Окрема таблиця без RLS, як `platform_audit_events`, чи спільна — не вирішено.
5. **Термін зберігання** завершених операцій і файлів результату.
6. **Де живе модуль** у графі (`modules.config.ts`): імовірно рівень `core`, поруч з
   notifications, щоб feature-модулі залежали від нього вниз.
7. ~~`Idempotency-Key` і власник транзакції~~ — **вирішено 2026-11-17**: interceptor лише читає
   заголовок і кладе ключ у контекст запиту, вставку робить сервіс у своїй транзакції
   (`claim(tx)`); помилки не кешуються. Обґрунтування — [idempotency.md](idempotency.md) §2.
8. ~~Порядок відносно операцій~~ — **вирішено**: окремою зміною перед `UserOperation`, з двома
   наявними ендпоінтами як першими споживачами.

## 10. Порядок

Кожен пункт — окрема зміна в OpenSpec, названа з номером фази (`uo-N-…`); поведінка, що лишиться
чинною після реалізації, переноситься в `docs/` перед архівуванням.

| Зміна | Що | Стан |
| --- | --- | --- |
| `uo-0-idempotency-key` | спільний `Idempotency-Key` для REST-мутацій — [idempotency.md](idempotency.md) | зроблено 2026-11-17 |
| `uo-1-…` | менеджер завантажень + `StepProgress` + лоток — лише фронтенд, невеликий обсяг | не почато |
| `uo-2-…` | `UserOperation` + експорт гріда — перший споживач, перевіряє весь контур без кроків | не почато |
| `uo-3-…` | імпорт клієнтів — додає кроки, скасування, файл помилок | не почато |

Далі — решта споживачів з §7 за потребою.

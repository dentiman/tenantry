# Налаштування організації (Settings)

**Статус: РЕАЛІЗОВАНО і перевірено 2026-09-01** (секція `general` + нумерація + журнал змін).
Історія імен: «tenant-settings / System Settings» (пропозиція) → «Workspace Settings» →
**Settings**. Що і чому переглядали — § «Перегляд рішень».

Налаштування, що живуть **на сутності тенанта** й читаються/редагуються з обох plane-ів:
адмін організації (data plane, `apps/api` + `apps/web`) і платформа-оператор (control plane,
`apps/platform-api` + `apps/platform-web`).

## Межа: що сюди, а що в особисті

Тест один: **«якщо цей юзер завтра піде з компанії — налаштування піде з ним?»**

|                      | Розділ                                                 | Приклади                                                            | Хто змінює |
| -------------------- | ------------------------------------------------------ | ------------------------------------------------------------------- | ---------- |
| **Ні** → організація | **Settings** (`/settings`, API `/settings/*`)          | назва компанії, валюта, локаль, нумерація, згодом бренд/модулі/SMTP | ADMIN      |
| **Так** → людина     | **User settings** (`/user-settings`, API `/account/*`) | профіль, пароль, «вийти звідусіль», свої сповіщення, тема           | сам юзер   |

Нумерація — показовий приклад першого: зсув лічильника незворотний і діє на всю компанію,
це не «моя перевага відображення».

## Іменування: чому «Settings» належить організації

На ринку два усталені патерни:

| Патерн                                           | Продукти                                                            | Організація                           | Особисте                                                |
| ------------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------- |
| **A — «Settings» в організації** (домінує в B2B) | GitLab, Stripe, Notion, HubSpot, Salesforce, Odoo, Shopify, Zendesk | **Settings** / Setup / Admin Center   | **User settings** / Preferences / Profile / My Settings |
| B — «Settings» у людини                          | GitHub, Figma                                                       | Organization settings / Team settings | **Settings**                                            |
| C — один розділ, дві групи                       | Linear, частково Slack                                              | група «Workspace»                     | група «Account»                                         |

Обрано **патерн A**: у B2B людина йде в «налаштування», коли їй треба налаштувати БІЗНЕС, а
не власну тему оформлення. Особисте отримує кваліфікатор — **User settings**, як у GitLab
(там це буквальна назва розділу профілю).

**Чому не «Preferences»** для особистого: у нашому розділі лежать пароль, «вийти звідусіль»
і безпека сесій. Зміна пароля — не преференція. GitLab розвʼязує так само: парасолька
зветься User settings, а Preferences — лише одна сторінка всередині (у нас її роль грає
Appearance).

**Чому не «Workspace»** (перша спроба, відкинуто того ж дня): слово зайняте фронтом —
це підзаголовок бренду в сайдбарі й місце під майбутній перемикач контексту. Розділ
налаштувань не має конкурувати з навігаційним поняттям. **І не «Organization settings»**
як назва розділу: `ORGANIZATION` — це вже значення `CustomerKind` (клієнт-юрособа), тому
слово вживається в доку як пояснення, але не як лейбл в UI.

Термінологія по шарах: **`Tenant`** — рядок БД і межа ізоляції (RLS, JWT, черги);
**організація** — те саме людською мовою в документації; **Settings** — як це зветься в UI.

## Де вхід

Два «Settings» в одному меню плутали б, тому вони рознесені — як у GitLab/Notion:

- **Settings (організація)** — пункт ГОЛОВНОЇ навігації в сайдбарі, видимий лише ADMIN-у.
- **User settings (особисте)** — під аватаром, у меню профілю; видно всім.

## Форма API: два питання визначають шлях

**1. Хто суб'єкт?** Доктрина з `docs/account-settings.md`: суб'єкт береться з токена,
**id у шляху немає взагалі**. `/account/*` — «я», `/settings/*` — «моя організація».
Відсутність id і є твердженням «чужа організація через цей ендпоінт недосяжна», і воно не
залежить від уважності в сервісі.

**2. Що це за формою?**

| Форма                                | Дієслова                                   | Реалізовано                                                  |
| ------------------------------------ | ------------------------------------------ | ------------------------------------------------------------ |
| Секція налаштувань = один документ   | `GET` + `PUT` (повна заміна, ідемпотентна) | `GET/PUT /settings/general`                                  |
| Колекція сутностей                   | REST по елементу                           | `GET /settings/numbering`, `PATCH /settings/numbering/:name` |
| Операція, яку не виразиш станом поля | `POST` на дієслівний під-ресурс            | `POST /settings/numbering/:name/next-number`                 |
| Курований зріз для SPA               | `GET`                                      | `GET /settings/bootstrap`                                    |
| Журнал секції                        | `GET`                                      | `GET /settings/activity`                                     |

Нумерація свідомо **не** «секція-документ»: `PUT` як повна заміна не вміє виразити «зсунути
лічильник, тільки вгору» — у цієї дії інше правило (монотонність) і інші наслідки
(не відкочується). Той самий поділ у репо вже є: `PATCH /users/:id` (стан) проти
`POST /users/:id/password` і `POST /account/sessions/revoke-all` (операції).

`GET /settings/activity` існує окремо від generic `GET /activities?entityType=…&entityId=…`
рівно з тієї ж причини, що й решта секції: id організації клієнту не віддається і в шляху не
фігурує. Сервіс під ним — той самий, другої реалізації keyset-пагінації немає. У БД
`entityType` лишається технічно точним `'tenant'`: назовні воно не витікає (у
`ActivityResponse` лінків немає).

## Доступ

| Ендпоінт                                                                         | Хто                                                                              |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `GET /settings/general`, `/bootstrap`, `/numbering`, `/activity`                 | будь-який автентифікований (валюта й наступний номер потрібні звичайним екранам) |
| `PUT /settings/general`, `PATCH /settings/numbering/:name`, `POST …/next-number` | **тільки ADMIN**                                                                 |
| `GET`/`PUT /settings/ai` (AI-1c)                                                 | **тільки ADMIN** — і читання: секцію не потребує жоден інший екран               |

Enforcement — `@Roles(Role.ADMIN)` + глобальний `RolesGuard` (другий APP_GUARD, після
`JwtAuthGuard`). Це **зародок RBAC, а не він сам**: жодних ієрархій ролей і «власника
ресурсу», тільки перелік дозволених ролей на хендлері. Хендлер без декоратора пропускається —
гейт opt-in, інакше введення guard-а вимагало б розмітити одночасно всі наявні ендпоінти.
Повний RBAC (`permissions`-рядки + `@RequirePermissions('settings:write')`) **замінить**
`@Roles`.

Фронт дублює гейт роутом (`beforeLoad: requireAdmin` на `/settings`) — не «замість»
серверного, а щоб USER не дивився на форми, які однаково не збережуться.

## Головна абстракція: секція — це вигляд, а не сховище

API оперує **секціями** (`general`, `email`, `features`, `branding`…). Сховище — **суміш
типізованих колонок `Tenant` і namespace-ключів у `Tenant.settings Json`**. Сервіс/мапер
збирає DTO секції з того, де фізично лежить кожне поле.

Наслідок, що знімає ризик вибору сховища: **місце зберігання поля — приватна деталь
реалізації**. Wire-контракт `GET/PUT /settings/:section` не залежить від того,
колонка це чи json. Поле можна почати в `settings Json` і **підвищити до колонки пізніше**
(коли зʼявиться потреба запитувати/констрейнити) без зміни контракту й коду фронта.

## Секція `calendar` — перший реальний споживач `settings Json`

Додано 2026-09-07 разом із календарем (`docs/calendar.md` §9.5): `GET`/`PUT
/settings/calendar` — документ із зоною за замовчуванням, першим днем тижня, робочими
годинами, типовою тривалістю події і дефолтними нагадуваннями (окремо для all-day).

Зберігається **в `Tenant.settings` під ключем `calendar`**, а не в колонках — евристика
нижче зійшлася на JSON за трьома пунктами з чотирьох: секція згрупована, БД її ніколи не
запитує (платформа не питатиме «усі тенанти з `weekStartsOn = 1`»), а тумблери тут
додаватимуться частіше, ніж хочеться писати міграцію. Наявним тенантам бекфіл не потрібен:
відсутній ключ читається як дефолти (`CALENDAR_SETTINGS_DEFAULTS` у контрактах), рядок
змінюється лише коли адмін щось зберіг — той самий патерн, що `notification_preferences`.

Запис — `read-modify-write` у `withTenantTx`, як і передбачає § «RLS та транзакційність»:
конкурентний `PUT` сусідньої секції не має затирати ключі, яких не чіпав. Дефолти живуть
**константою, а не `.default()` у схемі** — інакше кожне поле стає опційним у `z.input`, і
форма на react-hook-form перестає збігатися з резолвером.

Секція їде і в `GET /settings/bootstrap`: без першого дня тижня і робочих годин сітку
календаря неможливо намалювати першим рендером, а другий запит дав би стрибок розкладки.

## Секція `ai` — персона й інструкції AI-асистента

Додано 2026-09-27 (AI-1c, [ai-assistant-implementation.md](ai-assistant-implementation.md) §15):
`GET`/`PUT /settings/ai` — документ `{ persona, instructions }` (≤ 500 і ≤ 4000 символів,
`trim` до ліміту, порожній рядок = «не задано»), який воркер додає до промпту асистента **після**
незмінних меж, що лишаються в коді. Той самий JSON-патерн, що `calendar`: ключ `ai` у
`Tenant.settings`, відсутній ключ = `AI_SETTINGS_DEFAULTS`, запис — read-modify-write у
`withTenantTx`, журнал `settings.updated { section: 'ai' }` **без тексту**.

Два відхилення від `calendar`, обидва свідомі:

- **Читання теж тільки ADMIN.** Жоден екран поза редактором секцію не потребує (воркер читає
  рядок тенанта напряму, не через API), а адмін може писати туди внутрішні формулювання —
  найменші привілеї. З тієї ж причини її немає в `bootstrap`.
- **Читач спільний із воркером** — `readAiSettings()` у `libs/shared`, а не приватний метод
  сервісу: «що збережено» має означати одне й те саме для редактора і для промпту.

**Власник — модуль `ai`, не `settings`** (з 2026-10-05, docs/modules.md §4). Схема секції — у
`libs/contracts/src/ai/ai-settings.schema.ts`, ендпоінти — `AiSettingsController`
(`apps/api/src/ai/`, URL той самий `/settings/ai`), прапорець `features.ai` у bootstrap фіча
реєструє сама (`BootstrapFeatures`). Settings лише зберігає секцію: `SettingsService.updateSection`
— спільний read-modify-write для всіх JSON-секцій під `SELECT … FOR UPDATE` рядка тенанта (без
блокування два паралельні PUT різних секцій затирали б одна одну). Секція `calendar` поки живе
в settings — це відоме порушення графа модулів (docs/modules.md §7).

Екран `/settings/ai` несе попередження на самому екрані, що текст їде до зовнішнього
AI-провайдера з кожним питанням (`ai-assistant.md` §9.3).

## Сховище: колонка vs `settings Json`

Рекомендація — **гібрид**, не «все в JSON» і не «все в колонки». Кожне поле вирішується
за евристикою.

**Колонка, коли поле:**

1. запитується/фільтрується/сортується **між тенантами** (платформа: «усі тенанти з
   `currency=EUR`», звіти, білінг);
2. має жорсткий констрейнт — enum / FK / `NOT NULL` / unique / `CHECK`;
3. стабільне й універсальне — є в кожного тенанта, форма поля не змінюється;
4. бере участь у логіці БД — default, generated-колонка, join.

**`settings Json`, коли поле:**

1. згруповане/вкладене — smtp-блок, branding-блок це обʼєкт, а не скаляр;
2. опційне/розріджене або feature-flag-подібне — мапа `boolean`, часто змінюється;
3. БД його ніколи не запитує — застосунок читає секцію цілком;
4. швидко ітерується/експериментальне — не хочемо міграцію на кожен тумблер.

**Чому не все в JSON:**

- немає БД-констрейнтів — валідація лише в застосунку (Zod); сирий SQL/інший райтер покладе сміття;
- слабка типізація в Prisma (`JsonValue` + касти);
- дорогі запити/індекси (GIN/expression) — «знайти тенантів з валютою X» стає хаком;
- **merge-hazard**: конкурентні `PUT` різних секцій затирають сусідні ключі — треба tx / jsonb-merge;
- секрети (smtp-пароль) у plaintext jsonb — погано; шифрувати/зберігати окремо.

**Чому не все в колонки:**

- міграція (expand→backfill→notnull) на кожне дрібне/експериментальне поле;
- широка розріджена таблиця з nullable-колонками під рідкі опції;
- вкладені групи (smtp) погано лягають на скаляри.

**Правило за замовчуванням:** сумніваєшся → клади в `settings Json`, промоуть у колонку за потреби.

Рішення **не приймається наперед для всіх майбутніх полів** — воно ухвалюється per-field у
момент, коли зʼявляється конкретне бізнес-поле чи секція. Секційна абстракція гарантує, що
пізніше перенесення поля JSON→колонка не ламає контракт. Таблиця нижче — лише поточно відомий
набір, а не закритий список.

**Розподіл поточно відомих полів:**

| Поле                                            | Де                  | Чому                                                            |
| ----------------------------------------------- | ------------------- | --------------------------------------------------------------- |
| `name`                                          | колонка (є)         | універсальне, показується скрізь                                |
| `locale`                                        | колонка (є)         | дефолт нових юзерів, читає бекенд                               |
| `currency`                                      | **нова колонка**    | закритий enum ISO-4217, потенційно для звітів/білінгу платформи |
| `timezone` (згодом)                             | колонка             | скаляр, універсальне                                            |
| `features`/модулі                               | `settings.features` | мапа boolean, часто змінюється, БД не запитує                   |
| `branding` (лого/кольори)                       | `settings.branding` | вкладений опційний обʼєкт                                       |
| `email`/`smtp` (згодом)                         | `settings.email`    | вкладений обʼєкт; секрети — шифрувати окремо                    |
| план/квоти/entitlements (platform-only, згодом) | скоріше колонки     | білінг/звіти їх запитують                                       |

## Безпека: розмежування даних

Налаштування лежать на рядку `Tenant`; обидва plane-и до нього тягнуться з різною владою.
Розмежування — кілька незалежних шарів (шар RBAC поки **вимкнено**, решта діють):

1. **Межа plane-ів (діє).** Різні JWT-секрети (`JWT_SECRET` vs `PLATFORM_JWT_SECRET`) — токен
   tenant-api не пройде verify у platform-api. Platform-only поля просто **не мають
   data-plane-ендпоінта** — редагуються лише через tenant-CRUD control plane.
2. **RLS `own_tenant` (діє).** Tenant-користувач фізично не прочитає/не змінить чужий рядок
   `tenants` (`id = current_setting('app.tenant_id')`). Сервіс інжектить звичайний
   `PrismaService`, **без ручного tenant-фільтра**; RLS — подвійний запобіжник.
3. **Scope на рівні контракту (діє).** Кожне поле має editability scope: `tenant` (редагують і
   адмін data plane, і оператор), `platform` (тільки оператор), `readonly` (похідні). Data-plane
   схема секції містить **лише `tenant`-scoped поля** — платформенні неможливо прислати, бо їх
   немає в DTO.
4. **Роль (ДІЄ з 2026-09-01).** Запис — `@Roles(Role.ADMIN)` + глобальний `RolesGuard`;
   читання і bootstrap лишились для всіх ролей. Це вузький зародок RBAC, який замінить
   повна система permissions.

## RLS та транзакційність на бекенді

- Читання/запис власного рядка: `this.prisma.tenant.update({ where: { id: actor.tenantId }, data })`
  — RLS `own_tenant` скоупить автоматично.
- Json-секція = **read-modify-write у `TenantTransactions.withTenantTx`** (щоб не затерти сусідні
  секції в `settings`), або jsonb-merge `settings || '{...}'`. Голий `$transaction` заборонений
  ESLint-ом (обходить tenant-extension).
- Зміна пише активність `settings.updated` у тій самій транзакції (фід ніколи не бреше).
- Control plane пише через `SystemPrismaService` (BYPASSRLS), як наявний `TenantsService`.

## Bootstrap / «гарячі» налаштування

`GET /settings/bootstrap` — read-only курований зріз, доступний **будь-якому
автентифікованому** (не лише адміну), який SPA вантажить один раз на старті й кладе в Zustand:

```jsonc
{
  "tenant": { "name": "...", "locale": "en", "currency": "USD", "timezone": null },
  "features": { "billing": true, "tickets": false },
}
```

Без секретів. Фронт бере його для форматування валюти, feature-gating UI, дефолтної локалі.
Розмежування: `bootstrap` — дешевий публічно-безпечний снапшот для всіх; `:section` GET/PUT —
редактор. Кеш оновлюється інвалідацією ключа після успішного PUT.

## Frontend

- Роут **`/settings`** (організація) із бічною навігацією General / Numbering / Activity й
  **`/user-settings`** (особисте) — два окремі розділи з ОДНИМ візуальним каркасом. Спільний
  каркас — навмисно: це одна ментальна модель «розділ із бічною навігацією». Вхід:
  організаційний — у головній навігації (ADMIN), особистий — у меню профілю.
  Каркас із часом розібрали на вже наявні механізми: бічна навігація розділу переїхала в
  колонку шела (2026-09-06, `SectionNav` знято), а заголовок і опис секції — у `PageHeader`
  хедера (2026-09-08); від `components/section/` лишився `ContentSection` як метрика ширини.
- Кожна секція — проста RHF-форма за наявним патерном (`login.tsx` / `create-user-modal.tsx`):
  `zodResolver(GeneralSettingsSchema)` + orval-хуки `useSystemSettings*`, `defaultValues` з GET,
  `applyServerError` на submit, інвалідація ключа після PUT.
- Bootstrap-стор (Zustand) підвантажується при вході; після PUT — інвалідація/оновлення.

## Перша вертикаль (name + currency) — ЗРОБЛЕНО 2026-09-01

1. **Міграція:** `Tenant.currency String @default("USD")` (як `locale`). RLS не чіпаємо — поле на
   наявному рядку.
2. **Контракти** `libs/contracts/src/settings/`: `GeneralSettingsSchema` (`name`, `currency` —
   ISO-4217, `locale`), `SystemSettingsBootstrapSchema`; реекспорт з `index.ts`.
3. **tenant-api** `settings`-модуль: `GET/PUT /system-settings/general` +
   `GET /system-settings/bootstrap` (обидва — будь-який auth поки що).
4. **control plane:** `UpdateTenantSchema` += `currency` (name/locale/isActive уже є) — оператор
   редагує через наявний `PATCH /tenants/:id`.
5. **web:** сторінка `/settings` з General-формою + bootstrap-стор.
6. `openapi:generate` → `web:codegen`; e2e (RLS-ізоляція налаштувань між тенантами, bootstrap-доступ,
   PUT оновлює й пише активність).
7. Оновити цей документ статусом «реалізовано».

Фактично зроблено все перелічене, крім п. 4 (control plane): `PATCH /tenants/:id` поки не
приймає `currency` — оператор платформи редагує тільки `name`/`locale`/`isActive`. Це
найдешевший наступний крок і він у беклозі нижче.

## Перегляд рішень 2026-09-01

| Було в пропозиції                  | Стало                         | Чому                                                                                                                                        |
| ---------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Назва «System Settings»            | **Workspace**                 | «System» читається як платформенне/технічне, а це налаштування КОМПАНІЇ. «Organization» не взяли: слово зайняте `CustomerKind.ORGANIZATION` |
| База `/system-settings`            | **`/workspace`**              | Дзеркало `/account`: суб'єкт із токена, id у шляху немає. Одна доктрина на обидві «мої» сутності                                            |
| Фронтовий роут `/settings`         | **`/workspace`**              | `/settings` зайняв особистий розділ (Account Settings V1, 2026-08-29) — і це правильно: там усе, що йде за людиною                          |
| RBAC відкладено                    | **Запис — ADMIN**             | Разом із нумерацією зʼявилась дія, яку не можна лишати будь-кому: зсув лічильника незворотний і діє на всіх                                 |
| Секції — тільки `GET/PUT`          | **+ колекції й операції**     | Нумерація не влазить у «документ»: `PUT` не виражає «тільки вгору». Форма ресурсу диктує дієслова, а не навпаки                             |
| Журнал через generic `/activities` | **`GET /workspace/activity`** | id воркспейсу клієнту не віддається — фід не можна адресувати парою `{entityType, entityId}`                                                |

Нове, чого в пропозиції не було: колонка `Tenant.currency`, типи активностей
`workspace.settings_updated` і `workspace.numbering_shifted`, `libs/contracts/src/money/`
(довідник валюти — один на воркспейс, кастомера і майбутні документи).

**Перевірено живим прогоном** (dev-API, 2026-09-01): `GET /settings/general` і `/bootstrap`
віддають стан організації; `PUT` із підсунутими `slug`/`isActive` їх мовчки відкидає (slug
лишився `default`), `currency: "eur"` нормалізується в `EUR`; новий кастомер успадковує
валюту компанії; журнал показує `workspace.settings_updated` з реальним актором; USER
отримує 200 на читаннях і **403** на всіх трьох записах.

## Беклог

- `PATCH /tenants/:id` у control plane += `currency` (оператор поки її не бачить).
- **Повний RBAC** — `permissions`-рядки замість `@Roles`; bootstrap лишається для всіх.
- Секції `email`/`smtp` — з шифруванням секретів (не plaintext jsonb).
- Секція `features`/модулі — джерело для feature-gating на фронті й гейтингу модулів на бекенді.
- `branding` — лого через файлову підсистему (`avatarFileId`-патерн), кольори теми.
- Platform-only поля (план/квоти/entitlements) — дизайн разом із білінгом (MT-4).
- Валідація значень секцій на рівні реєстру типів (аналог payload-валідації Activity Log).

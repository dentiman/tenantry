# Кастомери (Customers) — базова бізнес-сутність

**Статус: РЕАЛІЗОВАНО і перевірено 2026-09-01.** Оновлено: 2026-09-01.
Що розійшлося з початковим дизайном під час роботи — §15.
Нумерація переведена на **цілі номери з конфігом серії** того ж дня (§5, §16).

Документ відповідає на питання: **як має виглядати перша доменна сутність скелетона**, від
якої форк розвиває свій бізнес-напрям. Це не «ще один CRUD»: `customers` — це вузол, у який
далі впираються тікети, рахунки, чат, документи і workflow. Помилка в її формі коштує
дорожче за будь-яку іншу в скелетоні, бо на неї посилаються всі наступні таблиці.

доменного модуля), [activity-log.md](activity-log.md), [notifications.md](notifications.md),

## 1. Як цю сутність називають у відомих системах

| Система                                              | Ім'я сутності                                                                                                                                         | Форма моделі                                                                                                       |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **SAP ERP (класика)**                                | `Kunde` / **Customer master**: таблиці `KNA1` (загальні дані), `KNB1` (дані бухгалтерського коду), `KNVV` (дані збутової області)                     | Один майстер, **розрізаний по організаційних рівнях**: та сама компанія має різні платіжні умови в різних юрособах |
| **SAP S/4HANA**                                      | **Business Partner (BP)** — обов'язковий з S/4; ролі `FLCU00` (customer), `FLVN00` (vendor); категорія: Person / Organization / Group                 | **Party-модель**: одна сутність, ролі накладаються. Customer — це _роль_ партнера, а не окрема таблиця             |
| **Microsoft Dynamics 365 F&O**                       | `CustTable` поверх `DirPartyTable` (Global Address Book)                                                                                              | Party-модель, як у SAP                                                                                             |
| **Odoo**                                             | **`res.partner`** — одна таблиця на компанії, фізосіб, контактні особи й адреси; прапорці `is_company`, `customer_rank`, `supplier_rank`, `parent_id` | Party-модель + **ієрархія самопосиланням**                                                                         |
| **ERPNext**                                          | **Customer** (`customer_type`: Company / Individual) + Contact + Address, зшиті через `Dynamic Link`                                                  | Customer окремо, контакти/адреси — спільні поліморфні довідники                                                    |
| **Salesforce**                                       | **Account** (організація) + **Contact** (людина); для B2C — Person Account (склейка двох записів)                                                     | Дві сутності                                                                                                       |
| **MS Dynamics 365 Sales**, **Zoho CRM**, **HubSpot** | Account / Company + Contact                                                                                                                           | Дві сутності                                                                                                       |
| **Pipedrive**                                        | Organization + Person                                                                                                                                 | Дві сутності                                                                                                       |
| **NetSuite**                                         | **Customer** з прапорцем `isPerson`; **Lead → Prospect → Customer — це `status` ОДНОГО запису**, не різні таблиці                                     | Одна сутність зі стадіями                                                                                          |
| **Stripe / QuickBooks / Xero**                       | **Customer**                                                                                                                                          | Одна пласка сутність                                                                                               |

**Три висновки, які має врахувати скелетон:**

1. **Ім'я «Customer» — найпоширеніше і найменш двозначне.** «Account» у CRM означає
   організацію, а в 90% решти софту — обліковий запис для входу. У нашому репо це слово вже
   зайняте: `apps/api/src/account/` і розділ `/settings` — це self-service «мій акаунт»
   ([account-settings.md](account-settings.md)). `AccountService` як CRM-сутність поруч із
   наявним `AccountService` — гарантована плутанина на роки.
2. **Дорослі ERP усі прийшли до party-моделі** (SAP BP, Dynamics DirParty, Odoo res.partner) —
   бо той самий контрагент буває водночас клієнтом, постачальником і працедавцем, і дублювати
   його реквізити тричі виявилось дорожче, ніж один раз зробити ролі. Але вони приходили до
   цього **через 20 років і болючі міграції** (SAP примусово ввів CVI лише в S/4).
3. **Ніхто не робить «Lead» окремою таблицею від «Customer»** — крім Salesforce, і саме її
   Lead-конверсія вважається найгіршою частиною моделі. NetSuite має рацію: це стадія одного
   запису.

## 2. Рішення: як називаємо і якої форми

> **`Customer` — одна сутність, що грає роль контрагента, з дискримінатором `kind`
> (`ORGANIZATION` | `PERSON`) і дочірніми контактними особами `CustomerContact`.**

Чому саме так, а не двома іншими способами:

| Варіант                                              | Що це                                                                     | Чому не він                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Повна party-модель (`Party` + `PartyRole`)           | Одна таблиця контрагентів, ролі customer/vendor/employee окремо           | Це правильна кінцева форма для ERP, але в скелетоні без закупівель і без зарплати вона додає рівень непрямості, яким ніхто не користується. Кожен запит стає join-ом, кожен екран — «а якої ролі?». Ціна відкладення низька: `Customer` → `Party` мігрується перейменуванням таблиці + додаванням `party_roles`, і ця міграція робиться **тоді, коли з'явиться другий тип контрагента**, а не наперед |
| `Account` + `Contact` (Salesforce)                   | Дві незалежні сутності, контакт може існувати без акаунта                 | Ім'я `Account` зайняте (§1.1). А незалежний контакт без організації — це вже адресна книга, окрема підсистема з власним дедупом; у V1 вона не потрібна нікому                                                                                                                                                                                                                                         |
| **`Customer` + `kind` + `CustomerContact` (обране)** | Контрагент = організація або фізособа; контактні особи — діти контрагента | Покриває і B2B (компанія + троє людей), і B2C (`kind = PERSON`, контактів нема або один — сам клієнт). Один запит на список, нуль join-ів на гріді. Дає точку зчеплення для `chat.md` (`CustomerChannelIdentity` вішається на контакт або на кастомера)                                                                                                                                               |

**`kind` вводимо з першого дня і саме як enum-колонку.** Це єдине поле, яке справді дорого
додати потім: від нього залежить обов'язковість `legalName`/`taxId`, форма UI, правила GDPR
(право на забуття стосується PERSON і не стосується ORGANIZATION) і формат номера. Odoo
(`is_company`), NetSuite (`isPerson`), ERPNext (`customer_type`), SAP (BP category) — усі
чотири мають цей прапорець, жодна система не обійшлася без нього.

## 3. Модель даних V1

### 3.1. `Customer`

```prisma
enum CustomerKind {
  ORGANIZATION
  PERSON
}

enum CustomerStatus {
  ACTIVE
  INACTIVE
  ARCHIVED
}

model Customer {
  id       String @id @default(uuid())
  tenantId String @default(dbgenerated("nullif(current_setting('app.tenant_id'::text, true), ''::text)")) @map("tenant_id")

  // Людський ідентифікатор (§5). Генерує сервер, унікальний у межах тенанта
  number   String
  kind     CustomerKind   @default(ORGANIZATION)
  status   CustomerStatus @default(ACTIVE)

  // Те, що бачить людина в гріді і в шапці картки. НЕ унікальне (§11.3)
  name      String
  // Юридична назва / ПІБ у документах, коли вона відрізняється від робочої
  legalName String? @map("legal_name")

  // Основні канали зв'язку рівня організації (reception). Персональні — у контактах
  email        String?
  phone        String?
  phoneCountry String? @map("phone_country") @db.Char(2)
  website      String?

  // Податковий/реєстраційний номер: VAT, ЄДРПОУ, EIN — рядок як прийшов, без валідації (§11.11)
  taxId String? @map("tax_id")

  // Валюта розрахунків (ISO 4217). Потрібна ДО білінгу: без неї не відрендериш жодної суми
  currency String @default("USD") @db.Char(3)
  // Мова листів ДО КАСТОМЕРА. Окрема від users.locale: адресат не співробітник
  locale   String @default("en")

  // Відповідальний менеджер. NULL — «нічий» (легальний стан, не помилка)
  ownerId String? @map("owner_id")

  // Id у системі-джерелі при імпорті/інтеграції. Ключ ідемпотентності імпорту (§11.12)
  externalId String? @map("external_id")

  tags  String[] @default([])
  notes String?

  // Одна адреса рівня V1 (§4.3). country — ISO 3166-1 alpha-2, як phoneCountry
  addressLine1 String? @map("address_line1")
  addressLine2 String? @map("address_line2")
  city         String?
  region       String?
  postalCode   String? @map("postal_code")
  country      String? @db.Char(2)

  createdById String? @map("created_by_id")

  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  tenant   Tenant            @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  // FK НЕ композитний — та сама причина, що в User.avatarFile: Prisma не вміє
  // SET NULL з переліком колонок і занулила б заодно tenant_id. Крос-tenant захист — RLS
  owner    User?             @relation("CustomerOwner", fields: [ownerId], references: [id], onDelete: SetNull)
  contacts CustomerContact[]

  @@unique([tenantId, number])
  @@unique([tenantId, externalId])
  @@unique([tenantId, id])                                  // опора під композитні FK майбутніх модулів
  @@index([tenantId, status, createdAt(sort: Desc), id])     // дефолтний грід
  @@index([tenantId, ownerId])                               // «мої кастомери»
  @@map("customers")
}
```

**Чого тут свідомо НЕМАЄ і чому** (кожен рядок — це поле, яке проситься, але шкодить):

| Поле                                         | Чому не у V1                                                                                                                                                |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deletedAt` (soft delete)                    | §7. Стан «архівний» виражається `status`, а не тінню в кожному запиті                                                                                       |
| `archivedAt`                                 | Дублює `status = ARCHIVED` і здатний із ним розійтися. «Коли і хто заархівував» — це питання до журналу, і в нас на нього вже відповідає `activities`       |
| `creditLimit`, `paymentTermsDays`, `balance` | Мертві поля без білінгу. Приходять разом із EDA-3 і мають сенс лише з валютою і проводками. `balance` — взагалі не колонка, а сума `ledger_entries` (§11.9) |
| `industry`, `segment`, `source`              | Форк-специфічні довідники. Скелетон дає `tags` — цього досить, щоб не блокувати нікого, і не досить, щоб нав'язати чужу класифікацію                        |
| `customFields Json`                          | Найпопулярніша SaaS-пастка (§11.14). Форк додає **колонки** — це його форк і його міграції                                                                  |
| `parentId` (холдинг → філії)                 | Nullable самопосилання додається однією міграцією без бекфілу. Наперед тягне за собою питання «а сума по гілці?», на яке V1 не має відповіді                |
| `logoFileId`                                 | Механіка вже є (`files`, як аватар юзера). Не додає нової інформації про домен — вішається за 20 хвилин, коли знадобиться                                   |

### 3.2. `CustomerContact`

```prisma
model CustomerContact {
  id         String @id @default(uuid())
  tenantId   String @default(dbgenerated("nullif(current_setting('app.tenant_id'::text, true), ''::text)")) @map("tenant_id")
  customerId String @map("customer_id")

  name         String
  position     String?  // посада: «CFO», «комірник»
  email        String?
  phone        String?
  phoneCountry String?  @map("phone_country") @db.Char(2)
  isPrimary    Boolean  @default(false) @map("is_primary")
  notes        String?

  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  tenant   Tenant   @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  // Композитний FK: контакт не може вказати на кастомера чужого тенанта
  customer Customer @relation(fields: [tenantId, customerId], references: [tenantId, id], onDelete: Cascade)

  @@unique([tenantId, id])
  @@index([tenantId, customerId])
  @@map("customer_contacts")
}
```

**Рівно один основний контакт** — частковий унікальний індекс, сирим SQL у міграції (Prisma
часткові індекси не вміє — той самий випадок, що колапс сповіщень):

```sql
CREATE UNIQUE INDEX customer_contacts_primary_unique
  ON "customer_contacts" (tenant_id, customer_id)
  WHERE is_primary;
```

Індекс, а не перевірка в сервісі: «два основні контакти» — це стан, у який система не має
вміти потрапити навіть через гонку двох вкладок.

### 3.3. Нумерація — `NumberSeries` + `NumberSequence`

Дві таблиці, **спільні для всіх майбутніх нумерацій** (invoice, ticket), а не «таблиці
кастомерів»: конфіг серії та її лічильник. Схема, механіка видачі й обґрунтування — §5.

### 3.4. RLS

Три нові таблиці отримують той самий шаблон, що всі tenant-таблиці з MT-2 — дослівно, зі
зміненим ім'ям:

```sql
ALTER TABLE "customers" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "customers" FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "customers"
  FOR ALL
  USING (tenant_id = (SELECT nullif(current_setting('app.tenant_id', true), '')))
  WITH CHECK (tenant_id = (SELECT nullif(current_setting('app.tenant_id', true), '')));
```

Тест `rls.e2e-spec.ts` ловить пропуск автоматично: він звіряє `pg_policies` з переліком
таблиць, що мають `tenant_id`. Забути політику неможливо — впаде наявний тест.

## 4. Поля: обґрунтування трьох неочевидних

### 4.1. `name` — один рядок, не `firstName`/`lastName`

Розділення імені має сенс рівно для сортування «за прізвищем» і звертання в листах. Ціна —
дві колонки, які для `kind = ORGANIZATION` завжди порожні, плюс обчислюване поле для показу
(яке рано чи пізно розійдеться з реальністю). Skeleton бере `name` як **єдине джерело
відображення**; форк, якому потрібне прізвище, додає колонки й індекс — це його домен.

### 4.2. `currency` — є, `creditLimit` — немає

Валюта потрібна найпершому екрану, що показує суму, і **не може бути виведена постфактум**:
історичні рахунки вже виставлені в чомусь. Кредитний ліміт, навпаки, без рахунків нічого не
обмежує і став би полем, яке заповнюють, а система ігнорує — гірший вид мертвого поля.

Дефолт валюти має прийти з налаштувань тенанта, коли з'явиться секція `general`
([settings.md](settings.md) — саме `name + currency` названі там першою
вертикаллю). **Зроблено 2026-09-01:** дефолт справді приходить із налаштувань воркспейсу,
константи в коді для цього більше немає.

### 4.3. Адреса — колонки у V1, окрема таблиця пізніше

| Варіант                              | За                                                                                           | Проти                                                                |
| ------------------------------------ | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **Колонки на `Customer` (обране)**   | Один запит на грід і картку; форма — плаский набір полів; 80% форків мають рівно одну адресу | Друга адреса (доставки) потребує міграції                            |
| Окрема `customer_addresses` з `type` | Одразу правильно для ERP: billing / shipping / N складів                                     | Таблиця без другого споживача = зайвий join і зайвий CRUD-екран у V1 |
| `Json`                               | Гнучко                                                                                       | Не індексується, не валідується, не фільтрується. Найгірше з обох    |

Міграція «колонки → таблиця» одноразова і тривіальна (`INSERT ... SELECT` з `type='BILLING'`

- `DROP COLUMN`). Міграція назад — ні. Тому починаємо з колонок.

**Важливо (§11.5):** коли з'являться документи, адреса й назва **копіюються в документ на
момент виставлення**, а не читаються join-ом. Рахунок не має мінятися через перейменування
клієнта.

## 5. Номер кастомера (account number) — так, потрібен

**Так, потрібен, і це не косметика.** Причини, у порядку ваги:

1. **UUID неможливо промовити.** «Клієнт 000123» у телефонній розмові, у листі, на паперовому
   акті — щоденна операція. Жодна ERP не обходиться без короткого номера.
2. **Це ключ зчеплення з зовнішнім світом** — банківська виписка, 1С, бухгалтерія, старий
   Excel. Мігруючи з чогось, форк принесе свої номери.
3. **Пошук.** Оператор шукає «000123», а не «f47ac10b-…».
4. **id назовні не світимо.** Номер у URL і на екрані — це також те, що можна показати, не
   розкриваючи внутрішній ключ.

### 5.1. Що саме зберігається

**Номер — ціле число, формат — presentation.** Це дві різні речі, і плутати їх дорого:

|                       | Що це                                                                        | Де живе                                                             |
| --------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `number: Int`         | Ідентичність. По ньому сортування, фільтри, точний пошук, майбутні FK-звірки | Колонка `customers.number`, унікальна в межах тенанта               |
| `numberLabel: String` | Те, що людина називає в розмові й пише в листі (`C-000123`)                  | **Не зберігається**: рахується з конфігу тенанта на кожну відповідь |

Чому Int, а не рядок `C-000123`: рядкове сортування правильне рівно доти, доки padding
однаковий — після переходу за `999999` `C-1000000` стає «меншим» за `C-999999`. Плюс зміна
формату (префікс, кількість нулів) вимагала б переписати всі рядки.

**Для документів правило дзеркальне.** Рахунок — юридичний артефакт: його номер
**заморожується в колонку** на момент виставлення, бо виданий папір не має мінятися від
того, що адмін поправив padding. Для майстер-даних перемальовування — навпаки, бажана
поведінка («ми змінили префікс»).

### 5.2. Двигун: конфіг + лічильник

Дві таблиці, бо в них різні життєві цикли — конфіг редагує людина раз на рік, лічильник
блокується на кожній видачі:

```prisma
model NumberSeries {           // КОНФІГ тенанта
  tenantId String
  name     String              // 'customer' | далі 'invoice', 'ticket'
  prefix      String            @default("")
  padding     Int               @default(0)
  startValue  Int               @default(1)    // перший номер у КОЖНОМУ новому періоді
  resetPeriod NumberResetPeriod @default(NONE)
  @@id([tenantId, name])
}

model NumberSequence {         // ЛІЧИЛЬНИК
  tenantId  String
  name      String
  scope     String @default("")  // '' | '2026' | '2026-09' — бакет скидання
  lastValue Int    @default(0)
  @@id([tenantId, name, scope])
}
```

Рядок `NumberSeries` існує **тільки коли тенант змінив дефолт** — той самий патерн, що в
`notification_preferences`: дефолти (`NUMBER_SERIES_DEFAULTS`) живуть у контрактах, і нова
серія не потребує бекфілу для наявних тенантів.

`scope` заведений з першого дня, хоч у кастомерів завжди `''`: **скидання за періодом —
властивість документів, а не майстер-даних** («рахунок №1 за 2027 рік» — норма, «клієнт №1
за 2027 рік» — ні), а додати колонку в PK згодом дорожче, ніж завести її порожньою зараз.
Для інвойсів `scope` рахується з **ділової дати документа**, а не з `now()`: рахунок,
виставлений 31 грудня і збережений 1 січня, мусить потрапити у свій рік.

### 5.3. Механіка видачі

```ts
// libs/shared NumberingService.allocate(), усередині withTenantTx домену
await tx.$queryRaw`
  INSERT INTO number_sequences (name, scope, last_value)
  VALUES (${name}, ${scope}, ${series.startValue})
  ON CONFLICT (tenant_id, name, scope)
    DO UPDATE SET last_value = number_sequences.last_value + 1
  RETURNING last_value
`;
```

- `tenant_id` не згадується **ніде**: у INSERT його ставить DB-default із CLS, підзапит до
  конфігу скоупить RLS. Мультитенантність лишається невидимою і тут.
- Гілка INSERT спрацьовує рівно раз на (серія, період) і кладе `startValue` — саме так
  «початковий номер» стає **першим виданим**, а не першим+1.
- Один атомарний стейтмент; відкат транзакції забирає і номер.

**Номер видається якомога пізніше** — безпосередньо перед `INSERT`-ом, якому він потрібен.
Блокування рядка лічильника тримається **до коміту**, тож усе, що можна зробити раніше
(перевірки, читання), робиться поза ним, а зовнішнього I/O (SMTP, платіжний провайдер) у
такій транзакції бути не може взагалі — воно тримало б чергу на створення для всього тенанта.

### 5.4. Чому таблиця-лічильник, а не `SEQUENCE` і не `MAX+1`

|                 | `CREATE SEQUENCE`                                            | `MAX(number)+1` під advisory-локом                    | Таблиця-лічильник (обране)                         |
| --------------- | ------------------------------------------------------------ | ----------------------------------------------------- | -------------------------------------------------- |
| Тенанти         | Одна на всю БД → номери «скачуть» і **витікає обсяг сусіда** | Своя по суті                                          | Рядок на (tenant, серія, період)                   |
| RLS             | Послідовності поза RLS                                       | —                                                     | Звичайна tenant-таблиця з політикою                |
| Відкат          | `nextval` **не відкочується** → дірки                        | Дірок немає                                           | Інкремент у тій самій транзакції → **дірок немає** |
| Видалення рядка | Номер не повертається                                        | Номер **перевикористовується** — для рахунка фатально | Лічильник монотонний                               |
| Конкурентність  | Не блокує                                                    | Серіалізує локом                                      | Серіалізує блокуванням рядка                       |

Серіалізація — свідома ціна: створення кастомера чи рахунка — операція частотою одиниці на
хвилину. Натомість маємо **безрозривну нумерацію**, без якої не обійдуться документи (у
більшості юрисдикцій пропуск у нумерації фіскальних документів — це питання від податкової).
Патерн ставиться на дешевій сутності, щоб на дорогій він уже був відпрацьований.

Якщо імпорт на 100k рядків колись упреться в цей лок — він бере діапазон **одним**
інкрементом (`last_value + N`), а не N інкрементами. Схему це не міняє.

### 5.5. «Задати початковий номер» — дві різні операції

| Операція                                                             | Коли діє                       | Механіка                                                     |
| -------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| `startValue` у конфігу (`PATCH /settings/numbering/:name`)           | до першого документа в періоді | застосовується в момент створення бакета — гілка INSERT вище |
| «наступний номер = N» (`POST /settings/numbering/:name/next-number`) | коли лічильник уже живий       | `last_value = GREATEST(last_value, N-1)` — **тільки вгору**  |

Вниз кнопки немає взагалі: попередні номери вже видані, зниження гарантує колізію на
унікальному індексі. Спроба знизити — **тихий no-op**, і у відповіді видно реальний
наступний номер (щоб адмін не думав, що спрацювало).

Головний сценарій другої операції — міграція зі старої системи: імпорт кладе чужі номери
напряму, після чого лічильник одноразово підіймається до максимуму використаного.

### 5.6. Правила навколо номера

- **Генерує тільки сервер.** У `CreateCustomerSchema` поля `number` немає.
- **Номер не змінюється.** `UpdateCustomerSchema` його не приймає: на нього посилаються в
  листуванні й у документах.
- **Номер не перевикористовується** після видалення. Лічильник монотонний.
- **Пошук** по номеру — точний збіг по цифрах із запиту: `K5000`, `5000` і `005000` знаходять
  той самий запис (`contains` тут був би шкідливий — «1» знаходило б половину бази).
- **Формат і початковий номер** редагуються адміном на `/settings/numbering` (docs/settings.md); період скидання —
  ні: він приходить із коду, бо в майстер-даних безглуздий, а ввімкнути його означало б
  зламати унікальність номера.

## 6. Логіка створення

**Мінімум для створення — `name`.** Це не спрощення, а свідоме правило CRM: форма на 15
обов'язкових полів призводить до того, що менеджер заводить «ТОВ Ромашка» у блокнот, а не в
систему. Усе інше добирається на картці.

Порядок усередині одного `withTenantTx` (чужого коду не редагуємо — все нове):

1. **Резерв номера** (§5.1) — першим, бо він бере блокування; далі транзакція коротка.
2. **`tx.customer.create`** — `tenantId` не передаємо (DB-default), `ownerId` за
   замовчуванням = `actor.sub` (той, хто завів, і веде — найчастіший випадок; явно
   переданий `ownerId` перекриває), `createdById = actor.sub`.
3. **`activities.record(tx, { type: 'customer.created', … })`** з лінком
   `{ entityType: 'customer', entityId, role: 'subject' }`. Фід кастомера після цього працює
   **без жодного рядка нового коду** — `GET /activities?entityType=customer&entityId=…` уже
   generic.
4. **`notifications.notify(tx, …)`** — **не всім адмінам**. Поява кастомера цікава рівно
   одній людині: власнику, якщо це не автор дії. `recipientIds: ownerId !== actor.sub ?
[ownerId] : []`; recorder однаково відсіє «актор == отримувач». Розсилати всім адмінам,
   як на `user.created`, тут не можна: юзерів заводять десятками на рік, кастомерів —
   десятками на день, і це перше, що змусить людей вимкнути сповіщення взагалі.
5. **Події в чергу V1 не публікує.** `MESSAGE_TOPOLOGY` за побудовою забороняє повідомлення
   без споживачів (кидає на старті), а реального підписника на `customer.created.v1` зараз
   немає. Подія з'явиться разом із першим споживачем — чат (`chat.md`), білінг (EDA-3) або
   інтеграція. Це не борг: публікувати факт у нікуди — гірше, ніж не публікувати.

**Дедуплікація на створенні — м'яка.** Жодних unique на `name`/`email`/`taxId`: два
підрозділи однієї компанії з тією самою поштою — норма, а жорсткий констрейнт призведе до
«ТОВ Ромашка 2» замість правильного запису. V1: створюємо. Підказка «схоже на існуючого» —
§11.3.

## 7. Життєвий цикл: статус, архів і видалення

**Статуси V1: `ACTIVE` → `INACTIVE` → `ARCHIVED`** (і назад, окрім видалених).

- `INACTIVE` — «зараз не працюємо», запис лишається в пошуку і звітах;
- `ARCHIVED` — «прибрати з очей»: за замовчуванням не потрапляє в грід (фільтр за
  замовчуванням `status != ARCHIVED`), але доступний за прямим лінком і в звітах.

**Стадій продажу (`LEAD`/`PROSPECT`) у V1 немає** свідомо. Воронка — це не стан контрагента,
а стан **угоди** з ним; змішавши їх, отримуємо запис, який одночасно «лід» і має три
оплачені рахунки. Форк, чий бізнес — продажі, або додає значення в enum (одна міграція), або
заводить `deals` — і другий шлях правильніший.

**Зміна статусу — окремий ендпоінт `PATCH /customers/:id/status`**, не поле в `PATCH`. Точно
та сама причина, що в `users`: це подія, яку читають у журналі («хто заархівував клієнта»),
а не редагування атрибута. Повторний виклик із тим самим значенням — no-op **без запису в
журнал**.

**Видалення — справжній `DELETE`, а не soft delete.** Аргументація:

- soft delete отруює **кожен** запит системи (`WHERE deleted_at IS NULL` у ста місцях, і
  досить забути в одному, щоб клієнт «воскрес» у звіті);
- він конфліктує з унікальними індексами (номер видаленого рядка лишається зайнятим);
- бізнес-потреба «щоб не заважав, але лишився» вже покрита `ARCHIVED`;
- від справжніх помилок захищає цілісність: коли з'являться `tickets`/`invoices`, їхній FK
  на кастомера ставиться `onDelete: Restrict`, і БД сама не дасть видалити того, на кого
  посилаються документи. `DELETE` лишається тим, чим має бути, — виправленням щойно
  зробленої помилки («завів дубль»).

Для PERSON-кастомерів існує третій сценарій — **анонімізація** (§11.7), і це не видалення.

## 9. Активності і сповіщення

Нові типи в `ACTIVITY_TYPES` (закритий enum + payload-схема на тип):

| Тип                      | Коли                         | Payload                                                                                     |
| ------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------- |
| `customer.created`       | створення                    | `{ customer: EntityRef }`                                                                   |
| `customer.archived`      | `status → ARCHIVED`          | `{ customer }`                                                                              |
| `customer.restored`      | `ARCHIVED → ACTIVE/INACTIVE` | `{ customer, status }`                                                                      |
| `customer.owner_changed` | зміна відповідального        | `{ customer, previousOwner: EntityRef \| null, owner: EntityRef \| null }`                  |
| `customer.deleted`       | видалення                    | `{ customer }` — лінк лишається на неіснуючий id, і це нормально: журнал переживає сутність |

`customer.updated` із діффом **не заводимо** — та сама доктрина, що в юзерах: журнал читають
люди, і «хто змінив відповідального» має фільтруватися по `type`, а не розбором payload-у.
Редагування другорядних полів у журнал не потрапляє взагалі.

`NOTIFICATION_TYPES` поповнюється одним типом — **`customer.assigned`** (категорія
`workspace`, вимикається, дефолт увімкнено), ціль кліку `{ kind: 'customer', id }`. Плюс
рядок `customer: '/customers'` у `apps/web/src/lib/entity-routes.ts` — після нього і
сповіщення, і фід починають лінкувати на картку.

## 11. Підводні камені (те, на чому спотикаються SaaS CRM/ERP)

### 11.1. Кастомер — це НЕ користувач системи

Найдорожча помилка на старті: зробити кастомера рядком у `users`, «щоб він міг зайти в
кабінет». Наслідки: клієнт бачить внутрішні екрани; RBAC ділиться навпіл посеред однієї
таблиці; звіт «скільки в нас співробітників» починає рахувати клієнтів; RLS-політика на
`users` вже написана під персонал.

**Рішення у скелетоні:** `customers` і `users` — різні таблиці **назавжди**. Клієнтський
портал, коли знадобиться, — це третя identity (як `platform_users` у control plane:
`REVOKE`, свій JWT-secret, свій guard), або nullable `users.customerId` під окремою роллю —
але це рішення MT-рівня, і воно приймається окремо, а не випадково.

### 11.2. Номери: дірки, гонки, імпорт

Розписано в §5. Коротко: не `SEQUENCE` (глобальна, поза RLS, дає дірки), не `MAX(number)+1`
(і гонка, і перевикористання номера після видалення), не UUID замість номера, ніколи не
перевикористовувати. Номер зберігати **числом**, формат тримати окремо — інакше зміна
формату означає переписати всі рядки, а сортування ламається на переході через padding.

### 11.3. Дублікати і злиття

Дублікати з'являються **завжди**: імпорт, два менеджери, «ТОВ Ромашка» / «Ромашка ТОВ». Це
головна проблема даних будь-якої CRM, і вона не вирішується unique-констрейнтом.

**Рішення у скелетоні:** V1 не заважає створювати дублі, але зобов'язаний закласти шлях до
merge. Мінімум, який треба передбачити **зараз**, поки таблиць мало:

- усі майбутні посилання на кастомера — через FK, а не через денормалізовану назву (тоді
  merge = `UPDATE ... SET customer_id = :survivor` по N таблицях);
- `mergedIntoId String?` додається однією міграцією, коли merge реалізують: старий рядок не
  видаляється (лишаються посилання і людська пам'ять), а стає вказівником;
- підказка «схоже на існуючого» на формі створення (пошук по нормалізованих `name`/`email`/
  `taxId`) — дешева і знімає 80% дублів **до** їх появи. Це кандидат №1 у V2.

### 11.4. Видалення проти цілісності

Див. §7. Головне правило: **FK з документів на кастомера — `Restrict`, не `Cascade`.**
Каскадне видалення кастомера разом із його рахунками — це втрата бухгалтерії одним кліком.

### 11.5. Документи мусять зберігати снапшот

Рахунок, акт, договір фіксують назву, адресу і податковий номер **на момент виставлення**.
Клієнт перейменувався або переїхав — старі документи не змінюються. Join на живу таблицю в
рендері документа = мовчазна фальсифікація вже виданого паперу.

У нас цей патерн уже прийнято і працює: `activities`/`notifications` зберігають `actorLabel`
і `label` у payload саме як снапшоти. Документи мають робити так само — але не в payload, а
в **колонках рядка документа**.

### 11.6. Перейменування і пошук по історії

Наслідок §11.5: після перейменування пошук «за старою назвою» перестає знаходити. Дорослі
системи тримають `customer_name_history`. У скелетоні цього немає; журнал (`activities`)
частково закриває потребу, і це задокументована межа, а не забутий пункт.

### 11.7. PII і право на забуття

Для `kind = PERSON` кастомер — це персональні дані. GDPR-запит «видаліть мене» стикається з
вимогою зберігати фінансові документи 5–7 років. Видалення рядка неможливе, тому потрібна
**анонімізація**: `name → 'Deleted customer 000123'`, порожні email/phone/адреса, а документи
лишаються зі своїми снапшотами.

**Пастка, специфічна для нашої архітектури:** снапшоти імені лежать ще й у `activities.payload`
і `notifications.payload`. Процедура анонімізації зобов'язана або пройтись по них, або мати
задокументовану відповідь, чому ні. Це треба вирішити **до** того, як прийде перший реальний
запит, а не після.

### 11.8. Пошук і продуктивність списку

`ILIKE '%щось%'` не використовує btree-індекс — до ~20–50k рядків на тенант це непомітно,
далі список починає «думати». Лікування — `pg_trgm` + GIN-індекс по нормалізованому полю
(`lower(name)`), плюс пошук по `number`/`taxId` окремою точною гілкою (шукаючи «000123»,
людина хоче збіг, а не входження).

Другий бік — `COUNT(*)` для `totalPages` в offset-пагінації: на сотнях тисяч рядків він
дорожчий за саму вибірку. Курсорна пагінація в проєкті вже є (`activities`) — це шлях
відходу, коли впремося.

**V1:** `ILIKE`, як у `users`. Trgm-індекс — перший рядок беклогу цього документа (§12), бо
`CREATE EXTENSION` — це операційна зміна для трьох середовищ (dev-init, тестова БД, прод), і
її треба робити окремим свідомим ходом, а не побічним ефектом доменної міграції.

### 11.9. Гроші

Ніколи `Float`. `Decimal` (Prisma `@db.Decimal(18,4)`) або цілі в мінорних одиницях. Валюта
зберігається поруч із сумою **у кожному документі**, а не тільки на кастомері (кастомер
може змінити валюту — виставлені рахунки не змінюються). Баланс кастомера — це **сума
проводок**, а не колонка: колонка `balance` розсинхронізується першим же ретраєм job-а.
Деталі — EDA-3 (`ledger_entries` + звірка).

### 11.10. Адреси

Не валідувати надто суворо. Немає універсального формату поштового індексу (Ірландія його
взагалі не мала до 2015), «region» — це і штат, і область, і префектура. Обов'язковим має
бути максимум `country` (ISO alpha-2, той самий словник, що для телефонів). Автопідстановка
з поштових API — інтеграція, не ядро.

### 11.11. Податкові номери

VAT / ЄДРПОУ / EIN / ІПН — різні формати, різні довжини, різні алгоритми контрольної суми,
і вони змінюються. Валідувати їх у контракті — гарантований баг «не приймає валідний номер
клієнта». Зберігати як рядок, нормалізувати (прибрати пробіли/дефіси) для пошуку і
порівняння, перевірку через VIES/зовнішній сервіс робити окремою фічею з явним статусом
«перевірено / не перевірено».

### 11.12. Імпорт і зовнішні id

Перше, що зробить форк, — заллє існуючу базу. Тому `externalId` (унікальний у межах тенанта)
закладається зараз: він робить імпорт **ідемпотентним** (повторний запуск оновлює, а не
дублює) і дає зчеплення з системою-джерелом на майбутнє. Сам імпорт — це `dispatch`-режим із
[bulk-operations.md](bulk-operations.md): множина задана файлом, робота довга, часткова
відмова осмислена.

### 11.13. Видимість записів (record-level security)

У «дорослих» CRM це окремий двигун: «менеджер бачить лише своїх», «керівник — усю
територію». Спокуса зробити це фільтром у сервісі закінчується тим, що фільтр забувають в
експорті, у звіті й у пошуку.

**Рішення у скелетоні:** V1 — **усі кастомери видно всім у межах тенанта**, `ownerId` — це
атрибут відповідальності й фільтр «мої», а не право доступу. Це задокументована межа. Коли
знадобиться справжня видимість, вона робиться **тим самим механізмом, що tenant-ізоляція** —
RLS-політикою поверх `app.user_id`, а не умовами в коді; ця дорога вже вимощена MT-2.

### 11.14. Кастомні поля на тенанта

Класична пастка SaaS: EAV-таблиця (запити стають нечитабельними, типів немає, індексів
немає) або `JSONB`-смітник (те саме, плюс ілюзія порядку). Обидва варіанти означають, що
жодна форма і жоден звіт не знають своєї схеми.

**Рішення у скелетоні: кастомних полів немає.** Скелетон **форкають** — форк додає свої
колонки і свої міграції, отримуючи типізацію, індекси і валідацію безкоштовно. Механізм
per-tenant полів потрібен лише продукту, який не можна форкати під клієнта; це свідомо не
наш випадок.

### 11.15. Статус як вільний рядок

Статуси мусять бути enum у БД. `status String` перетворюється на «active», «Active»,
«ACTIVE » за півроку. Переходи між статусами пишуться в журнал окремими типами (§9) — інакше
питання «коли клієнта заархівували» не має відповіді.

### 11.16. `updatedAt` як шум

Уже спіймано на `users.last_seen_at`: фонові записи піднімали `@updatedAt`, і присутність
виглядала як редагування профілю. Для кастомерів це повториться з першою ж інтеграцією, що
синхронізує їх у фоні. Правило: фонові оновлення технічних полів — сирим `UPDATE` без
`@updatedAt`, і кожен такий випадок називається в документі.

## 16. Нумерація: перехід на цілі номери (2026-09-01, того ж дня)

Перша реалізація видавала номер **рядком** (`C-000123`) із форматом у константах модуля.
Переглянуто на вимогу: номер має бути **цілим автоінкрементом, своїм у кожного тенанта, з
можливістю задати початкове значення** — і за тим самим принципом далі підуть рахунки.

Що змінилось:

|                  | Було                                          | Стало                                                                        |
| ---------------- | --------------------------------------------- | ---------------------------------------------------------------------------- |
| Колонка          | `number String`, формат зашитий у код модуля  | `number Int`; формат — конфіг тенанта `number_series`                        |
| Відповідь API    | `number: "C-000123"`                          | `number: 123` + `numberLabel: "C-000123"` (рахується на льоту)               |
| Двигун           | приватний метод `CustomersService.nextNumber` | `NumberingService` у `libs/shared` — щоб рахунки не переписували його з нуля |
| Ключ лічильника  | `(tenant, name)`                              | `(tenant, name, scope)` — бакет скидання під річну нумерацію документів      |
| Початковий номер | недоступний                                   | `startValue` у конфігу + монотонний зсув лічильника (§5.5)                   |
| Пошук            | `contains` по рядку                           | точний збіг по цифрах із запиту                                              |
| Налаштування     | немає                                         | `/settings/numbering` (дві форми: формат і зсув лічильника)                  |

**Міграція** робить `ALTER COLUMN … TYPE INTEGER USING regexp_replace(...)`, а не
`DROP + ADD`, який згенерував Prisma: згенерований варіант **мовчки втратив би дані**.
Разом із колонкою переживає й унікальний індекс, тому згенерований `CREATE UNIQUE INDEX`
із міграції прибраний.

**Перевірено живим прогоном** (dev-БД, `pnpm db:reset` → чиста схема + сід): дефолти серії
віддаються без рядка в БД (`isCustomized: false`), сід дав 1…3 і `nextNumber` = 4; зміна
формату на `K` + 4 знаки перемалювала **вже створених** (`C-000001` → `K0001`), не чіпаючи
`number`; зсув лічильника на 5000 → наступний кастомер отримав рівно 5000; спроба знизити до
7 — тихий no-op (лишилось 5001); пошук `K5000` / `5000` / `005000` знаходить той самий запис;
`startValue: 0` → 400, невідома серія → 404. **162 tenant-e2e** (+7 нумераційних) і 11
platform-e2e зелені.

# AI-асистент: PostgreSQL-вектори, джерела знань і майбутні доменні запити

Статус: впроваджується; PG foundation готовий · Оновлено: 2026-10-03

Цей документ уточнює **майбутні AI-2…AI-4** у [плані асистента](ai-assistant.md).
Поточна реалізація AI-0…AI-1 описана в [довіднику реалізації](ai-assistant-implementation.md).
Перший крок AI-2a.1 уже реалізовано: tenant-таблиці, pgvector bootstrap та
точний SQL search за готовим вектором. FMS ingest і підключення до чату ще
попереду; послідовність змін — у [технічному плані](ai-assistant-implementation-plan.md).
Рішення наступної фази: **відразу
використати PostgreSQL 17 + pgvector для індексу знань**; Postgres FTS додати в тому
самому пошуку для точних назв, кодів і номерів. Окрему векторну БД та окремий RAG-сервіс
поки не вводити.

## 1. Що показав приклад FMS Docs

Локальний зріз `/path/to/fms-docs`
від 2026-10-03: **416 Markdown-файлів, 3 959 549 байтів Markdown** (36 МБ усієї теки,
включно з іншими файлами). За frontmatter: 88 `current`, 240 `draft`, 3 `historical`,
85 без `status`; є англійські й російські сторінки, а також робочі та інженерні зони.
Серед бізнесових зон `010`–`190` лише **16 сторінок `current` (85 730 байтів)**,
і всі вони належать `010_saas_platform/`. Для пілота з клієнтами, білінгом або
підтримкою потрібне явне затвердження відповідних `draft`-сторінок.
Це приклад **масштабу й форми джерела**, а не дозвіл автоматично включити в асистента
весь сторонній репозиторій. Зокрема, `300_workbench/`, `000_docs/`, інженерні посилання,
чернетки та переклади можуть мати іншу аудиторію або повторювати контент. Навіть
позначка `current` у FMS означає стан документа, а не дозвіл на показ певному користувачу.

Поточні 13 файлів `docs/ai-knowledge/` генерують компактний корпус, який цілком іде в
промпт. На корпусі розміру FMS та при додаванні нових документацій ця схема перестає
бути керованою за ціною, контекстом і правами доступу. Індекс має бути **багатоджерельним**:

| Джерело                                                     | Власник і шлях додавання                                                                                                  | Початкове правило доступу                                                                                      |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `docs/ai-knowledge/`                                        | PR → CI → деплой; наявне джерело                                                                                          | глобальне, чинний `audience`                                                                                   |
| Документація продукту в іншому Git-репозиторії, як FMS Docs | явна конфігурація репозиторію, ревізії, кореня й дозволених зон; початково артефакт із контрольованого CI/deploy checkout | лише затверджені сторінки й явно зіставлені ролі; локальний абсолютний шлях не входить у runtime-конфіг форків |
| Глобальні матеріали платформи                               | контрольований імпорт через control plane                                                                                 | доступні відповідним tenant-користувачам після публікації                                                      |
| Матеріали конкретного тенанта                               | Tenant Admin через наявний Files/S3-процес                                                                                | тільки свій тенант; додаткові права визначає майбутній RBAC                                                    |

Починати з Markdown і `.txt`. PDF/таблиці та зовнішні сайти додавати як окремі
адаптери після перевірки парсингу, прав доступу та якості цитат. Джерело зберігає
`source kind`, стабільний `canonical_id`/URI, `revision`, `language`, `status`,
`audience`, власника, час синхронізації та політику публікації. Для FMS за замовчуванням
допускати лише явно вибрані бізнесові зони з `status: current`, `publish != false` і
відомим `audience`; невідомий статус чи аудиторія — **не індексувати** до ручного рішення.
Для такого корпусу цього буде замало: контент-власник може окремо затвердити
конкретну `draft`-сторінку через allowlist із ревізією та терміном повторної
перевірки. Це не змінює її статусу у вихідному репозиторії й не публікує решту
чернеток. `audience` з FMS (`sales`, `support`, `finance` тощо) не дорівнює ролям
`ADMIN`/`USER` нашого скелетона; відповідність задається окремою політикою.
Мовні версії мають окремі ідентичності, але однакові концепти пов'язуються через
`canonical_id`/`related_ids`; чернетки й архіви не з'являються випадково в пошуку.
Пілотний CLI читає вказаний оператором локальний checkout; production-адаптер
читає контрольований checkout під час CI/деплою й передає перевірений
manifest/артефакт, доступний у runtime-образі, для ingest.
Довільні локальні шляхи чи Git URL з UI не
дозволяються; віддалена синхронізація з окремими credentials може з'явитись пізніше.

## 2. Варіанти та розмір архітектури

| Варіант                                   | Перевага                                                  | Обмеження                                                          | Рішення                                                                    |
| ----------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Повний корпус у промпті                   | найпростіший і вже працює для 13 файлів                   | масштабується разом із корпусом; ускладнює дозволи й цитування     | зберегти як fallback на час міграції, не як режим для FMS-подібного обсягу |
| Лише FTS у Postgres                       | точні терміни та коди, без виклику embedding API          | пропускає перефразування й міжмовні запити                         | гілка гібридного пошуку, не окрема проміжна фаза                           |
| **pgvector + FTS у тому самому Postgres** | семантика й точні збіги, ті самі бекапи, транзакції й RLS | потрібні pgvector-образ, embedding provider та контроль індексації | **обрано для AI-2**                                                        |
| Окрема vector DB / пошуковий кластер      | окреме масштабування за дуже великого навантаження        | друге сховище прав, синхронізація, операційна складність           | лише після виміряного обмеження Postgres                                   |

Для сотень Markdown-сторінок почати з **точного** vector search після фільтрів прав
доступу й FTS/GIN; pgvector підтримує точний пошук без ANN-індексу. HNSW додавати за
`EXPLAIN ANALYZE`, p95 і recall на реальному корпусі. Спільний HNSW-індекс у
мультитенантній таблиці може втрачати релевантні результати після фільтрації; за
потреби перевіряти iterative scan, часткові індекси або партиціювання. Немає підстав
одразу створювати індекс чи партицію на кожен тенант. Це **план перевірки**, а не
обіцянка конкретної латентності на невідомому навантаженні.
Формула сирого зберігання одного `vector` — `4 × dimensions + 8` байтів
([pgvector](https://github.com/pgvector/pgvector)). Наприклад, **умовні** 3 000
чанків × 1 536 вимірів дають близько 18,5 МБ самих векторів, до тексту,
індексів та накладних витрат Postgres. Це оцінка порядку величини, не вибір
embedding-моделі чи прогноз кількості чанків; реальний обсяг залежить від
редакторського відбору, парсингу й розміру чанка.

## 3. Поставка по етапах: ранній робочий FMS-пошук

Оцінки нижче — **інженерні діапазони для одного розробника, знайомого з цим
репозиторієм**, а не календарні обіцянки. Вони не включають редакторське
затвердження FMS-сторінок, вибір/оплату провайдера та зовнішній аудит безпеки.
Кожен етап закінчується результатом, який можна показати й перевірити.

| Етап                                    | Орієнтир | Що з'являється                                                                                                                                                            | Критерій завершення                                                                                                                                   |
| --------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AI-2a.0 — FMS manifest і baseline**   | 1–2 дні  | Конфіг джерела `fms`, правила зон/статусів/мов/аудиторій, список затверджених `draft`, набір реальних питань; dry-run рахує документи, чанки й приблизні embedding-токени | Оператор бачить точний список включених/відхилених файлів і причину, не відправляючи контент провайдеру                                               |
| **AI-2a.1 — база й межі доступу**       | 2–4 дні  | PG17-образ із pgvector в усіх середовищах, bootstrap extension, SQL-міграції джерел/чанків, RLS, окремий `EmbeddingProvider`                                              | `ws:init`/reset/e2e створюють той самий стан; `saas_app` не читає чужий tenant-контент                                                                |
| **AI-2a.2 — робочий FMS vector search** | 4–7 днів | Ідемпотентний імпорт із **цього** FMS checkout у PostgreSQL; Markdown → секції → чанки → embeddings; команда пошуку за питанням показує релевантні фрагменти й джерела    | На локальному слоті повторний імпорт не дублює чанки; питання про затверджені FMS-сторінки повертає їх через `pgvector` без LLM-генерації             |
| **AI-2a.3 — відповіді в асистенті**     | 3–5 днів | `AiPanel` бере FMS-фрагменти через `KnowledgeSource`, обмежує контекст і показує перевірені цитати; вибір продуктового джерела не змішує FMS з довідкою SaaS Skeleton     | Авторизований тестовий користувач ставить питання про FMS і отримує відповідь із клікабельним джерелом; за відсутності підстав асистент це повідомляє |
| **AI-2a.4 — hybrid і якість**           | 3–5 днів | FTS/GIN, режими `vector`/`fts`/`hybrid`, злиття кандидатів, виміри recall, latency і токенів; HNSW лише за потреби                                                        | На одному наборі питань порівняно три режими; режим за замовчуванням обраний за результатом, tenant/role leakage тести зелені                         |
| **AI-2b — керовані джерела**            | 5–8 днів | Завантаження `.md`/`.txt` для глобального й tenant-scope, публікація/зняття, статус ingest, ліміти й видалення в UI                                                       | Tenant Admin бачить лише свої джерела; зміна прав або видалення прибирає фрагмент із наступної відповіді                                              |

**Перший повністю робочий векторний пошук — AI-2a.2**, ще без витрат на генерацію
відповіді. **Перший робочий FMS-асистент — AI-2a.3**. Після AI-2a.4 пошук стає
гібридним; векторна частина вже працює з AI-2a.2. AI-2b додає способи подачі
документації до того самого індексу. Сумарний порядок для AI-2a — **13–23
інженерні дні**, для AI-2a+AI-2b — **18–31 день**; найбільша невизначеність —
якість/права FMS-контенту та фактична робота embedding-провайдера з `en`/`ru`/`uk`.

Для локального пілота CLI отримує шлях
`/path/to/fms-docs` **як явний
операторський параметр**, а не як захардкоджений шлях у скелетоні чи значення з
користувацького запиту. Заплановані команди: `ai:docs:preview` (жодних API-викликів),
`ai:docs:ingest` (публікація нової ревізії після успішної індексації) та
`ai:docs:search` (питання → top-K фрагментів з ID/заголовком/ревізією). **Цих
команд зараз немає.** У production той самий parser читає артефакт із
контрольованого checkout на зафіксованому commit, який потрапив у runtime-образ.
Тестовий manifest може містити ширший набір `draft` лише в непублічному
середовищі; для відповідей кінцевим користувачам потрібне явне затвердження.

FMS описує інший продукт. Відповідь по ньому потребує scope `product=fms` або
окремого тестового tenant/інсталяції; пошук за замовчуванням **не змішує** його
з `docs/ai-knowledge/` цього скелетона.

### Технічні контури етапів

Уточнення першого інкременту: індекс tenant-owned, `tenant_id` обов'язковий.
Для пілота обрано `text-embedding-3-small`, 1536 вимірів, cosine; provider API
adapter ще не реалізовано. FTS/GIN додаються на AI-2a.4. Глобальна публікація
переходить до AI-2b через окремі global-таблиці з read-only доступом tenant-ролі;
правила глобального доступу нижче описують цільову архітектуру.

1. **Інфраструктура.** Замінити `postgres:17-alpine` у локальному, production і stack
   compose на перевірений, зафіксований PostgreSQL 17 образ із pgvector; перевірити
   оновлення існуючого volume, backup/restore, workspace slots і CI/e2e.
   `saas_migrator` не є суперкористувачем, а pgvector не позначений trusted extension:
   `CREATE EXTENSION IF NOT EXISTS vector` має бути відтворюваним привілейованим
   bootstrap-кроком у **кожній** dev/test/prod БД (або еквівалентом керованого сервісу),
   включно з `db:reset`; міграція під `saas_migrator` перевіряє наявність/версію
   extension і створює таблиці та індекси. Роль мігратора не підвищувати.
   [PostgreSQL: CREATE EXTENSION](https://www.postgresql.org/docs/17/sql-createextension.html),
   [pgvector control file](https://raw.githubusercontent.com/pgvector/pgvector/v0.8.6/vector.control).
   За Prisma 7 `vector` потребує SQL-міграцій та
   параметризованих raw/TypedSQL-запитів; `Unsupported`-поле не слід повертати як
   звичайну Prisma-модель. [Prisma: extensions](https://docs.prisma.io/docs/postgres/database/postgres-extensions),
   [pgvector: Docker і пошук](https://github.com/pgvector/pgvector).
2. **Модель знань.** Таблиці джерел/документів/чанків у PostgreSQL: стабільні ID,
   `source_revision`, `content_hash`, текст, метадані, `tsvector`, `embedding`,
   `embedding_model` і стан індексації. Обрана модель embedding фіксує розмірність
   `vector(n)` та метрику й має покривати мови документів і запитів (`en`/`ru`/`uk`);
   зміна моделі означає версіонований повторний ingest і
   переключення індексу після перевірки, без змішування векторів різних моделей.
   Точний набір колонок і спосіб перевірки відповідності scope у джерела/чанка —
   предмет міграції, а не новий доменний API.
3. **Ізоляція.** Глобальні документи читаються tenant-роллю, але редагуються лише
   control plane; tenant-документи й чанки мають `tenant_id`, RLS `USING`/`WITH CHECK`
   і DB-перевірку того, що чанк має scope свого джерела. Пошук у воркері працює
   через `TenantTransactions.withTenantTx` з `saas_app`, без `SystemPrismaService` та
   без `tenantId` у бізнесовому `KnowledgeSource`. Фільтр `audience`/майбутній RBAC
   застосовується **до** видачі тексту моделі; RLS закриває межу тенанта, не права
   окремої людини. Стан публікації та поточні права перевіряти також під час
   кожного пошукового запиту: застарілий embedding не дає права читати текст.
   Для майбутнього RBAC серверний `KnowledgeQuery` може отримати ID користувача,
   локаль і його дозволи; ці поля потрібні авторизації, але не передаються в LLM.
   Сирий SQL для vector/FTS є деталлю сховища і лишається
   параметризованим. [PostgreSQL 17: RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).
4. **Ingest.** Окремий `EmbeddingProvider` з конфігурацією на рівні деплою, лімітами
   викликів/витрат і обліком; не підміняти ним чатний `LlmProvider`. Парсер прибирає
   frontmatter, навігаційний MDX/HTML, нецільові code blocks і дублікати; ріже за
   заголовками з контрольованим overlap, зберігає breadcrumb розділу. За
   `content_hash` незмінні чанки не переембедяться. Індексація йде в
   `apps/worker`/pg-boss з ідемпотентним upsert, ретраями, видаленням зниклих
   джерел і атомарною публікацією нової ревізії. Зовнішньому embedding API текст
   теж передається назовні: для tenant-файлів потрібні така сама видима згода та
   політика провайдера, як для генерації.
5. **Пошук і відповідь.** `KnowledgeSource.select` повертає лише дозволені чанки
   та їхні ідентифікатори. Поточний виклик `select()` міститься в `prepare()`
   **всередині tenant-транзакції**. Перед мережевим embedding-викликом цей шлях
   треба розділити: прочитати стан/роль/питання, відпустити транзакцію, отримати
   embedding, потім у короткій `withTenantTx` заново перевірити стан/права,
   виконати RLS-пошук і лише після добору зробити fenced `claim()`. Не тримати
   транзакцію Postgres відкритою протягом виклику провайдера. Запит проходить
   semantic top-K і FTS top-K; результати
   об'єднуються, наприклад RRF, з дедуплікацією за документом/розділом. Для
   питань з точним кодом, номером чи назвою оцінювати посилення FTS; додатковий
   reranker вмикати лише після eval. У промпті залишаються незмінні межі,
   далі довірена організаційна інструкція, а фрагменти джерел передаються як
   **недовірені дані**, з ID та шляхом для цитування. Обмежити токени і кількість
   чанків, просити відповідати з посиланнями або прямо сказати, що підстав немає.
   Перевіряти кожне посилання за списком реально відібраних чанків; посилання на
   tenant-документ відкривати тільки через авторизований маршрут.
6. **Відтворюваність.** Наявний `ai_messages.knowledge_version` лишити як ревізію
   індексу/корпусу, але для RAG додати запис фактично відібраних `chunk_id`,
   `source_revision`, моделі embedding і версії пошукового пайплайна. Самого
   `knowledge_version` вже недостатньо, щоб відтворити конкретний промпт;
   повний replay можливий лише поки збережено відповідні версії контенту.
   Після видалення tenant-джерела зберігати лише дозволені політикою ретенції
   метадані, а цитату робити недоступною, не повертати видалений текст.
   Контракт відповіді/цитат і UI змінювати через Zod → OpenAPI → orval.

AI-2a індексує реальний локальний FMS checkout у пілоті, а після перевірки —
контрольований артефакт того самого джерела для деплою. Наявний репозиторний
корпус можна перенести в той самий індекс окремим manifest без змішування продуктів.
Гібридний пошук і цитати завершують AI-2a.
AI-2b додає контрольоване публікування глобальних і tenant-документів через UI.
Обидва використовують одну модель знань і той самий пошук: додавання нової
документації означає додати адаптер/джерело та політику допуску, а не новий RAG-сервіс.

## 4. Практики, важливі станом на 2026 рік

| Практика                                    | Що беремо зараз                                                                                                                                                                                                      | Що перевіряємо до ускладнення                                           |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Гібридний retrieval замість самих embedding | vector + Postgres FTS, злиття результатів і збережені цитати; [pgvector](https://github.com/pgvector/pgvector) прямо описує hybrid search                                                                            | ваги, RRF і reranker за власним набором питань                          |
| Контекст для чанка                          | заголовок, breadcrumb, мова й canonical ID у тексті для embedding; [дослідження Anthropic](https://www.anthropic.com/engineering/contextual-retrieval) показує користь цього підходу на їхніх даних                  | чи покращує це саме FMS-подібні сторінки, особливо переклади й таблиці  |
| Керованість корпусу                         | явна публікація, scope, ревізія, видалення і правила аудиторії до індексації                                                                                                                                         | додаткові конектори та складні ACL лише з реальним джерелом прав        |
| Оцінювання до оптимізації                   | retrieval/answer eval, citation check, tenant-leak tests, p95/витрати                                                                                                                                                | HNSW, reranker, інша БД або модель embedding лише після вимірів         |
| Обмежені агентні інструменти                | read-only allowlist на майбутній AI-4, без загального SQL/MCP-доступу; [OWASP Agentic AI 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) описує ризики надмірних повноважень | write-дії й зовнішні MCP-конектори як окремі функції з власним дозволом |

Це не твердження, що один метод завжди точніший: результати Anthropic та поради
pgvector — підстава **порівняти** варіанти на нашому корпусі, а не переносити
чужі відсотки чи параметри індексу без тесту.

## 5. Доменні дані тенанта — окремий маршрут AI-4

Запит «як оформити рахунок» — пошук у документації; «який баланс клієнта X зараз» —
авторизоване читання live-даних. Векторний індекс **не** є реплікою CRM і не має
містити знімки клієнтів, балансів, квитків чи PII за замовчуванням. Для таких
запитів планувати read-only typed tools (`findCustomer`, `getCustomerSummary`,
`countOpenTickets` тощо): Zod-схеми аргументів/результатів, явний allowlist,
обмеження кількості викликів і розміру відповіді, перевірка прав людини та
виклик наявних доменних сервісів під tenant-контекстом/RLS. Модель не отримує
SQL, Prisma Client, системну роль чи довільний HTTP-доступ. Персональні поля
мінімізувати перед відправкою провайдеру; результати tools вважати недовіреним
вмістом. Записи/зміни бізнес-даних — окреме рішення з явним підтвердженням людини.

Поточні `ASSISTANT_BOUNDARIES` прямо кажуть, що доступу до бізнес-даних немає.
Перед запуском AI-4 треба змінити ці межі, згоду/розкриття в UI, контракт провайдера
для tool-calling, правила авторизації й тести. Саме зараз потрібен лише **шов**
для маршрутизації «питання про продукт → knowledge», «питання про дані →
доменний tool або чесна відмова», без удаваного доступу до БД. MCP доречний
лише для зовнішньої сумісності з контрольованими інструментами; він сам не
вирішує авторизацію чи ізоляцію. [OWASP: Agentic AI 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/),
[OWASP: MCP security](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html).

## 6. Перевірка якості й умови збільшення системи

- Перед перемиканням із повного корпусу зібрати тестові питання з поточного
  продукту та FMS-подібного джерела: точні терміни, перефразування,
  міжмовні запити, відповідь у кількох документах, відсутню відповідь,
  draft/архів, роль `USER`/`ADMIN`, два tenant-и, зміну/видалення джерела.
  Окремо перевірити спроби prompt injection у Markdown та в майбутніх tools.
- Порівняти baseline (повний корпус для малого набору), vector-only, FTS-only,
  hybrid; виміряти `Recall@k` для відомих релевантних сторінок, коректність
  цитат/утримання від відповіді, p50/p95 затримки, токени й вартість ingest та
  запиту. Модельну оцінку відповіді доповнити ручною перевіркою; вибір `K`,
  chunk size, reranker і HNSW — за цими результатами, а не за модою.
- Показувати revision, стан ingest, помилки, кількість чанків і ціну в
  адмініструванні. Повторний запуск не створює дублікатів; видалення/зміна
  дозволів прибирає фрагменти з видачі до наступної відповіді. Тести
  доводять, що tenant B і `USER` не отримують заборонений текст навіть у
  цитатах і після індексації.
- Окремий векторний сервіс, workflow engine або постійний reranker з'являються
  лише після зафіксованої проблеми: неприйнятна затримка/recall чи операційний
  ліміт Postgres, який не виправляється локально. Додаткові джерела самі по
  собі не є такою підставою.

Актуальна практика, на яку спирається цей план: pgvector документує **точний
пошук, hybrid FTS+vector та ризик filtered ANN**
([pgvector](https://github.com/pgvector/pgvector)); дослідження Anthropic показує
перевагу контексту чанка, лексичного пошуку й reranking на своїх наборах даних,
але ці цифри не переносяться автоматично на наш корпус
([Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval));
OWASP у рекомендаціях 2026 окремо розглядає ризики агентних дій, а RAG-документи
залишаються вектором prompt injection
([Agentic AI 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/),
[Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)).

## 7. Як працюватиме стек

```text
FMS checkout / інші джерела
  → manifest: продукт, ревізія, дозволені файли й аудиторії
  → parser Markdown → секції → чанки + breadcrumb + content hash
  → EmbeddingProvider (лише нові/змінені чанки)
  → PostgreSQL 17: source + document + chunk + vector + tsvector

Питання користувача → tenant JWT → ai.generate-reply у worker
  → embedding питання (один виклик, якщо обрано vector/hybrid)
  → tenant-транзакція: RLS + права джерела → vector top-N / FTS top-N
  → злиття, дедуплікація, контекстний бюджет → LLM → відповідь + цитати
```

`pgvector` зберігає вектор і обчислює близькість; embedding-модель — окремий
провайдер у воркері. `tsvector` — лексичний індекс PostgreSQL на тому самому
тексті, не embedding. Chat LLM теж окремий провайдер. Отже два зовнішні види
викликів: embedding для індексації/питання і генерація відповіді. FTS працює
без LLM-виклику. Застосунки `api`, `worker`, `platform-api` та наявні
`pg-boss`/Socket.IO/Valkey залишаються на своїх місцях.

Мінімальна модель записів у Postgres:

| Запис        | Що містить                                                                                                                | Навіщо                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `source`     | `product`, тип (`repo`/`upload`), scope (`global`/`tenant`), власника, активну ревізію, правила публікації                | не змішувати продукти й тенантів; вмикати/відкочувати джерело |
| `document`   | стабільний ID із `canonical_id` або шляху, локаль, заголовок, статус, URI, hash                                           | посилання на оригінал, дедуплікація перекладів/ревізій        |
| `chunk`      | ID документа, heading path, порядковий номер, текст, hash, `vector(n)`, `tsvector`, embedding model/version, tenant scope | одна одиниця пошуку й цитування                               |
| `ingest run` | ревізія джерела, кількість файлів/чанків, unchanged/embedded/skipped/failed, токени й помилки без вмісту                  | повторний імпорт, контроль витрат і діагностика               |

Зберігати нову ревізію чанків **неактивною**, поки не завершиться весь ingest;
після перевірок атомарно переключати активну ревізію source. Помилка посеред
batch не залишає половину документів у видачі. ID/хеш чанка дають повторний
запуск без дублювання і без повторної оплати незміненого тексту. Зміна
embedding-моделі створює нову версію індексу, яку можна порівняти й переключити;
вектори різних моделей в одному пошуку не порівнюються.

Перший chunker: різати по заголовках, ціль **≈400 токенів** на чанк, overlap
**≈50 токенів**, зберігати breadcrumb (`Customers → Dunning → Warning`) разом із
текстом для embedding. Таблиці/правила не рвати механічно посеред рядка;
довгу таблицю ділити на самодостатні частини з повтореним заголовком. Це
початкові параметри для eval, не універсальні межі. У preview показувати
фактичні токени за обраною моделлю або чітко позначену оцінку, якщо її
токенайзер недоступний. Конкретні файли FMS із HTML/MDX і перекладами
перевіряти на витік навігаційного шуму та дублікати перед embedding.

## 8. Керування пошуком і питанням

Три режими працюють над **тим самим набором опублікованих і дозволених чанків**:

| Режим    | Виклики й ранжування                                                          | Для чого                                                                   |
| -------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `vector` | embedding питання → cosine distance у pgvector                                | перший пілот AI-2a.2; перефразування й міжмовний пошук                     |
| `fts`    | `websearch_to_tsquery`/`ts_rank_cd` у PostgreSQL; embedding-виклику немає     | точні терміни, коди, діагностика та резерв при недоступності embedding API |
| `hybrid` | паралельні списки vector і FTS → злиття рангів (початково RRF) → дедуплікація | цільовий режим після AI-2a.4                                               |

RRF складає внески від **позиції** фрагмента в кожному списку, тому не потрібно
вдавати, що cosine distance і FTS score мають однакову шкалу. Наприклад,
питання «як призупинити послугу абонента?» у FMS-scope дає vector top-12 і
FTS top-12; після злиття/дедуплікації лише п'ять дозволених фрагментів
потрапляють у промпт. Якщо користувач питає точний код, FTS може підняти
відповідний фрагмент; якщо формулювання не збігається зі словами документа,
допомагає vector-гілка. Ваги й кількість кандидатів підтверджуються eval.

На вході в search сервер бере **tenant і користувача з автентифікованого job-контексту**,
а `product/source set` — з конфігурації інсталяції/дозволеного робочого простору.
З тексту питання не приймаються `tenantId`, довільний SQL, file path чи URL для
нового джерела. Опційні фільтри `area`/`language` можна дати через валідований
контракт; `role`/доступ до документів сервер встановлює сам. Права й статус
публікації перевіряються під RLS до віддачі тексту моделі та повторно при
відкритті цитати. Підсумковий список — орієнтовно **5 чанків**, обмежений
токенами; два сусідні чанки одного розділу можна об'єднати, якщо це не
витіснить інші релевантні джерела.

У AI-2a.2 команда пошуку показує `source/document/chunk`, score, heading,
мову й короткий excerpt — так можна перевірити retrieval **без LLM**. У
AI-2a.3 `AiPanel` показує лише дозволені цитати, а LLM отримує відібраний
текст як недовірені дані. Відповідь без підтвердження у фрагментах має бути
відмовою/уточненням. LLM може запропонувати citation ID, але сервер приймає
тільки ID з фактичного результату пошуку. Коли embedding API недоступний у
гібридному режимі, можна перейти на FTS із явною позначкою деградації в
діагностиці; у чистому `vector` режимі — явна помилка, а не вигадана відповідь.

Після AI-2a.4 режим обирає оператор інсталяції, а не звичайний користувач.
Діагностична команда/екран порівнює всі три режими на одному питанні. LLM
rewrite питання, multi-query, reranker і HNSW — **вимкнені у першому релізі**;
кожен додає ціну або складність і потребує виміряного виграшу. Для коротких
уточнень на кшталт «а де це?» пошуковий запит може додати останній хід
користувача детерміновано; окремий LLM rewrite вмикати лише якщо eval покаже
проблему. FTS-конфігурацію перевірити окремо для `en`/`ru`/`uk`; не застосовувати
мовний stemmer іншої мови до всіх документів. PostgreSQL підтримує
`websearch_to_tsquery`, `ts_rank_cd` та GIN для цього сценарію
([FTS-запити](https://www.postgresql.org/docs/17/textsearch-controls.html),
[GIN](https://www.postgresql.org/docs/17/textsearch-indexes.html)).

## 9. Налаштування й економіка токенів

Це **заплановані параметри**, їх ще немає в `AiConfig`. Значення — старт для
пілота, змінювати після замірів, без tenant-керування моделлю чи ключем.
Налаштування провайдера живуть лише у воркері/секретах деплою; API не отримує
embedding-ключ. Конфіг `source manifest` версіонується разом із кодом.

Для пілота достатньо одного зовнішнього embedding API за окремим адаптером
`EmbeddingProvider` і детермінованого fake для CI. Це не той самий виклик, що
чатний `OpenAiCompatProvider`; навіть якщо URL/вендор збігаються, модель,
ліміти й облік окремі. Альтернатива для документації, яку не можна відправляти
зовнішньому провайдеру, — локальна embedding-модель за тим самим інтерфейсом;
вона прибирає тариф за токени, але додає обслуговування й обчислювальні
ресурси. Вибір робиться до першого ingest, бо зміна embedding-моделі вимагає
повторної індексації. Провайдер має бути протестований на `en`/`ru`/`uk`,
сталій розмірності й ліміті токенів на один запит.

| Група                                            | Початкове значення / правило                                                                                        | Вплив                                                                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `AI_KNOWLEDGE_BACKEND`                           | `static` до перемикання, `postgres` для FMS-пілота й фінального PG-режиму                                           | контрольований перехід; у PG-режимі не додавати повний статичний корпус у промпт                    |
| `AI_EMBEDDING_PROVIDER`, URL, key, model         | явний провайдер і **одна зафіксована модель** з підтримкою `en`/`ru`/`uk`; розмірність/метрика валідовані зі схемою | зміна моделі вимагає нової версії індексу, не лише env-змінної                                      |
| `AI_DOCS_CHUNK_TARGET_TOKENS` / `OVERLAP_TOKENS` | ≈400 / ≈50                                                                                                          | менші чанки зменшують контекст відповіді, але можуть втратити правило; overlap збільшує ціну ingest |
| `AI_DOCS_EMBED_BATCH_SIZE` / `CONCURRENCY`       | 32 тексти / 2 запити як початкове обмеження, з урахуванням ліміту API                                               | контролює швидкість, 429 і пікові витрати; не міняє кількість токенів тексту                        |
| `AI_DOCS_SEARCH_MODE`                            | `vector` на AI-2a.2; `hybrid` після оцінювання AI-2a.4; `fts` для діагностики/резерву                               | дає чесне порівняння якості й витрат                                                                |
| `AI_DOCS_VECTOR_CANDIDATES` / `FTS_CANDIDATES`   | 12 / 12                                                                                                             | скільки кандидатів гілки віддають до злиття; не означає 24 чанки в промпті                          |
| `AI_DOCS_FINAL_CHUNKS` / `MAX_CONTEXT_TOKENS`    | 5 / 2 500 токенів разом із заголовками й citation ID                                                                | основна стеля витрат на знання в кожній відповіді                                                   |
| `AI_DOCS_RERANK`, `AI_DOCS_QUERY_REWRITE`        | `false`                                                                                                             | немає додаткового LLM-виклику та його затримки без підтвердженої користі                            |
| `AI_DOCS_INGEST_TOKEN_BUDGET`                    | явний ліміт на запуск; preview показує обсяг до відправлення                                                        | захист від випадкового індексування всього checkout                                                 |

Наявні `AI_MAX_OUTPUT_TOKENS=1024`, `AI_HISTORY_TURNS=10` та добові квоти
генерації лишаються параметрами **чатного** конвеєра. У FMS-пілоті порівняти
`AI_HISTORY_TURNS=4` проти 10 і стелю відповіді 768 проти 1024 на контрольних
питаннях; міняти дефолти лише якщо якість не погіршується. Поточні
`ai_usage_counters` рахують генерацію, а не embedding ingest/питання:
AI-2a має окремо фіксувати фактичні embedding-токени й вартість на source/run
та на query/tenant (без тексту). Добові квоти на embedding-запити й окремий
ліміт ingest потрібні до публічного tenant upload.

Рахунок для розуміння витрат:

```text
ingest:  токени embedding = сума токенів НОВИХ/ЗМІНЕНИХ чанків з overlap і breadcrumb
питання: токени embedding = токени одного нормалізованого пошукового запиту
відповідь: input = межі + організація + коротка історія + обрані чанки + питання
           output = фактично згенеровані токени, але не більше AI_MAX_OUTPUT_TOKENS
```

При орієнтирі 5 × 400 токенів корпус дає близько **2 000 токенів фрагментів**
плюс заголовки/цитати, обмежених стелею 2 500. Поточний живий прогін малого
корпусу мав близько **11 000 токенів усього промпту**, з яких на повторному
ході близько 98% читалося з кешу
([вимір у реалізації](ai-assistant-implementation.md)). Отже зменшення сирих
токенів промпту **не дорівнює** такому самому зменшенню рахунку: динамічні
чанки можуть втратити частину prompt cache. В AI-2a.3 порядок повідомлень
потрібно свідомо змінити на стабільні межі → інструкція організації →
динамічні чанки → історія → питання й виміряти `cachedPromptTokens`, input,
output, embedding-токени та час відповіді на холодному/теплому ході.

Економія без втрати знань: пропуск незмінених чанків за `content_hash`, короткий
контекст після дедуплікації, обмежена історія й відповідь, нуль LLM-викликів
для query rewrite/rerank за замовчуванням. **Гібридний запит усе одно оплачує
embedding питання**; FTS заощаджує його лише в окремому `fts` режимі або в
майбутньому перевіреному маршрутизаторі точних кодів.
Кешування **готової відповіді** на питання між tenant-ами не планується:
права/ревізії можуть відрізнятися. Кеш embedding однакового нормалізованого
питання можна дослідити окремо з ключем за model/version і політикою
приватності; це не заміна перевірки RLS при кожному пошуку.

Оператор бачить не лише суму токенів, а розклад по `ingest embedding`,
`query embedding`, `generation input`, `cached input`, `generation output`
та source/tenant. Без цього не можна об'єктивно обрати `vector` чи `hybrid`,
розмір чанків, модель або ліміти. Конкретну грошову ціну підставляють із
тарифу обраного провайдера на день налаштування; цей план не фіксує тариф,
який може змінитися.

### Приклад ціни одного питання по FMS (тарифи на 2026-10-03)

Для одного питання припускаємо 100 токенів на embedding запиту, 4 000 вхідних
токенів генерації (з них до 2 500 — знайдені FMS-фрагменти з посиланнями,
решта — інструкції, історія та питання) і **500 оплачених вихідних токенів**.
Останні включають невидимі reasoning-токени, якщо модель їх витрачає. Кеш,
повторні спроби й додаткові LLM-кроки не враховані. FTS/vector виконуються
у власному Postgres без окремої плати за пошуковий API.

| Генерація                                                 | Вхід / вихід за 1M токенів | Embedding питання | Разом за питання | За 1 000 питань |
| --------------------------------------------------------- | -------------------------- | ----------------- | ---------------- | --------------- |
| `gpt-5.6-luna` (модель поточного живого прогону)          | $0.20 / $1.20              | $0.000002         | **$0.001402**    | **$1.40**       |
| `gpt-6-luna` (кандидат після перевірки адаптера й якості) | $0.10 / $0.50              | $0.000002         | **$0.000652**    | **$0.65**       |

У таблиці embedding — `text-embedding-3-small` за $0.02/1M токенів.
Формула: `input_tokens × input_rate / 1M + output_tokens × output_rate / 1M +
query_embedding_tokens × embedding_rate / 1M`. Тарифи:
[GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna),
[GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna),
[text-embedding-3-small](https://developers.openai.com/api/docs/models/text-embedding-3-small).
Це **оцінка API-витрат**, не вимір FMS-пілота. Для `gpt-6-luna` поточний
`OpenAiCompatProvider` ще не перевірено з його параметрами ліміту відповіді та
`reasoning_effort: none`; без явного налаштування reasoning-модель за
замовчуванням працює з `medium`, тому оплачений вихід може бути більшим.
Тариф OpenRouter, якщо залишити його маршрутом, звіряється окремо.

Обсяг FMS-корпусу впливає насамперед на **одноразовий ingest** та зберігання:
у генерацію входять тільки відібрані чанки, не всі 416 Markdown-файлів.
Якщо після відбору й overlap до embedding надійде 1–2M токенів, перша
індексація коштуватиме приблизно $0.02–$0.04 за тарифом вище; це сценарій,
а не підрахунок токенів відібраного корпусу. Оновлення оплачує тільки змінені
чанки. Робота Postgres/диску входить у вартість власної інфраструктури й тут
не оцінена. Реальний рахунок пілота слід перерахувати за usage від провайдера.

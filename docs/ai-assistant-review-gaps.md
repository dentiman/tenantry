# AI-асистент: прогалини рев’ю та план виправлення

Дата: 2026-09-21. Обсяг: реалізація AI-0 із `FakeLlmProvider`.
Це результати статичного рев’ю та план робіт; наведені сценарії ще не підтверджені
окремим інтеграційним прогоном. Статус усіх пунктів: відкриті.
Контекст: [поточна реалізація](ai-assistant-implementation.md).

## 1. Немає атомарного захоплення генерації та захисту від застарілої спроби

**Ризик: високий за паралельної повторної доставки.**

**Місце:** [AiGenerateReplySubscriber](../apps/worker/src/subscribers/ai-generate-reply.subscriber.ts),
методи `prepare`, `persistPartial`, `finalize`.

`prepare()` допускає як `PENDING`, так і `STREAMING`. Перевірка статусу та запис
не встановлюють виключного власника генерації. Якщо повторна доставка перекриється
з попередньою спробою, обидві можуть викликати LLM, надсилати дельти й перезаписувати
результат. Сам статус захищає від повтору після завершення, але не від перекриття
спроб. Це умовний сценарій відмови, а не твердження, що pg-boss дублює кожен job.

**План:** атомарно захоплювати генерацію через conditional update; зберігати
`attemptId` і строк дії lease. Відновлювати `STREAMING` лише після закінчення lease.
Partial/final writes дозволяти тільки чинній спробі; додати ідентифікатор спроби
до realtime-протоколу, щоб клієнт відкидав застарілі дельти. Узгодити lease,
таймаут провайдера та `expireInSeconds` черги.

**Перевірка:** дві конкурентні доставки; відновлення після падіння; стара спроба
не може перезаписати результат нової або змішати її дельти зі своїми.

## 2. Поточне питання дублюється в prompt

**Ризик: середній; дефект підтверджується кодом.**

**Місце:** `prepare()` у
[subscriber](../apps/worker/src/subscribers/ai-generate-reply.subscriber.ts) та
[buildPrompt](../libs/shared/src/ai/prompt/prompt-builder.ts).

Запит історії з `seq < reply.seq` включає поточне питання на `reply.seq - 1`.
Потім `buildPrompt()` додає його ще раз як `question`. Fake-провайдер цього
не виявляє, оскільки бере останнє user-повідомлення.

**План:** виключити поточне питання з history (`seq < reply.seq - 1`).
Уточнити семантику `historyTurns`: вибирати завершені пари питання/відповідь,
щоб після failed/cancelled відповідей не лишались непарні питання.

**Перевірка:** перше питання присутнє рівно один раз; історія має правильний
порядок і ліміт; failed/cancelled ходи не руйнують склад завершених пар.

## 3. Помилки провайдера не запускають заявлений автоматичний retry

**Ризик: середній; поведінка суперечить коментарю в topology.**

**Місце:** `handle()` і `prepare()` у
[subscriber](../apps/worker/src/subscribers/ai-generate-reply.subscriber.ts),
запис `ai-generator` у [topology](../libs/shared/src/messaging/topology.ts).

Worker ловить помилку провайдера, записує `FAILED` і успішно завершує handler.
Тому `retryLimit: 1` не запускає повтор для цієї помилки. Простого `throw`
після `finalize()` недостатньо: наступна доставка пропустить рядок `FAILED`.

**План:** розрізнити тимчасові та остаточні помилки. Для тимчасової помилки
звільняти спробу в придатний до retry стан і передавати помилку черзі; після
вичерпання спроб записувати `FAILED` та надсилати completion. Узгодити це з
атомарним захопленням із пункту 1 та обробкою остаточно невдалих jobs.
Якщо retry не потрібен продукту, альтернативою є явно задокументувати поточну
поведінку й прибрати обіцянку retry для provider errors.

**Перевірка:** провайдер падає один раз, потім успішний; постійна помилка
закінчується `FAILED`; cancellation не запускає retry.

## 4. Конкурентне створення розмови: fallback усередині зірваної транзакції

**Ризик: середній; потребує перевірки на PostgreSQL.**

**Місце:** `ask()`, `reset()`, `createActive()` у
[AiService](../apps/api/src/ai/ai.service.ts).

Уточнення попереднього рев’ю: конфлікт `seq` сам по собі не означає HTTP 500 —
[AllExceptionsFilter](../libs/shared/src/errors/all-exceptions.filter.ts)
уже перетворює `P2002` на 409.

Окремий ризик є в `createActive()`: після `P2002` метод робить `findActive()`
через той самий `tx`. У PostgreSQL unique violation перериває транзакцію,
тож повторне читання без rollback/savepoint не відновлює її. Це стосується
викликів із `ask()`/`reset()`, коли конкурентно створюється активна розмова.

**План:** обробляти конфлікт поза `withTenantTx` та, де це відповідає семантиці
операції, робити обмежений повтор усієї транзакції. Альтернатива — атомарний
insert із `ON CONFLICT DO NOTHING` і наступне читання. Не додавати дубльоване
глобальне перетворення `P2002`, яке вже існує.

**Перевірка:** конкурентні перші `ask()`/GET і `reset()`; рівно одна ACTIVE
розмова, відсутність 5xx через aborted transaction; конкурентні `ask()` в
наявній розмові не створюють дві пари з однаковим `seq`.

## 5. Stop може загубитися до підписки worker-а

**Ризик: середній для UX; з реальним провайдером — також для витрат.**

**Місце:** `cancel()` у [AiService](../apps/api/src/ai/ai.service.ts),
[AiCancelChannel](../libs/shared/src/ai/ai-cancel.channel.ts), початок `handle()`
у [subscriber](../apps/worker/src/subscribers/ai-generate-reply.subscriber.ts).

API приймає Stop і для `PENDING`, але лише публікує повідомлення в pub/sub.
До старту worker-а або до завершення його підписки слухача ще немає — команда
втрачається навіть за справної мережі. At-most-once доставка свідомо описана
в документації; питання тут у потрібній продуктовій гарантії Stop.

**План:** зберігати намір скасування в БД. Для `PENDING` атомарно переводити
рядок у `CANCELLED`; для активної генерації записувати cancel marker та
надсилати pub/sub для швидкого abort. Після підписки worker повторно перевіряє
marker, а перед фіналізацією враховує його. Для відновлення після втрати pub/sub
потрібна періодична перевірка marker, незалежна від надходження LLM-чанків.

**Перевірка:** Stop до старту job, під час підписки, посеред стріму та після
завершення; окремо — втрата pub/sub і провайдер, який не надсилає чанки.

## 6. Subscriber поєднує забагато відповідальностей для розвитку AI-1

**Ризик: низький зараз; рекомендація щодо підтримуваності.**

**Місце:** [AiGenerateReplySubscriber](../apps/worker/src/subscribers/ai-generate-reply.subscriber.ts).

Один клас керує станами БД, prompt preparation, streaming/coalescing,
таймаутами, cancellation, error mapping і realtime. Для AI-0 це ще керований
обсяг, але додавання реальних провайдерів і retry посилить зв’язність.

**План:** спочатку винести атомарні переходи станів і власність спроби в
`AiMessageStateService`, а накопичення/коалесування чанків — у незалежний helper.
Subscriber залишити координатором. Окремий error mapper додавати, коли з’являться
реальні категорії provider errors; не створювати чотири сервіси наперед.

**Перевірка:** зберегти тести життєвого циклу й окремо перевірити переходи
станів та накопичення чанків, включно з перериванням потоку.

## Порядок робіт

Спочатку виправити дублювання prompt (2). Далі разом спроєктувати власність
спроби та retry (1, 3), виправити транзакційну гонку (4) і гарантію Stop (5).
Рефакторинг (6) виконувати в межах цих змін. Після змін контрактів/realtime
оновити відповідні схеми, згенеровані артефакти та тести за правилами репозиторію.

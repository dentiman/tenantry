# AI: керованість платформи, витрати та якість (AI-5)

Оновлено: 2026-10-04. Статус: **AI-5a реалізовано** (change `ai-5a-platform-ai-settings`), **AI-5b
реалізовано** (change `ai-5b-cost-ledger`, §7), AI-5c запланований.

## 0. Курс

Після AI-2a (FMS-документація в чаті з перевіреними цитатами, гібридний пошук) власник
продукту зафіксував: **функціонал асистента далі не розширюємо**. Керовані джерела (AI-2b),
вкладення й експорт (AI-3) та доменні tools (AI-4) відкладено. Бракує не можливостей, а
керованості й видимості:

1. налаштування моделі, URL і ключа живуть у `.env` і міняються лише редеплоєм;
2. асистента не можна вимкнути ні одному tenant-у, ні платформі без редеплою;
3. скільки коштує відповідь, tenant чи місяць — невідомо: є токени, немає грошей, а токени
   невдалих спроб і embeddings не враховуються взагалі;
4. якість міняється наосліп: eval міряє пошук, але не відповідь і не її ціну.

Цей документ — причини й рішення для трьох кроків, які це закривають.

| Крок                               | Зміст                                                                                | Залежить від                                       |
| ---------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------- |
| **AI-5a — налаштування й вмикачі** | модель, провайдер, URL, ключ (зашифрований) у platform-web; три рівні вмикача        | —                                                  |
| **AI-5b — журнал витрат**          | вартість кожного виклику й відповіді, тарифи, зведення для суперадміна               | AI-5a (модель і провайдер із налаштувань)          |
| **AI-5c — якість**                 | eval відповідей разом із вартістю, перегляд набору питань, вибір моделі й параметрів | AI-5a (зміна без редеплою), AI-5b (ціна відповіді) |

## 1. Рішення власника (2026-10-03)

| Питання                         | Рішення                                                            |
| ------------------------------- | ------------------------------------------------------------------ |
| Де ключ API                     | **В UI суперадміна**, зашифрований у БД; показ/приховування «оком» |
| Модель на tenant                | **Одна модель на всю платформу**                                   |
| Скільки зберігати журнал витрат | **Повністю**, політику видалення визначимо пізніше                 |
| Хто бачить звітність            | **Лише суперадмін**                                                |

модель — env/секрети деплойменту, не UI»: тепер це UI **суперадміна** (не Tenant Admin) і
не per-tenant.

## 2. AI-5a: налаштування й вмикачі

### 2.1. Що переїжджає в UI, а що лишається в env

| У platform-web (суперадмін)                                              | Лишається в env                                                                      | Чому                                                                                    |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| вмикач платформи                                                         | `AI_ENABLED` — жорсткий гейт інсталяції                                              | без нього UI не може ввімкнути асистента, навіть якщо все налаштовано                   |
| провайдер (`fake` / `openai-compat`), **base URL**, **модель**, **ключ** | дефолти для чистої інсталяції                                                        | головне, що треба міняти без редеплою                                                   |
| —                                                                        | `AI_SECRETS_KEY` — майстер-ключ шифрування                                           | ключ, що шифрує ключ, не може лежати поруч із шифротекстом                              |
| —                                                                        | таймаути, оренда, `streamFlushMs`, concurrency черг                                  | внутрішні механізми worker-а, частина рахується на старті                               |
| —                                                                        | модель і ключ embeddings, параметри пошуку, квоти, `maxOutputTokens`, `historyTurns` | embeddings прив'язані до індексу; решта — важелі якості й ціни, переходять в UI в AI-5c |

Пріоритет: значення з БД, якщо воно задане; інакше env. Чиста інсталяція без рядка в БД
працює рівно як до AI-5a.

### 2.2. Зберігання

- `platform_ai_settings` — один рядок налаштувань платформи, без `tenant_id`. Пише лише
  platform-api (`saas_platform`); `saas_app` (tenant api і worker) має **лише SELECT** —
  той самий патерн, що `REVOKE ALL … FROM saas_app` у `platform_users`, але з читанням.
- `platform_ai_settings_events` — append-only журнал змін і розкриттів ключа: хто, коли,
  які поля (без значення ключа). `saas_app` доступу не має.

### 2.3. Ключ API: шифрування й «око»

- AES-256-GCM, майстер-ключ `AI_SECRETS_KEY` (32 байти, base64) — лише в env **worker-а й
  platform-api**. Tenant api цього ключа не отримує: він читає рядок, але розшифрувати не
  може й не має потреби — модель він не викликає.
- У БД — версія схеми шифрування, IV, тег і шифротекст. Бекап БД без env ключа не
  розкриває.
- Звичайне читання налаштувань повертає лише маску (`sk-or-…a1b2`) і ознаку «ключ задано».
- «Око» — окремий ендпоінт розкриття: лише суперадмін, кожне розкриття — подія в журналі.
- Ключ ніколи не потрапляє в логи й тексти помилок. Без `AI_SECRETS_KEY` зберегти ключ не
  можна (зрозуміла помилка), а налаштування без ключа (наприклад, `fake`) — можна.
- Ротація майстер-ключа — перешифрування; окрема операційна процедура, не частина AI-5a.

### 2.4. Застосування без перезапуску

Worker і tenant api читають налаштування через спільний сервіс із коротким кешем (секунди).
Зміна в UI набирає чинності на наступній генерації без перезапуску. Провайдер будується
заново лише коли змінилися провайдер, URL або ключ.

### 2.5. Три рівні вмикача

| Рівень          | Хто          | Де                               | Дефолт                                          |
| --------------- | ------------ | -------------------------------- | ----------------------------------------------- |
| Платформа       | суперадмін   | platform-web → AI → налаштування | увімкнено (чинний стан інсталяції зберігається) |
| Дозвіл tenant-у | суперадмін   | platform-web → картка tenant     | дозволено                                       |
| Вибір tenant-а  | Tenant Admin | `/settings/ai`                   | увімкнено                                       |

Ефективний стан = `AI_ENABLED` **і** платформа **і** дозвіл tenant-у **і** вибір tenant-а.

- Дозвіл tenant-у — окрема таблиця, яку пише лише platform-api; `saas_app` читає лише рядок
  свого tenant-а (RLS). Не секція `tenants.settings`: її пише сам tenant.
- Вимкнено — панель зникає (`settingsBootstrap.features.ai`), AI-ендпоінти відповідають 403,
  а worker закриває вже поставлену в чергу відповідь як скасовану, не викликаючи модель.
- Tenant Admin бачить, якщо платформа не дозволила, і не може ввімкнути сам.

## 3. AI-5b: журнал витрат і тарифи

### 3.1. Дві вартості

|          | Фактична                               | Розрахункова                                          |
| -------- | -------------------------------------- | ----------------------------------------------------- |
| Що       | скільки списав провайдер за виклик     | токени × наш тариф                                    |
| Звідки   | відповідь провайдера, у момент виклику | таблиця тарифів                                       |
| Є завжди | ні — лише якщо провайдер її повертає   | так, якщо для моделі є тариф                          |
| Для чого | звірка з рахунком                      | провайдери без вартості, прогнози, порівняння моделей |

Обидві пишуться в журнал. OpenRouter повертає вартість **завжди**, без параметрів:
`usage.cost` в останньому SSE-повідомленні чату і в відповіді embeddings, плюс
`cost_details.upstream_inference_cost`, `prompt_tokens_details.cached_tokens` /
`cache_write_tokens`, `completion_tokens_details.reasoning_tokens`
([usage accounting](https://openrouter.ai/docs/use-cases/usage-accounting),
[embeddings](https://openrouter.ai/docs/api/api-reference/embeddings/create-embeddings)).
Окремо питати ціну на кожен запит не треба. Скасована, обірвана чи невдала генерація
останнього повідомлення з `usage` не отримує — для неї фоновий добір через
`GET /api/v1/generation?id=gen-…` (`total_cost`, нативні токени, `cache_discount`;
[generation](https://openrouter.ai/docs/api/api-reference/generations/get-generation)).

### 3.2. Журнал (ledger)

Append-only, один рядок на платний виклик провайдера: tenant, користувач, id відповіді чи
джерела (без FK), тип (`generation`, `query_embedding`, `ingest_embedding`, `eval`; кожна
спроба відповіді — `generation` з номером `attempt` і результатом `outcome`, окремого
`generation_retry` немає — §7), провайдер, модель **як її назвав провайдер**, токени (input,
cached read, cache write, output, reasoning), фактична вартість і id запиту провайдера,
розрахункова вартість і id рядка тарифу (заморожені в момент запису), час. Без тексту.
Гроші — `NUMERIC`, не float.

- Переживає retention розмов і «видалити мої розмови» — це фінансова історія.
- Вартість відповіді = сума рядків з її id: усі спроби, зокрема невдалі (зараз губляться),
  плюс embedding питання.
- Щоденні агрегати (tenant × модель × тип × день) — cron, щоб дашборди не сканували журнал.

### 3.3. Тарифи

Платформна таблиця: провайдер + модель → ціни за 1M токенів (input, cached read, cache
write, output) і за запит, **дата початку дії**, джерело (`openrouter-sync` / `manual`).
Зміна ціни — новий рядок, історія не переписується.

- OpenRouter: синхронізація раз на добу й кнопкою з двох публічних списків без ключа —
  `GET /api/v1/models` (чат-моделі; embeddings там **немає**) і `GET /api/v1/embeddings/models`
  (ціни embeddings, напр. `text-embedding-3-small` — $0.02/1M). Поля `pricing.prompt`,
  `completion`, `input_cache_read`, `input_cache_write` (USD за токен, рядками; `request` зараз
  не має жодна модель). Новий рядок лише коли ціна змінилася. Не на кожен запит.
- Ступінчасті ціни (`pricing.overrides`, напр. у `gpt-5.6-luna` усе ×2 від 272k токенів
  промпту) зберігаються в рядку тарифу й застосовуються в розрахунку — інакше звірка
  «фактична проти розрахункової» дає хибні розбіжності на довгих промптах.
- Інші провайдери: ціни вручну в UI. Модель без тарифу не можна активувати.

Формула:
`(input − cached_read − cache_write) × input + cached_read × cache_read + cache_write ×
cache_write + output × output + за_запит` (reasoning уже в output).

### 3.4. Зміна провайдера

Кожен рядок журналу знає провайдера, модель і тариф — історія лишається правильною, звіт
за місяць зі зміною моделі розкладається по обох. Провайдер без вартості у відповіді — лише
розрахункова вартість за обов'язковим тарифом. Різні назви полів токенів (OpenAI
`prompt_tokens_details.cached_tokens`, DeepSeek `prompt_cache_hit_tokens`) вирівнює адаптер
провайдера. Зміна провайдера embeddings — те саме; зміна моделі embeddings — переіндексація,
не перемикач. Щомісяця: сума фактичних проти рахунку провайдера, розрахункових проти
фактичних (застарілий тариф).

### 3.5. Звітність суперадміна

Витрати по періоду, по tenant, по моделі, по типу виклику; середня вартість відповіді й
тренд; гроші на невдалі й скасовані відповіді; економія кешу; звірка з рахунком провайдера;
хто впирається в квоту. Читання крос-tenant — лише platform-api через `SystemPrismaService`.

## 4. AI-5c: якість (план)

Цикл «виміряти → змінити налаштування → виміряти». Перегляд `docs/ai-sources/fms-eval.json`
власником; eval **відповідей** (правильні цитати, відсутність вигаданих номерів, відмова без
підстав, мова відповіді) поруч із **середньою вартістю відповіді** для кожної конфігурації
(модель, кількість фрагментів, історія 4/10, вихід 768/1024); переможець застосовується через
UI, ефект підтверджує журнал витрат. Параметри якості переходять з env в UI суперадміна.

## 5. AI-5a: як реалізовано

- **Дані:** міграція `20261004150000_ai_platform_settings` — `platform_ai_settings` (один рядок,
  CHECK `id = 'default'`, ключ і підказка лише парою), `platform_ai_settings_events`,
  `tenant_ai_access` (RLS `FOR SELECT` на свій рядок). Привілеї: `saas_app` — SELECT на
  налаштування й дозвіл, нічого на журнал.
- **Знахідка під час реалізації (виправлено):** `db:roles` (`ensure-roles.ts`) при кожному запуску
  видавав `saas_app` DML на **всі** таблиці й так скасовував `REVOKE` міграцій — зокрема
  `platform_users` і `platform_auth_sessions` з MT-3, щойно ролі переналаштовували після міграцій
  (e2e global setup, `ws:init`, `db_roles` після деплою). Тепер скрипт після широкого GRANT
  заново застосовує обмеження зі списку `CONTROL_PLANE_TABLES`; e2e перевіряє, що `saas_app`
  не читає операторів, сесій операторів і журналу AI.
- **Шифрування:** `libs/shared/src/ai/platform/secret-box.ts` — AES-256-GCM, AAD колонки,
  формат `v1:iv:tag:ct`; невалідний `AI_SECRETS_KEY` валить старт worker-а й platform-api.
- **Runtime:** `PlatformAiSettingsReader` (кеш 5 с) + `resolveGenerationSettings()` (UI поверх env).
  Worker отримує провайдер і модель через `AI_RUNTIME` на кожну генерацію; провайдер
  перебудовується лише при зміні провайдера/URL/ключа (відбиток — хеш). Відсутній у env ключ
  більше не валить старт: генерація з неробочими налаштуваннями — `FAILED / PROVIDER_UNAVAILABLE`.
  Embeddings без окремої пари `AI_EMBEDDING_*` беруть URL і ключ генерації з того самого злиття.
- **Доступність:** `AiAvailabilityService.forCurrentTenant()` — чотири рівні; вимагає tenant-контекст
  (без нього кидає, а не відкриває доступ). Tenant api: 403 на всіх AI-роутах, `features.ai`,
  блок `availability` у `GET/PUT /settings/ai`. Worker: недоступно → `CANCELLED` до `claim()`,
  без виклику моделі, з `ai.message-completed` для відкритої панелі.
- **Control plane:** `GET/PUT /ai/settings`, `POST /ai/settings/api-key/reveal` (подія
  `key_revealed`), `GET /ai/settings/events`; `aiAllowed` у відповіді й PATCH tenant-а.
  Збереження `openai-compat` без URL, моделі чи ключа ні в UI, ні в env — 400 з `fieldErrors`.
- **UI:** platform-web — area «AI» → «Settings» (форма з підказкою «що діє зараз і звідки», ключ
  з «оком», журнал змін), перемикач дозволу в картці tenant-а; tenant web — вмикач у
  `/settings/ai` (неактивний із поясненням, коли платформа не дозволяє).

## 6. AI-5b: стартовий пакет (історичний — що було на старті)

Підготовлено 2026-10-04 після коміту AI-5a (`6d17978`). OpenSpec change —
`openspec/changes/ai-5b-cost-ledger/`; рішення D1–D6 і відкриті питання власник підтвердив
2026-10-04: агрегати лише за потреби, CLI ingest і eval пишуться в журнал під своїм tenant-ом,
вартість відповіді — лише в журналі (без колонки в `ai_messages`), валюта — USD. Рішення власника для AI-5b вже є в §1: журнал
зберігаємо повністю, звітність лише суперадміну, одна модель на платформу. Модель витрат і
джерела цін — §3.

### 6.1. Що є в коді зараз (точки входу)

### 6.2. Порядок робіт (пропозиція)

1. **Usage від провайдера.** Розширити `LlmUsage` / `EmbeddingBatch`: `reportedCost`,
   `providerRequestId`, `cacheWriteTokens`, `reasoningTokens`, модель відповіді. Юніт-тести на
   кадр OpenRouter із `cost` і на бекенд без нього.
2. **Тарифи.** Платформна таблиця тарифів з історією (§3.3) + чиста функція розрахункової
   вартості (`Prisma.Decimal`, не float). Юніт-тести формули з кешем.
3. **Журнал.** Таблиця подій витрат під RLS, append-only для `saas_app`; запис у тих самих
   транзакціях, що вже є: `finalize()` (усі спроби відповіді), `claim()`/`finalize()` (embedding
   питання), `write()` ingest-у. Шлях «власність утрачено» пише свої спроби окремо.
4. **Добір фактичної вартості.** System-scope cron: рядки `pending` з `gen-…` id →
   `GET /api/v1/generation?id=` (ключ — з налаштувань платформи, worker розшифровує);
   кілька спроб, далі `unknown` з розрахунковою вартістю.
5. **Синхронізація цін.** Cron раз на добу + кнопка: `GET /api/v1/models` і
   `GET /api/v1/embeddings/models` → новий рядок тарифу лише при зміні (перевірено 2026-10-04,
   §3.3).
6. **Звітність.** platform-api: зведення за період у розрізах tenant / модель / тип / день,
   середня вартість відповіді, витрати на невдалі відповіді, економія кешу, фактичне проти
   розрахункового. platform-web: сторінки `Costs` і `Prices` в area «AI».
7. **Активація моделі без тарифу.** Збереження налаштувань AI-5a з моделлю провайдера, який не
   повертає вартість, без тарифу → 400 на полі `model` (§3.3).

### 6.3. Перевірка

- Юніт: парсинг usage OpenRouter, формула з кешем і точністю, рядки на кожну спробу (успіх,
  ретрай, Stop, втрата власності), embedding питання з id відповіді.
- E2E: RLS журналу (tenant B не бачить A), `saas_app` не може UPDATE/DELETE журналу, вибір
  тарифу за датою, зведення platform-api, журнал переживає «видалити мої розмови» і retention.
- Живий прогін: питання через OpenRouter → сума фактичних вартостей у журналі збігається з
  записом у кабінеті OpenRouter (Activity) для того самого `gen-…`.

### 6.4. Підводні камені, виявлені в попередніх кроках

- **Prettier — лише на змінені файли.** Репозиторій не prettier-чистий: масовий запуск на
  теку переформатовує десятки чужих файлів (так було в AI-5a — довелося відкочувати).
- **Нова таблиця control plane → `CONTROL_PLANE_TABLES`** в `ensure-roles.ts` (тип треба буде
  розширити режимом «select + insert» для журналу, якщо його пише `saas_app`).
- **Міграція не може `UPDATE` tenant-рядки** (FORCE RLS діє й на власника) — backfill лише через
  `ADD COLUMN … DEFAULT` або STORED generated (CLAUDE.md правило 17).
- **Жодного виклику провайдера всередині транзакції** — і запиту `generation?id=` теж
  (правило 18).
- **Кеш налаштувань платформи 5 с** — у тестах `PlatformAiSettingsReader.invalidate()`.
- **Повний `pnpm api:test:e2e` не паралельно з живим dev-стеком**; цільові сьюти — так.
- **Локальне середовище:** `.env` має `AI_SECRETS_KEY` і робочий ключ OpenRouter;
  `AI_KNOWLEDGE_BACKEND=postgres`, FMS проіндексовано в tenant `default`; seed-входи
  `admin@example.com` / `Admin1234567`, `platform@example.com` / `Platform12345`.
- **Процес власника:** відповіді українською; дизайн-рішення — з варіантами й рекомендацією
  перед реалізацією; коміт лише на прохання.

## 7. AI-5b: як реалізовано

Change `ai-5b-cost-ledger`; рішення R1–R10 — у його `design.md`, тут те, що лишається правдою.

### 7.1. Дані

- **Міграція `20261004160000_ai_cost_ledger`:** `ai_model_prices` (control plane), `ai_usage_events`
  (tenant-scoped, RLS `tenant_isolation`), колонка `ai_messages.provider_request_id`. Закриті
  словники — CHECK-и: `kind` (`generation` | `query_embedding` | `ingest_embedding` | `eval`),
  `outcome` (`complete` | `failed` | `cancelled` | `timeout` | `retried` | `superseded` |
  `abandoned`), `cost_status` (`reported` | `estimated` | `pending` | `unknown`), `source`
  тарифу (`openrouter-sync` | `manual`), валюта лише `USD`. Гроші — `NUMERIC(18,10)`.
- **Привілеї.** `saas_app` — SELECT тарифів; SELECT + INSERT журналу (append-only: ні UPDATE,
  ні DELETE навіть у своєму tenant-і). UPDATE журналу робить лише добір під `saas_platform`.
  `ensure-roles.ts` отримав режим `select-insert` у `CONTROL_PLANE_TABLES`; e2e повторно запускає
  `db:roles` і перевіряє, що обмеження вціліло.
- **Без FK на users, розмови й повідомлення** — журнал переживає «видалити мої розмови» і
  ретенцію (e2e). FK на `tenants` з `ON DELETE CASCADE`, як у всіх tenant-таблиць: маршруту
  видалення tenant-а немає, але **майбутнє видалення tenant-а (MT-4) мусить вирішити долю
  журналу (експорт чи архів)** — каскад тихо зітре фінансову історію.
- **Тарифи без `valid_to`.** Тариф на момент T — останній рядок з `valid_from ≤ T`; унікальність
  `(provider, model, valid_from)`; таблиця повністю append-only. Ступені (`pricing.overrides`) —
  JSON `tiers`, ціни за 1M десятковими рядками.

### 7.2. Звідки береться вартість

- **Білінговий ключ провайдера** (`costs/billing.ts`): `fake`, `openrouter` (хост
  `openrouter.ai`) або хост base URL (`api.deepseek.com`). Ним позначені і рядок журналу, і тариф.
- **Чат.** `OpenAiCompatProvider` віддає id запиту (`gen-…`) **першим** порожнім кадром — ще до
  тексту, тож id мають і Stop, і таймаут, і обрив. Usage-кадр читається захищено (тип SDK не
  знає `cost`): `usage.cost`, `prompt_tokens_details.cache_write_tokens`,
  `completion_tokens_details.reasoning_tokens`. `FakeLlmProvider` повідомляє `cost: 0` — він
  безкоштовний, і CI проходить увесь шлях без мережі.
- **Embeddings.** `OpenAiEmbeddingProvider` повертає `billing` — провайдер, модель у назві
  провайдера (`openai/text-embedding-3-small`), `usage.cost`, `id`.
- **Гроші з JSON** → десятковий рядок на межі парсингу (`costs/money.ts`, `String(n)` без
  експоненти), далі лише `Prisma.Decimal`. На дроті platform-api — теж десяткові рядки; UI
  форматує їх `Intl.NumberFormat` зі строковим входом (ES2023), без float.
- **Статус вартості:** є `cost` → `reported`; OpenRouter без `cost`, але з id → `pending`; токени
  без вартості в провайдера, що її не повертає → `estimated`; нічого → `unknown`.
- **Розрахункова вартість** (`costs/tariff.ts`) рахується завжди, коли є тариф, і заморожується
  в рядку разом з `price_id`; `NULL`, коли тарифу чи токенів немає — ніколи не 0. Тариф шукається
  за моделлю, яку назвав провайдер, а потім за запитаною (роутер може назвати інакше).

### 7.3. Де пишуться рядки

Провайдер ніколи не викликається всередині транзакції; рядок пишеться в ту транзакцію, що вже є:

| Що | Де |
| --- | --- |
| спроба, що пішла на ретрай | транзакція `restart()` (`retried`; програний фенсинг — `superseded`) |
| остання спроба | транзакція `finalize()` (`complete` / `failed` / `cancelled` / `timeout`; програний фенсинг — `superseded`) |
| втрата власності посеред стріму | власна коротка транзакція (`superseded`) |
| embedding питання | транзакція `claim()` — **і коли `claim()` програв**: гроші вже витрачено, транзакція комітиться |
| спроба впалого воркера | транзакція `claim()` наступної доставки: `abandoned`, `pending` за збереженим `provider_request_id` |
| ingest / eval / search CLI | `RecordingEmbeddingProvider` — після кожного успішного HTTP-батча, власна tenant-транзакція |

- **Падіння воркера.** Id запиту пишеться в `ai_messages.provider_request_id` разом із частковим
  текстом — одразу, щойно відомий (а не лише раз на `AI_PARTIAL_PERSIST_MS`). Відома межа, свідомо
  не лікована: якщо API закриє покинуту відповідь на читанні раніше за редоставку job-а, рядка
  для мертвої спроби не буде.
- **CLI** працюють під `saas_app` у tenant-і, переданому `--tenant` (`withKnowledgeTenant`):
  ingest — `ingest_embedding`, `source_id = product/sourceKey`; eval і search — `eval`, `source_id` —
  назва команди. Eval пише лише справжні (не кешовані) виклики. Runtime воркера декоратор **не**
  використовує — інакше embedding питання рахувався б двічі; це стереже юніт-тест (фабрика джерела
  знань і структурна перевірка `apps/worker`/`apps/api`).
- **Квоти не змінились:** `ai-usage-quota.service.ts` лишився токенним і списує лише usage спроби,
  що завершилась; журнал — окремий фінансовий облік.

### 7.4. Добір і синхронізація цін

- **Добір** — cron `ai.reconcile-usage-costs` (`*/5 * * * *`, system scope): до 100 рядків
  `pending` з `reconcile_after ≤ now`, перша спроба — через хвилину після виклику (OpenRouter
  публікує запис генерації не миттєво). `GET /api/v1/generation?id=` поза транзакцією, ключ — з
  налаштувань платформи (розшифровує воркер). Невдача — пауза 5 / 15 / 60 хв / 6 год, після 5-ї
  спроби — `unknown` з розрахунковою вартістю. Успіх — `total_cost`, нативні токени, оцінка за
  тарифом на `occurred_at`, **лише якщо її ще не було**. Модель рядка не перезаписується: запис
  генерації називає її з датою (`openai/gpt-5.6-luna-20260709`), і звіт «за моделлю»
  розщепився б. Без OpenRouter у налаштуваннях спроби все одно витрачаються — рядки не висять.
- **Синхронізація цін** — одна функція (`costs/openrouter-prices.ts`) для cron-а
  `ai.sync-model-prices` (`15 4 * * *`) і кнопки «Sync with OpenRouter» (`POST /ai/prices/sync`,
  синхронно). Обидва публічні списки з таймаутом 15 с; збій одного не скасовує інший (кнопка
  показує, що саме не вдалося). Моделі з ціною `-1` (роутери на кшталт `openrouter/auto`)
  пропускаються. Новий рядок — лише коли ціна чи ступені змінились порівняно з **останнім рядком
  моделі будь-якого джерела**: ручна ціна на модель OpenRouter витісняється наступною
  синхронізацією, якщо відрізняється (UI каже це підказкою).
- **Активація моделі:** збереження налаштувань з провайдером, що не повертає вартість (не
  OpenRouter і не `fake`), без тарифу на (хост, модель) — `400` з `fieldErrors[model]`, код
  `model_price_missing`.

### 7.5. Звітність

- **platform-api:** `GET /ai/costs/summary?from&to` і `GET /ai/costs/breakdown?from&to&by=tenant|
  model|kind|day` — на льоту з журналу (`SystemPrismaService`), період напіввідкритий `[from, to)`,
  не довший за 366 днів. «Відповідь» = усі рядки з її `message_id` (спроби + embedding питання);
  її результат — `outcome` останньої спроби. Невдалі відповіді — сума відповідей, чия остання
  спроба не `complete`; окремо — гроші на спроби `retried`/`superseded`/`abandoned`. Економія кешу
  рахується за **базовими** цінами замороженого тарифу (ступені не враховано — наближення).
  Денних агрегатів немає (рішення власника: лише коли виміряно стане повільно).
- **Тарифи:** `GET /ai/prices` (чинна ціна кожної пари з пошуком), `GET /ai/prices/history`,
  `POST /ai/prices` (ручний), `POST /ai/prices/sync`.
- **platform-web**, area «AI»: **Costs** — період (цей / минулий місяць, 30 і 7 днів, UTC) в URL,
  шість KPI, розріз у картці з таблицею (рядків одиниці — без DataGrid); **Prices** — DataGrid
  чинних цін, історія моделі в контекстній панелі, діалог ручної ціни, кнопка синхронізації.
- **Поза AI-5b:** «хто впирається в квоту» з §3.5 — відкладено; tenant-контракти не змінювались.

### 7.6. Перевірка

- Юніт: парсинг usage (кадр із `cost` і без), формула з кешем і ступенями, статус вартості,
  рядок на кожну спробу (успіх, ретрай, вичерпані ретраї, Stop, таймаут, втрата власності,
  перезахоплення), embedding питання з id відповіді й при програному `claim()`, декоратор CLI,
  синхронізація цін, добір.
- E2E: RLS журналу (B не бачить A і не пише від його імені), `saas_app` без UPDATE/DELETE після
  повторного `db:roles`, тариф за датою й заморожена оцінка, журнал після «видалити мої розмови» й
  ретенції, підсумки й розрізи platform-api, ручний тариф, перевірка активації, синхронізація.
- **Живий прогін 2026-10-04 (слот 1, OpenRouter, `openai/gpt-5.6-luna`):** відповідь —
  214/18 токенів, журнал `0.0000644`, embedding питання — 12 токенів, `0.00000024`; ті самі суми
  (і нативні токени) повертає `GET /api/v1/generation?id=` для тих самих `gen-…`. Розрахункова
  вартість за синхронізованим тарифом збіглась із фактичною до останнього знака. Рядок `pending`
  з реальним `gen-…` cron добору перевів у `reported` з тими самими сумою й токенами. Stop
  живцем не відтворився: асистент відповідав коротше, ніж встигав Stop (шлях покритий юніт-тестом).

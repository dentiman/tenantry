# Ліниве завантаження: маршрути, великі компоненти, бюджет

> Рішення від 2026-11-11 (архітектурне рев'ю → цей документ). Стосується обох фронтендів
> (`apps/web`, `apps/platform-web`); механізм — один, у `libs/ui`.

## 1. Проблема і результат

До рішення `router.tsx` статично імпортував усі `*.routes.tsx`, а ті — усі сторінки: login,
`/about`, календар, чат, AI-панель з markdown, playground, усі налаштування лежали в **одному**
JS (web — 2 028 КБ raw / 600 КБ gzip). Захист від цього був лише ESLint-правилом для `*.nav.ts`.

| Вимір (production-збірка)             | До             | Після          |
| ------------------------------------- | -------------- | -------------- |
| web: JS, потрібний до першого рендера | 2 028 / 600 КБ | 1 152 / 359 КБ |
| platform-web: те саме                 | 1 246 / 384 КБ | 964 / 303 КБ   |
| web: JS-чанків                        | 1              | 142            |
| platform-web: JS-чанків               | 1              | 42             |

(raw / gzip. Далі `pnpm bundle:check --report` дає актуальні цифри.)

Що залишилось у старті й чому — §3. Залишок web — переважно спільні бібліотеки (react-dom,
`@base-ui/react`, zod, axios, router), а не код фіч: код фіч у старті — ≈70 КБ raw.

## 2. Соглашення (коротко)

1. **Сторінка = окремий чанк.** Маршрут оголошує компонент через `lazyPage`, а не статичний імпорт:

   ```tsx
   // features/chat/chat.routes.tsx
   import { lazyPage } from '@saas-skeleton/ui/lib/lazy';
   const ChatPage = lazyPage(() => import('./pages/chat'), 'ChatPage'); // іменований експорт
   export const chatIndexRoute = createRoute({
     getParentRoute: () => chatRoute,
     path: '/',
     component: ChatPage,
   });
   ```

   Файл маршрутів лишає у стартовому чанку лише те, що потрібно для МАТЧІНГУ: `createRoute`,
   `validateSearch`/схеми, `beforeLoad`, `staticData`. Це легке, і воно має бути доступне до
   того, як роутер вирішить, який чанк вантажити.

2. **Виняток один — сторінка входу** (`LoginPage`): перший екран кожного неавторизованого візиту,
   окремий чанк додав би RTT перед першим пейнтом. Статичний імпорт там позначений
   `eslint-disable-next-line no-restricted-imports` з причиною. `reset-password*`, `confirm-email`
   — ледачі: на них приходять із листа, один скелет не страшний.
3. **Важкий компонент усередині сторінки, внесок слота, панель area — `lazyComponent`**
   (`React.lazy` по іменованому експорту) під `LazyBoundary` (`Suspense` + перехоплення помилки):

   ```tsx
   const AiPanel = lazyComponent(() => import('./ai-panel'), 'AiPanel');
   <LazyBoundary fallback={<PanelPending />}>
     <AiPanel />
   </LazyBoundary>;
   ```

   Коли ліниво тягти компонент, а не маршрут: він (а) помітно важкий (≳ 30 КБ gzip або тягне
   важку залежність — markdown, редактор, графік, PDF, календар-сітка, підсвітка коду) **і**
   (б) потрібен не завжди (панель закрита, вкладка неактивна, діалог не відкрито). Якщо він
   потрібен будь-якій відкритій сторінці — він і так у чанку сторінки, окремий нічого не дасть.

4. **Composition roots не імпортують сторінок статично**: `router.tsx`, `main.tsx`,
   `slot-fills.ts`, `*.routes.tsx` (ESLint, `no-restricted-imports` на `**/pages/**`) і `*.nav.ts`
   (старе правило: ні `pages/`, ні `components/`). Динамічний `import()` правило не чіпає, тому
   `lazyPage`/`lazyComponent` у цих файлах — штатний шлях.
5. **Внески в слоти ледачі за замовчуванням** (`slot-fills.ts`: `fillSlot(slot, id, lazyComponent(…))`);
   `SlotOutlet` обгортає кожен внесок у `LazyBoundary`, тож чанк, що ще вантажиться (або не
   завантажився), не ламає сторінку-хост. **Друга колонка area** (`panel` у `*.nav.ts`) — так само
   `lazyComponent(() => import('./<модуль>-sidebar'), …)`; `AreaSidebar` обгортає її в `LazyBoundary`.

Імена. Чанк сторінки зветься `route-<модуль>-<сторінка>-<хеш>.js` (`libs/ui/src/build/chunking.ts`
→ `chunkFileNames`), решта — за іменем, яке дає Rollup. Це лише для читабельності аналізу
бандла; поведінку імена не міняють.

## 3. Що лишається в стартовому чанку, а що йде в чанки

Старт (потрібен будь-якому візиту): react/react-dom, роутер, query, i18n (усі ресурси —
англійська, ≈ 85 КБ raw), axios, socket-клієнт, zod, форми (react-hook-form — потрібен логіну),
`@base-ui/react`, реєстр навігації (`nav.ts` — лише метадані й іконки), слот-реєстр, гейт
`requireAuth` / `staticData.access`, `init*Sync` сокет-мости (`main.tsx`), сторінка входу.

У чанках: **шел** (`AppShell` — `lazyPage` у `app.routes.tsx`: гість на `/login` його не качає, а
залогінений тягне паралельно зі сторінкою — роутер вантажить чанки всіх збігів разом), усі сторінки
решти модулів, внески слотів, панелі area, AI-панель (markdown — окремий чанк ≈ 160 КБ raw, потрібен
лише відкритому асистенту), календар-пікер (`react-day-picker`) разом із календарем.

Dashboard — ледачий: це сторінка-контейнер віджетів (самі віджети теж ледачі), окремий чанк
коштує те саме, що чанк будь-якої іншої сторінки, а залогінений візит і так вантажить чанк
шела паралельно. Межа проходить по модулях `modules.config.ts`: composition root і `app-shell/`
(рівень shell) — старт; `features/<модуль>/pages|components` — чанки.

## 4. Збірка: чанки й кеш

`libs/ui/src/build/chunking.ts` (підключений у `vite.config.ts` обох апок відносним імпортом):

- `manualChunks` — лише **стабільні** вендор-групи, які старт тягне в будь-якому разі: `vendor-react`,
  `vendor-tanstack`, `vendor-i18n`, `vendor-net` (axios + socket.io), `vendor-forms` (zod + RHF).
  Код застосунку змінюється щодеплою, ці файли — лише при оновленні залежностей, тож браузер
  тримає їх у кеші. **Не додавати** сюди бібліотеки, потрібні лише ледачим чанкам (markdown,
  day-picker): ручна група вантажиться цілком разом з будь-яким її імпортером і затягла б їх у старт.
  `@base-ui/react` теж свідомо не групуємо — з ним було б так само.
- Свідомо **не** ставимо `experimentalMinChunkSize`: Rollup тоді зливав дрібні сторінки (1–3 КБ)
  у entry, і «кожна сторінка — окремий чанк» переставало бути інваріантом. Ціна — більше
  дрібних файлів (`142` чанки, більшість по 0,1–3 КБ), і HTTP/2 це переносить.

## 5. Захист від деградації

- `pnpm lint` (ESLint): статичний імпорт сторінки в `*.routes.tsx`/`router.tsx`/`main.tsx`/`slot-fills.ts`
  — помилка. Це перший і найдешевший бар'єр.
- `pnpm bundle:check` (`scripts/bundle-check.ts`): збирає обидва фронти у тимчасову теку
  (`--manifest --sourcemap`, ≈ 15 с), рахує gzip усього JS стартового набору (entry + транзитивні
  статичні імпорти) і порівнює з `BUDGETS` у скрипті (web 400 КБ, platform-web 335 КБ ≈ виміряне +10%).
  Додатково дивиться в sourcemap стартових чанків: сторінки модулів там бути не мають (`eagerPages`
  — виняток, зараз лише login). `--report` показує найбільші чанки. Це страховка за фактичним
  результатом збірки на випадок, що ESLint обійдено (`export *`, транзитивний імпорт з eager-файла,
  важка залежність у спільному коді).
- Бюджет піднімається свідомо: окремий рядок у `BUDGETS` + пояснення в коміті. Скрипт не входить
  у `ci-verify.sh` (там немає `vite build` і git-історії для `build-info`) — запускати перед
  релізом і після змін у composition roots/залежностях.

## 6. Pending, помилки, preload

Налаштовано один раз у `createRouter` обох апок (`router.tsx`), на роутах нічого не оголошується:

| Налаштування                               | Значення       | Навіщо                                                                                                                                                                                      |
| ------------------------------------------ | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `defaultPreload`                           | `'intent'`     | чанк (і loader) стартує на hover/focus/touchstart посилання — до кліку                                                                                                                      |
| `defaultPendingMs` / `defaultPendingMinMs` | 300 / 300 мс   | скелет з'являється лише для переходу довшого за 300 мс і тоді висить не менше 300 мс: швидкі переходи не мигають, повільні не схожі на зависання. До того стара сторінка лишається на місці |
| `defaultPendingComponent`                  | `RoutePending` | скелет області контенту; прозорий, тож скляний шел `/guide` (`staticData.backdrop`) не ламається; рендериться в outlet батька — рейл і колонка area на місці                                |
| `defaultErrorComponent`                    | `RouteError`   | помилка рендера/loader-а: «Try again» (`reset` + `router.invalidate()`); провал чанка: «Reload page»                                                                                        |

Усі тексти — `common:routeError.*` / `common:loading` (`libs/i18n`); компоненти — на примітивах
`libs/ui` (`Empty`, `Skeleton`, `Button`), `libs/ui/src/components/route-fallbacks.tsx`.

**Застарілий деплой.** Після нового релізу старих чанків на сервері вже немає, а відкрита вкладка
про них пам'ятає. `lazyRouteComponent` (з `lazyPage`) і `lazyComponent` ловлять провал `import()`
(«Failed to fetch dynamically imported module» та аналоги — `isChunkLoadError`) і **один раз**
перезавантажують сторінку (захист у `sessionStorage` за повідомленням — воно містить хеш чанка,
тож справжній обрив мережі не зациклює reload). Якщо й після reload чанка немає, `RouteError`
показує «Reload page». Повторювати сам `import()` не вдається: браузер кешує невдачу. Перевірено
руками: прибраний чанк `/guide` → reload один раз → екран помилки всередині скляного шела.

**Помилки і Sentry.** Усе, що UI-шар перехоплює сам, іде не в `console.error`, а в єдину точку
`reportError({ error, source, context })` (`libs/ui/src/lib/report-error.ts`): помилки меж роутів
(`defaultOnCatch` у `createRouter` — у production роутер сам їх не логує) і всі перехоплення
`LazyBoundary` (внески слотів, колонки area, ледачі панелі; `context.name` — хто саме,
`context.isChunkLoadError` — провал чанка, його варто фільтрувати від справжніх багів).
`LazyBoundary` свідомо не показує екран помилки (віджет не має класти дашборд), тому тихою вона бути
не може — звіт іде завжди.

Підключення збирача — **одне місце на фронтенд**: `apps/<апка>/src/lib/error-reporting.ts`
(`initErrorReporting()` у `main.tsx` до першого рендера; зараз — консоль із позначкою апки). Коли
зʼявиться Sentry, міняється лише цей файл (`Sentry.init` + `setErrorReporter(({ error, source,
context }) => Sentry.captureException(...))`, приклад — у коментарі файла); компоненти й роути
не чіпаються. Окремо при впровадженні: глобальні `window.onerror`/`unhandledrejection` (ставить сам
`Sentry.init`) і помилки API (`handleGlobalError` у `main.tsx`; 5xx вже логує бекенд за `requestId`).

**Дані.** Loader-ів у проєкті немає (сторінки тягнуть дані через TanStack Query у компонентах), тож
паралелізм «чанк ‖ дані» тут поки не діє. Якщо з'явиться маршрут із `loader`, його
`queryClient.ensureQueryData(...)` піде паралельно з чанком автоматично (роутер вантажить обоє).

## 7. Що розглядалося й чому не так

- **`autoCodeSplitting` (`@tanstack/router-plugin`)** — працює лише для file-based маршрутів
  (`createFileRoute`, каталог `routes/`, генерований `routeTree`). Наші маршрути code-based, і
  власник маршруту — модуль (docs/modules.md §7.4); переходити на файлові заради цього — зміна
  архітектури, а не оптимізація. Нова залежність не потрібна.
- **`route.lazy()` / `createLazyRoute`** — виносить `component`/`pendingComponent`/`errorComponent`
  в окремий файл `*.lazy.tsx`. Дало б ледачі pending/error самого маршруту, але вимагає друге
  оголошення маршруту на кожну сторінку; наш pending/error — спільні й малі, тож виграшу немає.
  `lazyRouteComponent` — один рядок, типізований за іменованим експортом. Якщо колись знадобиться
  ледача критична частина маршруту, `createLazyRoute` додається поруч без переробки.
- **`defaultPendingMs: 0` / завжди скелет** — мигання на швидких переходах; відхилено на користь 300/300.
- **Автоматичне розбиття `@base-ui/react` у vendor-чанк** — див. §4.
- **Реверс-інжиніринг через `rollup-plugin-visualizer`** — не додавали: хватило sourcemap/
  `generateBundle`-аналізу одноразовим скриптом, нова залежність не потрібна.

## 8. Відомий борг

- **`libphonenumber-js` (≈ 223 КБ raw) лишається в старті обох апок.** Ланцюг:
  `socket-events`/реєстри `libs/contracts` → `chat.channels` → `customer.schema` →
  `phone.schema` → `libphonenumber-js`; його тягнуть realtime-мости з `main.tsx`. Лікується в
  контрактах (відокремити payload-схеми подій сокета від доменних схем клієнта/телефону), не в
  роутингу — тут свідомо не чіпали.
- Усі i18n-ресурси вантажаться на старті (англійська, ≈ 85 КБ raw). Коли з'являться інші локалі —
  ледачі неймспейси за модулем.
- `apps/web/src/api/generated/api.ts` — один файл на всі теги (≈ 78 КБ raw у старті).
- Віджети дашборда з'являються без скелета (слот-хост малює `null`, поки чанк вантажиться).
- Інші модулі, що тягнуть важкі дочірні компоненти статично (форма події в `customer-events-*`), не
  перевірені на каскад — агенду дашборда виправлено (`EventPanel` — `lazyComponent`).
- Колонка area (`panel`) вантажиться на кліку, а не на hover рейлу — окремого preload немає.
- `platform-web` перевірено збіркою й `bundle:check`, у браузері — лише tenant-web.

# Шел `apps/web`: два рівні навігації

> Реалізовано і прийнято 2026-09-06 для tenant-web (`apps/web`). З 2026-09-12 ту
> саму модель отримав і `apps/platform-web` — див. §9.

Замість одного сайдбара застосунок має **вузьку смугу іконок** (перший рівень) і
**колонку активного розділу** (другий рівень) — модель VS Code, Slack і JetBrains.
Цей документ фіксує термінологію, прив'язку до роутингу і механіку розкладки.

## 1. Термінологія

Як цю пару називає індустрія:

| Продукт          | Перший рівень (смуга іконок)               | Другий рівень (колонка розділу)      |
| ---------------- | ------------------------------------------ | ------------------------------------ |
| VS Code          | **Activity Bar**; пункт = _View Container_ | **Primary Side Bar**; вміст = _View_ |
| JetBrains        | **Tool Window Stripe**                     | **Tool Window**                      |
| Slack (2023)     | **Navigation rail**                        | **Sidebar** (канали / DM)            |
| Material 3       | **Navigation rail**                        | **Navigation drawer**                |
| Atlassian (Nav4) | app switcher / rail                        | **Side navigation**                  |

Спільне в усіх: другий рівень — **контейнер вигляду, а не підменю**. Там може бути
список, дерево, пошук, фільтри.

**Наші імена** (обрані з урахуванням того, що половина очевидних слів у проєкті
вже зайнята):

| Наше                           | Що це                                  | Чому не інше                                                                                                                                                                               |
| ------------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`AppShell`**                 | контейнер усього (замінив `AppLayout`) | це вже не «layout», а шел із власною навігаційною моделлю                                                                                                                                  |
| **`AppRail`**                  | перший рівень                          | «Activity Bar» відпадає — `Activity` зайняте журналом подій; слово «rail» уживаємо тільки з префіксом, щоб не плутати з реєстровим `SidebarRail` (смужка-хапалка, ми її не використовуємо) |
| **area** (`AppArea`, `AreaId`) | одиниця першого рівня                  | `Section` зайняте `components/section/`, `Module` — модулями NestJS, `Workspace` — назвою однієї з area                                                                                    |
| **`AreaSidebar`**              | другий рівень                          | `Panel` зайняте `ActivityPanel` / `NotificationPanel`                                                                                                                                      |
| **`ContextPanel`**             | третя колонка праворуч від контенту    | ім'я з Notion Calendar; голе `Panel` зайняте `ActivityPanel` / `NotificationPanel`, тому кваліфікатор обов'язковий                                                                          |

## 2. Area

```ts
// apps/web/src/app-shell/areas.tsx
interface AppArea {
  id: AreaId;
  prefix: AreaPrefix; // префікс URL, він же «домівка» area
  labelKey: string; // namespace `layout`, ключі areas.*
  icon: LucideIcon;
  hiddenFromRail?: true;
  canSee?: (user: UserResponse) => boolean;
  Sidebar: () => ReactElement; // вміст ДРУГОЇ колонки
}
```

| Area              | Префікс          | У рейлі                      | Друга колонка                                             |
| ----------------- | ---------------- | ---------------------------- | --------------------------------------------------------- |
| **Workspace**     | `/workspace`     | так                          | Dashboard · Users · Customers                             |
| **Calendar**      | `/calendar`      | так                          | міні-місяць (НЕ меню — контейнер вигляду)                 |
| **Chat**          | `/chat`          | так                          | список розмов (поки порожній стан)                        |
| **Settings**      | `/settings`      | так, лише `ADMIN`            | General · Calendar · Numbering · Activity                 |
| **Playground**    | `/playground`    | так                          | Buttons (далі — стенди інших примітивів)                  |
| **Guide**         | `/guide`         | так                          | зміст путівника: параграфи ОДНІЄЇ сторінки, scroll-spy    |
| **User settings** | `/user-settings` | **ні** — з дропдауна аватара | Profile · Account · Security · Notifications · Appearance |

Чотири рішення, які тут не косметичні:

**`Sidebar` — компонент, а не `items: NavItem[]`.** Якби контракт був «масив
пунктів меню», чат не влазив би вже на першому кроці: у нього там список розмов із
пошуком і непрочитаними. Area, що справді є меню, беруть спільний `AreaNav`.

**Settings — окрема area, а не розділ усередині Workspace.** Її під-розділи —
повноцінне меню, і йому місце в навігаційній колонці шела. До цього розділ малював
собі бічну навігацію ВСЕРЕДИНІ сторінки (`SectionNav` у `SettingsLayout`) — тобто
той самий рівень навігації існував двічі й у двох різних виглядах. `SectionNav`
знятий, лишився `ContentSection`.

**User settings — area без пункту в рейлі.** Особисте не належить головній
навігації: словом «Settings» там володіє організація (`docs/settings.md`). Але
модель у нього та сама, що в Settings, — інакше вийшло б два різні візуальні
патерни для однієї ментальної моделі, чого `docs/settings.md` прямо не хоче.

**`canSee` — гейт ВИДИМОСТІ, не доступу.** Доступ enforce-ить `beforeLoad` роуту
(`requireAdmin`) і бекенд (`@Roles(ADMIN)`).

## 3. Прив'язка до роутингу

**Активна area — чиста функція від `location.pathname`.** Дубльованого стану «яка
area вибрана» в застосунку немає, тому F5, back/forward і зовнішнє посилання
дають той самий рейл, що й клік.

```ts
export function resolveArea(pathname: string): AppArea | undefined {
  return APP_AREAS.find((area) => isUnder(pathname, area.prefix));
}
```

`isUnder(p, prefix)` = `p === prefix || p.startsWith(prefix + '/')` — саме так, а не
`startsWith`: інакше `/chatbot` потрапив би в `/chat`, а `/settings-old` у
`/settings`.

`undefined` — легальний результат (шлях поза всіма area, напр. 404): рейл не
підсвічує нічого, а панель показує `DEFAULT_AREA`, щоб юзеру був вихід.

### Дерево роутів

```
rootRoute                     beforeLoad: нормалізатор legacy-URL (§4)
├ /login
└ appRoute  id:'app'  requireAuth  component: AppShell  notFoundComponent
  ├ /                         → redirect /workspace
  ├ /workspace                layout (без component — Outlet рендерить роутер)
  │ ├ /                       DashboardPage
  │ ├ users        users/$userId
  │ └ customers    customers/$customerId
  ├ /calendar                 layout
  │ ├ /                       → redirect /calendar/week
  │ ├ $view                   CalendarPage  (day|week|month|agenda; ?date=yyyy-MM-dd)
  │ └ events/$eventId         CalendarPage з відкритою панеллю події (deep link)
  ├ /chat                     layout
  │ └ /                       ChatPage
  ├ /settings                 layout, beforeLoad: requireAdmin
  │ └ /  calendar  numbering  activity
  ├ /playground               layout
  │ └ /                       PlaygroundPage (стенд кнопок)
  ├ /guide                    GuidePage — одна довга сторінка, параграфи — якорі
  ├ /user-settings            layout
  │ └ /  account  security  notifications  appearance
  └ $                         NotFoundPage — шлях поза будь-якою area
```

- **Layout-роут area без `component`**: TanStack Router рендерить `Outlet` сам, а
  навігація area живе в шелі. Layout потрібен саме як вузол — на ньому сидить гейт
  (`requireAdmin` для settings) і до нього дописуються дочірні роути.
- **Календар — другий випадок «колонка ≠ меню»** (перший був чат): у другій колонці
  живуть міні-місяць (`react-day-picker` рівно як date-picker) і перелік переглядів, а не
  `AreaNav`. Перегляд лежить у ШЛЯХУ (`/calendar/week`), період — у search (`?date=`):
  і те, і те мусить переживати F5 і жити в надісланому посиланні. Невідомий `$view` тихо
  редіректить у тиждень замість 404 — та сама логіка, що `.catch()` у search-схемах.
- **Чат — layout + index від першого дня**, хоча сторінка одна: `/chat/$conversationId`
  додається дитиною, а не переписуванням. Сам роут розмови **не заведений** —
  мертвих роутів не тримаємо.
- **404 у двох місцях і це не дубль**: splat `$` під `appRoute` ловить шляхи поза
  area (`/nonsense`) і проходить `requireAuth`, тому гість летить на `/login`, а не
  дивиться на 404; `notFoundComponent` на `appRoute` ловить промахи ВСЕРЕДИНІ area
  (`/chat/nope`), які до splat-а не доходять — статичний `/chat` перемагає splat за
  ранжуванням, а далі жоден дочірній роут не підходить.
- `/` окремої сторінки не має: корінь застосунку — це area workspace.

### Чому префікс на кожну area, а не «workspace = все інше»

Розглядався варіант із асиметрією (`/chat` має префікс, а workspace лишається
коренем) — він не вимагав би переносити URL. Відкинуто: у нас **чотири** area, і
три з них уже мали свій префікс (`/settings`, `/playground`, `/user-settings`).
Тобто симетричний варіант коштував переносу лише двох гілок — `/users` і
`/customers` — а взамін дав вузол дерева роутів під кожну area і однакове правило
для всіх п'яти. Асиметрія за таку ціну не купується.

## 4. Legacy-URL

Під `/workspace` переїхали `/`, `/users*`, `/customers*`. Зовнішні посилання і
закладки на них існують, тому в `rootRoute.beforeLoad` стоїть один нормалізатор:

```ts
const LEGACY_WORKSPACE_PREFIXES = ['/users', '/customers'];
// → redirect({ href: `/workspace${pathname}${searchStr}`, replace: true })
```

- **`href`, а не `to`**: джерело — довільний старий рядок, типізації тут не буде і
  не потрібно.
- **`searchStr` обов'язковий**: стан гріда (фільтри, сторінка, сортування) живе в
  URL, і редірект без нього викинув би юзера на порожній список.
- Один нормалізатор, а не дублюючі роути на кожен старий шлях: видаляється одним
  блоком, коли посилання протухнуть (орієнтир — кінець 2026).

`/settings`, `/playground`, `/user-settings` адреси **не змінили** — вони стали
area на своїх же префіксах.

## 5. Розкладка

```
SidebarProvider  --sidebar-width: calc(14rem + var(--sidebar-width-icon) + 2px)   → панель 224px
└ Sidebar collapsible="icon" className="overflow-hidden"
  └ div.flex.min-h-0.flex-1
      ├ AppRail       collapsible="none"  w-[calc(var(--sidebar-width-icon)+1px)]!
      │   SidebarHeader  h-14 border-b — бренд-плитка
      │   SidebarContent пункти area
      │   SidebarFooter  аватар + дропдаун
      └ AreaSidebar   collapsible="none"  w-auto flex-1
          SidebarHeader  h-14 border-b — назва інсталяції + активна area сірим
          SidebarContent <area.Sidebar />
└ SidebarInset
  ├ header  h-14 border-b  SidebarTrigger · PageHeaderSlot · дзвінок · тема
  └ Outlet
```

Реєстровий предок — блок [`@shadcn/sidebar-09`](https://ui.shadcn.com/view/new-york-v4/sidebar-09)
(«вкладені рейли»): дві `Sidebar collapsible="none"` всередині зовнішньої
`collapsible="icon"`. Склад рейлу теж від нього — бренд угорі, пункти посередині,
профіль у футері: і бренд, і профіль належать СЕСІЇ, а не area, тож стоять у смузі,
яка від area не залежить.

**Єдине відхилення від блоку: не використовуємо трюк
`*:data-[sidebar=sidebar]:flex-row`** — рядок із двох колонок обгортаємо самі.
Виграш великий: той трюк покладається на `className` зовнішнього сайдбара, а на
мобільному `Sidebar` рендериться як `Sheet` із хардкодженим класом, тому
`className` до нього не доїжджає і колонки стали б одна під одною. Саме через це
блок ховає другу колонку на телефоні (`hidden md:flex`) — тобто лишає смугу іконок
без навігації. Наша обгортка працює в обох гілках, і мобільний отримує **ті самі
дві колонки** в `Sheet` завширшки 18rem = 3rem рейлу + 15rem панелі. Окремого
мобільного режиму немає.

Метрики, які не випадкові:

- **`h-14` + `border-b` у трьох місцях** — шапка рейлу, шапка колонки і хедер
  контенту: три нижні межі складаються в одну неперервну лінію через усе вікно.
  Вміст усіх трьох центрований у цій висоті, тож бренд-плитка, двоярусний
  заголовок area і крихти стоять на одній осі (y=28px).
- **Групи ОБОХ колонок тримають стокові `p-2` — власного падінгу там бути не
  повинно.** Саме від них залежить вертикальна координата першого рядка:
  `56 (шапка) + 1 (межа) + 8 = 65px`, центр іконки — `81px`. Рейл довго мав `p-1`,
  і 4px різниці читались як видима сходинка між рівнями навігації. Побічно 8px
  жолоби дають рівно 32px під кнопку пункту (48 − 16), тобто вона займає рядок
  точно і центрувати її нічим не треба.
- **Рейл = 48px** (стокові `--sidebar-width-icon`, не перевизначаємо), жолоби 4px
  (`p-1`). Усередині — **дві різні метрики, і це навмисно**:

  |                          | Бокс | Падінг               | Іконка            | Клас                 |
  | ------------------------ | ---- | -------------------- | ----------------- | -------------------- |
  | **Пункт area**           | 32px | 8px (стоковий `p-2`) | 16px              | `RAIL_NAV_BUTTON`    |
  | **Якір** (бренд, аватар) | 40px | 0                    | 20px / вміст 32px | `RAIL_ANCHOR_BUTTON` |

  Пункт рейлу несе **рівно ту саму метрику, що пункт другої колонки** — падінг і
  розмір іконки там не перевизначаються взагалі, беруться з варіанта. Два рівні
  навігації мусять читатись як одна система, а не як два різні набори іконок.
  Якорі — не пункти: їх завжди рівно два, вони тримають смугу від верху до низу,
  тому метрика в них своя і більша. Пункт центрує `mx-auto` (32px кнопка у 40px
  комірці), бокс фіксується `size-8!` — інакше кнопка була б `w-full`, і підкладка
  наведення міняла б форму між станами (40×32 проти 32×32); горизонтально його
  центрує сама група — 48 − 16 = 32px.

- **Рейл сприймається за розміром іконки, а не за шириною смуги.** Спроба зробити
  його «більшим» через смугу (56px, кнопка 36px, іконка 18px) оком не читалась
  узагалі, хоча CSS був правильний — перевірено і в зібраному CSS, і в тому, що
  віддає dev-сервер. Смуга лишилась стоковою.
- **Шапка колонки — два яруси**: назва інсталяції (`font-semibold`) і під нею сірим
  активна area (`text-xs text-muted-foreground`). Це та сама форма, що мав брендовий
  блок у сайдбарі до появи рейлу — знак переїхав у смугу, а підзаголовок, який був
  статичним словом, став динамічним.
- **`--sidebar-width` задається ЧЕРЕЗ ширину панелі**, а не навпаки: стандартна тут
  панель, рейл — фіксована обшивка, яку до неї додають. Панель = `--area-sidebar-width`,
  дефолт і мінімум **14rem (224px)**, крок `w-56` шкали Tailwind і нижня межа
  класичного діапазону навігаційної панелі 224…256px (`15rem`/240px — Linear,
  Notion; `16rem`/256px — Material 2 і сток самого shadcn).

  **Тягуча** (`resizable-shell-panels`, 2026-09): `ResizeHandle` (`libs/ui`) на
  правій межі `AreaSidebar` тягне `--area-sidebar-width` — `useResizablePanelWidth`
  мутує змінну напряму на `document.documentElement` (не через React state, щоб не
  ререндерити на кожен піксель) і персистить у `localStorage`
  (`app-shell:area-sidebar-width`, окремо для web і platform-web — різні origin).
  Стеля — 40% ширини viewport, перераховується `ResizeObserver`. Тягнути нижче
  дефолту не можна: 224px — це floor, не просто стартове значення.

  `calc(var(--area-sidebar-width, 14rem) + var(--sidebar-width-icon) + 2px)` = 274px
  блоку за дефолтом. `+ 2px` — не магія, а компенсація двох меж по 1px: правої в
  контейнера сайдбара і правої в рейла; без них панель вийшла б 222px. Фолбек
  `, 14rem` у `var()` — той самий дефолт до першого пейнта хука. Згорнутий стан —
  `--sidebar-width-icon`, тобто самий рейл (`AreaSidebar` і її `ResizeHandle`
  лишаються змонтованими під `overflow-hidden`, тому збережена ширина не губиться).

- **Геометрія кнопок рейлу зібрана в одну константу `RAIL_BUTTON`** — розповзатись їй
  ніде: іконка по центру смуги мусить стояти однаково в обох станах.

### Згортання

Рейл **не згортається — він і є згорнутий стан**. `SidebarTrigger`, Cmd+B і cookie
`sidebar_state` лишились тими самими, просто тепер ховають ДРУГУ колонку:
зовнішній контейнер стискається до `--sidebar-width-icon`, а `overflow-hidden`
відрізає панель. Це поведінка VS Code (Cmd+B ховає Side Bar, Activity Bar
лишається).

### Клік по пункту рейлу

| Стан пункту                     | Елемент  | Дія                            |
| ------------------------------- | -------- | ------------------------------ |
| неактивна area                  | `Link`   | навігація + `setOpen(true)`    |
| активна area, панель розгорнута | `button` | `toggleSidebar()` — згорнути   |
| активна area, панель згорнута   | `button` | `toggleSidebar()` — розгорнути |

Неактивний мусить бути посиланням, щоб працювали Cmd+клік, «відкрити в новій
вкладці» і prefetch роутера. Активний навігувати НЕ має: ти вже в цій area, просто
глибше (`/workspace/users`), і перехід на префікс викинув би тебе на дашборд.

Робити це одним `Link` із `preventDefault` — погана ідея: порядок склеювання
обробників між `useRender` (Base UI) і `Link` не гарантований, тож «не навігувати»
трималось би на випадковості.

### 5.4 Лінії шела

Усі межі шасі — ОДИН токен `--border` (`border-sidebar-border` там, де елемент усередині
сайдбара, — це той самий колір). Чотири `h-14` (шапка рейлу, шапка колонки, хедер контенту
і — коли відкрита — шапка контекстної панелі, §5.6) складають одну неперервну лінію через усе
вікно, і будь-яка з них іншої щільності цю лінію розриває.

Смуга фільтрів списку підключається до тієї ж системи: лінію під нею малює ОБГОРТКА в
розкладці сторінки, а не сам `Grid.Toolbar`. Вона розділяє смугу і таблицю — це властивість
компонування екрана, а не фільтрів. Зверху лінії немає навмисно: там уже стоїть `border-b`
хедера, і друга дала б подвійну.

### 5.5 Відступи контенту: `padded` і `bleed`

Контейнер контенту має два режими, і вибирає їх **роут**, а не сторінка:

| Режим              | Клас             | Кому                                                                             |
| ------------------ | ---------------- | -------------------------------------------------------------------------------- |
| `padded` (дефолт)  | `px-6 pt-4 pb-6` | сторінка компонує картки й форми в колонку — поля навколо них потрібні            |
| `bleed`            | `p-0`            | сторінка САМА є полотном (таблиця гріда, сітка календаря) і впирається в краї     |

Оголошується як `staticData: { layout: 'bleed' }` на роуті; тип — `StaticDataRouteOption`
у `router.tsx`. Шел читає `useMatches().at(-1)`, тобто **режим оголошує сама сторінка, а не
її area**: `/workspace/users` — полотно, а сусідня `/workspace/users/$userId` — ні.

Чому staticData, а не проп сторінки чи ще один портал: це статична властивість екрана, вона
не залежить від даних і не міняється в часі, а в `routeTree` усі винятки видно одним
поглядом. Портал тут був би зайвий — шел нічого не рендерить від сторінки, він лише вибирає
клас контейнера.

**У `bleed` поля роздає сторінка**, і роздає не всім однаково: сітка календаря не отримує
жодних, тулбар фільтрів гріда отримує `px-6 pt-4 pb-3`, футер пагінації — `px-6 pb-6` (його
дає сам `DataGrid` у `surface="flush"`), agenda — звичайні `px-6 pt-4 pb-6`, бо вона список
карток, а не полотно. Крайні комірки таблиці теж беруть 24px: без них текст першої колонки
читався б приклеєним до краю вікна, а вміст таблиці розʼїхався б із крихтами хедера, які
стоять рівно на цій вертикалі.

### 5.6 Контекстна панель: третя колонка

Останній стовпчик вікна — **контекстна панель**
(`libs/ui/src/components/context-panel-slot.tsx`). Модель — «Context Panel» Notion
Calendar: вибір у центрі, розкриття праворуч.

**Вона стоїть НА РІВНІ сайдбара, а не всередині контенту**: сусід `Sidebar` і
`SidebarInset` усередині `SidebarProvider`, тобто йде від верху вікна до низу і
**підрізає хедер справа** рівно так, як лівий сайдбар підрізає його зліва. Перший
підхід ставив панель під хедером, усередині `SidebarInset` — і був знятий: там вона
читалась як частина сторінки, а не як рівноправна колонка шела, а хедер над нею
обіцяв, що керує і її вмістом теж.

Звідси метрика її шапки — така сама `h-14` з `border-b`, як у трьох інших рядків
(§5.4): чотири сегменти складають одну лінію через усе вікно. Тому в шапці два яруси
(назва + пояснення `text-xs`) у межах одного рядка, а **хрестик закриття стоїть у ній
справа зверху**. Кнопка показу — у правому куті хедера контенту, впритул до межі
панелі.

І звідси ж поверхня: панель стоїть на **`--sidebar`**, а не на `--background`. Обидві
бічні колонки — шасі шела, полотном лишається тільки контент посередині. У темній темі
ці токени різні (`#202020` проти `#191919`), і панель на кольорі полотна читалась би як
шматок сторінки, що втік до краю вікна; у світлій — те саме на крок меншим контрастом.
Правило формулюється так: **фон каже, чим елемент Є, а не де він лежить** — сайдбар,
рейл і контекстна панель однакові, бо всі троє шасі.

**Це не `Sheet`.** Панель не накриває сторінку, а СТИСКАЄ її: календарна сітка
лишається видимою і робочою, поки поруч відкрита подія. Різниця між панеллю і
драйвером не в геометрії, а у відповіді на одне питання:

| Чи мусить людина далі бачити сторінку? | Що беремо                                            |
| -------------------------------------- | ---------------------------------------------------- |
| так — сторінка і є контекстом рішення  | **`ContextPanelPortal`** (подія календаря, деталі рядка) |
| ні — рішення самодостатнє              | **`Sheet`** (`ActivityDrawer`, панель сповіщень)      |

Механіка — **той самий портал, що і в хедері** (`page-header-slot.tsx`; там же
розбір, чому портал, а не стан у шелі чи `staticData` роуту). Шел оголошує МІСЦЕ,
сторінка рендерить ЩО ЗАВГОДНО, типів між ними немає. `createPortal` міняє тільки
DOM-розташування, тож вміст панелі лишається дитиною сторінки — бачить її контекст
і, головне, її СТАН: «вибраний обʼєкт» не піднімається в шел.

```tsx
{target !== null && (
  <ContextPanelPortal contentKey={target.event?.id ?? 'draft'} label="CalendarPage">
    <EventPanel target={target} onClose={() => { setTarget(null); }} />
  </ContextPanelPortal>
)}
```

**Дві незалежні речі — вміст і видимість.** `hasContent` (чи змонтований портал)
належить СТОРІНЦІ, `isOpen` (чи розгорнув користувач) — ЛЮДИНІ. Панель видно, коли
обидва істинні; кнопки в хедері немає взагалі, доки нема вмісту — мертвий контрол
гірший за відсутній (те саме правило прибрало «Today» зі стрілками в агенді).

Хрестик у шапці панелі і кнопка в хедері — **різні дії**: хрестик знімає вибір
(`onClose` сторінки), кнопка лише ховає панель, лишаючи вибір. Плутати не можна.

Три граблі, закладені в контракт:

1. **`contentKey` обовʼязковий**, коли панель показує один обʼєкт із багатьох.
   Людина згорнула панель, клікнула СУСІДНЮ подію — портал лишився змонтованим,
   змінився лише `target`, і клік виглядав би як «нічого не сталося». Зміна
   `contentKey` розкриває панель знову: показати новий вибір важливіше, ніж
   памʼятати згортання попереднього.
2. **Закрита панель ховається класом, а не розмонтовується.** Якби слот не рендерив
   DOM-вузол, портал повертав би `null`, і вміст сторінки зник би разом із ним —
   наполовину заповнена форма події губилася б від натискання «сховати».
3. **`min-w-0` на `SidebarInset`.** Без нього широка таблиця гріда не дає себе стиснути,
   і панель виштовхує розкладку за край вікна.

**Ширина — `--context-panel-width`, дефолт і мінімум `18rem`/288px.** Це не підібране
число: 18rem — крок шкали (`w-72`, 72 × 4px) і водночас константа самого реєстру —
`SIDEBAR_WIDTH_MOBILE` у `ui/sidebar.tsx` рівно стільки. `libs/ui` тримає той самий
дефолт як фолбек у самому класі (`var(--context-panel-width,18rem)`) — `SidebarProvider`
більше не оголошує значення інлайном, воно живе тільки тут і в хуку нижче.

**Тягуча** (`resizable-shell-panels`, 2026-09): `ResizeHandle` на лівій межі (тільки
в docked-режимі, `md`+) тягне саме цю змінну тим самим `useResizablePanelWidth`, що й
`AreaSidebar` — пряма мутація `document.documentElement`, персист у `localStorage`
(`app-shell:context-panel-width`), стеля 40% viewport через `ResizeObserver`. 288px —
floor, а не просто стартове значення.

Урок загальний: **симетрія — це аргумент, а не вимір**; коли вміст просить інше число,
беремо найближчий крок шкали, а не тримаємось за красу дзеркала (панель не взяла
`var(--sidebar-width)` = 274px, рівну лівій парі, саме з цієї причини — тіснувато для
форми).

На вузькому екрані стискати нічого, тому до `md` панель лягає ПОВЕРХ (`fixed`) — це
єдиний випадок, коли вона поводиться як драйвер, і зроблено це геометрією, а не другим
компонентом.

#### Карта: де панель уже є і куди її ще треба завести

Панель заведена на двох поверхнях і свідомо НЕ розкочена далі одним махом — кожен
переїзд це рішення «сторінка під панеллю потрібна чи ні», а не механічна заміна
компонента. Список нижче — черга, а не беклог «колись»:

| Поверхня                                            | Зараз                                            | Що робити                                                                                                                              |
| --------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| Подія календаря (`/calendar/*`)                     | ✅ панель (`EventPanel`)                          | —                                                                                                                                        |
| «Upcoming» на картці кастомера                      | ✅ панель (той самий `EventPanel`)                 | —                                                                                                                                        |
| `ActivityDrawer` — row action «View activity» на `/users` | `Sheet` (`components/activity/activity-drawer.tsx`) | **переїзд**: стрічка подій юзера читається ПРОТИ рядка в таблиці («що сталося саме з цим»), а драйвер таблицю ховає. Кандидат №1        |
| Рядок гріда `/users` і `/customers`                 | тільки перехід на картку `$id`                    | **нове**: попередній перегляд у панелі без втрати місця в таблиці. Картка за прямим посиланням лишається — панель її не заміняє          |
| `ActivityPanel` на картках юзера й кастомера        | друга колонка ВСЕРЕДИНІ сторінки                  | **розглянути**: переїзд у панель віддав би картці всю ширину, але забрав би стрічку з друку і з вузького екрана. Рішення не прийняте     |
| Панель сповіщень (дзвінок)                          | `Sheet`                                           | **лишається `Sheet`**: рішення самодостатнє, сторінка під ним не потрібна — це і є межа з §5.6                                            |
| Area `Chat`                                         | порожня                                           | **за дизайном**: розмова в центрі, картка учасника / деталі треда — у панелі                                                              |
| `apps/platform-web` (`/tenants`, `/jobs`)           | панелі немає взагалі                              | **потребує шела**: механізм у `libs/ui` вже generic, але одноколонковий `app-layout` платформи ще не має ні слота, ні кнопки в хедері     |

Ознака, за якою поверхня потрапляє в цей список, одна і та сама: **людина дивиться на
деталь, не відпускаючи списку**. Якщо після закриття деталі сторінка під нею не
потрібна — це `Sheet`, і переїжджати нема куди.

**Панель має ВЛАСНУ метрику полів — `p-2` (8px), удвічі тіснішу за поля сторінки
(`px-6`/`p-4`).** І це не «трохи інший смак», а наслідок ширини: у 288px колонці кожні
зайві 8px по краях — це 6% ширини кожного поля вводу, тобто плата за повітря, якого тут
нема звідки взяти. Поля сторінки в цій колонці зʼїдали більше, ніж давали.

Метрику тримає ВСЯ панель, а не тільки форма: `px-2` у шапці (`ContextPanelHeader`),
`mx-2` у табах, `p-2` у вмісті вкладок. Перевірка, що це зроблено правильно, — одна
вертикаль: **назва в шапці і ліва межа полів форми стоять на одному піксельному
стовпчику** (виміряно: `titleLeft === firstInputLeft`). Розʼїхались — хтось лишив
`px-4` від сторінки.

#### Прокрутка вмісту панелі

Вміст панелі скролить **`ScrollArea`** з `libs/ui`, а не нативний `overflow-y-auto`. Тут це
не косметика: у 288px колонці постійна смуга відбирає 8–15px у полів вводу, тобто до 6%
ширини кожного. Оверлейна смуга не забирає нічого і зʼявляється, лише коли нею
користуються (механіка й тривалості — `ui-stack.md` § «Прокрутка»).

Шаблон панелі — три частини, і поділ між ними принциповий:

```tsx
<ContextPanelPortal contentKey={id} label="MyPage">
  <div className="flex min-h-0 flex-1 flex-col">
    <ContextPanelHeader title={…} description={…} onClose={…} />
    <ScrollArea className="min-h-0 flex-1">
      <div className="p-2">{/* вміст */}</div>
    </ScrollArea>
  </div>
</ContextPanelPortal>
```

- **Шапка — ПОЗА скролом.** Вона тримає лінію шела (§5.4) і хрестик; поїхавши вгору разом
  із вмістом, вона розірвала б лінію і забрала єдиний вихід із панелі.
- **Скролить `ScrollArea`, а не контейнер вкладки.** З табами кожен `TabsContent` стає
  `flex min-h-0 flex-1 flex-col`, а `ScrollArea` лежить усередині — інакше скролерів два,
  і смуга малюється не там, де скрол.
- **Поля `p-2` — усередині скрол-області.** Тоді вони належать вмісту, а не рамці, і смуга
  лягає поверх них, а не поруч.

**Горизонтального скролу в панелі не буває** — і це вже не домовленість, а властивість
примітива: `ScrollArea` за замовчуванням `axis="vertical"` і глушить горизонталь на самому
viewport.

Два джерела горизонтального переповнення, які пояснюють, чому дефолт саме такий:

1. **Футер форми події** — `Cancel event` + `Delete` + `Save` в один рядок із
   `justify-between` виштовхували панель на 26px. Полагоджено по-справжньому, а не сховано:
   у вузькій панелі головна дія йде на всю ширину зверху, вторинні — рядком під нею з
   переносом. Це і є розкладка футера для панелі взагалі.
2. **Прихований нативний `<input>` усередині `Switch`** — `clientWidth: 1`,
   `scrollWidth: 63`, і ці фантомні пікселі течуть угору до `form`. Видимого переповнення
   немає, смуга є. Деталі й процедура перевірки — `ui-known-issues.md` UI-2.

Друге і є причина, чому глушник живе в примітиві, а не в кожній панелі: перше можна
полагодити розкладкою, друге приходить із чужого коду і полагодити його в себе неможливо.

Панель `sticky top-0 h-svh` зі своїм скролом (ідіом `ActivityPanel`), а не `fixed`:
сторінка поруч скролиться вікном і панель лишається на місці, але при цьому не виходить
із потоку — інакше вона не віднімала б ширину, а накривала контент.

`/tenants`, і спільний компонент не має знати шляхів конкретного плану (хардкод
`to="/"` там після міграції просто не збереться).

## 7. Граблі

0. **`AreaSidebar` мусить мати `min-w-0`** — інакше друга колонка не влазить у
   свою ж ширину. Flex-елемент за замовчуванням має `min-width: auto`, тобто
   відмовляється стискатися нижче min-content свого вмісту: щойно в area
   з'явилося щось широке (міні-місяць календаря — сітка 7×28px плюс три вкладені
   відступи), колонка розпирала себе до 236px замість відведених 225 і виїжджала
   за праву межу шела, а `overflow-hidden` зовнішнього `Sidebar` цю смугу
   зрізав. Симптом оманливий: виглядає, ніби «вміст з'їхав праворуч і сховався за
   лінією», хоча насправді за лінією опинилась уся колонка — включно з кнопкою на
   `w-full`, яка чесно займала 100% завеликого контейнера. Спіймано в браузері
   2026-09-07 на календарі; без `min-w-0` та сама пастка чекала б на списку
   розмов у чаті й на будь-якому довгому лейблі.

   **Наслідок для вмісту area — ОДИН інсет, а не нуль.** Спокуса після цієї
   граблі — зняти падінги взагалі (`px-0` на групі) і віддати блоку всю ширину.
   Так робити не варто, і це теж перевірено оком: міні-місяць уперся в обидві
   стінки, а плитка вибраного дня легла прямо на межу колонки. Правильна мета не
   «на всю ширину», а **вирівняно з рештою пунктів**: стокові `p-2` групи дають
   ті самі 8px, з якими стоять `SidebarMenuButton` вище й нижче, тож блок
   потрапляє з ними в одну вертикаль.

   Прибирати треба **вкладені** відступи, а не єдиний зовнішній: у першій версії
   міні-місяця їх було три (група 8 + мій `px-1` на контенті 4 + власний `p-2`
   календаря 8 = 20px з боку), і саме вони не давали сітці 7×28px влізти в 225px.
   Тепер лишився один: `SidebarGroup` без класу, `Calendar className="p-0"` і
   `classNames={{ root: 'w-full' }}` — саме `classNames`, бо корінь реєстрового
   `Calendar` отримує `w-fit` через нього, і клас із `className` програє йому в
   CSS-порядку. Виміряно: сітка `57→265`, кнопка «Today» `57→265`, пункт
   «Week» `57→265` — три різні компоненти в одну лінію.

1. **Кожне перевизначення геометрії кнопки рейлу треба дублювати з модифікатором
   `group-data-[collapsible=icon]:`.** `sidebarMenuButtonVariants` містить
   `group-data-[collapsible=icon]:size-8!` і `:p-2!`, а голі `size-9!`/`p-0!` їм НЕ
   конкуренти: модифікатори різні, тож tailwind-merge лишає обидва правила, і в
   згорнутому стані кнопка отримує чужий розмір із чужим падінгом. Вміст на всю
   кнопку (бренд-плитка, аватар) тоді стискається, з'їжджає вправо і обрізається
   `overflow-hidden` самої кнопки; іконки симптому не показують — вони у звужений
   бокс якраз влазять, тому видно лише на плитці й аватарі. Геометрія зібрана в
   `RAIL_BUTTON`, щоб правило не розповзалось.

   Там же — чому розмір іконок рейлу задає саме `[&_svg]` на кнопці, а не клас на
   самій іконці: селектор нащадка специфічніший за клас на елементі, тож перебити
   його «на місці» можна лише через `!`. Одне правило на весь рейл — і піктограми
   area, і знак у бренд-плитці.

   Побічне спостереження з тієї ж перевірки: **`p-2` і `w-full` із варіанта в рядку
   лишаються** — tailwind-merge не вважає їх конфліктом для `p-0!` / `size-8!`, бо
   важливість різна. У CSS `!important` усе одно виграє, і це рівно та причина, через
   яку реєстр ставить `!` у таких перевизначеннях; покладатись на дедуплікацію тут
   не можна, важливо лише щоб класи з `!` стояли пізніше.

2. **Блок ідентичності в дропдауні профілю мусить лежати в `DropdownMenuGroup`.**
   `DropdownMenuLabel` = `MenuPrimitive.GroupLabel`, і Base UI без групи-батька падає в
   рантаймі (`MenuGroupContext is missing`). У блоці `nav-user` реєстру він лежить прямо
   в `DropdownMenuContent` — так можна в Radix, не в Base UI. Заодно це семантично
   правильніше: ідентичність підписує групу особистих дій, а не висить над меню.
3. **Tooltip у рейлі мусить бути `{ children, hidden: isMobile }`.** Реєстровий
   `SidebarMenuButton` показує tooltip лише при `state === 'collapsed'`, а
   `useSidebar()` віддає стан ЗОВНІШНЬОГО сайдбара — тобто при розгорнутій панелі
   підказки не було б, хоча підписів у рейлі не видно НІКОЛИ. Спред `{...tooltip}`
   у компоненті йде після `hidden`, тому перевизначення легальне
   (`libs/ui/src/components/ui/sidebar.tsx`). На мобільному підказка вимкнена —
   там смуга в `Sheet` поруч із панеллю, і тапати нічого не мішає.
4. **`w-[...]!` і `w-auto` на вкладених сайдбарах обов'язкові**: `collapsible="none"`
   рендерить `w-(--sidebar-width)`, тобто без перевизначення обидві колонки були б
   на всю ширину блоку.
5. **`useParams({ from })` бере ID роуту, а не URL** — і його TS перевіряє. Після
   переносу гілки під `/workspace` довелось правити `from: '/app/users/$userId'` →
   `from: '/app/workspace/users/$userId'` (`/app` у префіксі — це `id: 'app'`
   pathless-роуту).
6. **`Crumb.to` у `PageBreadcrumbs` типізований як `string`**, тому крихти
   компілятор НЕ перевіряє. При переносі URL їх треба правити вручну — на відміну
   від `Link to` і `useParams({ from })`, які падають самі.
7. **Один `SidebarProvider` на обидві колонки.** Другий провайдер = другий cookie і
   зламаний Cmd+B.

## 9. Шел `apps/platform-web`

Реалізовано 2026-09-12: control plane отримав ту саму МОДЕЛЬ шела, що tenant-web
(§0 плану `docs/frontend/platform-web-shell-plan.md`) — рейл + колонка area,
нижня смуга акаунта, контекстна панель, `ScrollArea`-скрол сторінки, друга вісь
теми, `padded`/`bleed`. Раніше тут був один сайдбар (патерн `sidebar-07`), тепер
— два рівні навігації, як у tenant-web (`sidebar-09`).

### 9.1 Склад area

| Area              | Префікс          | У рейлі                      | Друга колонка             | Іконка      |
| ----------------- | ---------------- | ----------------------------- | -------------------------- | ----------- |
| **Tenants**       | `/tenants`       | так                            | `All tenants`               | `Building2` |
| **Operations**    | `/operations`    | так                            | `Jobs` · `Queues`            | `Activity`  |
| **User settings** | `/user-settings` | ні — з дропдауна аватара       | `Profile` · `Appearance`     | `UserCog`   |

Рейл вимагає ≥2 area, інакше він декорація (саме тому в platform-web його довго
не було) — Tenants (клієнти платформи) і Operations (машинерія системи) дають
природну межу. Колонка Tenants має рівно один пункт — легально: контракт
`AppArea.Sidebar` — компонент-контейнер area, а не підменю (те саме
підтверджував порожній `ChatSidebar` у web); тут вона наповнюється на MT-4
(оператори, сегменти тенантів). «Черги» переїхали з карток над таблицею джоб на
власну сторінку `/operations/queues` — інакше `/operations/jobs` не могла стати
`bleed`-полотном, як `/users` у web. Розділу «Settings» (організаційного) в
platform-web НЕМАЄ: суб'єкт контрол-плейну — сама платформа, і в `platform-api`
немає жодного ендпоінта її налаштувань.

### 9.2 Контекстна панель

Один реальний споживач — `JobDetailsPanel` на `/operations/jobs`: повний
`data`/`output` (у гріді вони обрізані `max-w-56`), таймінги, спроби. Відкриття
— row action «View details» (той самий патерн, що «View activity» на `/users`).

### 9.3 Копіюємо, а не витягуємо в `libs/ui`

Файли шела platform-web (`src/app-shell/…`) — СКОПІЙОВАНІ з `apps/web`, не
екстраговані в пакет: реєстр area, бренд (`ShieldCheck` замість `Layers`),
футер (свій `useAuthStore` з `operator` замість `user`, logout без виклику API —
`POST /auth/logout` у platform-api не існує), шапка колонки (тут немає
`GET /settings/bootstrap`, тож бренд статичний, без фолбека на назву тенанта).
Так само народжувався сам `libs/ui` (UI-0): спершу два побайтово однакові
набори, потім екстракція. Кандидати на екстракцію після цієї ітерації —
`area-nav.tsx` (generic по `NavPath`), `RAIL_*`-константи, композиція
`app-shell.tsx` з інжекцією «рейл/колонка/футер/хедерні кнопки» — робити третім
ходом, коли зʼявиться третій споживач або коли файли справді зійдуться
побайтово (сценарій UI-0).

### 9.4 Що лишилось різним (і має лишитись)

Дзвінок сповіщень, presence/last-seen і стрічка активностей — tenant-фічі:
`activities` живуть під RLS у tenant-плані, платформа їх не читає.
Refresh-токен: у платформи access-токен (60m) напряму в localStorage без
refresh-механіки (MT-3, свідомий trade-off). `/user-settings/profile` у
platform-web — READ-ONLY (нема `PATCH` для `platform_users`), на відміну від
форми в tenant-web.

### 9.5 Пагінований `GET /tenants`

Передумова для `DataGrid` на `/tenants`: контракт отримав
`TenantQuerySchema` (`page`/`limit`/`search`/`isActive`/`sortBy`/`sortOrder`,
той самий whitelist-патерн, що `UserQuerySchema`) і `TenantListResponseSchema`
через спільний `paginatedResponseSchema` — раніше ендпоінт віддавав
`{ items, total }` без пагінації, і сторінка була плоскою таблицею без
`DataGrid`-фреймворку (задокументований виняток, знятий цією ітерацією).

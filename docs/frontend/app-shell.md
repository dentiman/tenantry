# Шел `apps/web`: два рівні навігації

> Реалізовано і прийнято 2026-09-06. Стосується **тільки tenant-web** (`apps/web`):
> у `apps/platform-web` один рівень навігації і одна area, тому там лишився
> одноколонковий шел за патерном `sidebar-07` (див. `ui-stack.md`).

Замість одного сайдбара застосунок має **вузьку смугу іконок** (перший рівень) і
**колонку активного розділу** (другий рівень) — модель VS Code, Slack і JetBrains.
Цей документ фіксує термінологію, прив'язку до роутингу і механіку розкладки.

## 1. Термінологія

Як цю пару називає індустрія:

| Продукт          | Перший рівень (смуга іконок)               | Другий рівень (колонка розділу)      |
| ---------------- | ------------------------------------------ | ------------------------------------ |
| VS Code          | **Activity Bar**; пункт = _View Container_ | **Primary Side Bar**; вміст = _View_ |
| JetBrains        | **Tool Window Stripe**                     | **Tool Window**                      |
| Slack (2023)     | **Navigation rail**                        | **Sidebar** (канали / DM)            |
| Material 3       | **Navigation rail**                        | **Navigation drawer**                |
| Atlassian (Nav4) | app switcher / rail                        | **Side navigation**                  |

Спільне в усіх: другий рівень — **контейнер вигляду, а не підменю**. Там може бути
список, дерево, пошук, фільтри.

**Наші імена** (обрані з урахуванням того, що половина очевидних слів у проєкті
вже зайнята):

| Наше                           | Що це                                  | Чому не інше                                                                                                                                                                               |
| ------------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`AppShell`**                 | контейнер усього (замінив `AppLayout`) | це вже не «layout», а шел із власною навігаційною моделлю                                                                                                                                  |
| **`AppRail`**                  | перший рівень                          | «Activity Bar» відпадає — `Activity` зайняте журналом подій; слово «rail» уживаємо тільки з префіксом, щоб не плутати з реєстровим `SidebarRail` (смужка-хапалка, ми її не використовуємо) |
| **area** (`AppArea`, `AreaId`) | одиниця першого рівня                  | `Section` зайняте `components/section/`, `Module` — модулями NestJS, `Workspace` — назвою однієї з area                                                                                    |
| **`AreaSidebar`**              | другий рівень                          | `Panel` зайняте `ActivityPanel` / `NotificationPanel`                                                                                                                                      |

## 2. Area

```ts
// apps/web/src/app-shell/areas.tsx
interface AppArea {
  id: AreaId;
  prefix: AreaPrefix; // префікс URL, він же «домівка» area
  labelKey: string; // namespace `layout`, ключі areas.*
  icon: LucideIcon;
  hiddenFromRail?: true;
  canSee?: (user: UserResponse) => boolean;
  Sidebar: () => ReactElement; // вміст ДРУГОЇ колонки
}
```

| Area              | Префікс          | У рейлі                      | Друга колонка                                             |
| ----------------- | ---------------- | ---------------------------- | --------------------------------------------------------- |
| **Workspace**     | `/workspace`     | так                          | Dashboard · Users · Customers                             |
| **Calendar**      | `/calendar`      | так                          | міні-місяць (НЕ меню — контейнер вигляду)                 |
| **Chat**          | `/chat`          | так                          | список розмов (поки порожній стан)                        |
| **Settings**      | `/settings`      | так, лише `ADMIN`            | General · Calendar · Numbering · Activity                 |
| **Playground**    | `/playground`    | так                          | Buttons (далі — стенди інших примітивів)                  |
| **User settings** | `/user-settings` | **ні** — з дропдауна аватара | Profile · Account · Security · Notifications · Appearance |

Чотири рішення, які тут не косметичні:

**`Sidebar` — компонент, а не `items: NavItem[]`.** Якби контракт був «масив
пунктів меню», чат не влазив би вже на першому кроці: у нього там список розмов із
пошуком і непрочитаними. Area, що справді є меню, беруть спільний `AreaNav`.

**Settings — окрема area, а не розділ усередині Workspace.** Її під-розділи —
повноцінне меню, і йому місце в навігаційній колонці шела. До цього розділ малював
собі бічну навігацію ВСЕРЕДИНІ сторінки (`SectionNav` у `SettingsLayout`) — тобто
той самий рівень навігації існував двічі й у двох різних виглядах. `SectionNav`
знятий, лишився `ContentSection`.

**User settings — area без пункту в рейлі.** Особисте не належить головній
навігації: словом «Settings» там володіє організація (`docs/settings.md`). Але
модель у нього та сама, що в Settings, — інакше вийшло б два різні візуальні
патерни для однієї ментальної моделі, чого `docs/settings.md` прямо не хоче.

**`canSee` — гейт ВИДИМОСТІ, не доступу.** Доступ enforce-ить `beforeLoad` роуту
(`requireAdmin`) і бекенд (`@Roles(ADMIN)`).

## 3. Прив'язка до роутингу

**Активна area — чиста функція від `location.pathname`.** Дубльованого стану «яка
area вибрана» в застосунку немає, тому F5, back/forward і зовнішнє посилання
дають той самий рейл, що й клік.

```ts
export function resolveArea(pathname: string): AppArea | undefined {
  return APP_AREAS.find((area) => isUnder(pathname, area.prefix));
}
```

`isUnder(p, prefix)` = `p === prefix || p.startsWith(prefix + '/')` — саме так, а не
`startsWith`: інакше `/chatbot` потрапив би в `/chat`, а `/settings-old` у
`/settings`.

`undefined` — легальний результат (шлях поза всіма area, напр. 404): рейл не
підсвічує нічого, а панель показує `DEFAULT_AREA`, щоб юзеру був вихід.

### Дерево роутів

```
rootRoute                     beforeLoad: нормалізатор legacy-URL (§4)
├ /login
└ appRoute  id:'app'  requireAuth  component: AppShell  notFoundComponent
  ├ /                         → redirect /workspace
  ├ /workspace                layout (без component — Outlet рендерить роутер)
  │ ├ /                       DashboardPage
  │ ├ users        users/$userId
  │ └ customers    customers/$customerId
  ├ /calendar                 layout
  │ ├ /                       → redirect /calendar/week
  │ ├ $view                   CalendarPage  (day|week|month|agenda; ?date=yyyy-MM-dd)
  │ └ events/$eventId         CalendarPage з відкритою панеллю події (deep link)
  ├ /chat                     layout
  │ └ /                       ChatPage
  ├ /settings                 layout, beforeLoad: requireAdmin
  │ └ /  calendar  numbering  activity
  ├ /playground               layout
  │ └ /                       PlaygroundPage (стенд кнопок)
  ├ /user-settings            layout
  │ └ /  account  security  notifications  appearance
  └ $                         NotFoundPage — шлях поза будь-якою area
```

- **Layout-роут area без `component`**: TanStack Router рендерить `Outlet` сам, а
  навігація area живе в шелі. Layout потрібен саме як вузол — на ньому сидить гейт
  (`requireAdmin` для settings) і до нього дописуються дочірні роути.
- **Календар — другий випадок «колонка ≠ меню»** (перший був чат): у другій колонці
  живуть міні-місяць (`react-day-picker` рівно як date-picker) і перелік переглядів, а не
  `AreaNav`. Перегляд лежить у ШЛЯХУ (`/calendar/week`), період — у search (`?date=`):
  і те, і те мусить переживати F5 і жити в надісланому посиланні. Невідомий `$view` тихо
  редіректить у тиждень замість 404 — та сама логіка, що `.catch()` у search-схемах.
- **Чат — layout + index від першого дня**, хоча сторінка одна: `/chat/$conversationId`
  додається дитиною, а не переписуванням. Сам роут розмови **не заведений** —
  мертвих роутів не тримаємо.
- **404 у двох місцях і це не дубль**: splat `$` під `appRoute` ловить шляхи поза
  area (`/nonsense`) і проходить `requireAuth`, тому гість летить на `/login`, а не
  дивиться на 404; `notFoundComponent` на `appRoute` ловить промахи ВСЕРЕДИНІ area
  (`/chat/nope`), які до splat-а не доходять — статичний `/chat` перемагає splat за
  ранжуванням, а далі жоден дочірній роут не підходить.
- `/` окремої сторінки не має: корінь застосунку — це area workspace.

### Чому префікс на кожну area, а не «workspace = все інше»

Розглядався варіант із асиметрією (`/chat` має префікс, а workspace лишається
коренем) — він не вимагав би переносити URL. Відкинуто: у нас **чотири** area, і
три з них уже мали свій префікс (`/settings`, `/playground`, `/user-settings`).
Тобто симетричний варіант коштував переносу лише двох гілок — `/users` і
`/customers` — а взамін дав вузол дерева роутів під кожну area і однакове правило
для всіх п'яти. Асиметрія за таку ціну не купується.

## 4. Legacy-URL

Під `/workspace` переїхали `/`, `/users*`, `/customers*`. Зовнішні посилання і
закладки на них існують, тому в `rootRoute.beforeLoad` стоїть один нормалізатор:

```ts
const LEGACY_WORKSPACE_PREFIXES = ['/users', '/customers'];
// → redirect({ href: `/workspace${pathname}${searchStr}`, replace: true })
```

- **`href`, а не `to`**: джерело — довільний старий рядок, типізації тут не буде і
  не потрібно.
- **`searchStr` обов'язковий**: стан гріда (фільтри, сторінка, сортування) живе в
  URL, і редірект без нього викинув би юзера на порожній список.
- Один нормалізатор, а не дублюючі роути на кожен старий шлях: видаляється одним
  блоком, коли посилання протухнуть (орієнтир — кінець 2026).

`/settings`, `/playground`, `/user-settings` адреси **не змінили** — вони стали
area на своїх же префіксах.

## 5. Розкладка

```
SidebarProvider  --sidebar-width: calc(14rem + var(--sidebar-width-icon) + 2px)   → панель 224px
└ Sidebar collapsible="icon" className="overflow-hidden"
  └ div.flex.min-h-0.flex-1
      ├ AppRail       collapsible="none"  w-[calc(var(--sidebar-width-icon)+1px)]!
      │   SidebarHeader  h-14 border-b — бренд-плитка
      │   SidebarContent пункти area
      │   SidebarFooter  аватар + дропдаун
      └ AreaSidebar   collapsible="none"  w-auto flex-1
          SidebarHeader  h-14 border-b — назва інсталяції + активна area сірим
          SidebarContent <area.Sidebar />
└ SidebarInset
  ├ header  h-14 border-b  SidebarTrigger · PageHeaderSlot · дзвінок · тема
  └ Outlet
```

Реєстровий предок — блок [`@shadcn/sidebar-09`](https://ui.shadcn.com/view/new-york-v4/sidebar-09)
(«вкладені рейли»): дві `Sidebar collapsible="none"` всередині зовнішньої
`collapsible="icon"`. Склад рейлу теж від нього — бренд угорі, пункти посередині,
профіль у футері: і бренд, і профіль належать СЕСІЇ, а не area, тож стоять у смузі,
яка від area не залежить.

**Єдине відхилення від блоку: не використовуємо трюк
`*:data-[sidebar=sidebar]:flex-row`** — рядок із двох колонок обгортаємо самі.
Виграш великий: той трюк покладається на `className` зовнішнього сайдбара, а на
мобільному `Sidebar` рендериться як `Sheet` із хардкодженим класом, тому
`className` до нього не доїжджає і колонки стали б одна під одною. Саме через це
блок ховає другу колонку на телефоні (`hidden md:flex`) — тобто лишає смугу іконок
без навігації. Наша обгортка працює в обох гілках, і мобільний отримує **ті самі
дві колонки** в `Sheet` завширшки 18rem = 3rem рейлу + 15rem панелі. Окремого
мобільного режиму немає.

Метрики, які не випадкові:

- **`h-14` + `border-b` у трьох місцях** — шапка рейлу, шапка колонки і хедер
  контенту: три нижні межі складаються в одну неперервну лінію через усе вікно.
  Вміст усіх трьох центрований у цій висоті, тож бренд-плитка, двоярусний
  заголовок area і крихти стоять на одній осі (y=28px).
- **Групи ОБОХ колонок тримають стокові `p-2` — власного падінгу там бути не
  повинно.** Саме від них залежить вертикальна координата першого рядка:
  `56 (шапка) + 1 (межа) + 8 = 65px`, центр іконки — `81px`. Рейл довго мав `p-1`,
  і 4px різниці читались як видима сходинка між рівнями навігації. Побічно 8px
  жолоби дають рівно 32px під кнопку пункту (48 − 16), тобто вона займає рядок
  точно і центрувати її нічим не треба.
- **Рейл = 48px** (стокові `--sidebar-width-icon`, не перевизначаємо), жолоби 4px
  (`p-1`). Усередині — **дві різні метрики, і це навмисно**:

  |                          | Бокс | Падінг               | Іконка            | Клас                 |
  | ------------------------ | ---- | -------------------- | ----------------- | -------------------- |
  | **Пункт area**           | 32px | 8px (стоковий `p-2`) | 16px              | `RAIL_NAV_BUTTON`    |
  | **Якір** (бренд, аватар) | 40px | 0                    | 20px / вміст 32px | `RAIL_ANCHOR_BUTTON` |

  Пункт рейлу несе **рівно ту саму метрику, що пункт другої колонки** — падінг і
  розмір іконки там не перевизначаються взагалі, беруться з варіанта. Два рівні
  навігації мусять читатись як одна система, а не як два різні набори іконок.
  Якорі — не пункти: їх завжди рівно два, вони тримають смугу від верху до низу,
  тому метрика в них своя і більша. Пункт центрує `mx-auto` (32px кнопка у 40px
  комірці), бокс фіксується `size-8!` — інакше кнопка була б `w-full`, і підкладка
  наведення міняла б форму між станами (40×32 проти 32×32); горизонтально його
  центрує сама група — 48 − 16 = 32px.

- **Рейл сприймається за розміром іконки, а не за шириною смуги.** Спроба зробити
  його «більшим» через смугу (56px, кнопка 36px, іконка 18px) оком не читалась
  узагалі, хоча CSS був правильний — перевірено і в зібраному CSS, і в тому, що
  віддає dev-сервер. Смуга лишилась стоковою.
- **Шапка колонки — два яруси**: назва інсталяції (`font-semibold`) і під нею сірим
  активна area (`text-xs text-muted-foreground`). Це та сама форма, що мав брендовий
  блок у сайдбарі до появи рейлу — знак переїхав у смугу, а підзаголовок, який був
  статичним словом, став динамічним.
- **`--sidebar-width` задається ЧЕРЕЗ ширину панелі**, а не навпаки: стандартна тут
  панель, рейл — фіксована обшивка, яку до неї додають. Панель = **14rem (224px)**,
  крок `w-56` шкали Tailwind і нижня межа класичного діапазону навігаційної панелі
  224…256px (`15rem`/240px — Linear, Notion; `16rem`/256px — Material 2 і сток самого
  shadcn). Наступний крок угору, якщо стане тісно, — `15rem`.

  `calc(14rem + var(--sidebar-width-icon) + 2px)` = 274px блоку. `+ 2px` — не магія,
  а компенсація двох меж по 1px: правої в контейнера сайдбара і правої в рейла; без
  них панель вийшла б 222px. Згорнутий стан — `--sidebar-width-icon`, тобто самий рейл.

- **Геометрія кнопок рейлу зібрана в одну константу `RAIL_BUTTON`** — розповзатись їй
  ніде: іконка по центру смуги мусить стояти однаково в обох станах.

### Згортання

Рейл **не згортається — він і є згорнутий стан**. `SidebarTrigger`, Cmd+B і cookie
`sidebar_state` лишились тими самими, просто тепер ховають ДРУГУ колонку:
зовнішній контейнер стискається до `--sidebar-width-icon`, а `overflow-hidden`
відрізає панель. Це поведінка VS Code (Cmd+B ховає Side Bar, Activity Bar
лишається).

### Клік по пункту рейлу

| Стан пункту                     | Елемент  | Дія                            |
| ------------------------------- | -------- | ------------------------------ |
| неактивна area                  | `Link`   | навігація + `setOpen(true)`    |
| активна area, панель розгорнута | `button` | `toggleSidebar()` — згорнути   |
| активна area, панель згорнута   | `button` | `toggleSidebar()` — розгорнути |

Неактивний мусить бути посиланням, щоб працювали Cmd+клік, «відкрити в новій
вкладці» і prefetch роутера. Активний навігувати НЕ має: ти вже в цій area, просто
глибше (`/workspace/users`), і перехід на префікс викинув би тебе на дашборд.

Робити це одним `Link` із `preventDefault` — погана ідея: порядок склеювання
обробників між `useRender` (Base UI) і `Link` не гарантований, тож «не навігувати»
трималось би на випадковості.

## 6. Файли

```
apps/web/src/app-shell/
  app-shell.tsx                  провайдери, дві колонки, SidebarInset
  app-rail.tsx                   перший рівень: бренд, пункти area, дропдаун профілю
  area-sidebar.tsx               друга колонка: шапка з назвою area + її вміст
  area-nav.tsx                   список пунктів (для тих area, що є меню)
  areas.tsx                      реєстр area, resolveArea, DEFAULT_AREA
  paths.ts                       NavPath / AreaPrefix (літерали) + isUnder
  areas/
    workspace-sidebar.tsx  chat-sidebar.tsx  settings-sidebar.tsx
    playground-sidebar.tsx  user-settings-sidebar.tsx
```

`paths.ts` — прямий спадкоємець знятого `SectionPath`: шляхи перелічені літералами,
бо `Link to` типізований юніоном реальних роутів, і друкарська помилка в навігації
ловиться компіляцією, а не кліком.

Знято разом із міграцією: `components/app-layout.tsx`,
`components/section/section-nav.tsx`, `pages/settings/layout.tsx`,
`pages/user-settings/layout.tsx`.

У `libs/ui` не переїхало нічого: `app-layout` там свідомо ніколи не жив (бренд і
навігація в двох фронтах різні), і двоколонковість лишається локальною, поки
platform-web має одну area. Єдина правка пакета — `NotFoundPage` дістав проп
`homeTo`: «головна» у tenant-web тепер `/workspace`, у platform-web `/`, і спільний
компонент не має знати шляхів конкретного плану (хардкод `to="/"` там після
міграції просто не збереться).

## 7. Граблі

0. **`AreaSidebar` мусить мати `min-w-0`** — інакше друга колонка не влазить у
   свою ж ширину. Flex-елемент за замовчуванням має `min-width: auto`, тобто
   відмовляється стискатися нижче min-content свого вмісту: щойно в area
   з'явилося щось широке (міні-місяць календаря — сітка 7×28px плюс три вкладені
   відступи), колонка розпирала себе до 236px замість відведених 225 і виїжджала
   за праву межу шела, а `overflow-hidden` зовнішнього `Sidebar` цю смугу
   зрізав. Симптом оманливий: виглядає, ніби «вміст з'їхав праворуч і сховався за
   лінією», хоча насправді за лінією опинилась уся колонка — включно з кнопкою на
   `w-full`, яка чесно займала 100% завеликого контейнера. Спіймано в браузері
   2026-09-07 на календарі; без `min-w-0` та сама пастка чекала б на списку
   розмов у чаті й на будь-якому довгому лейблі.

   **Наслідок для вмісту area — ОДИН інсет, а не нуль.** Спокуса після цієї
   граблі — зняти падінги взагалі (`px-0` на групі) і віддати блоку всю ширину.
   Так робити не варто, і це теж перевірено оком: міні-місяць уперся в обидві
   стінки, а плитка вибраного дня легла прямо на межу колонки. Правильна мета не
   «на всю ширину», а **вирівняно з рештою пунктів**: стокові `p-2` групи дають
   ті самі 8px, з якими стоять `SidebarMenuButton` вище й нижче, тож блок
   потрапляє з ними в одну вертикаль.

   Прибирати треба **вкладені** відступи, а не єдиний зовнішній: у першій версії
   міні-місяця їх було три (група 8 + мій `px-1` на контенті 4 + власний `p-2`
   календаря 8 = 20px з боку), і саме вони не давали сітці 7×28px влізти в 225px.
   Тепер лишився один: `SidebarGroup` без класу, `Calendar className="p-0"` і
   `classNames={{ root: 'w-full' }}` — саме `classNames`, бо корінь реєстрового
   `Calendar` отримує `w-fit` через нього, і клас із `className` програє йому в
   CSS-порядку. Виміряно: сітка `57→265`, кнопка «Today» `57→265`, пункт
   «Week» `57→265` — три різні компоненти в одну лінію.

1. **Кожне перевизначення геометрії кнопки рейлу треба дублювати з модифікатором
   `group-data-[collapsible=icon]:`.** `sidebarMenuButtonVariants` містить
   `group-data-[collapsible=icon]:size-8!` і `:p-2!`, а голі `size-9!`/`p-0!` їм НЕ
   конкуренти: модифікатори різні, тож tailwind-merge лишає обидва правила, і в
   згорнутому стані кнопка отримує чужий розмір із чужим падінгом. Вміст на всю
   кнопку (бренд-плитка, аватар) тоді стискається, з'їжджає вправо і обрізається
   `overflow-hidden` самої кнопки; іконки симптому не показують — вони у звужений
   бокс якраз влазять, тому видно лише на плитці й аватарі. Геометрія зібрана в
   `RAIL_BUTTON`, щоб правило не розповзалось.

   Там же — чому розмір іконок рейлу задає саме `[&_svg]` на кнопці, а не клас на
   самій іконці: селектор нащадка специфічніший за клас на елементі, тож перебити
   його «на місці» можна лише через `!`. Одне правило на весь рейл — і піктограми
   area, і знак у бренд-плитці.

   Побічне спостереження з тієї ж перевірки: **`p-2` і `w-full` із варіанта в рядку
   лишаються** — tailwind-merge не вважає їх конфліктом для `p-0!` / `size-8!`, бо
   важливість різна. У CSS `!important` усе одно виграє, і це рівно та причина, через
   яку реєстр ставить `!` у таких перевизначеннях; покладатись на дедуплікацію тут
   не можна, важливо лише щоб класи з `!` стояли пізніше.

2. **Блок ідентичності в дропдауні профілю мусить лежати в `DropdownMenuGroup`.**
   `DropdownMenuLabel` = `MenuPrimitive.GroupLabel`, і Base UI без групи-батька падає в
   рантаймі (`MenuGroupContext is missing`). У блоці `nav-user` реєстру він лежить прямо
   в `DropdownMenuContent` — так можна в Radix, не в Base UI. Заодно це семантично
   правильніше: ідентичність підписує групу особистих дій, а не висить над меню.
3. **Tooltip у рейлі мусить бути `{ children, hidden: isMobile }`.** Реєстровий
   `SidebarMenuButton` показує tooltip лише при `state === 'collapsed'`, а
   `useSidebar()` віддає стан ЗОВНІШНЬОГО сайдбара — тобто при розгорнутій панелі
   підказки не було б, хоча підписів у рейлі не видно НІКОЛИ. Спред `{...tooltip}`
   у компоненті йде після `hidden`, тому перевизначення легальне
   (`libs/ui/src/components/ui/sidebar.tsx`). На мобільному підказка вимкнена —
   там смуга в `Sheet` поруч із панеллю, і тапати нічого не мішає.
4. **`w-[...]!` і `w-auto` на вкладених сайдбарах обов'язкові**: `collapsible="none"`
   рендерить `w-(--sidebar-width)`, тобто без перевизначення обидві колонки були б
   на всю ширину блоку.
5. **`useParams({ from })` бере ID роуту, а не URL** — і його TS перевіряє. Після
   переносу гілки під `/workspace` довелось правити `from: '/app/users/$userId'` →
   `from: '/app/workspace/users/$userId'` (`/app` у префіксі — це `id: 'app'`
   pathless-роуту).
6. **`Crumb.to` у `PageBreadcrumbs` типізований як `string`**, тому крихти
   компілятор НЕ перевіряє. При переносі URL їх треба правити вручну — на відміну
   від `Link to` і `useParams({ from })`, які падають самі.
7. **Один `SidebarProvider` на обидві колонки.** Другий провайдер = другий cookie і
   зламаний Cmd+B.

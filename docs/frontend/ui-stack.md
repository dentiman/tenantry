# UI-стек фронтендів

Довідник поточного стану. Відповідає на питання «як у нас зроблений UI і за якими правилами
його продовжувати». Звідки брати новий компонент — `ui-registry.md`; як ми до цього стану
дійшли — `ui-migration-history.md`.

Стан на 2026-08-26. Обидва фронти (`apps/web`, `apps/platform-web`) на одному стеку;
спільний код — у `libs/ui`.

---

## 1. Стек

| Шар       | Рішення                                                       |
| --------- | ------------------------------------------------------------- |
| Примітиви | **shadcn/ui на Base UI**, стиль `base-nova`, CLI 4.19.0       |
| CSS       | Tailwind CSS 4 (`@theme inline`, `@custom-variant dark`)      |
| Іконки    | `lucide-react`, per-icon імпорти                              |

| Шрифт     | Inter (`@fontsource-variable/inter`)                          |

Примітиви **вендоряться** (код лежить у репо, не в `node_modules`) — це модель shadcn, а не
обхід. Оновлення — `shadcn diff <name>` у теці пакета.

## 2. `libs/ui` — спільний шар обох фронтів

Source-only workspace-пакет `@saas-skeleton/ui` (той самий тип, що `libs/i18n` і
`libs/contracts`: без білда, консюмер компілює джерела). Резолюція — через `exports`-мапу
`package.json`, тому окремих `paths` у застосунку не потрібно.

### Що в пакеті

```
libs/ui/src/
  styles.css                  ЄДИНА тема обох фронтів (:root/.dark, @theme inline, @layer base)
  components/ui/**            вендорені примітиви реєстру (33)
  components/data-grid/**     грід (generic по TFilters/TItem)
  components/form/**          FormTextField/FormPasswordField/FormSelect + server-error
  components/page-header-slot.tsx   портал у хедер layout-а
  components/page-breadcrumbs.tsx   крихти через цей портал (CrumbTrail — розмітка без порталу)
  components/page-header.tsx        хедер сторінки: крихти + підзаголовок + дії
  components/theme-switcher.tsx
  components/user-identity.tsx
  api/api-error.ts            нормалізація конверта ApiError
  lib/{utils,page-items,format,error-toast}.ts
  hooks/use-mobile.ts
  components.json             конфіг shadcn CLI пакета
```

### Що лишається в застосунку

Тільки те, що справді різне: `app-layout` (навігація й бренд), `toast-host` (у web два регіони
тостів, у platform-web один), `api/http-client`, `i18n/index`, `lib/init-auth`, стори, роутер і
весь домен. Плюс `FormPhoneField` + `phone/**` — він generic, але тягне `libphonenumber-js` і
`country-flag-icons`, які потрібні лише `apps/web` (див. відкриті питання в `README.md`).

### Правило i18n у пакеті

Пакет імпортує **`import i18n from 'i18next'`** — дефолтний синглтон, який конфігурує кожен
фронт (`i18n.use(initReactI18next).init(…)`, не `createInstance`). Тому пакет не знає про
неймспейси застосунку, а спільні ключі приходять із `libs/i18n`.

### Підключення в застосунку

`index.css` застосунку зводиться до трьох рядків:

```css
@import 'tailwindcss';
@import '@saas-skeleton/ui/styles.css';
@source '../../../libs/ui/src';
```

Без `@source` Tailwind **не бачить класи пакета** — утиліти просто не генеруються.

Аліас `@/*` (локальний код застосунку) дублюється у `tsconfig.json` **і** `vite.config.ts` —
vite не читає tsconfig paths.

### Імпорти всередині пакета

Конвенція — **самопосилання** `@saas-skeleton/ui/…` (документований монорепо-режим shadcn:
`aliases.ui` у `components.json` вказує на workspace-пакет, і CLI сам переписує імпорти в
доданих файлах). Зараз так зроблено в 41 файлі; три файли, що переїхали останнім ходом
(`page-breadcrumbs.tsx`, `lib/error-toast.ts`, `lib/format.ts`), використовують відносні
шляхи — розбіжність відома, див. відкриті питання.

## 3. Тема

Одна на обидва фронти — `libs/ui/src/styles.css`. Палітра перенесена з
[HeroUI v3](https://github.com/heroui-inc/heroui/blob/v3/packages/styles/themes/default/variables.css)
у семантичну структуру shadcn. Ми не підключаємо HeroUI і не копіюємо його компонентні
рецепти: беремо лише модель canvas → surface → overlay, zinc-нейтралі, слабкі межі та
багатошарові тіні. У `components.json` лишається `baseColor: "neutral"`: це метадані
генератора, а не назва runtime-теми; фактичну палітру задають CSS-токени.

| Параметр    | Значення                                                                                          |
| ----------- | ------------------------------------------------------------------------------------------------- |
| Нейтралі    | zinc, hue ≈ 286, chroma 0…0.014 — майже ахроматичні, без синьої «сталі»                           |
| Світла тема | canvas `oklch(0.9702 0 0)`; card/popover/fields білі; поля мають мʼяку тінь і видиму zinc-обводку |
| Темна тема  | сирий чорний canvas `oklch(0.12 0.005 285.823)`; card/popover `oklch(0.2103 0.0059 285.89)`       |
| `--radius`  | `0.625rem`                                                                                        |
| Тіні        | HeroUI-подібні: слабка `surface` для полів/панелей, глибша `overlay`; у dark без зовнішнього glow |
| Шрифт       | Inter (`@fontsource-variable/inter`)                                                              |
| Перемикач   | `attribute="class"`; storageKey `saas_theme` / `saas_platform_theme`                              |

### Три свідомі відхилення від стоку

Зафіксовані рішенням користувача — **не переглядати без запиту**:

1. **`--primary` (і `--ring`) — точний accent HeroUI v3.** В обох темах
   `oklch(0.6204 0.195 253.83)` із `oklch(0.9911 0 0)` foreground. Destructive також бере
   точні HeroUI danger-пари: `oklch(0.6532 0.2328 25.74)` у light і
   `oklch(0.594 0.1967 24.63)` у dark. Hover обчислюється так само, як у HeroUI:
   90% semantic color + 10% його foreground. Фокус синій, бо `--ring` = `--primary`.
2. **Метрика однорядкових контролів — 36px.** `default` кнопка, `input`, `select` та
   `input-group` мають 36px; кнопки `sm` 32, `xs` 28, `lg` 40, іконкові — `size-7/8/9/10`.
   `textarea` багаторядкова і лишається `min-h-16`. Горизонтальні відступи полів — `px-3`.
   Фокус form controls — суцільний `ring-1` кольору `--ring` без відступу; error-state
   лишається помітнішим `ring-2`. Кнопки й навігаційні примітиви зберігають `ring-2`.
3. **Опційна повна округлість кнопок.** `Button radius="full"` дає pill-форму текстовій
   кнопці, а разом із `size="icon*"` — геометрично круглу icon-only кнопку. Дефолт
   `radius="default"` зберігає стандартний `rounded-lg` / `rounded-md` і сумісність усіх
   наявних викликів.

Саме ці три відхилення — причина, чому `button`/`input`/`select`/`input-group` лишаються
з коментарем «ЛОКАЛЬНА ПРАВКА реєстру». **Нову висоту не задавати класом на місці
використання** — вона дефолтна. Для компактних toolbar-ів `Input`, `SelectTrigger` і `Button`
мають opt-in `size="sm"` (32px); звичайні поля форм лишаються 36px.

**Хедер шела — суцільна зона 32px.** Це не виняток із метрики 36px, а її застосування: у
рядку заввишки 56px усе стоїть пліч-о-пліч — `SidebarTrigger`, тулбар сторінки, головна дія,
дзвінок, перемикач теми — і будь-який контрол повної метрики стає єдиним вищим елементом
рядка. Тому в зоні дій `PageHeader` кнопки йдуть `size="sm"` / `size="icon-sm"`, а дзвінок
приведений із стокового `icon` до `icon-sm` (2026-09-08). Таби отримали для цього власний
`size="sm"`: міряється ЖОЛОБ (він і є видимий контур контрола) — 32px, рівно як `h-8` кнопки,
а тригер усередині вираховує висоту сам і стискається разом із ним до 25px.

`--success` / `--warning` (+`-foreground`) — **наше розширення**: у shadcn таких ролей немає.
Це нейтрально сумісні emerald/amber; lightness скоригований так, щоб дрібний текст у мʼяких
`bg-*/10` badge мав контраст не нижче 4.5:1. Варіанти — у cva `ui/badge.tsx`.
`--destructive-foreground` доповнює суцільну semantic pair і має різне значення в light/dark.

### Межа між темою і компонентом

- **У темі:** семантичні кольори та їхні `*-foreground` пари, шрифт, базовий radius і ті
  значення, які справді перемикаються між light/dark або брендами.
- **У рецепті компонента (`cva`/класи):** висота, padding, розмір іконки, геометрія focus ring,
  popup placement/width, анімація та поведінкові варіанти.
- Тому висота `SelectTrigger` — у recipe `select.tsx`, а не в `--select-height` теми.
  Дефолт — `h-9`; компактний toolbar використовує спільний opt-in `size="sm"`, а не локальні
  height-класи чи select-специфічний токен.

### Семантична мапа: роль у UI → токен

| Роль                                         | Токен                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Фон сторінки                                 | `bg-background`                                                                                   |
| Сайдбар                                      | `bg-sidebar` (+ `--sidebar-border` / `--sidebar-accent`)                                          |
| Хедер                                        | `bg-background` + `border-b`                                                                      |
| Контентна картка                             | `bg-card text-card-foreground shadow-sm` без зовнішнього border                                   |

| Вибраний / активний стан                     | **той самий `bg-accent`, що й наведення** — стан показує ЗНАК (`text-icon-strong`), а не другий відтінок фону. Окремого «сильнішого» токена в темі немає навмисно |

| **Службова іконка** (шеврон, адорн поля)     | `text-icon-muted` — нижній рівень (`--c-icoTer`)                                                   |
| Небезпека: текст / суцільна заливка / мʼяка  | `text-destructive` / `bg-destructive text-destructive-foreground` / `Badge variant="destructive"` |
| Успіх, попередження                          | наше розширення `--success` / `--warning`                                                         |

| Подія календаря (заливка / смужка типу / текст) | палітра подій Notion: `bg-event-<колір>-bg` / `bg-event-<колір>-line` / `text-event-<колір>` — **не semantic-роль**, а іменований колір; мапінг «тип події → колір» живе в `apps/web/src/components/calendar/event-kind.ts` |
| Вихідні в сітці календаря                    | `bg-calendar-weekend`                                                                             |

| Бренд                                        | `text-primary`                                                                                    |
| Посилання в тексті                           | `text-primary underline underline-offset-4`                                                       |
| Присутність offline                          | `bg-muted-foreground/40` (`bg-muted` — світлий фон, крапка була б невидима)                       |

## 4. Конвенції коду

- **Композиція замість compound-неймспейсів**: `DialogContent`/`DialogTitle`,
  `TableHead`/`TableCell`, `DropdownMenuItem` — а не `Dialog.Content`.
- **Підміна елемента — `render={<Button/>}`** (Base UI), **не** `asChild`.
- **Кустарних обгорток над примітивами не заводимо.** Медіа-обʼєкт — `Item*`, порожні стани —
  `Empty*`, індикатор на аватарі — `AvatarBadge`, набір фільтрів — `ToggleGroup`, бокова
  панель — `Sheet`, навігація — `Sidebar*`. Якщо примітив є в реєстрі, свій не пишемо.
  Винятків два, і обидва — там, де реєстр порожній: `FileDropzone` (дропзони немає; оболонка
  все одно складена з `Empty` + `Button`) і **`CopyToClipboard`** (`libs/ui/src/components/`,
  примітива копіювання в `@shadcn` немає — перевірено пошуком).
- **Копіювання в буфер — `CopyToClipboard`** (`@saas-skeleton/ui/components/copy-to-clipboard`):
  обгортає видиме значення кнопкою, копіює переданий `value` і показує підтвердження **у
  підказці на місці**, а не тостом — копіювання це локальна дія над конкретним рядком, а два
  наявні регіони тостів (помилки API, живі сповіщення) третій клас подій не приймають. Патерн
  GitHub/Linear/Stripe: у спокої підказка каже «Copy», після кліку та сама підказка
  перемикається на «Copied» (тултіп КЕРОВАНИЙ: `open = наведення || скопійовано`, інакше
  клавіатурний клік не показав би підтвердження). Сам запис — нативний `navigator.clipboard`
  плюс легасі-фолбек `execCommand` у хуку `hooks/use-copy-to-clipboard`: фолбек потрібен НЕ
  заради старих браузерів, а заради незахищеного контексту — на тестовому проді (http на
  IP:port) `navigator.clipboard` просто відсутній. Пакети (`copy-to-clipboard`,
  `react-copy-to-clipboard`, `usehooks-ts`) відхилені: важать більше за сам хук і зводяться до
  тієї ж пари API. Перевірка в автоматизації обмежена: у ФОНОВІЙ вкладці
  (`document.visibilityState === 'hidden'`) Chrome не резолвить `writeText` взагалі — промис
  висить, і стан «Copied» не настає; це третя грабля цього роду після drag-жестів і
  `ResizeObserver`.
- **Правки вендореного коду позначаються коментарем «ЛОКАЛЬНА ПРАВКА реєстру»** — інакше
  наступне оновлення тихо їх знесе. Перед ним запускати `shadcn diff <name>`. Реєстр правок —
  §6.
- **Вкладеність HTML.** `AlertDialogDescription` / `ItemDescription` уже є `<p>`, а
  `Item render={<button/>}` уже є `<button>` — не класти всередину ще один абзац або кнопку
  (React пише про це в консоль).
- **Частини, які вимагають батька, Base UI перевіряє в РАНТАЙМІ, а не типами.**
  `DropdownMenuLabel` — це `MenuPrimitive.GroupLabel`, і без `DropdownMenuGroup` навколо він
  падає з `MenuGroupContext is missing` уже в браузері; те саме стосується інших `*GroupLabel`
  і радіо-частин. Це головна пастка при переносі блоків із реєстру: shadcn-блоки писались під
  Radix, де `DropdownMenuLabel` лежить прямо в `DropdownMenuContent` (див. `nav-user`), і
  компілятор різницю не бачить — **кожен перенесений дропдаун треба відкрити руками**.
- **Іконки** — `lucide-react`, per-icon імпорти; у компонентах через
  `data-icon="inline-start"|"inline-end"` **без** класів розміру (компонент керує сам).
- **Неосновні button-actions** — `variant="secondary"`; `outline` лишається частиною
  дизайн-системи, але не є стандартним cancel/load-more/edit action у продуктових екранах.
- **Icon-only X-close/clear/remove** — `radius="full"`: це стосується `Dialog`, `Sheet`, toast,
  notification card та Combobox. Розмір як і раніше задається через `size="icon*"`.

### Форми

`useController` → `Field` + `FieldLabel htmlFor` + `Input id` (`useId()`) + `FieldError`.
Стан помилки — `data-invalid` на `Field` і `aria-invalid` на контролі; підказка —
`FieldDescription` усередині `Field`. Серверні помилки — `applyServerError(error, form)`:
`fieldErrors` → `setError` по імені поля, решта → `errors.root.server`. Тому форми **мусять
мати повні `defaultValues`** (звірка йде через `getValues`).

`FormSelect` **мусить** діставати `items` — без мапи value→label Base UI малює в тригері сире
значення (`USER` замість `User`).

**Дата в інтерфейсі — `yyyy-MM-dd`** (рішення 2026-09-09). Один стандарт на весь скелетон:
`formatDate`/`formatDateTime` у `libs/ui/lib/format.ts` (грід, картка, мета-рядок) і `DatePicker`
(дефолт `format="iso"`, плейсхолдер-маска `yyyy-MM-dd`). Причини не декоративні: локальний формат
`03-04-2026` не має однієї відповіді, ISO має сталу ширину в будь-якій мові, і побачене на екрані
збігається з тим, що поїде в експорт, лог і URL. **Перевизначає це КОД конкретного екрана**
(`DatePicker format="long"` там, де дата — головний зміст), а не юзер у налаштуваннях: формат дати
не стає перемикачем в адмінці. Виняток — **календар**: `apps/web/src/lib/calendar-date.ts` лишається
на своїх людських формах («Wednesday, September 9», «5 minutes ago»), бо там дата не дані, а зміст
екрана.

**Поле дати — `DatePicker`** (`libs/ui/components/date-picker.tsx`), нативний `<input type="date">`
не використовуємо: його малює браузер, тобто вигляд, порядок полів і поповер не належать нашій темі.
Значення — рядок `yyyy-MM-dd`, а не `Date`: цивільна дата не має зони, і `Date` щоразу приносить
зсув на сусідню добу. Ввід із клавіатури — головний шлях (`lib/date-value.ts` розбирає ISO, порядок
поточної локалі, дату без року, сам день, вісім цифр і місяць словом), календар — другий;
нерозпізнаний ввід мовчки відкочується до останнього валідного значення, а не заводить другий канал
помилок поруч зі схемою. Стенди — `/playground/vertical-form` і `/playground/inline-form`.

### Розкладка

- **Шел `apps/web` — ДВА рівні навігації** (смуга іконок area + колонка активної area):
  окремий документ [`app-shell.md`](app-shell.md), реєстровий предок — `sidebar-09`.
  Термінологія (`AppRail` / area / `AreaSidebar`), прив'язка до роутингу і метрики
  розкладки — там.
- **Шел `apps/platform-web` — патерн `sidebar-07`** реєстру: бренд-плитка + назва +
  підзаголовок у `SidebarHeader`, профіль юзера з дропдауном у `SidebarFooter` (`UserIdentity`
  із `libs/ui`), у хедері лише `SidebarTrigger` + дзвінок + перемикач теми.
  `collapsible="icon"` — згорнутий сайдбар стає смугою іконок 48px. Другого рівня там немає
  навмисно: одна area, і рейл був би декорацією.
- **Хедер сторінки — через портал.** Сторінка рендерить `PageHeader` (або мінімальний
  `PageBreadcrumbs`), а `PageHeaderPortal` телепортує розмітку в слот хедера layout-а. Портал
  міняє лише місце в DOM — дерево React те саме, тож `Link` роутера, контексти сторінки і
  головне — її СТАН лишаються доступні: кнопка в `actions` відкриває модалку, що живе у
  сторінці, без підняття стану вгору. Новий вміст хедера додається без зміни контракту
  layout-а.
- **Ідентичність сторінки живе рівно в одному місці — у хедері.** До 2026-09-08 списки мали
  заголовок ДВІЧІ: крихта «Customers» у хедері й `<h1>Customers</h1>` першим рядком контенту.
  Тепер `<h1>` зі списків прибрано, підзаголовок і головна дія переїхали в `PageHeader`, а
  контент починається одразу з тулбара фільтрів — той належить ТАБЛИЦІ, а не сторінці, і при
  десятку фільтрів у 56px хедера не вміститься. Шапка СУТНОСТІ (картка юзера, кастомера,
  тенанта) лишається в контенті: там заголовок несе аватар, статуси і набір дій — це не назва
  сторінки, а сама сутність. **Секції налаштувань пройшли той самий шлях**: `ContentSection`
  втратив пропси `title`/`description` (їх дублювали крихти «Settings › General»), а разом із
  заголовком пішла й лінійка `Separator` — відділяти стало нічого. Компонент лишився як
  метрика розділу, щоб ширини не розповзлись по девʼятьох сторінках.
- **Підзаголовок — ОДИН рядок із крихтами**, за вертикальним роздільником, `muted`. Другий
  рядок під ними був спробуваний і знятий того ж дня: хедер має фіксовану `h-14`, і два рядки
  в ньому або зсувають крихти з центру (ламаючи неперервну лінію, яку складають три `h-14` —
  шапка рейлу, шапка колонки, хедер), або мусять висіти `absolute` у 18px, що лишаються знизу.
  Обидва варіанти платять розкладкою за текст, який є довідкою, а не заголовком. В одному
  рядку ієрархія читається сама: «де я» (крихти) — роздільник — «що це» (пояснення, `muted`).
  Опис іде `text-muted-foreground/70` — на тон нижче другого рівня тексту: у темі рівнів два,
  а довідка мусить лягти нижче за них обидва. Третій токен заради цього НЕ заводимо — рівень
  на одного споживача це виняток зі шкали, а не її щабель (той самий аргумент, що свого часу
  зняв `--accent-strong`).
  Роздільник ВЕРТИКАЛЬНИЙ, бо крапкою (`›`) вже розділені крихти між собою; він слабший за
  межу поверхні (`bg-border/60`) і опущений на 1px (`translate-y-px`) — line-height лишає над
  великими літерами більше повітря, ніж під ними, тож геометрично центрована риска читається
  задертою. Пояснення гнеться першим (`min-w-0 truncate`), крихти не стискаються ніколи.
- **Ліва зона хедера — не обовʼязково крихти.** `PageHeader` приймає замість них довільний
  `children`, і календар цим користується: там «де я» виражає ПЕРІОД (`Today ‹ September 2026 ›`),
  яким ті самі кнопки й керують, а назва розділу і так стоїть у колонці area. Разом із періодом
  у хедер переїхали перемикач виглядів і `New event`, тож на сторінці лишилась ЛИШЕ сітка — і
  вона забрала звільнені 4rem висоти. Це і є практичний доказ, навіщо саме портал: тулбар
  керує станом сторінки (`goto`, `openDraft`) і дістає його як звичайна дитина, без підняття
  вгору.
- **Слот у хедері ОДИН.** Два портали промалюються в один вузол ПОРУЧ — це не помилка React, а
  рівно те, про що його попросили. Тому на екрані має бути рівно один `PageHeader` **або**
  `PageBreadcrumbs`; провайдер тримає лічильник активних порталів і кричить у консоль на
  другий, називаючи його `label`-ом.
- **Межі шасі — один токен.** Хедер контенту, шапки обох навігаційних колонок і права межа
  сайдбара беруть `--border` без ослаблення: три `h-14` складають одну неперервну лінію через
  усе вікно, і сегмент на `/70` її розривав (знято 2026-09-08).
- **Хедер layout-а — sticky glass surface.** Він закріплений зверху в єдиному scroll-контексті
  сторінки; контент проходить під напівпрозорим `background` із `backdrop-blur`. Не додавайте
  `overflow-y-auto` внутрішньому контейнеру сторінки без явно обмеженої висоти — це створить
  другий scroll-контекст і порушить sticky-поведінку.
- **Верхній відступ контенту — 16px**, бічні та нижній — 24px. Це тримає заголовки й primary
  actions ближче до sticky-хедера, не стискаючи основний контент сторінки.
- **Сторінка списку**: назва, підзаголовок і головна дія — у `PageHeader` (хедер layout-а);
  контент починається з рядка тулбара над таблицею (пошук і фільтри ліворуч, `Reset`
  зʼявляється лише коли є що скидати; проп `actions` праворуч) → таблиця → пагінація.
  Попередня розкладка з shadcn-admin (рядок шапки всередині контенту) знята 2026-09-08 —
  вона дублювала назву сторінки, яка вже стоїть у крихтах.
- **Список — полотно, а не картка на полотні.** Роут списку йде в режимі `bleed`
  (`docs/frontend/app-shell.md` §5.4), а `Grid.Table` — у `surface="flush"`: ні рамки, ні
  `Card`, таблиця впирається в краї вікна. Крайні комірки при цьому беруть поле шела (24px)
  через `[&_tr>*:first-child]:pl-6` — інакше текст першої колонки читався б приклеєним до
  краю, а вміст таблиці розʼїхався б із крихтами хедера, які стоять рівно на цій вертикалі.
  `surface="card"` лишається для таблиць ВСЕРЕДИНІ сторінки, де вони справді один із блоків.
- **Тулбар має ту саму розвилку: `panel` і `band`.** `panel` (дефолт) — плаваюча плитка
  `w-fit rounded-lg bg-secondary` над таблицею; `band` — смуга на всю ширину без скруглень, на
  `bg-sidebar`. Бокове поле смуги — `px-4`, а не `px-6`: перший елемент (метрика «Total») несе
  власні `pl-2`, і разом виходить рівно 24px, тобто та сама вертикаль, що в комірок таблиці.

  **Фон у них РІЗНИЙ, і це не недогляд, а різна роль.** Плитка — контрол над полотном, їй
  належить виділятись, тому `secondary` (найконтрастніша нейтраль теми). Смуга — шасі: вона
  йде від краю до краю, і `secondary`, розтягнутий на всю ширину, кричав. Тому `sidebar` —
  токен обраний за роллю: та сама поверхня, що ліва колонка, тобто обрамлення робочої області.
  У темряві він до того ж дорівнює `card`, тобто шапці календарної сітки (`#202020`), тож усе
  обрамлення екрана виявляється одного тону; у світлі теми розходяться (`card` білий,
  `sidebar` — 0.9524 проти полотна 0.9702), і саме `sidebar` дає ту делікатну різницю, яка
  відділяє смугу від полотна, не перетягуючи увагу.

  Обидва варіанти живуть поруч, і це свідомо: `band` прив'язаний до `bleed`-роуту, а в
  `padded`-сторінці смуга впреться в поля і виглядатиме обрізаною. Перемикання — один проп;
  повернення до плитки не коштує нічого, крім самого пропа.

  **Лінію під смугою малює обгортка сторінки, а не тулбар** — вона розділяє смугу й таблицю,
  тобто належить компонуванню екрана, а не компоненту фільтрів, і бере той самий `--border`,
  що межі шела (`docs/frontend/app-shell.md` §5.4).
- `SidebarInset` реєстру САМ рендериться як `<main>` — не вкладати всередину ще один.

### Прокрутка: оверлейна смуга, що згасає

Еталон поведінки — **список чатів Telegram Web**: смуги не видно, доки нею не користуються;
вона зʼявляється на прокрутку або наведення і повільно згасає; місця у вмісту не забирає.
Реалізує це `ScrollArea` з `libs/ui` (Base UI). Ставити нативний `overflow-y-auto` там, де
скрол бачить людина, більше не треба.

**Чому не рецепт Telegram.** Знято з їхньої живої сторінки 2026-09-09:

```css
.custom-scroll { scrollbar-color: transparent transparent; scrollbar-width: thin;
                 transition: scrollbar-color .3s; }
.custom-scroll:hover, .custom-scroll:focus-within { scrollbar-color: var(--color-scrollbar) transparent; }
.chat-list { overflow: hidden scroll; padding-inline-end: max(.5rem - var(--scrollbar-width), 0px); }
```

Тобто вони фарбують НАТИВНУ смугу в прозоре. Три речі, яких цей підхід не дає:

1. **Оверлея немає.** `overflow: scroll` резервує місце завжди, а «накладання» імітується
   відʼємним падінгом — ширину все одно відібрано, просто в іншого відступу.
2. **Плавність половинчаста.** `transition: scrollbar-color` анімується у Firefox; у Chrome
   псевдоелементи `::-webkit-scrollbar-*` переходів не підтримують — там перемикання різке.
3. **Тригер лише `:hover`.** «Показати під час прокрутки» нативна смуга не вміє: про факт
   прокрутки CSS не знає.

Base UI ховає нативну смугу і малює свою звичайним `div` — звідси все три: `absolute` дає
справжній оверлей, `opacity` анімується скрізь, а `data-scrolling` / `data-hovering` дають
обидва тригери.

**Асиметрія тривалостей — це правило, не смак.** Поява 75–100 мс, згасання 500 мс: поява
супроводжує дію людини, і затримка в ній читається як гальмування; згасання дії не
супроводжує, і різке зникнення читається як блимання. Технічно асиметрію дає те, що
`transition-duration` береться зі стану, В ЯКИЙ елемент переходить: у станових класах вона
коротка, у базовому — довга. Плюс сам Base UI тримає `data-scrolling` ще 500 мс після зупинки
(`SCROLL_TIMEOUT`), тож повний хвіст ≈ секунда.

**`pointer-events` обовʼязкові.** Невидима смуга лежить поверх вмісту біля правого краю; без
`pointer-events-none` у спокої останні 8px кожного рядка (у календарі — остання колонка дня)
мовчки перестали б клікатись.

**Вісь — `vertical` за замовчуванням.** Viewport Base UI отримує `overflow: scroll` по обох
осях, тож навіть без видимої смуги вміст лишається зсувним убік трекпадом. У вузьких
поверхнях це чистий баг: зайві пікселі там приходять не з розкладки, а з примітивів (див.
`ui-known-issues.md` UI-2). Тому примітив глушить горизонталь сам — інлайновим стилем на
viewport, бо клас `overflow-x-hidden` не переб'є інлайновий `overflow: scroll` від Base UI.
`axis="both"` вмикає горизонталь і другу смугу — для справді широкого вмісту.

**Товщина — `size`.** `default` (8px) для панелей, сіток і діалогів; `lg` (10px) для
ГОЛОВНОГО скролу сторінки. Різниця в один крок шкали — навмисно: перша спроба дала `lg`
12px, і смуга почала читатись як елемент інтерфейсу, а не як службовий індикатор. Оверлейна
смуга лежить ПОВЕРХ вмісту, тож кожен зайвий піксель вона забирає не в розкладки, а в уваги. Різниця не декоративна: та смуга одна на екран, нею користуються
найчастіше, і в неї немає сусіда, з яким треба збігтися за розміром — та сама логіка, чому в
будь-якій ОС смуга вікна товща за смугу випадайки.

**Висота — через flex, а не відсотки.** Корінь `flex flex-col`, viewport `min-h-0 flex-1`.
Обидві очевидні альтернативи спробувані й відкинуті на стенді `/playground/dialog`:

| Спроба                             | Що ламається                                                                                                                                                          |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `h-full` (реєстровий `size-full`)  | Мовчки стає `height: auto`, коли предок обмежений `max-height`, а не `height`: відсоткова висота розвʼязується проти SPECIFIED висоти, а ланцюг `flex-1` передає розмір, але не його ВИЗНАЧЕНІСТЬ. У діалозі viewport виріс на 1953px замість 602, скрол не ввімкнувся, Base UI не побачив переповнення і не змонтував смугу, а `overflow-hidden` кореня відрізав половину форми |
| `absolute inset-0`                 | Ламає протилежний бік: корінь лишається без вмісту в потоці, `flex-1` у контейнері з `max-height` дає йому нуль — діалог схлопується до хедера з футером                 |

Flex не має ні тієї, ні іншої проблеми: корінь отримує used height ззовні і РОЗПОДІЛЯЄ її
своїм items, визначеність specified-висоти тут не потрібна взагалі. Цінне тут не саме
виправлення, а те, що обидві помилки видно ЛИШЕ в діалозі — у сітках і панелі того ж дня
`h-full` працював, бо там ланцюг починається з `h-svh`. Стенд `/playground/dialog` існує
рівно для цього.

**`Content` обовʼязковий — і саме його немає в реєстровому shadcn.** Base UI перераховує
переповнення на прокрутку і на resize VIEWPORT-а. Коли вміст міняє висоту, а viewport
лишається того ж розміру — а це рівно перехід між роутами всередині шела, — жоден із цих
каналів не спрацьовує. Симптом: пішов з високої картки юзера на короткий грід і смуга
лишилась висіти, хоча скролити нічого; зайшов на грід одразу — смуги немає. Частина
`ScrollAreaPrimitive.Content` вішає на обгортку вмісту `ResizeObserver` і кличе
`computeThumbPosition()`, тобто закриває саме той канал. Класи вмісту йдуть у
`contentClassName`, а не в `viewportClassName`: flex-контейнером для елементів має бути
їхній ПРЯМИЙ предок, а це тепер `Content`.

RO — канал єдиний, тому шел має другий, незалежний: `scrollTo({ top: 0 })` на зміну
`pathname` (`app-shell.tsx`). Він і так потрібен — доки скролило вікно, позицію скидав
браузер, а тепер ніхто, — і заразом гарантує подію `scroll` при переході з довгої сторінки
на коротку.

**Керована прокрутка — через `viewportRef`.** Скролиться viewport Base UI, а не корінь, тому
`scrollTo` і автоскрол перетягування беруть саме його: `<ScrollArea viewportRef={scrollRef}>`.
`viewportClassName` — коли скролер мусить бути ще й flex-контейнером (сітка місяця).

Порядок переїзду — згори вниз; кожен рядок це заміна `overflow-y-auto` на `ScrollArea` з
`viewportRef` там, де прокруткою керує код.

Два наслідки переїзду головного скролу, які легко проґавити:

- **Хедер більше не `sticky`.** Він поза скролером, тож `sticky top-0 z-10` і напівпрозорий
  фон із `backdrop-blur` втратили сенс — під ним нічого не проїжджає. Фон став суцільним.
- **Координати `sticky` всередині сторінки зсунулись на висоту хедера.** `ActivityPanel`
  стояв на `lg:top-[4.5rem]` (хедер 3.5rem + відступ 1rem) — став `lg:top-4`. Будь-який
  новий `sticky` всередині контенту рахується від верху СКРОЛЕРА, а не вікна.

### Регіони тостів

два (сповіщення і помилки), у `apps/platform-web` один. **Позиції спільні для обох** — людина,
яка ходить між двома консолями, шукає повідомлення в тому самому куті:

| Що                         | Де                                                              |
| -------------------------- | --------------------------------------------------------------- |
| Помилки API                | **знизу праворуч**                                              |
| Живі сповіщення (web)      | **зверху праворуч під дзвінком**, зміщені вниз на висоту хедера |

### DataGrid

Публічний API — фабрика `createDataGrid<TFilters, TItem>()` на рівні модуля сторінки; повертає
компаунд-набір `Grid.Root` / `Grid.Filters` / `Grid.Toolbar` / `Grid.Table` /
`Grid.SelectionSummary` / `Grid.filter`. Повний контракт (фетчинг через проп `useListQuery`,
скидання вибору, headless escape hatches, wire-формат boolean-фільтрів) — у `CLAUDE.md`,
розділ про DataGrid; він не змінювався від міграції UI.

**Дата в комірці списку — `DateTimeCell`** (`@saas-skeleton/ui/components/date-time-cell`):
дата зверху, час під нею, кегль на щабель менший (`text-xs`), дві сходинки сірого — дата
`foreground/80`, час `muted-foreground`. Стандарт для КОЖНОЇ часової колонки обох фронтів
(`Created` у tenant Users/Customers і platform Tenants, `Created`/`Started`/`Completed` у
`/jobs`) — до нього те саме значення показувалось трьома способами: у частині гріді лише дата
(час губився), у `/jobs` — одним рядком `formatDateTime`. Два рядки замість одного не лише
через ширину: `2026-09-09 14:30` суцільним рядком читається як позначка з лога. `formatTime`
(тільки `HH:mm`) винесений із `formatDateTime` — 24-годинність лишається одним рішенням.

`Grid.Table isRowMuted={(item) => …}` — приглушений рядок «вимкненої» сутності (неактивний
юзер, кастомер поза `ACTIVE`). Приглушується ВЕСЬ рядок, а не колонка статусу: стан належить
запису, і око має ловити його розгорткою списку, не читаючи бейдж у кожному рядку. Інструмент —
`opacity-65`, а не `text-muted-foreground`: у рядку є текст, бейджі й
перемикач, у кожного власна палітра, і колірний токен подіяв би тільки на текст. Прозорість
кладеться на КОНТЕНТНІ комірки — чекбокс вибору і меню дій лишаються в повному тоні
(приглушується зміст запису, а не керування ним); інакше й не вийшло б — `opacity` на `<tr>`
перемножується на дітей, і повернути окремій комірці повний тон неможливо. Значення підбиралось
оком на темній темі: 75% там майже не читалось — приглушений текст і так світліший за
`foreground`, і чверть прозорості на ньому губиться.

`Grid.Table surface="card"` — опційна HeroUI-подібна поверхня: спільний `Card size="sm"`
дає radius/background/shadow, а прозора таблиця заповнює її без внутрішнього padding. Режим
`Table separator="inset"` малює горизонтальні separator-и через комірки й відступає лише саму
лінію на 12 px від обох країв. Режим використовується в tenant Users і platform Jobs grids.
Platform Tenants має ту саму композицію `Card + Table separator="inset"` вручну, бо цей список
не потребує DataGrid-фільтрів чи пагінації. `bordered` лишається backward-compatible дефолтом.

`Grid.Toolbar` — контекстна панель списку для business actions. У звичайному стані вона показує
`Total: N` і компактні фільтри, у selection-стані — `Selected: N`, передані сторінкою
bulk actions і Clear. Обидва стани накладені в одну CSS grid-комірку: неактивний невидимий,
але продовжує резервувати найбільші ширину й висоту, тому surface не стрибає при перемиканні.
Панель має `bg-secondary` без тіні й споріднена з `TabsList`; її Reset — доступна icon-only
кнопка (`aria-label` + `Tooltip`) з `radius="full"` і `ghost` hover. Нижчорівневий
`Grid.Filters` лишається для plain toolbar-ів без selection business logic.

Власний тип `SortDescriptor { column: string; direction: 'ascending' | 'descending' }` живе в
`data-grid/types.ts` і реекспортується з барелю — раніше він приходив із UI-бібліотеки.

## 5. Оновлення примітивів

`components.json` лежить **і в пакеті, і в кожному застосунку**. Межа така:

- запуск із `libs/ui` додає/оновлює спільні примітиви;
- запуск із `apps/web` або `apps/platform-web` додає сторінковий блок у застосунок;
- в app-конфігах `components`/`lib`/`hooks` локальні (`@/...`), а `ui`/`utils` і CSS теми
  вказують на `@saas-skeleton/ui`. Тому registry dependencies блоку не дублюють примітиви.

```bash
cd libs/ui
pnpm dlx shadcn@4.19.0 diff <name>   # побачити дельту апстріму
pnpm dlx shadcn@4.19.0 add <name>    # додати новий примітив

cd ../../apps/web
pnpm dlx shadcn@4.19.0 add @shadcn/<block> --dry-run
```

Перед прийняттям дифу — звірити з реєстром локальних правок (§6), інакше вони зникнуть.

**Що це коштує.** `pnpm dlx shadcn@4.19.0 diff <name>` на цих файлах тепер шумить сильніше — але
кожна правка позначена коментарем «ЛОКАЛЬНА ПРАВКА реєстру» з поясненням ЧОМУ, тож при оновленні
реєстру видно, що зберігати. Альтернатива — тримати шкалу знаків і накладки на місцях
використання — коштувала б дорожче: кожен новий екран мусив би про них памʼятати, а «забув
написати `text-icon`» не ловиться ні типами, ні лінтером.

Про `alignItemWithTrigger`: дефолт Base UI `true` — це macOS-поведінка, коли попап
«підіймається» так, щоб обраний пункт став на місце тригера. У формах адмінки це збиває.

Про глушник autofill: `[transition:…]` — це **shorthand**, і поруч зі стоковим
`transition-colors` вони конфліктують (перемагає порядок генерації утиліт, а не наміри). Тому
обидва склеєні в один: `background-color 5000000s, border-color 150ms, box-shadow 150ms`.

Єдиний легальний хардкод у вендореному шарі — `<span className="sr-only">Close</span>` у
`DialogContent` / `SheetContent`: правити означало б завести `useTranslation` у вендорений код.

## 7. Граблі, які варто знати наперед

- **Бекендні tsconfig-и НЕ мають підбирати фронтові ліби.** `include` у
  `apps/{api,platform-api,worker}/tsconfig*.json` перелічує `libs/{contracts,database,shared}`
  **явно**. Колишній wildcard `libs/*/src/**/*` затягнув `libs/ui` у webpack-збірку і дав 353
  помилки `TS17004` (JSX без флага). Turbo при цьому віддавав закешований зелений
  `typecheck` — нова ліба не інвалідує таск застосунку, тому перевіряти `--force`.
- **Пакет `shadcn` у `dependencies` тягне zod 3.** Він потрібен насправді (з нього йде
  `@import 'shadcn/tailwind.css'`), а `shamefully-hoist=true` піднімає його zod у корінь;
  `@hookform/resolvers` оголошує `zod` опційним peer-ом і підхоплює хойстнутий — `zodResolver`
  перестає типізуватись в обох фронтах. Тримає на місці `pnpm.overrides: { "zod": "^4.4.3" }`
  у кореневому `package.json`. **Не прибирати.**
- Через цей глобальний Zod 4 override локальний `pnpm exec shadcn` несумісний із CLI 4.19.0
  (`deepPartial is not a function`). Для CLI використовувати ізольований і зафіксований
  `pnpm dlx shadcn@4.19.0`; `@latest` не дає відтворюваного diff.
- **`pnpm-lock.yaml` у репо тримається відформатованим prettier-ом.** Будь-який
  `pnpm install` переписує його у власний компактний формат і дає диф на ~6000 рядків. Після
  install — `pnpm exec prettier --write pnpm-lock.yaml`.
- **`SidebarProvider` тримає стан згортання в cookie**, не в localStorage.
- **Клас із модифікатором перебивається ТІЛЬКИ класом із тим самим модифікатором.**
  tailwind-merge знімає конфліктний клас лише в межах однакового набору варіантів, тож голий
  `self-center` не витісняє базовий `data-vertical:self-stretch` вендереного `separator` —
  лишаються обидва, і виграє атрибутний селектор. Пастка підступна тим, що `align-self:
stretch` при ЗАДАНІЙ висоті нічого не розтягує: він тихо поводиться як `flex-start`, і
  роздільник у `PageHeader` тулився до верху рядка замість центру. Лікування — збіг
  модифікаторів (`data-vertical:self-center`), не `!important`. Той самий механізм уже ловив
  нас на рейлі (`group-data-[collapsible=icon]:` у `sidebarMenuButtonVariants`), тому правило
  загальне: перш ніж перебивати клас реєстрового примітива, подивіться, під яким варіантом він
  оголошений.

#### Пастка перевірки: `ResizeObserver` у фоновій вкладці

Chrome заморожує `ResizeObserver` у вкладці з `document.visibilityState === 'hidden'` —
layout при цьому рахується (`innerHeight`, `clientHeight` оновлюються), а колбеки RO не
доставляються ВЗАГАЛІ, навіть власний `ro.observe(el)` не дає обовʼязкового першого fire.
Це робить неперевірюваним усе, що на ньому тримається: смуга «не оновлюється», хоча в
реальному вікні все правильно.

Тому: перш ніж шукати регресію в коді, дивимось `document.visibilityState` — це той самий
клас пастки, що вже описаний для drag-жестів (§ «Перевірка UI в браузері» нижче), і другий
його випадок.

### Перевірка UI в браузері

- У вкладці з нульовим viewport (`0×0`) **не можна** вимірювати позицію тостів — трансформи
  стеку рахуються від висоти вікна і всі значення виходять відʼємними. Спершу `resize_window`.
- **У прихованій вкладці не програються CSS-анімації.** Base UI знімає попап із DOM після
  `animationend`, тож закритий `AlertDialog` лишається у дереві з `data-closed`. Судити треба
  за `data-open`/`data-closed`, а не за наявністю вузла.
- Буфер консолі в браузерних інструментах кумулятивний — `console.clear()` і перезавантаження
  його не чистять; «чистоту після правки» доводити структурою DOM.
- Dev-сервер, піднятий посеред великої правки, може тримати застарілий модульний граф —
  рестарт. HMR зміни в `libs/ui` підхоплює штатно.

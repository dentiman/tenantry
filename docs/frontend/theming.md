# Теми: дослідження і план

**Питання:** що треба переробити, щоб користувач міг вибирати між кількома темами, і в кожної
теми був свій світлий та темний режим — це лише CSS, чи доведеться заводити токени в компонентах?

**Коротка відповідь:** компоненти чіпати НЕ треба. Кольори в них уже повністю токенізовані —
жодного хекса, `oklch()` чи палітрового класу Tailwind у `.tsx` немає (перевірено grep-ом, цифри
нижче). Уся кольорова робота — це CSS-файли тем. Поза CSS потрібні рівно три дрібниці: атрибут на
`<html>`, крихітний провайдер, який його ставить, і UI-перемикач. Оцінка — один робочий підхід,
~7 файлів, без ризику для наявних екранів.

---

## 1. Що показало дослідження

### 1.1 Кольори в компонентах: їх немає

| Що шукали                                                                  | Знайдено                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `#hex`, `oklch(`, `rgb(`/`rgba(` у `.tsx`/`.ts` (`libs/ui`, обидва фронти) | **0** у логіці екранів; `oklch` лишився лише там, де він виправданий: свотчі превʼю в `themes/registry.ts`, детермінований колір аватара (`lib/avatar-color.ts`), варіант `tinted` у `bubble.tsx` (зашита світлота — тема на нього не впливає), `alert.tsx` |
| Сирі палітрові класи (`bg-slate-500`, `text-blue-600`, `bg-white`…)        | **0**                                                                                                                                                                                                                                                       |
| Виняток                                                                    | `bg-black/10` × 3 — scrim у `dialog`, `sheet`, `alert-dialog`                                                                                                                                                                                               |

Тобто кожен колір в інтерфейсі приходить із семантичного токена (`bg-card`, `text-muted-foreground`,
`border-border`, `bg-primary`…). Це і є та передумова, заради якої зазвичай і роблять «токени в
компонентах» — у нас вона вже виконана з часів UI-міграції.

**Єдиний борг:** `bg-black/10` — підкладка модалок. Вона однакова в обох режимах і темі не
підпорядкована. Якщо якась тема захоче іншу підкладку (наприклад, тепліший scrim), це три рядки:
завести `--overlay-scrim` у темі й замінити клас на `bg-(--overlay-scrim)`. Робити зараз не треба.

### 1.2 Де «темнота» все ж зашита в компонент

У примітивах є ~35 варіантів `dark:` — вони описують не колір, а **поправку форми** саме для
темного режиму:

```
button.tsx      dark:border-input dark:bg-input/30 dark:hover:bg-input/50
badge.tsx       dark:bg-destructive/[8%]  dark:focus-visible:ring-destructive/60
checkbox.tsx    dark:data-checked:… ; input/textarea — dark:aria-invalid:…
```

Наслідок для тем, і це головне обмеження механіки: **тема вільно міняє ЗНАЧЕННЯ токенів у темному
режимі, але не може скасувати ці правила.** Для тем, що відрізняються палітрою (а це наш випадок),
цього достатньо — правила посилаються на ті самі токени. Тема, яка захотіла б у темряві іншу
_конструкцію_ (скажімо, картки з обводкою замість заливки), вимагала б винести ці `dark:` у токени.
До такої теми — не чіпати.

### 1.3 Структура `libs/ui/src/styles.css`

```
@import 'tw-animate-css' / 'shadcn/tailwind.css' / інтер        ← вендорне
@import './themes/tenantry.css' / './themes/gray.css'           ← палітри (ВСІ, разом із дефолтом)
@custom-variant dark (&:is(.dark *))                            ← що таке «темний режим»
:root { … }        .dark { … }                                  ← СПІЛЬНА БАЗА: лише палітра подій
@theme inline { --color-*: var(--*) ; --radius-* ; --font-* }    ← міст «токен → утиліта Tailwind»
@layer base { … }                                               ← border-border, bg-background, шрифт
```

Важливо для плану: `@theme inline` — це **мапа імен**, а не значень. `--color-card: var(--card)`
означає «утиліта `bg-card` читає токен `--card` у момент рендера». Тому нова тема НІКОЛИ не дублює
`@theme inline` — вона перевизначає самі `--card`, `--primary`, `--border` тощо, і всі утиліти
підхоплюють це автоматично. Те саме стосується `--radius` (з нього рахуються `--radius-sm…4xl`),
тож тема може мати власну скруглість безкоштовно.

Що зараз НЕ входить у тему, хоч технічно могло б: `--font-sans` (оголошений у `@theme inline`).
Якщо колись знадобиться тема з іншим шрифтом — рядок треба перенести в блоки тем.

Тінями тема володіє: чотири токени шкали висот (§1.3.6) різні у світлі й темряві, і кожна тема
оголошує їх сама.

### 1.3.6 Шкала висот: чотири рівні, один ряд для карток, попапів і діалогів

До 2026-11-10 рівнів було два (`surface`, `overlay`), діалог тіні не мав узагалі (тримався лише на
scrim), а картка входу носила власну `--auth-card-shadow` поза темою. Три поверхні виглядали як із
трьох систем. Тепер це одна драбина; тема оголошує значення, примітив обирає РІВЕНЬ:

| Рівень    | Токен теми         | Утиліта             | Що на ньому                                                                                                                              |
| --------- | ------------------ | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `surface` | `--surface-shadow` | `shadow-xs` / `-sm` | поля, активний сегмент, підняті плитки в потоці сторінки                                                                                 |
| `raised`  | `--raised-shadow`  | `shadow-raised`     | самостійна картка-сцена на голому полотні: `<Card elevation="raised">` (вхід)                                                            |
| `overlay` | `--overlay-shadow` | `shadow-md`         | усе прив'язане до тригера й без scrim: `Popover`, меню й підменю, `Select`, `Combobox`, `HoverCard`, тост, елемент під час перетягування |
| `modal`   | `--modal-shadow`   | `shadow-lg` / `-xl` | усе над scrim: `Dialog`, `AlertDialog`, `Sheet`, мобільні шторки панелей                                                                 |

Правила:

- **Рівень визначає РОЛЬ, а не смак.** «Над scrim» → `modal`; «прив'язане до тригера» → `overlay`.
  Підменю не глибше за меню, тост не глибший за попап — стокові `shadow-lg` у них замінено на
  `shadow-md` (правки позначені «ЛОКАЛЬНА ПРАВКА реєстру»).
- **Власних `shadow-[…]` і `box-shadow` на місці виклику немає.** Якщо поверхні бракує рівня —
  це нова сходинка в темі (чотири блоки), а не значення в компоненті.
- **Картка плоска за замовчуванням** (рівні в сітці сторінки несе заливка, `ui-stack.md`), а
  `elevation="raised"` — лише для картки, яка на екрані одна. Рівнів `overlay`/`modal` у `Card`
  немає: плаваюче — це `Popover`/`Dialog`.
- **У темряві тінь щільна й коротка; у світлі — довга й прозора.** Причина — квантування. Темне
  полотно `tenantry` ≈ 48/255, один рівень яскравості там — ~4% різниці, помітна сходинка; у світлі
  той самий рівень ≈ 0.9% і невидимий. Довга слабка темна тінь (`0 48px 128px / 18%`) закінчувалась
  плато ~36px і сходинкою в один рівень — контуром навколо плями, «обрубаним краєм». Плато тим
  ширше, що довший блюр і що НИЖЧА альфа, тому помітнішу тінь у темряві роблять щільнішою, а не
  довшою: блюр шару ≤ ~40px, великий від'ємний spread тримає тінь під поверхнею. Усі три рівні
  `tenantry.dark` — одна будова (три шари, чорний), різниться масштаб:

  | Рівень    | Глибина (рівнів) | Хвіст знизу | Останнє плато |
  | --------- | ---------------- | ----------- | ------------- |
  | `raised`  | 9                | 25px        | 8px           |
  | `overlay` | 13               | 28px        | 7px           |
  | `modal`   | 14               | 35px        | 11px          |

  Виміряно на діалозі «Add user» (застосувати значення, зняти профіль яскравості під вікном).
  Тонований колір тіні пробували й відкинули: при тій самій альфі глибина менша, а останнє плато
  довше (21px проти 11).

- **Підняті поверхні мають спільний контур `--raised-outline`** (`styles.css`: 16% `--foreground`
  у світлі, 7% у темряві) — картка входу й `Dialog`/`AlertDialog`. Це внутрішній `outline`
  (`-outline-offset-1`), а не зовнішній `ring`: лінія лягає на заливку самої поверхні й у темряві
  світліша за неї (підсвічений край), тоді як `ring` на тіні темний і губиться.
- **Попапи лишають зовнішнє кільце, але колір бере токен `--overlay-outline`**
  (`ring-1 ring-(--overlay-outline)`, у реєстрі було `ring-foreground/10`): 10% `--foreground` за
  замовчуванням (`styles.css`), 16% у `tenantry.dark`, 14% в `ink.dark`, де кільце на тіні інакше
  майже не видно. З 2026-11-12 токен **непрозорий**: частка `--foreground` домішується до
  `--popover`, а не до `transparent`. Кільце лежить зовні, на тому, що під попапом, і
  напівпрозоре воно світлішало над діалогом і темнішало над полотном — один попап над двома
  сходинками мав шов різної яскравості по одному краю. Виняток — скляні попапи на брендовому
  фоні, там кільце знову напівпрозоре (`brand-backdrop.css` §5). Контур карток, діалогу й полів
  не чіпали: у перших двох він лежить усередині на власній заливці, у полів адаптація до
  сходинки — бажана.
- **Діалог має власну поверхню: `--dialog` і `--dialog-header`** (утиліти `bg-dialog`,
  `bg-dialog-header`; оголошує тема, усі чотири блоки). У `tenantry.dark` `--dialog` — колір картки
  входу, зведений у суцільний (`color-mix(--card-base 30%, --sidebar)` ≈ 0.322), а не `--popover`
  (0.368): поля `--field` (0.368) на `--popover` зливались із вікном і трималися лише на рамці, на
  `--dialog` вони світліші за поверхню. `--dialog-header` там = `--popover` — світліша смуга шапки.
  У світлі й у `gray` обидва токени дорівнюють `--popover`. `Dialog`/`AlertDialog` беруть
  `bg-dialog` самі; смугу шапки ставить місце виклику (`<DialogHeader className="… bg-dialog-header">`)
  і лише в діалогах без внутрішнього відступу (`p-0`) — поки що тільки «Add user»; лінія під смугою
  в темряві приглушена (`dark:border-border/40`), бо межу вже дає різниця заливок. Меню, списки,
  тости лишаються на `--popover`, сайдбар шела — на `--sidebar`. `Sheet` (а з ним центр сповіщень у
  темряві) теж на `bg-dialog`, з межею `--raised-outline` у темряві. У світлі центр сповіщень
  лишає `bg-sidebar` — його білі картки тримаються на цьому фоні.
- **Поверхні `tenantry.dark` — чотири іменовані сходинки**, кожна записана в темі один раз:
  `--tone-chassis` 0.293 (сайдбар, тулбар гріда) → `--tone-canvas` 0.315 (полотно, хедер, діалог,
  шторка) → `--tone-surface` 0.368 (картка, поле, попап, шапка діалогу) → `--tone-emphasis` 0.390
  (`--muted`, `--secondary`). Семантичні токени — посилання на сходинки, тож зсув тону ролі — одна
  правка. Полотно 0.315 — рішення власника 2026-11-10 (зняте з Orca було 0.337): поля й картки на
  ньому контрастніші. `--dialog` спершу був формулою кольору картки входу (≈ 0.322); різниця з
  полотном 0.007 невидима, тому він зведений до `--tone-canvas`. Світлий блок і `gray` сходинок не
  мають: там ролі розкладені інакше (`--muted` = `--sidebar`), і спільна драбина була б натяжкою.
  Не зведено: `--card-base` (0.389) — база напівпрозорої картки; на новому полотні картка `default`
  ≈ 0.359 замість 0.368. Виміри в §3.2 і в коментарях теми зняті на полотні 0.337 і не перераховані.
- **Контур — не частина рівня** (крім `gray` у темряві, §1.3.5): його несе кільце оверлея або
  `outline` картки. Тому токени `tenantry.dark` — тільки тінь.
- У світлі `raised` тонований `--foreground` (тема міняє відтінок тіні), у темряві всі рівні —
  чорні: світла тінь на темному полотні не читається.

### 1.3.7 Фокус і помилка поля: 1px, зміна кольору обводки, без кільця

До 2026-11-12 поле у фокусі носило `border-ring` + `ring-1 ring-ring` (разом 2px), а в помилці —
`border-destructive` + `ring-2 ring-destructive/60` (рамка з «сяйвом») та ще й послаблену
`dark:border-destructive/50`. Рішення власника: обводка поля **міняє колір, а не товщину**.

- **Фокус** — лише `focus-visible:border-ring` (1px). Колір `--ring` у всіх темах —
  **приглушений primary**: `color-mix(in oklab, var(--primary) 60%, var(--input))`, тобто між
  звичайною обводкою поля й акцентом; чистий primary на 1px кричав. Той самий `--ring` читають
  фокус-кільця кнопок і `outline-ring/50` бази — вони стали тихішими разом із полем.
- **Помилка** — лише `aria-invalid:border-destructive` (1px, повний колір в обох режимах).
- Правило застосовано до `Input`, `Textarea`, `SelectTrigger`, `ComboboxInput`, `InputGroup`
  (пометка «ЛОКАЛЬНА ПРАВКА реєстру (2026-11-12)») і до тригерів `customer-select`,
  `user-select` у `apps/web`. Кнопки, чекбокси, перемикачі й бейджі лишаються на `ring-2`:
  у них немає власної рамки, яку можна перефарбувати. Так само `country-select` у телефонному
  полі — це безрамковий тригер усередині поля, його фокус лишається кільцем.

### 1.3.1 Палітра подій — СПІЛЬНА; службові тони календаря — частина теми

`--event-{blue,green,red,orange}` × `{ , -line, -bg}` оголошені в `:root` / `.dark` і **навмисно
не входять до контракту тем**. Після 2026-11-08 це єдине, що там лишилось: `:root`/`.dark` більше
не дефолтна тема, а спільна база всіх палітр. Заливки (`-bg`) при цьому не мають власних значень — вони
виводяться з кольору смужки (`color-mix(… var(--event-*-line) 22%, var(--card))`) і тому
оголошені ОДИН раз, у `:root`: custom properties обчислюються ліниво, тож у темряві вираз
перерахується сам, щойно `.dark` перевизначить `-line`. Виглядає це як «колір події з альфою»
(так у Notion Calendar), але результат лишається непрозорим — під плиткою є лінії годин, і крізь
справді прозору заливку вони просвічували б через кожну подію: тема шела визначає нейтралі й бренд, а колір зустрічі від неї не
залежить — «дзвінок зелений» мусить лишитись зеленим у будь-якій палітрі. Значення взяті з Notion
Calendar (через MIT-клон calendarcn, `../calendar.md` §11.9).

`--calendar-{weekend,in-view,day-hover}` — **навпаки, частина контракту теми** (переведені
2026-09-08). Це не кольори подій, а три сусідні сходинки поверхонь шела: підсвітка тижня стоїть
поруч із сайдбаром і полотном, тож теплий сірий Notion у холодній slate читався б як бруд, а
холодний slate у темному Notion — як чужа пляма. Кожна тема оголошує
їх сама, і правило порядку однакове в обох режимах: наведення (`day-hover`, він же `--accent`)
мусить лишатись на сходинку контрастнішим за `in-view`, інакше наведення на вже підсвічений
тиждень стає невидимим.

Наслідок для §5 («як додати нову тему»): нова тема оголошує календарні тони і НЕ оголошує
`--event-*`. Якщо колись знадобиться тема з власною палітрою подій — рядки переносяться в блоки
тем разом, як описано для `--font-sans`.

### 1.3.2 Іконки — окрема шкала з трьох рівнів

`--icon-strong` / `--icon` / `--icon-muted` — **частина контракту теми** (усі три, в обох
режимах). Правило взяте в Notion, який тримає для знаків окрему шкалу поруч зі шкалою тексту.
Причина: суцільна форма іконки важить оком більше за штрихи літер, тож зрівняні в кольорі знак і
підпис читаються як знак, що перетягує увагу. Ставити його блідішим — не косметика, а
вирівнювання ваги.

| Токен           | Рівень шкали | Роль                                                      |
| --------------- | ------------ | --------------------------------------------------------- |
| `--icon-strong` | 850          | знак під ВЗАЄМОДІЄЮ — наведення або активний пункт        |
| `--icon`        | 600          | звичайний знак поруч із текстом (меню, кнопки, навігація) |
| `--icon-muted`  | 500          | службовий знак (шеврон селекта, адорн поля)               |

Головне тут — не три значення, а те, що **знак реагує на взаємодію КОЛЬОРОМ**: у спокої відступає
(46%), під курсором і у вибраному пункті виходить наперед (87%). Це єдине місце в темі, де стан
елемента міняє колір знака, а не лише фон під ним, і саме воно робить навігацію «живою» при майже
невидимій накладці фону. Наведення і вибране дають ОДНАКОВИЙ результат — різницю несе фон
сторінки, а не два відтінки знака.

**Значення — рівні тієї самої парної шкали, що й накладки** (§1.3.3), тобто
`color-mix(in oklab, var(--foreground) N%, transparent)`. Два продукти Notion тут розходяться:
в `app.notion.com` темний знак суцільний ~`#ada9a3` (≈0.68 еквіваленту), у `calendar.notion.so`
— 0.445, **вдвічі тьмяніше**; у них же рівень 600 обслуговує і `--text-body`, і
`--nds-icon-contr-graySecondary`, тобто буквально іконку меню. Ми взяли календарну щільність.

Чому альфа, а не суцільний колір: вона тримає знак у правильному відношенні до БУДЬ-ЯКОЇ поверхні
під ним — полотна, картки, попапа (а він у нас світліший за картку). Одне суцільне значення не
може бути правильним на всіх трьох. Заодно світлий режим від переходу на альфу візуально не
змінився: перерахунок показав, що колишні суцільні `oklch(0.646)` / `oklch(0.727)` і були рівнями
600 / 500 цієї шкали.

**Хто ставить токен.** Не сторінки — ПРИМІТИВИ: `button` (варіанти `outline`/`secondary`/`ghost`/
`toolbar`; у суцільних `default`/`destructive` знак лишається кольором foreground заливки),
`sidebar` (обидва рівні навігації; на `--icon-strong` перемикають І `hover`, І `data-active`), пункти
`dropdown-menu` / `context-menu` / `select` / `combobox`, шеврон селекта й адорни `input-group`.
Селектор скрізь однаковий — `[&_svg:not([class*='text-'])]:text-icon`: `:not` лишає недоторканими
знаки з власним кольором (`text-destructive` у пункті меню, `text-primary` у кнопці-посиланні).
Активний стан важчий за базовий рівно тому, що несе ще й атрибут (`data-active:` → 0-3-1 проти
0-2-1). Обидва фронти отримують це з `libs/ui`; писати `text-icon` на місці використання не треба.

**У навігації колірне правило звужене до ПРЯМОГО нащадка** (`[&>svg]`; розмір лишився на
`[&_svg]`). Селектор нащадка перебиває успадкування, тож ширший варіант фарбував і ті знаки, що
лежать усередині ВЛАСНОЇ кольорової поверхні: бренд-плитка рейлу — синій квадрат із
`text-sidebar-primary-foreground`, і її логотип виходив сірим. Правило: **на кольоровій підкладці
знак бере foreground цієї підкладки**, а шкала `--icon` керує лише знаками, що лежать прямо на
кнопці.

Наслідок, який легко проґавити: `bg-border` для ПОВЗУНКА скролбара після переходу на напівпрозору
межу перестав працювати (5.5% білого — це не повзунок, а невидимість). `scroll-area.tsx` тому
бере `bg-icon-muted` — повзунок не розділювач, а керований елемент.

### 1.3.5 Тінь оверлея не малює СВОЮ межу

`--overlay-shadow` у темряві несе hairline першим шаром — на темному полотні тінь не читається,
і саме він відділяє попап від фону. Але доки hairline був суцільним `#383836`, а межі теми
переїхали на 5.5% прозорості, кожен оверлей, у якого Є власний `border`, малював **два кільця
різних відтінків одне на одному**: тост помилки, картка сповіщення, будь-що з `border` +
`shadow-lg`. Оком це читалось як «межа завтовшки два пікселі й розмита».

Тому hairline тепер `var(--border)`, а не власне значення. Там, де межа є, обидві лінії
збігаються в одну; там, де її немає (`Sheet`, `Popover`), hairline лишається єдиним контуром і
за визначенням має той самий тон, що решта меж теми.

Правило на майбутнє: **тінь не заводить власного кольору межі**. Якщо оверлею потрібен контур —
він бере `--border`, а не наближене значення.

### 1.3.4 `--segment`: підняття в темряві робиться ІНВЕРСІЄЮ

Активний сегмент (таб у `TabsList`, кнопка `variant="elevated"`) у світлій темі — біла плитка з
обводкою й тінню на сірому жолобі: вона читається як піднята НАД ним. У темній тій самій ролі
потрібен протилежний хід: «на сходинку світліший сірий» (`#383836`, як було до 2026-09-08) на
темному полотні виглядає не піднятим, а просто тьмяним — тіні на темному не працюють, і підняття
там передається світлом.

Тому `--segment` у темряві — 96% кольору тексту, а `--segment-foreground` — колір полотна: майже
біла плитка з темним написом. Не 100%: чиста біла на темному ріже око на великій площі, а 4%
домішки полотна це знімають, лишаючи плитку «білою» на око. Патерн узятий у Notion.

Жолоб під сегментом при цьому — **прозора накладка** (`--accent`), а не суцільний `--secondary`:
таби стоять і на картці, і на полотні, і в тулбарі календаря, і суцільний фон довелося б
підбирати під кожну з цих поверхонь.

### 1.3.3 Накладки: hover і вибраний стан

`--accent` — **не поверхня, а прозорий шар**
поверх того, що вже намальовано. Джерело — парна шкала Notion Calendar `--ca-palTraGra*`, у якої
однакові номери рівнів в обох режимах:

| Рівень | Світло (чорний) | Темрява (білий) | Наша роль                                           |
| ------ | --------------- | --------------- | --------------------------------------------------- |
| 75     | `.05`           | `.016`          | `--calendar-weekend`                                |
| 100    | `.06`           | `.03`           | `--calendar-grid-line`                              |
| 200    | `.07`           | `.055`          | `--border`, `--calendar-in-view`                    |
| 300    | `.11`           | `.094`          | `--accent` — наведення, вибране, активне; `--input` |
| 500    | `.333`          | `.282`          | `--icon-muted`                                      |
| 600    | `.46`           | `.46`           | `--icon`                                            |
| 850    | `.89`           | `.87`           | `--icon-strong`                                     |

**Чому суцільний колір тут програвав за визначенням.** У шела три поверхні на різній світлоті
(полотно, сайдбар, картка), а в темряві попап ще й світліший за картку. Одне значення, підібране
під полотно, на сайдбарі майже зливалося — саме та скарга, з якої почалась ця правка. Накладка
дає ОДНАКОВУ різницю до будь-якої поверхні під нею, тому й підходить.

База — `--foreground` теми, а не чистий чорний/білий: наші нейтралі теплі, і нейтральна накладка
вибивалася б холодним. Технічно це `color-mix(in oklab, var(--foreground) N%, transparent)`, тож
альтернативні теми отримують свій відтінок накладки безкоштовно.

**Межа застосування.** Прозорість працює тільки на елементах БЕЗ власного фону: ghost/outline/
toolbar-кнопка, іконкова кнопка, пункт меню, пункт навігації, рядок таблиці, комірка календаря,
`Badge` ghost/outline, `Toggle` outline. Там, де фон Є (`--field` у полів, `--secondary` у
кнопки), накладка-заміна показала б полотно замість власної поверхні елемента — такі місця
лишаються на суцільних `*-hover`, і це не непослідовність, а різниця між «пофарбувати поверх» і
«замінити фон».

**Наведення, вибране й активне дають ОДИН фон** — `--accent`, рівень 300: у навігації, у
кнопках, у `Toggle`, у рядку таблиці з `data-state=selected`. Спроба розвести їх на 300/400
виглядала як два різні відтінки сірого поруч, замість одного стану «цей рядок зараз при ділі»;
різницю натомість несе ЗНАК (§1.3.2: 46% у спокої проти 87% під курсором і у вибраному) — це
помітніше за різницю фонів і не додає темі ще одного тону.

Рівень 400 у темі **не оголошений узагалі**: `--accent-strong` прожив кілька годин 2026-09-08 і
був знятий, щойно його єдиний споживач (вибраний рядок) перейшов на 300. Токен, що обслуговує
один випадок, — не рівень шкали, а виняток із неї.

## 2. Модель: дві незалежні осі

|      | Вісь                 | Значення                    | Носій у DOM              | Хто керує     |
| ---- | -------------------- | --------------------------- | ------------------------ | ------------- |
| Мода | **режим**            | `light` / `dark` / `system` | клас `.dark` на `<html>` | `next-themes` |
| Тема | **палітра (родина)** | `tenantry` / `gray` / …     | `data-theme` на `<html>` | наш провайдер |

Осі перемножуються: кожна тема зобов'язана мати обидва режими.

**Чому не зробити 2N тем у самому `next-themes`** (`slate-light`, `slate-dark`, `gray-light`…), хоч
він це вміє через проп `themes`:

1. Зникає `system` — він у `next-themes` розрізняє рівно `light`/`dark`, і при 2N темах довелося б
   писати власну логіку «яка родина + що каже ОС».
2. Ламається `dark:` Tailwind: варіант оголошений як `&:is(.dark *)`, тобто зав'язаний на клас
   `dark`. З темами-рядками на `<html>` висів би клас `slate-dark`, і всі ~35 `dark:`-правил у
   примітивах перестали б спрацьовувати.
3. Вибір «тема» і вибір «світло/темрява» — різні рішення користувача; злиті в один список вони
   дають N×2 пунктів меню замість N + 3.

Тому режим лишається за `next-themes` як є, а родина — окремим атрибутом.

### Контракт селекторів

```css
/* спільна база всіх палітр — лише те, що однакове в КОЖНІЙ темі */
:root            { …палітра подій… }
.dark            { …палітра подій… }

/* кожна тема, включно з дефолтною */
:root[data-theme='gray']      { …light… }   /* вага 0-2-0 > :root  0-1-0 */
:root[data-theme='gray'].dark { …dark…  }   /* вага 0-3-0 > .dark  0-1-0 */

/* дефолтна (`tenantry`) — те саме плюс пара на випадок «атрибута ще немає» */
:root:not([data-theme]),
:root[data-theme='tenantry']      { …light… }   /* обидва 0-2-0 */
:root:not([data-theme]).dark,
:root[data-theme='tenantry'].dark { …dark…  }   /* обидва 0-3-0 */
```

Специфічність тут не косметика: файли тем підключаються через `@import`, а імпорти в CSS завжди
спливають на початок файла — на порядок джерела спиратися не можна, виграти має саме вага
селектора. Тому обидва селектори теми навмисно важчі за базові.

Чому в дефолта саме `:not([data-theme])`, а не голий `:root`, як було до 2026-11-08: атрибут
з'являється на `<html>` лише після блокувального скрипта в `index.html`, тож дефолт мусить
малюватись і без нього — але голий `:root` важить 0-1-0, а `brand-backdrop.css` оголошує
частину токенів теж у `:root`/`.dark` і підключається пізніше. Дефолт програвав би йому за
порядком. `:not()` бере вагу свого аргумента, тож виходить 0-2-0 / 0-3-0 — рівно як у решти тем.

Наслідок, заради якого це робилось: **жодна тема більше не є базою для іншої.** Доти дефолт
стояв у `:root`, і тема, яка забула токен, мовчки діставала його з дефолтної палітри — саме так
`slate` жила без власних `--event-*`. Тепер «яка тема дефолтна» — один рядок `DEFAULT_UI_THEME`
у реєстрі, а не місце в CSS.

Блокувальний скрипт в `index.html` обох фронтів просіює збережений id **списком відомих палітр**,
а не регуляркою форми: id переживає перейменування в localStorage (`slate` → `tenantry`), і
невідомий `data-theme` не підхопила б жодна тема — до гідратації сторінка лишилась би з самою
базою. Список — дзеркало реєстру.

Три правила теми:

1. **Тема оголошує ВЕСЬ набір токенів, а не дельту.** Часткова тема мовчки успадкує половину
   значень від дефолтної — і зламається рівно тоді, коли дефолтна зміниться.
2. **`color-scheme` обов'язковий** у кожному блоці: від нього залежать нативні скролбари, чекбокси,
   автозаповнення й дефолтний колір тексту в контролях.
3. **Метрики в тему не переїжджають.** Висоти контролів (36px), падінги, фокус-геометрія — рецепт
   компонента; тема тримає кольорові пари, радіус і тіні. Інакше кожна нова тема ставатиме новим
   дизайном, а не новою палітрою.

### 3.1 Палітра `gray` (дефолт 2026-09-08 … 2026-11-08): два режими — два джерела

**Рішення користувача 2026-09-08 (переглянуло ранкове):** повна тема Notion не потрібна, потрібна
її **темна половина**. Тому дефолт складений з двох різних палітр:

| Режим   | Джерело                                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------- |
| Світлий | zinc-нейтралі HeroUI v3 (`packages/styles/themes/default/variables.css`) — попередня тема `gray` як вона була |
| Темний  | **власні токени Notion**, зняті з живого бандла `app.notion.com` (`/_assets/84388-*.css`, вересень 2026)      |

Асиметрія свідома. Тема — це **контракт ролей** (`--background`, `--card`, `--popover`, …), а не
одна палітра, розтягнута на два режими: режими ніхто не бачить одночасно, тож кожен має право
взяти найкращі для себе значення. Практичний наслідок, про який треба памʼятати: **похідні токени
одного режиму не можна виводити з іншого** — обидва блоки оголошують повний набір, як і будь-яка
альтернативна тема.

Темні значення взяті з 265 перевизначень `--c-*` у `.notion-dark-theme` (те, чого dark не
перевизначає, він успадковує зі світлого — такі рядки звірялись зі світлим блоком бандла). Кожен
рядок у `.dark` підписаний іменем токена-джерела, щоб значення можна було звірити, а не приймати
на віру. Скорочення Notion: `bac` background, `bor` border, `tex` text, `ico` icon, `pal` palette,
`but` button, `inp` input, `sha` shadow; `Pri/Sec/Ter` — primary/secondary/tertiary, `Ele`
elevated, `Int` interactive, `Str` strong, `Foc` focus, `Hov` hover.

| Наша роль                  | Light (HeroUI zinc)           | Dark (Notion)     | Токен Notion                |
| -------------------------- | ----------------------------- | ----------------- | --------------------------- |

### 3.2 `tenantry` (дефолт із 2026-11-08; до того `slate`): світло — Tailwind slate, темрява — Orca

**Стан на 2026-09-08.** Сесія «звірка з Notion» переписала дефолт глибоко: шкала знаків, прозорі
накладки станів, інверсія `--segment`, тони календарної сітки. Усе це — вирази від `--foreground`
теми, тож `slate` отримала їх **автоматично й у своєму відтінку**, і набори токенів у двох тем
збігаються один в один.

Перевірено скриптом, а не оком: у `slate` рівно ті самі імена, що в дефолті, за єдиним винятком —
`--event-*` (12 у світлі, 8 у темряві), які й НЕ входять до контракту тем (§1.3.1). Тобто
розбіжності немає: тема оголошує рівно те, що мусить.

**Чого бракує:** `slate` жодного разу не дивились у браузері після цих змін. Формули коректні,
але «коректні формули» ≠ «правильний вигляд»: щільність накладки, яка добре читається на теплих
нейтралях Notion, на холодних slate-нейтралях може виявитись на сходинку не тою.

**Що робити далі** (рішення користувача 2026-09-08): загальний вигляд `slate` доводиться до
ДЕФОЛТНОЇ теми — та сама конструкція, ті самі рівні, інші кольори. Тобто це не «інший дизайн»,
а та сама система в іншій палітрі; будь-яка розбіжність у наборі токенів — дефект, а не
особливість теми.

**Рішення користувача 2026-11-07 — темний режим `slate` перезнято з Orca.** Доведення до
дефолту (абзац вище) стосується далі лише СВІТЛОГО режиму. Темний був відхилений на вигляд:
на темних сходинках Tailwind slate `chroma 0.042` при `hue 264.7` читається як **фіолетовий
відтінок**, а не як холодний нейтраль, і акцент `blue-500` (`chroma 0.214`) посилював це
враження.

Нові значення зняті **піксельно зі скриншота Orca** (аналіз у `libs/ui/src/themes/tenantry.css`,
до перейменування 2026-11-08 — `slate.css`
над блоком `.dark`), а не підібрані на око. Два відхилення, які тепер відрізняють цю тему від
решти — і які НЕ треба «виправляти» вирівнюванням:

| Що                  | Було (Tailwind slate)            | Стало (Orca)                                    |
| ------------------- | -------------------------------- | ----------------------------------------------- |
| Хрома нейтралей     | 0.042 @ hue 264.7                | **0.011…0.015** @ hue 264…269                   |
| Полотно / навігація | 0.129 / 0.208 — шел СВІТЛІШИЙ    | **0.337 / 0.293** — шел ТЕМНІШИЙ                |
| Межі                | 0.279 — один токен на все        | **два рівні**: прозорий контент, шов шела 0.376 |
| Primary             | `blue-500` 0.623 **0.214** 259.8 | `#438ff9` 0.655 **0.175** 257.4                 |

Наслідок для контракту: набір токенів лишився повним і незмінним (§1.3.1), тож це розбіжність
ПАЛІТРИ, а не конструкції. Дві похідні величини довелось перерахувати саме тому, що база
поверхонь зсунулась майже на 0.2: `--accent` (12% замість 9.4% — відтворює обидва наведення
Orca одночасно) і тони календарної сітки. `--popover` навмисно НЕ дорівнює знятому з Orca
значенню 0.325: там попап лежить над навігацією, у нас — і над полотном теж, де він би зник.

Свотчі в `registry.ts` беруться зі СВІТЛОГО режиму, тож перезняття темряви їх не зачіпає.

#### Межі: два рівні, обидва світліші за фон (уточнення 2026-11-07)

Перший захід зняв межу з хибної точки й поставив `--border` ТЕМНІШИМ за полотно. Повторний
замір по всіх швах Orca дав протилежне правило: **жодна лінія там не темніша за свій фон**, а
рівнів рівно два.

| Шов                            | Поверхні      | Лінія Orca |
| ------------------------------ | ------------- | ---------- |
| Бульбашка ↔ полотно            | 0.390 / 0.337 | 0.431      |
| Поле вводу ↔ полотно           | 0.368 / 0.330 | 0.428      |
| Попап ↔ навігація              | 0.325 / 0.293 | 0.420      |
| Картка в навігації ↔ навігація | 0.379 / 0.293 | 0.447      |
| **Сайдбар ↔ полотно**          | 0.293 / 0.337 | **0.376**  |
| **Топбар ↔ полотно**           | 0.293 / 0.337 | **0.376**  |
| **Полотно ↔ права панель**     | 0.337 / 0.293 | **0.376**  |

Перші чотири — межа КОНТЕНТУ (~0.43), останні три — шов ШЕЛА (0.376). Саме тому
`--sidebar-border` у цій темі вперше перестав бути `var(--border)`: до Orca ці два токени
скрізь збігались, і різниця ніде не виявлялась.

Три наслідки, які коштували окремого розбору:

1. **`Card` не має `border`** — `border-width: 0`, весь його контур лежить на `shadow-sm`,
   тобто на `--surface-shadow`. У темряві там стояло `0 0 0 0 transparent`, тому картки були
   без обводки взагалі. Тепер це `0 0 0 1px var(--border)`: токен тіні використаний як контур,
   а не як тінь.
2. **Вендорений `sidebar.tsx` малював зовнішню межу не тим токеном.** У реєстрі `border-r`
   стоїть без кольору й падає на `--border`; в апстрімі це непомітно, бо там
   `--sidebar-border === --border`. `AppRail` передавав `border-sidebar-border` явно і тому
   був правий, а `AreaSidebar` — ні. Виправлено в примітиві (тег `ЛОКАЛЬНА ПРАВКА реєстру`),
   щоб обидва фронтенди й усі теми отримали це разом.
3. **Розмитий inset гасне.** `inset 0 0 1px 0 rgb(255 255 255 / 22%)` давав 0.399 замість
   0.431 — попап був окреслений слабше за картку, хоча стоїть вище за неї. Контур має бути
   `0 0 0 1px` (без blur) і тим самим `--border`.

**Рішення користувача 2026-11-07 (друге уточнення): `--border` став НАПІВПРОЗОРИМ** —
`color-mix(in oklab, var(--foreground) 7%, transparent)` замість суцільного `oklch(0.431 …)`.
Причина — товщина на вигляд, а не тон: суцільна лінія на retina лягає двома фізичними
пікселями одного кольору й читається як рамка, тоді як накладка змішується з фоном і лишає
контур. Побічна вигода — одне значення саме підлаштовується під сходинку, на якій стоїть, і
відтворює розкид Orca без трьох окремих токенів:

Відсоток знижувався двічі на вимогу вигляду — 100% (суцільний) → 10% → **7%**:

| Де                                         | Підкладка | Суцільний | 10%   | 7% (поточне) |
| ------------------------------------------ | --------- | --------- | ----- | ------------ |
| Обводка картки (зовнішня, на полотні)      | 0.337     | 0.421     | 0.396 | **0.376**    |
| Обводка попапу (`inset`, на самому попапі) | 0.368     | 0.417     | 0.424 | **0.402**    |
| Лінія під топбаром                         | 0.337     | 0.421     | 0.396 | **0.376**    |
| Шов шела (`--sidebar-border`)              | 0.293     | 0.366     | 0.362 | **0.346**    |

Нижче 7% опускати нікуди: на 5% лінія на полотні вже зникає.

Різниця між першими двома рядками системна, а не дефект: зовнішній `0 0 0 1px` лягає на
полотно, inset — на фон попапу. В Orca те саме співвідношення (попап 0.420 не нижчий за
бульбашку 0.431).

**`--sidebar-border` довелось знизити слідом** — з 0.376 (знятого з Orca) до 0.357. На 7%
межа контенту дає рівно 0.376 на полотні, тож при вихідному значенні два рівні злились би в
один і ієрархія «контент помітніший за шов шела» зникла б. Тримаємо те саме СПІВВІДНОШЕННЯ,
що в Orca, а не ті самі числа. Непрозорим він лишився з попередньої причини: розділяє дві
різні поверхні, і накладка дала б різний тон залежно від того, на чиєму боці намальована
межа.

#### Наслідок: контур у токені тіні не можна поєднувати з `border`

`--surface-shadow`/`--overlay-shadow` у цій темі несуть КОНТУР, а не тінь (§вище). Це створює
правило, якого в інших темах не було: **елемент не може мати одночасно власну межу
(`border`, `ring-1`) і `shadow-sm`/`shadow-md`** — вийдуть дві світлі лінії в сусідніх
пікселях, що читається як подвійна обводка. У світлих темах той самий код виглядав нормально,
бо тінь там не контур.

плитки й на ній невидимий), `sidebar.tsx` з `variant="floating"` і `field-settings.tsx` під

#### Акцентні поверхні (`warning`) у темряві — окремі значення

Рецепт `border-warning/30 bg-warning/10 text-warning` (той самий у `Alert variant="warning"`,
у банері часового поясу календаря і, з власними токенами, у плитці Product tour) розрахований
на СВІТЛЕ полотно. У темряві він перестає бути акцентом і стає найяскравішою плямою екрана:
`--warning` тут `oklch(0.791 0.162 88)`, тобто **світліший за будь-яку поверхню теми**, тоді
як у світлому режимі він темніший за полотно. Ті самі відсотки дають протилежний результат.

Рішення користувача 2026-11-07: у темряві заливка прозоріша, а межа зведена **майже до
нейтральної — теплим лишається відтінок, а не сила**. Сигнал несуть текст та іконка, які
кольору не втратили.

| Що                         | Світло (без змін)   | Темрява                          | Виміряно (L / chroma)             |
| -------------------------- | ------------------- | -------------------------------- | --------------------------------- |
| Межа alert-блоків          | `border-warning/30` | `dark:border-warning/15`         | 0.458 / 0.055 → **0.384 / 0.027** |
| Заливка                    | `bg-warning/10`     | `dark:bg-warning/[0.06]`         | 0.348 / 0.012 → **0.326 / 0.002** |
| Ліва акцентна смуга банера | `border-l-warning`  | `dark:border-l-warning/70`       | 0.801 / 0.148 → **0.664 / 0.114** |
| Плитка туру: теплі плями   | `0.85`              | `--tour-glow-opacity: 0.42`      | —                                 |
| Плитка туру: кант          | 50/32%              | `--tour-edge-from/to: 30% / 10%` | 0.510 / 0.062 → **0.369 / 0.008** |

Орієнтир для межі — звичайний `--border`, який на тих самих поверхнях дає 0.376: після
зниження тепла межа потрапляє в той самий діапазон (0.384…0.423) і відрізняється від
нейтральної лише хромою. Кант плитки туру градієнтний, тож тепло лишилось у верхньому лівому
куті (chroma 0.043) і зійшло нанівець у правому (0.004) — саме так він і задуманий.

Відкрите: топбар у нашому шелі стоїть на `bg-background`, тобто належить ПОЛОТНУ, а не шелу
(в Orca він має колір навігації). Тому лінія під ним лишилась контентною, а не швом шела.
Зрівняти її зі швом шела можна тільки разом із перенесенням топбара на `bg-sidebar` — це вже
зміна конструкції шела, не палітри, і робиться окремим рішенням.

### 3.3 `ink` (додана 2026-11-12): еталон «стандартної» будови поверхонь

Третя тема зроблена не заради кольору, а як **референс драбини без інверсій** — тієї, що
спільна для Material 3, Atlassian, Notion і JetBrains Islands (порівняння — §8). Від
`tenantry` і `gray` її відрізняють два правила (рішення власника 2026-11-12):

1. **Полотно контенту — найглибша поверхня; шел і бічні панелі СВІТЛІШІ за нього в обох
   режимах.** Рейл, бічне меню, права панель, шторка, картка й **діалог** стоять на одній
   сходинці над полотном. У світлі — полотно zinc-50 (0.97), шел і картки білі; у темряві —
   полотно 0.22, усе підняте 0.27. Напрямок сходинки не міняється при перемиканні режиму
   (`gray` дзеркальний; `tenantry` ставить шел НИЖЧЕ полотна — експериментальний «силует
   Orca», не правило).
2. **У темряві «вище = світліше» без винятків.** Чотири сходинки, кожна записана один раз:

   | `--tone-*` | L     | Ролі                                                                    | Аналог M3 / Atlassian                        |
   | ---------- | ----- | ----------------------------------------------------------------------- | -------------------------------------------- |
   | `canvas`   | 0.220 | полотно, хедер, **втоплені поля** (`--field`)                           | `surface` / `elevation.surface`              |
   | `surface`  | 0.270 | рейл, бічне меню, права панель, шторка, картка, **діалог** і його шапка | `surface-container-low` / `surface.raised`   |
   | `raised`   | 0.305 | попап, меню, список, тост                                               | `surface-container-high` / `surface.overlay` |
   | `emphasis` | 0.335 | чіпи, `--muted`, `--secondary`                                          | `surface-container-highest`                  |

   Діалог і сайдбар на одній сходинці навмисно: обоє — «піднята поверхня над контентом»; діалог
   від сторінки відділяють scrim (він ще й притемнює полотно), тінь і контур, а не власний тон.
   Меню над діалогом — на `raised`, тобто ще на сходинку світліше: драбина без розривів. Поля
   стоять на тій самій сходинці `raised` (рішення власника 2026-11-12): на полотні, на картці й
   у діалозі поле СВІТЛІШЕ за підкладку і читається заливкою, як у `tenantry`/`gray`; обводка
   `--input` 12% лише відокремлює його від сусідніх піднятих плиток. Втоплене поле (GitHub
   `bgColor-inset`, поле темніше за вікно) пробували й відхилили: у темряві воно читалось як
   порожня «ямка», а не як поле.

Нейтралі майже без хроми (0.004…0.006), нижче навіть за Orca — ближче до бази Linear (LCH
C=2).

**Акценти — Atlassian Design System (Jira), рішення власника 2026-11-12.** Значення зняті з
токенів `--ds-*` збереженої сторінки Jira (темний режим) і пакета `@atlaskit/tokens@20.11`
(світлий), палітра ADS 2025 «refresh»:

| Роль                            | ADS-токен                                 | Light               | Dark                      |
| ------------------------------- | ----------------------------------------- | ------------------- | ------------------------- |
| `--primary` / `-foreground`     | `background.brand.bold` / `text.inverse`  | `#1868DB` / `#fff`  | `#669DF1` / **`#1F1F21`** |
| `--primary-hover`               | `background.brand.bold.hovered`           | `#1558BC` (темніше) | `#8FB8F6` (світліше)      |
| `--secondary`                   | `background.neutral`                      | 6% `--foreground`   | 7% `--foreground`         |
| `--destructive` / `-foreground` | `background.danger.bold` / `text.inverse` | `#C9372C` / `#fff`  | `#F87168` / **`#1F1F21`** |
| `--destructive-hover`           | `background.danger.bold.hovered`          | `#AE2E24`           | `#FD9891`                 |

Що тут важливо, а не просто скопійовано:

- **Інверсія bold-кнопки в темряві** — головне, заради чого взято Jira: заливка світло-синя,
  текст ТЕМНИЙ. Білий текст на насиченому синьому в темряві «світиться», а той самий
  `#669DF1` служить і текстом посилань/іконок бренду, тож на полотні 0.22 не провалюється.
- **Hover у двох режимах іде в різні боки** (світло — темніше, темрява — світліше), тому
  формула решти тем «`--primary` + 10% `--primary-foreground`» тут непридатна: у темряві
  foreground кнопки темний і затемнив би її. Обидва hover записані літералами.
- **Secondary — накладка, не суцільний сірий** (у ADS `#0515240F`): та сама кнопка на
  полотні, картці й у діалозі лишається «на сходинку темнішою за підкладку». Сам примітив
  `Button` уже так працює (8%/15% `--foreground`), токен лише вирівняно з ним для бейджів.
- `--success`/`--warning` не чіпали: ADS тримає їх із темним текстом на жовтому
  (`#FBC828`), а наші бейджі очікують світлий foreground — це окрема правка `badge.tsx`.
  Шкала висот і контури — будова `tenantry.dark` без змін (щільні короткі тіні, контур у
  примітиві). Перевірено наживо 2026-11-12 на `/workspace/customers`, діалозі «Add customer» і
  `Select` у обох режимах.

**Чого в `ink` немає навмисно:** власних значень для брендового фону — скло береться з її
`--sidebar`/`--card` як у решти тем (§6.1).

## 4. Перемикач (реалізовано 2026-09-06)

Рішення користувача: вибір теми живе в `localStorage` (як і режим); дефолт — `tenantry` (з
2026-11-08; до того `gray`, ще раніше `slate` і короткий час `notion`).

| Файл                                                  | Роль                                                                                                                                                                                                                            |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `libs/ui/src/themes/registry.ts`                      | Реєстр тем: `id`, ключ назви, три свотчі превʼю (полотно / межа / primary), `DEFAULT_UI_THEME`, `isUiThemeId`, `getUiTheme`.                                                                                                    |
| `libs/ui/src/themes/ui-theme-provider.tsx`            | `UiThemeProvider` — читає `localStorage`, ставить `document.documentElement.dataset.theme`, слухає `storage` (синхронізація вкладок); `useUiTheme()`.                                                                           |
| `libs/ui/src/components/theme-select.tsx`             | Дропдаун вибору палітри: `DropdownMenuRadioGroup` зі свотчами.                                                                                                                                                                  |
| `apps/web/index.html`, `apps/platform-web/index.html` | Блокувальний скрипт: виставляє атрибут ДО першого малювання (дзеркало того, що `next-themes` робить для класу). Значення просіюється **списком відомих палітр** (`['tenantry','gray']`) — дзеркало реєстру, яке ніщо не звіряє. |
| `apps/web/src/main.tsx`                               | `<UiThemeProvider storageKey="saas_theme_palette">` усередині `ThemeProvider` next-themes.                                                                                                                                      |
| `apps/web/src/features/account/pages/appearance.tsx`  | Другий рядок розділу: **Color theme** + `ThemeSelect` (перший лишається Theme + `ThemeSwitcher`).                                                                                                                               |
| `apps/web/src/locales/en/{layout,user-settings}.json` | Ключі `theme.paletteLabel`, `theme.palettes.*`, `appearance.palette*`.                                                                                                                                                          |

Два контроли, а не один список: режим перемикають щодня (він у хедері), палітру обирають раз
(вона в налаштуваннях). Злиті, вони дали б N×2 пунктів меню.

`apps/platform-web` отримав те саме (`UiThemeProvider storageKey="saas_platform_theme_palette"` у
`main.tsx`, блокувальний скрипт в `index.html`, `ThemeSelect` у `features/account/pages/appearance.tsx`,
ключі `theme.palettes.*` у власному `layout.json`), тож палітру можна вибрати і в control plane.

**Перевірено наживо** (dev-сервер, обидва режими): вибір у меню перемальовує сторінку миттєво,
`localStorage` і `data-theme` збігаються, після F5 тема лишається (скрипт відпрацьовує до першого
кадру — спалаху дефолтної теми немає), зняття атрибута повертає дефолт. Тестів **на теми** немає
(у `libs/ui` Vitest є на логіку гріда, навігації й хуки, але контракт тем і паритет токенів не
перевіряються), тож нижче ручний чекліст.

### Чекліст після зміни теми

6 екранів × 2 режими × N тем: `/login`, `/workspace` (шел цілком), `/workspace/users` (грід,
бейджі, тумблери), картка юзера, `/settings/general` (форми), модалка + тост + дропдаун (оверлеї,
де живе `bg-black/10`).

## 5. Як додати нову тему

1. Скопіювати `themes/gray.css` у `themes/<id>.css`, замінити селектори на `<id>`. Саме
   `gray`, а не дефолтну `tenantry`: у дефолта селектори подвоєні парою
   `:root:not([data-theme])`, і скопійована разом із нею тема перехопила б дефолт.
2. Перевизначити ВСІ токени в обох блоках (світло + темрява), не забути `color-scheme`,
   три `--calendar-*` і трійку `--icon-strong` / `--icon` / `--icon-muted` (§1.3.2); `--event-*` НЕ оголошувати
   (§1.3.1).
3. Додати `@import './themes/<id>.css';` у `styles.css` і рядок у `registry.ts` (разом із типом
   `UiThemeId`).
4. Додати `<id>` у список палітр блокувального скрипта в **обох** `index.html`
   (`apps/web`, `apps/platform-web`) — інакше до гідратації сторінка малюється дефолтом (спалах).
5. Додати ключ `theme.palettes.<id>` у `layout.json` обох фронтендів — інакше меню покаже сирий ключ.
6. Пройти чекліст із розділу 4.

Тобто тема — це не «три кроки», а CSS-файл плюс правки в шести місцях. Усі шість звіряє тест
контракту `libs/ui/src/themes/themes.contract.test.ts` (`pnpm --filter @saas-skeleton/ui test`,
входить в `pnpm test`): файл і `@import` для кожної теми реєстру, селектори, обидва `index.html`,
обидва `layout.json`. Він же стереже повноту токенів: світлий блок кожної теми мусить оголошувати
той самий набір, що й дефолтна (бракує — помилка, зайвий — теж, це описка), темний — усе, що
світлий, крім `--radius`; усе, чого немає у світлому блоці, мусить бути перевизначенням бази або
внутрішнім `--tone-*`. Тест НЕ перевіряє значення (контраст, відтінки) — це чекліст розділу 4.
Базові токени, які теми перевизначають вибірково (`--raised-outline`, `--overlay-outline` у
`styles.css`), в «повний набір» §2 не входять — дивись базу, перш ніж копіювати `gray.css`.

Що варто тримати в голові, підбираючи значення: пари «поверхня + її foreground» мусять лишатися
контрастними в обох режимах (`--primary` / `--primary-foreground`, `--success` / …); `--accent` —
поверхня наведення, вона мусить бути на сходинку щільніша за `--sidebar`, інакше hover у навігації
не видно; `--input` — обводка поля, а не фон (фон — `--field`).

## 6. Відкриті рішення (потрібна ваша відповідь)

1. ~~**Де живе вибір теми**~~ — вирішено 2026-09-06: `localStorage`, як і режим. Перенесення в
   профіль (колонка в `users`, поле в `GET /account` і `UpdateAccountProfileSchema`) лишається
   можливим кроком, якщо тема має їхати за людиною між пристроями.
2. **Чи дає тему тенант.** Корпоративна тема на рівні організації (MT-4, brandable) — це вже інша
   задача: значення приїжджають з API і вставляються `<style>`-тегом у рантаймі, а не імпортом.
   Механіка `data-theme` цьому не заважає, але це окрема фаза.
3. ~~**Дефолт для наявних інсталяцій**~~ — вирішено 2026-11-08: `tenantry`. Збережений у
   `localStorage` вибір переживає зміну дефолта, але НЕ перейменування: id `slate` більше не
   валідний, `isUiThemeId` відсіє його і поверне дефолт — тобто хто сидів на `slate`, просто
   лишиться на тій самій палітрі під новим іменем. Міграцію значення не робили навмисно:
   результат той самий, а код лишається без одноразового коду.
4. ~~**Скільки тем робити зараз**~~ — зараз їх дві: `tenantry` (дефолт) і `gray`.
   З намальованих напрямків лишаються нерозгорнутими Ink (темний рейл), Emerald, Violet,
   Paper — кожен це ~70 рядків.
5. **Чи потрібні теми в `apps/platform-web`**, чи control plane лишається на одній.

## 6.1 Брендовий фон — не тема

Скляний шел на брендовому фоні (`/guide`) — не третя тема і не третій режим, а перевизначення
кількох токенів лише під `[data-backdrop='brand']`: поверхні → скло, `--secondary`/`--muted` →
накладки. Працює поверх будь-якої теми, бо скляні значення виводяться з її власних
`--sidebar`/`--card`. Деталі — `docs/frontend/brand-backdrop.md`.

---

## 7. Чого робити НЕ треба

- **Не заводити «токени в компонентах»** — вони там уже є у вигляді семантичних утиліт; додатковий
  шар тільки віддалить компонент від теми.
- **Не дублювати `@theme inline` у темах** — це мапа імен, а не значень.
- **Не робити 2N тем у `next-themes`** (див. §2).
- **Не переносити метрики й типографіку в тему** — інакше кожна тема стане окремим дизайном.
- **Не робити тему «дельтою» від дефолтної** — тільки повний набір токенів.

Висновки, якими керуємось:

- **Стандарт один:** у темряві вище = світліше, рівнів 4…5. Куди ставити шел, системи
  розходяться: GitHub/Linear/Slack тримають його НИЖЧЕ полотна, Notion/JetBrains Islands —
  ВИЩЕ. Для нас обрано друге (власник, 2026-11-12): полотно контенту — найглибше, шел, панелі,
  картки й діалог на одній сходинці над ним. `tenantry.dark` відхиляється тричі (шел нижче
  полотна, попап на рівні картки, діалог на рівні полотна) — це свідомий «силует Orca», не
  помилка, але **не база для нових тем**; база — `ink` (§3.3).
- **Блюр — не стандарт для робочих екранів.** Жодна з систем вище не кладе скло на сайдбар
  звичайного застосунку; Apple робить це лише для навігаційного шару і сама знижує прозорість.
  Наш поділ (скло тільки під `[data-backdrop='brand']`: `/guide`, `/about`, вхід; робочі екрани
  суцільні) збігається з цим. Не розширювати.
- **Брендовий фон із аурами** (DeepSeek, Linear-лендинги, Vercel) — патерн вітрин і онбордингу,
  не CRM-екранів. Наш `brand-backdrop` + скляні попапи над ним — уже «як у кращих», і його
  правильне місце саме там, де він зараз.
- **Поля в діалозі:** три способи зробити поле видимим на вікні — підняти поле (`ink`,
  `tenantry`/`gray`: поле на сходинку світліше за вікно), опустити вікно (`tenantry`, діалог на
  полотні) або втопити поле (GitHub `bgColor-inset`). Для нас обрано перше (власник, 2026-11-12):
  поле завжди світліше за підкладку в темряві й біле у світлі; втоплене читалось як «ямка».

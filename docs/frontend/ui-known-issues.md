# Відомі проблеми UI-шару

Журнал проблем UI-бібліотеки, які доводиться обходити в коді. Мета — щоб обхід був **один і
названий**, а не костиль на кожному місці використання, і щоб було видно, коли проблему можна
закрити (вийшла нова версія — перевірити за процедурою й прибрати обхід).

Стек, до якого стосується журнал, — `ui-stack.md` §1.

---

## UI-2. `Switch` роздуває `scrollWidth` предків на ~11px

**Статус:** відкрита (заведена 2026-09-08)

### Симптом

Будь-який контейнер зі скролом, усередині якого є `Switch`, отримує ПАРАЗИТНИЙ
горизонтальний скролбар — навіть коли жоден видимий елемент за край не виходить. Спіймано в
контекстній панелі (288px): смуга прокрутки внизу панелі, при цьому обхід DOM за
`getBoundingClientRect()` не знаходить жодного елемента, що перетинає праву межу.

### Що перевірено

| Гіпотеза                                                    | Результат                                                                       |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Переповнює видимий вміст форми                              | ✗ — `offenders` за `getBoundingClientRect()` порожній                             |
| Винен футер із трьома кнопками в рядок                      | ✓ частково — давав 26px, полагоджено розкладкою; але 3px лишились                 |
| Винен `Field orientation="horizontal"`                      | ✗ — сам по собі не переповнює                                                     |
| **Прихований нативний `<input>` усередині `SwitchPrimitive`** | ✓ — `clientWidth: 1`, `scrollWidth: 63`: нативний input віддає INTRINSIC ширину  |
| Негативний контроль: та сама форма без `Switch`             | ✓ — `form.scrollWidth === form.clientWidth`                                       |

Ланцюг: input `1 → 63` ⇒ `[data-slot=switch]` `30 → 42` ⇒ `[data-slot=field]` `256 → 267` ⇒
`form` `272 → 275`. У широкому контейнері це непомітно, у вузькому дає видиму смугу.

### Поточний обхід

`overflow-x-hidden` на контейнері зі скролом — у контекстній панелі це обидва
`TabsContent` в `apps/web/src/components/calendar/event-panel.tsx`. Обхід свідомо стоїть на
КОНТЕЙНЕРІ, а не в примітиві: він же закриває і будь-яке інше фантомне переповнення у вузькій
колонці, а правка вендереного `switch.tsx` вимагала б лізти в розмітку, яку рендерить Base UI,
а не наш код.

### Варіанти системного рішення

- **A (зараз).** Політика «панель ніколи не скролиться горизонтально» — `overflow-x-hidden` на
  кожному скролері панелі. Дешево, і формулює правило, а не латку.
- **B.** Обгорнути `Switch` у `<span className="contents overflow-hidden">` — не працює:
  `contents` не створює блока формування.
- **C.** Issue в Base UI: прихований input мусить мати `width: 1px; overflow: hidden` або
  `appearance: none`. Правильно, але чекати не можна.

### Як перевірити, що проблема зникла

Оновити `@base-ui/react`, у консолі на відкритій панелі події виконати
`const f = document.querySelector('[data-slot=context-panel] form'); [f.clientWidth, f.scrollWidth]`
— рівні значення означають, що обхід можна знімати.

## Коли заводити запис

Запис потрібен, якщо виконуються **обидві** умови:

1. компонент бібліотеки поводиться не так, як документовано, і це не помилка використання;
2. обійти це можна лише кодом, який не є нашим доменом — тобто обхід житиме у вендореному
   шарі або в обгортці над примітивом.

Якщо проблема лише в тому, що потрібної поведінки немає, — це не запис журналу, а вибір
компонента: див. `ui-registry.md`. Якщо потрібна поведінка є, але вимкнена дефолтом, — це
**локальна правка реєстру** (`ui-stack.md` §6), а не проблема.

## Формат запису

```markdown
## UI-N. Короткий симптом одним рядком

**Статус:** відкрита / закрита <дата> — <як саме закрита>

### Симптом

Що бачить користувач. Без діагнозу.

### Що перевірено

Таблиця проб: кожен рядок — окрема гіпотеза і її результат (✓/✗). Обовʼязково включити
**негативний контроль** (нативний елемент, сирий шар під бібліотекою, той самий компонент
поза підозрюваним контекстом) — без нього невідомо, що саме зламане.

### Поточний обхід

Код обходу і **де рівно він живе**. Одне місце, названий компонент.

### Варіанти системного рішення

A/B/C… з вартістю кожного і рекомендацією на зараз.

### Як перевірити, що проблема зникла

Покроково: що оновити, який мінімальний проб покласти на сторінку, який атрибут DOM дивитись.
```

Два правила, які виправдали себе на першому ж записі:

- **Мінімальне репро складати відразу** — воно ж потім іде в issue апстріму і в процедуру
  перевірки. Дописати його «потім» ніхто не встигає.
- **Журнал — лічильник, а не звалище.** Поки в ньому один пункт, він не привід міняти
  бібліотеку; коли записи починають накопичуватись — це і є сигнал, і рішення приймається за
  сумою, а не за останнім роздратуванням.
